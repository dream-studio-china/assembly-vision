was identified. The highest risks affect central credential compromise
recovery, configuration identity, evidence integrity, tenant attribution,
availability, and the accuracy of pilot-readiness claims.

## 3. Positive Findings

The following controls are implemented well and should be preserved:

- The edge runtime imports no central implementation, and central remains out
  of the inspection decision path.
- Device upload authentication and administrator authentication use separate
  code paths and cannot be substituted for each other.
- Credentials are stored as independently salted scrypt hashes and compared in
  constant time (`auth/passwords.py:31-60`).
- Browser sessions use a high-entropy lookup/secret split, store only a salted
  secret hash, expire server-side, and use `HttpOnly` and `SameSite=Strict`
  cookies (`repository.py:896-980`, `routers/auth.py:55-67`).
- Inspection ingestion atomically commits the immutable inspection projection,
  component evidence, receipt, and acceptance audit event.
- Device sequence, inspection ID, and idempotency constraints provide a strong
  duplicate-prevention backstop.
- Media uploads are bound to the accepted parent manifest by source media ID,
  expected size, and expected SHA-256 before object storage
  (`ingest/__init__.py:125-145`).
- Object keys are generated by central and tenant-scoped; clients cannot supply
  storage paths (`ingest/__init__.py:226-237`).
- Principal history, detail, review, and media HTTP paths scope queries to the
  authenticated administrator organization.
- Human review is additive and does not update the original machine decision.
- Schema migration is a controlled release step; the API checks migration head
  in readiness and does not migrate on startup.
- RFC 7807 responses generally avoid stack traces, SQL, secrets, absolute
  paths, and model paths.
- Compose publishes the pilot UI on loopback by default, and the central API
  image runs as a non-root user.
- OpenAPI and generated TypeScript artifacts have deterministic drift checks.

## 4. High-Severity Findings

### H01. Published development credentials become active credentials

**Evidence**

- `apps/central-service/compose.env.example:1-18` contains working PostgreSQL,
  MinIO root, administrator, and device-upload values.
- The documented workflow tells operators to copy this file to `.env`
  (`compose.env.example:1-3`, `README.md:226-230`).
- Compose provisions the administrator and device tokens into the durable
  credential store (`compose.yaml:58-73`).
- PostgreSQL and MinIO also retain known fallback passwords
  (`compose.yaml:19-21`, `compose.yaml:35-36`).

The claim that administrator/device tokens have no defaults is misleading in
the documented path: the Compose file has no interpolation default, but the
published example supplies known values. A copied example produces a ready
stack with publicly known credentials.

**Impact**

An accidentally exposed pilot can be accessed as administrator or registered
device. The published MinIO root credential also grants unrestricted object
store administration.

**Required change**

- Remove usable secrets from the example. Use empty required variables or
  explicit placeholders that fail the Compose required-variable expression.
- Require high-entropy generated values and reject known development sentinels
  unless an explicit loopback-only development mode is enabled.
- Use Docker secrets or mounted secret files for non-local deployment.
- Remove PostgreSQL and MinIO password fallbacks from the controlled-pilot
  profile.

**Acceptance**

- Compose fails before starting when secrets are unset or still equal published
  sentinels.
- A test inspects effective Compose configuration without printing secret
  values and proves the controlled-pilot profile has no known credentials.

### H02. The credential-compromise runbook cannot perform its promised rotation

**Evidence**

- `docs/runbooks/central-credential-compromise.md:13-21` instructs operators to
  disable/re-enroll a device and rerun bootstrap for administrator rotation.
- `persistence/bootstrap.py:3-10` explicitly states that existing devices and
  administrators are never re-keyed.
- `repository.py:1073-1137` hashes credentials only when creating a new row.
- No supported device-disable, credential-rotation, or revoke-all-admin-
  sessions command/API exists.

**Impact**

Operators can follow the emergency procedure and incorrectly conclude that a
stolen credential was revoked while it remains valid.

**Required change**

Implement explicit transactional commands for administrator token rotation,
device token rotation, device disable/re-enable, and organization-wide session
revocation. Every operation must write an audit event with actor, target,
request/incident correlation, reason, and outcome. Until implemented, amend the
runbook to state that rerunning bootstrap does not rotate credentials and that
central access must remain stopped during an approved database-level response.

**Acceptance**

- The old token returns `401` immediately after rotation and the new token is
  scoped to the same principal.
- Administrator rotation revokes all sessions selected by policy.
- Rotation/revocation and failed attempts are auditable.
- The runbook is executable without undocumented SQL.

### H03. Desired-configuration assignment corrupts public version identity

**Evidence**

- `repository.py:4036-4039` assigns `product_versions.id` to `product_pk` and
  then queries `products.id == product_pk`. It should use
  `product_versions.product_id`.
- `repository.py:4177-4196` correctly stores internal integer foreign keys.
- `repository.py:4549-4560` then serializes those internal keys directly as
  strings instead of joining to the public `version_id` UUIDs.
- Existing tests assert revision/device only and even preserve the wrong
  internal value in audit state (`test_metadata_repository.py:1142-1197`,
  `test_metadata_api.py:537-562`).

**Impact**

Once product and product-version integer sequences differ, a valid assignment
can fail or validate the product detector against the wrong product code. A
successful response returns values such as `"1"` instead of the requested
public UUIDs, breaking traceability and any consumer that uses the desired
bundle identity.

**Required change**

- Resolve product code through `product_versions.product_id`.
- Join all four stored foreign keys to their version tables when returning a
  desired configuration.
- Keep internal integer keys private to persistence.

**Acceptance**

- Seed diverging product/product-version primary keys and prove assignment
  validates the intended product.
- Assert create, update, fetch, list, and audit outputs contain exactly the four
  public UUIDs submitted by the caller.

### H04. PostgreSQL desired-configuration concurrency is last-write-wins

**Evidence**

- `repository.py:3997-4016` reads the current revision before mutation.
- `repository.py:4172-4185` performs an unconditional update by device row ID.
- `_metadata_write` relies on an ordinary PostgreSQL transaction and uniqueness
  constraints (`repository.py:2297-2319`); no row lock or conditional revision
  predicate protects this update.

Two PostgreSQL transactions can read the same revision, both pass `If-Match`,
both write the same next revision, and silently overwrite one another. SQLite
tests do not expose this because `BEGIN IMMEDIATE` serializes writers.

**Required change**

Use `UPDATE ... WHERE device_row_id = :id AND revision = :expected`, verify one
affected row, and map zero rows to `412 REVISION_MISMATCH`. `SELECT ... FOR
UPDATE` is also acceptable if the locking semantics are covered explicitly.

**Acceptance**

A real PostgreSQL barrier test submits two updates with the same `If-Match`:
exactly one succeeds, one returns `412`, revision increments once, and one
corresponding audit event is committed.

### H05. Central issues an `AVAILABLE` media receipt without verifying stored bytes

**Evidence**

- `ingest/__init__.py:181-214` calls `put_object` and immediately persists an
  `AVAILABLE` binding and receipt.
- `storage/object_store.py:69-77` performs a single PUT but no post-write stat,
  trusted checksum check, or read-back.
- Design 14 requires size/checksum verification before availability
  (`docs/design/14-data-model-and-database.md:528-532`).
- The M1 exit criterion calls these "verified compatible receipts"
  (`docs/tasks/C1-central-server-m1.md:663-665`).

**Impact**

A short write, storage corruption, object replacement, or S3-compatible
implementation defect can leave a database row and verified receipt claiming
that evidence exists with the expected hash when retained bytes differ.

**Required change**

Extend the object-storage protocol to return or retrieve trustworthy stored
size and SHA-256 metadata. Verify both before committing `AVAILABLE`. Do not
use multipart ETag as SHA-256. For the bounded 16 MiB pilot, read-back hashing
is acceptable if measured; otherwise store and verify supported S3 checksum
metadata.

**Acceptance**

- Simulated truncation/corruption after a successful PUT produces no
  `AVAILABLE` row and no success receipt.
- A valid object passes exact size and SHA-256 verification.
- Reconciliation independently detects later corruption, not only absence.

### H06. Reconciliation can delete an upload that is still committing

**Evidence**

- Ingestion writes an object before its database binding
  (`ingest/__init__.py:181-214`).
- Reconciliation independently snapshots bindings and lists object keys
  (`storage/object_store.py:139-159`).
- The maintenance command can remove every object not in that snapshot.

If reconciliation runs after object PUT but before the binding commit, it can
classify the active upload as orphan, delete it, and allow ingestion to commit
an `AVAILABLE` row pointing to missing evidence.

**Required change**

Use an explicit staging namespace/state with an age threshold and finalization
protocol. Reconciliation must never delete recently staged or leased objects.
Coordinate final object publication and binding recovery with durable state.

**Acceptance**

A barrier test pauses ingestion between PUT and binding commit while
reconciliation runs with orphan removal. The active upload must survive and
finish available, or fail without an available binding.

### H07. Inspection ingestion accepts records that violate central safety and governance claims

**Evidence**

- `ingest/envelope.py:138-189` validates Pydantic shape, device identity, and
  inspection identity only.
- `InspectionRecord` has no cross-field validator for finalized lifecycle,
  timestamp order, or decision mapping (`domain/models.py:264-290`).
- Central does not resolve the referenced product/rule/model versions or their
  compatibility before acceptance.
- Design 05 says central validates compatible references
  (`docs/design/05-central-server-architecture.md:39-43`).
- Contract 05 requires product-configuration version traceability
  (`docs/contracts/05-data-api-and-versioning-contracts.md:20-29,103-113`),
  but the persisted field is nullable (`persistence/schema.py:265`).

Examples currently accepted include a non-final lifecycle, completion before
start, `internal_decision=UNCERTAIN` with `business_result=OK`, missing product
configuration identity, and arbitrary unknown version UUIDs.

**Impact**

A compromised or defective device can obtain a verified receipt for evidence
that central later presents as governed/finalized even though it violates the
documented decision and traceability model.

**Required change**

Choose and document one explicit reference policy:

- Governed pilot: resolve organization-owned published versions, validate
  product/rule/model compatibility and checksums, and reject unknown versions.
- Compatibility ingestion: accept immutable unknown edge references but mark
  the inspection `UNGOVERNED` and never describe the receipt as compatibility
  verification.

In both cases, enforce final lifecycle, timestamp ordering, `UNCERTAIN -> NG`,
decision/evidence coherence, unique media manifest identities, and mandatory
product-configuration identity for production/pilot records.

**Acceptance**

Negative ingestion tests cover every invariant above. Invalid records return a
stable `409` or `422`, write no accepted inspection/receipt, and retain a
bounded integrity audit where appropriate.

### H08. Review idempotency and validation do not preserve request identity

**Evidence**

- Review records persist an idempotency key but no canonical request hash
  (`persistence/schema.py:383-413`).
- Any repeat of the key returns the old record without comparing content
  (`repository.py:2109-2123`).
- The replay path omits `inspection_id`, whose mapper default is an empty string
  (`repository.py:2123`, `repository.py:4571-4586`).
- `ReviewSubmit` does not enforce a reason for `INCONCLUSIVE`, normalize/reject
  duplicate component codes, or prove corrections belong to the inspection
  (`api/schemas.py:225-241`).
- Equivalent domain invariants exist but are bypassed
  (`domain/models.py:365-414`).

**Impact**

The same key can be retried with contradictory content and silently return the
first review. A replay response loses its inspection identity. Invalid or
ambiguous ground-truth corrections can enter an append-only record that cannot
be repaired in place.

**Required change**

Persist a canonical request hash with each review key. Replay only identical
content; return `409 IDEMPOTENCY_CONFLICT` for changed content. Construct the
domain review command, or reproduce all domain validators at the API boundary,
and validate correction component codes against the inspection evidence or
governed product version.

**Acceptance**

- Same key/same body returns the original review with the correct inspection
  ID.
- Same key/different body returns `409` without another row.
- `INCONCLUSIVE` without reason, duplicate normalized components, and unknown
  component codes return `422`.

### H09. Rate limiting trusts attacker-controlled identity and leaks memory

**Evidence**

- Nginx appends client-supplied `X-Forwarded-For`
  (`apps/admin-web/nginx.conf:8-14`).
- The API trusts the first value (`api/rate_limit.py:46-57`).
- `_hits` never evicts inactive keys (`api/rate_limit.py:17-39`).
- Authentication scans all principals and performs scrypt verification
  (`repository.py:867-892`), increasing CPU amplification.
- `CENTRAL_RATE_LIMIT_REQUESTS_PER_MINUTE` is published in the env example but
  is not passed to the API container (`compose.env.example:16-18`,
  `compose.yaml:79-88`).

**Impact**

A caller can rotate forged forwarding values to bypass limits, grow process
memory, and amplify credential-guessing CPU cost. Operators can also believe a
configured limit is active when Compose silently uses the default.

**Required change**

- Strip inbound forwarding headers at the trusted outer proxy and set a single
  verified client address.
- Ignore forwarding headers unless the socket peer is an approved proxy.
- Bound and expire limiter keys.
- Add stricter credential/principal-specific authentication limits.
- Wire the documented Compose setting explicitly.

**Acceptance**

Tests cover spoofed forwarding chains, trusted/untrusted proxies, key eviction,
authentication-specific limits, shared-NAT behavior, and effective Compose
configuration.

### H10. Proxy/body handling breaks valid media and permits memory amplification

**Evidence**

- Nginx has no `client_max_body_size` (`apps/admin-web/nginx.conf:1-20`), so its
  standard 1 MiB limit conflicts with the API's 32 MiB envelope and 16 MiB
  decoded media limits (`api/settings.py:55-63`).
- The API calls `await request.body()` before checking the configured bound
  (`routers/ingest.py:78-95`).
- Blocking SQLAlchemy/MinIO work then runs in the async route.

**Impact**

Legitimate media fails through the shipped proxy, often with Nginx HTML rather
than typed problem JSON. If the proxy limit is raised without fixing the API,
concurrent requests can force full raw JSON, Base64, and decoded payloads into
memory while blocking the event loop.

**Required change**

Set an explicit proxy bound consistent with encoded envelope overhead. Enforce
`Content-Length` early, stream into a bounded buffer or temporary file, cap
concurrent ingestion, and offload synchronous database/object-store work from
the event loop. Add container memory/PID limits.

**Acceptance**

Compose integration tests submit valid media near the supported limit and one
byte over each configured limit. Valid uploads succeed; oversized requests
fail with bounded `413`; concurrent maximum requests stay within an approved
memory/latency envelope.

### H11. Backup instructions do not create a consistent PostgreSQL/MinIO recovery point

**Evidence**

- The runbook dumps PostgreSQL while API writes continue, then mirrors MinIO
  "approximately" at the same point
  (`docs/runbooks/central-backup-restore.md:19-45`).
- The API is stopped only during restore (`central-backup-restore.md:47-54`).
- Container names are hard-coded and depend on the Compose project name
  (`central-backup-restore.md:26-27,61-62`).

**Impact**

A restored pair can contain an available binding without its object, or an
object without its binding. This does not satisfy the M1 exit criterion that
PostgreSQL history and MinIO bindings survive representative backup/restore.

**Required change**

For the pilot, quiesce central writes before both backups, record a common
backup ID/time, back up both stores, generate a checksummed manifest, reconcile
the copy, and only then resume. Use Compose service names rather than generated
container names. Production needs a separately approved snapshot/PITR,
encryption, retention, and off-host strategy.

**Acceptance**

A real PostgreSQL/MinIO restore test runs while upload attempts are present,
restores to fresh services, verifies every available binding's exact bytes,
finds no unexplained orphan, and replays receipts duplicate-free.

### H12. Duplicate principal secrets can authenticate as the wrong principal

**Evidence**

- Device and administrator authentication scan all salted hashes and return
  the first match (`repository.py:867-892`).
- Bootstrap does not reject a token already used by another device or
  administrator (`repository.py:1073-1137`).

**Impact**

If the same token is accidentally assigned to multiple devices or tenants, the
caller authenticates as whichever matching row is returned first. Uploads can
be attributed to the wrong device/organization.

**Required change**

Use a unique public credential lookup ID plus a hashed secret, analogous to
browser sessions. Bind the lookup ID to one principal with a database unique
constraint. Reject enrollment/rotation that reuses an existing credential
identity.

**Acceptance**

Multi-tenant tests prove that duplicate credential registration fails and that
each token resolves deterministically to exactly one principal.

## 5. Medium-Severity Findings

### M01. Pilot authentication has no backend authorization roles

Every authenticated administrator can review, publish metadata, and assign
desired configuration (`api/deps.py:84-96`, `routers/reviews.py:172-230`,
`routers/metadata.py:408-455`, `routers/device_configurations.py:116-165`).
This is disclosed as an M1 deferral, but it conflicts with contract 08's
elevated-permission requirement (`docs/contracts/08-security-permissions-and-audit.md:11-27`).

Before any user beyond a tightly controlled single pilot administrator is
enrolled, add deny-by-default organization-scoped reviewer, configuration
manager, fleet administrator, and organization administrator permissions. In
the interim, record a formal risk acceptance and keep metadata mutation routes
inaccessible to ordinary viewers.

### M02. Append-only/immutable data is protected only by repository convention

The API and migration process share the PostgreSQL owner credential
(`compose.yaml:46-88`). Database privileges/triggers do not prevent update or
delete of inspections, reviews, audit rows, or published versions, and several
foreign keys cascade deletion. Design 14 requires reviews/audit rows to be
append-only to the application role (`docs/design/14-data-model-and-database.md:547-554`).

Use a migration owner and a restricted runtime role. Revoke update/delete on
append-only tables and protect publication transitions with explicit grants or
database-enforced routines.

### M03. Audit entries do not reliably identify the administrator

Review audit writes `actor_id=None` (`repository.py:2180-2189`), metadata audit
helpers receive a username but do not consistently persist the administrator
row ID, and successful/failed session creation is not fully audited. This falls
short of contract 08 actor/trace requirements.

Pass the authenticated administrator ID and request ID through all mutation
services; retain username only as a display snapshot. Audit login/session,
review, publish, assignment, rotation, and denied privileged attempts.

### M04. Tenant ownership is not consistently database-enforced

Several child tables omit `organization_id` despite design 14's literal "every
tenant-owned row" statement (`docs/design/14-data-model-and-database.md:464-466`).
Many foreign keys do not bind child and parent organization. The desired-
configuration device existence lookup is also not organization-scoped
(`repository.py:3997-4002`). HTTP routes currently resolve the principal in
scope, but repository misuse or future maintenance code can create cross-tenant
relations.

Add organization-scoped mutation predicates and composite tenant-bound foreign
keys for safety-relevant relationships, or formally narrow the design invariant
for child ownership and prove every chain at the database boundary.

### M05. Arbitrary media MIME is reflected into the admin origin

The inspection manifest can declare an arbitrary MIME value, which is stored
and returned as `Content-Type` from the authenticated same-origin media route
(`ingest/__init__.py:133-145`, `routers/media.py:68-72`). There is no kind/MIME
allowlist, magic-byte validation, or attachment policy.

Allowlist media types by kind, validate magic bytes, bound normalized MIME
length, and serve unsafe formats as attachments from a separate non-privileged
origin. Preserve `nosniff`.

### M06. Missing object data remains falsely `AVAILABLE`

Reconciliation reports missing objects but does not transition lifecycle, and
streaming begins a `200` response before a missing-object iterator failure can
be mapped (`storage/object_store.py:139-159`, `routers/media.py:48-72`). Mark a
missing/corrupt object `FAILED` transactionally with reason/time and verify
availability before sending response headers.

### M07. Metadata uniqueness and query indexes are incomplete

The schema permits duplicate model semantic versions within a package and can
surface unhandled uniqueness failures for duplicate request-list values. Query
indexes do not cover all contract-required organization/result/product/model/
rule paths (`docs/contracts/05-data-api-and-versioning-contracts.md:39-49`).

Add the documented stable-identity constraints, validate duplicate request
values before insert, map expected constraints to typed errors, and validate
query plans with production-like cardinality.

### M08. Generated TypeScript types are treated as runtime validation

`CentralApiClient.request` casts arbitrary successful JSON directly to `T`
(`packages/typescript/api-client-central/src/client.ts:230-247`). Generated
interfaces provide compile-time checking only. Malformed session identity,
tenant data, media records, review revisions, or desired configuration can
reach UI workflows unchecked.

Add runtime schemas at the client boundary for security/workflow-critical
responses and validate RFC 7807 errors before accessing `code`/`detail`.

### M09. Admin session restoration, expiry, and logout are not safely coordinated

- Protected routes have no router guard (`apps/admin-web/src/router/index.ts:16-51`).
- Session restoration runs after components mount (`App.vue:18-23`), allowing
  protected pages to issue requests first.
- `401` is not intercepted centrally and old protected data remains rendered.
- Failed logout rejects before navigation (`session.ts:51-56`, `App.vue:25-28`),
  while the server session may remain valid.
- In-flight requests cannot be cancelled and can repopulate a page after
  logout/session replacement.

Restore the session before route resolution, enforce a global guard, centrally
clear protected state and redirect on `401`, navigate in a logout `finally`
while warning if revocation failed, and bind/abort requests by session
generation.

### M10. Admin filters and lists have correctness gaps

- Overview scope changes race and stale responses can overwrite new scope
  (`OverviewPage.vue:38-55,137-156`).
- Site/line loads race in overview and history.
- The `to_at` date is serialized as midnight while the backend uses an
  exclusive upper bound, excluding the selected day
  (`OverviewPage.vue:176-188`, `InspectionsPage.vue:162-176`).
- Product/rule/model/desired-configuration pages ignore `next_cursor`; only
  history/review pages paginate.
- UTC labels use browser-local `toLocaleString()` in several pages.

Add request generation/abort handling, submit the following midnight for an
inclusive date picker, implement cursor navigation, and use an explicit
selected locale plus UTC formatter.

### M11. Admin document and sensitive media lack browser/cache controls

The FastAPI CSP applies to API responses, not the Nginx-served SPA document.
`apps/admin-web/nginx.conf:1-20` lacks CSP, `frame-ancestors`, `nosniff`,
referrer, permissions, and server disclosure controls. Authenticated media has
no `Cache-Control: private, no-store` (`routers/media.py:68-72`).

Set strict headers on the SPA document at Nginx/TLS ingress and an approved
cache policy on sensitive evidence. HSTS belongs at the actual TLS terminator.

### M12. Containers and runtime credentials are not least-privileged

- The API uses MinIO root credentials (`compose.yaml:31-36,81-84`).
- Migration/bootstrap/API use the same PostgreSQL owner.
- Admin Nginx runs the stock root master (`apps/admin-web/Dockerfile:21-29`).
- Compose lacks read-only filesystems, capability drops, no-new-privileges,
  PID/resource limits, and bounded log rotation.
- Base/service images use mutable tags and are not digest-pinned.

Use a bucket-scoped MinIO service account, restricted database runtime role,
unprivileged Nginx, container hardening controls, bounded logs/resources, and
digest-pinned/scanned images with an SBOM before production exposure.

### M13. CSRF protection relies only on cookie attributes

Cookie-authenticated logout, review, and configuration updates have no CSRF
token or server-side `Origin`/`Sec-Fetch-Site` check. `SameSite=Strict` and JSON
preflight are meaningful mitigations, but design 17 requires an explicit CSRF
boundary. Require a session-bound token or strict origin/fetch-metadata
validation for all cookie-authenticated mutations.

### M14. Readiness and maintenance have lifecycle gaps

PostgreSQL/MinIO readiness calls do not consistently set bounded application-
level network timeouts. Docker marks an unhealthy process but does not restart
it solely because health checks fail. Expired sessions have a purge repository
method but no scheduled command. Add dependency timeouts, external alert/
restart policy, and a controlled expired-session maintenance job.

## 6. Documentation and Evidence Consistency Findings

### D01. Object-store runbook describes states and repairs that do not exist

`docs/runbooks/central-object-store-failure.md:11-18,42-52` says failed uploads
leave `PENDING` bindings and reconciliation promotes them to `AVAILABLE` or
marks them `FAILED`. The implementation creates no binding after a failed PUT,
writes successful bindings directly as `AVAILABLE`, and reconciliation only
reports missing/orphan objects (`storage/object_store.py:139-159`). The same
stale `PENDING` claim appears in
`docs/runbooks/central-ingestion-backlog.md:53-55`.

Either implement the documented staged lifecycle or rewrite both runbooks to
the actual report/delete and edge-replay behavior. Do not claim integrity was

## 9. Residual Risks and Explicit Deferrals

The following remain legitimate M1 deferrals only while deployment stays a
tightly controlled pilot and documentation does not imply otherwise:

- No OIDC, MFA, mature user lifecycle, or full organization-scoped RBAC.
- No device PKI/mTLS or automated credential lifecycle.
- No production HA, horizontal rate-limit coordination, final RPO/RTO, PITR,
  or continuous replication.
- No central retention/legal-hold/deletion enforcement or final data-residency
  controls.
- No malware scanning or final media data-classification policy.
- No server-side model artifact verification, signature verification, remote
  package delivery, activation acknowledgement, or rollback orchestration.
- No resumable large-media protocol.
- No production capacity/soak evidence, partition strategy, or worker topology.

These deferrals become release blockers before broader network exposure,
multiple human users, multiple organizations, production evidence retention,
or remote configuration/model management.

## 10. Improvement Design

### 10.1 Security and credential design

1. Replace shared plaintext bootstrap tokens with a credential identifier plus
   independently rotatable secret.
2. Add audited principal lifecycle commands: enroll, disable, rotate, revoke,
   and session revoke-all.
3. Split database owner/migration/runtime roles and MinIO root/service-account
   roles.
4. Add backend permission dependencies and a role matrix before multiple pilot
   administrators.
5. Establish one trusted TLS/forwarding boundary and reject untrusted proxy
   headers.

### 10.2 Evidence integrity design

1. Introduce durable media staging with lease/age semantics.
2. Verify retained object size and SHA-256 before `AVAILABLE` and receipt.
3. Reconcile absence and corruption into explicit lifecycle/audit state.
4. Quiesce writes for pilot backup or implement snapshot-aligned backup.
5. Add a restore manifest that cross-checks database bindings and object hashes.

### 10.3 Governance and traceability design

1. Fix public/internal desired-configuration identities and PostgreSQL CAS.
2. Decide governed versus ungoverned ingestion reference policy.
3. Require finalized cross-field decision invariants and product-configuration
   identity.
4. Make review idempotency content-addressed and reuse domain validation.
5. Separate declarative model registration from validated release publication.

### 10.4 API and frontend design

1. Stream and bound ingestion before allocation; move blocking work off the
   event loop.
2. Add runtime response validation and centralized `401` handling.
3. Restore/authenticate before protected route mounting and cancel stale work.
4. Correct date/pagination/race/timezone behavior.
5. Add explicit CSRF, browser security headers, and sensitive-media cache
   controls.

### 10.5 Documentation and evidence design

1. Create a central M1 ADR for bounded deviations and supersession criteria.
2. Separate target architecture from the implemented M1 OpenAPI/status table.
3. Make every runbook executable against existing commands only.
4. Distinguish CI-enforced, locally executed, deployment-gated, and deferred
   evidence.
5. Track open questions with owner, state, horizon, and closure evidence.

## 12. Pilot Decision Gate

The central implementation has a substantial, typed, and well-tested M1
foundation. The edge-first safety boundary remains intact, and the existing
idempotent inspection path is stronger than a typical prototype. However, the
current workspace should not be represented as ready for the section 13.2
controlled-pilot go-live checklist because:

1. The documented deployment path can activate public credentials.
2. The documented compromise procedure does not revoke those credentials.
3. Desired configuration can return or validate the wrong identities.
4. PostgreSQL optimistic concurrency is not enforced atomically.
5. Media receipts do not prove retained bytes match the accepted checksum.
6. Reconciliation can race active uploads.
7. Central accepts evidence that contradicts its finalized/governed claims.
8. Review retries can silently alias contradictory requests.
9. The shipped proxy defeats both the intended media limit and rate limiter.
10. The backup pair is not a consistent recovery point.
11. Several runbooks and exit-criteria claims describe behavior that does not
    exist or is not CI-enforced.

Recommended status wording until Phase 0 closes:

> The Central M1 feature set is implemented and passes current static/unit
> gates. Controlled-pilot closure is pending the AUDIT-002 Phase 0 security,
> evidence-integrity, concurrency, recovery, and documentation findings. It is
> not a production release and remains outside the edge decision path.

No production or pilot code was modified by this audit.
