    22. 测试和质量保证¶

    22.1 目的和质量目标¶

    AssemblyVision 测试展示了在代表性生产条件下测量的行为。主要质量目标是真实 NG 产品的高召回率和极低的假阴性率，并有可追溯的证据和谨慎的人工验证支持。没有任何测试计划或模型能够保证 100% 的准确性。

    22.2 按交付阶段划分的范围¶

    • 静态训练和检查 MVP： YOLO 数据集布局和标签验证、产品/ROI/组件坐标重新映射测试、合成夹具训练试运行、静态管道集成测试、确定性夹具、CLI 冒烟测试、保留文件名真实验证和基线模型评估。
    • 一个月目标： 相机/条形码适配器、本地持久性、时间聚合、边缘 API/仪表板、一个中央摄取/历史/审核路径、有针对性的同步/重启/幂等性测试、部署冒烟测试以及访问允许的受控客户站点基线。
    • 生产目标：独立验收数据、长时间运行测试、断电和磁盘满恢复、安全/合约测试、发布回归套件以及模型/规则升级门。
    • 未来范围： 多线负载模拟、硬件在环装置、自动化车队金丝雀和其他相机域测试集。

    22.3 测试级别¶

    水平 焦点 代表性事例
    单位 纯行为和边界条件 ROI 裁剪、置信度聚合、规则原因代码、保留资格
    组件 具有受控依赖性的一项服务 相机适配器重新连接、SQLite 存储库、上传状态机
    整合 真正的边界 API 加数据库、对象存储校验和、模型运行时加 ROI 映射
    端到端 用户/产品工作流程 通过当地决策捕获；通过中央审核上传
    模型评估 坚持小组的统计表现 按组件/产品和置信度分布进行的 NG 召回
    韧性 恢复和安全降解 网络中断、重复网络抖动、断电、磁盘已满、加速器/推理故障、损坏、重新启动
    验收 客户生产行为 使用未见过的生产数据在文件 26 中商定矩阵

    测试使用与发布时相同的版本化模型、规则、应用程序和配置工件。

    22.4 单元和组件测试¶

    Python 测试使用 Pytest 并涵盖有效、无效和边界数据。基于属性的测试适用于边界框裁剪、坐标变换、幂等性和状态转换。时间、UUID 生成、摄像头输入和网络行为都是可注入的。

    所需的单元科目包括：

    • 产品窗口打开/关闭和不明确的身份处理。
    • ROI 边际扩展、边界裁剪、协调往返和无产品行为。
    • 帧质量拒绝和每个组件的时间证据策略。
    • 确定性规则评估，包括缺失和低置信度原因代码。
    • 产品/条形码映射和故障关闭行为。
    • 上传重试/退避、幂等密钥稳定性、校验和不匹配以及终端错误。
    • 保护待处理媒体的保留规则。
    • 配置/模型清单验证和兼容性检查。
    • 数据库事务行为和不完整记录恢复。

    Vue 组件测试使用 Vitest 进行状态状态、表格、检测覆盖、审查控件、表单验证、权限行为和离线/错误呈现。浏览器端到端测试可验证关键工作流程，而无需替代实际的相机测试。

    22.5 集成和契约测试¶

    针对支持的数据库和对象存储版本运行集成测试。 SQLite 边缘测试包括写入争用和不干净的进程终止。 PostgreSQL 迁移测试涵盖每个受支持版本的升级和回滚约束。

    OpenAPI 是生成的 TypeScript 客户端的合约源。合约测试验证状态代码、模式、分页、授权、幂等上传重放、WebSocket 事件信封、媒体范围/下载行为以及前向兼容的未知字段。边缘/中心兼容性在明确支持的版本矩阵中进行了测试。

    相机适配器有一个通用的一致性套件：

    1. 枚举/连接/断开并重新连接。
    2. 获取带有时间戳和相机元数据的帧。
    3. 应用或报告曝光和触发配置。
    4. 处理超时、畸形帧、SDK 异常、设备移除。
    5. 释放资源而不阻止重启。

    真实相机测试在选定的硬件上运行，因为模拟无法验证 SDK、驱动程序、触发时序、曝光、焦点或帧传输。

    22.6 端到端场景¶

    至少，自动化或重复执行：

    • 具有所有必需组件的合格产品。
    • 缺少每个必需的组件，包括手册。
    • 无产品、部分产品和无法使用的框架。
    • 条码成功、条码无法读取、条码未知以及产品不匹配。
    • 轻微的位置变化和正常的生产变化。
    • 一个窗口中的多种产品和框架混合尝试。
    • 连续 OK、连续 NG 和混合产品类型。
    • 在中央服务和网络不可用时进行边缘检查。
    • 具有队列耗尽、重复重放和校验和验证的网络恢复。
    • 应用程序在捕获、决策持久性和上传期间重新启动。
    • 手动审查和更正审核历史记录。
    • 模型/规则安装、兼容性拒绝、激活和回滚。

    每个场景都断言最终决策和原因代码，而不仅仅是 HTTP 成功。

    22.7 模型和系统评估¶

    数据集分区按物理产品实例、批次、捕获会话和生产日期进行分组。一个产品的相邻视频帧不得在训练和验证中分开。验收数据与模型开发保持分离。

    所需报告包括：

    公制 定义和用途
    不良召回 真实 NG 产品被分类为 NG 或路由至采用的不确定/手动路径除以真实 NG 产品
    假阴性率 真实 NG 产品分类为 OK 除以真实 NG 产品
    假阳性率 真正的 OK 产品被分类为 NG 除以真正的 OK 产品
    每个组件的召回 回忆一下每个缺少必需组件的场景
    按产品召回 按产品类型细分的不良召回
    产品检测成功 产品可检查时产生的可用产品投资回报率
    投资回报率生成的成功 产品检测中有效、正确映射的 ROI
    条码读取成功 正确解析可读目标条形码中的条形码
    延迟 捕获/触发持久决策；报告平均值和 P95
    吞吐量 每次在经过验证的生产线概况下完成产品决策
    上传延迟 中央持久收据的决策时间，按连接性分段
    查看指标 按决策/版本划分的人工审核率和纠正率

    总体准确性可能会被报告，但绝不是唯一的晋升标准，因为类别不平衡可能会掩盖遗漏的缺陷。置信区间和样本计数伴随着比率。任何模棱两可的事实都会被裁决和报告，而不是默默地被删除。

    22.8 故障和弹性测试¶

    故障 注射 所需行为
    相机断开连接 删除设备/停止模拟器 没有捏造OK；报警、重新连接、安全恢复
    网络中断 阻止中央端点/DNS 地方决定继续进行；队列持续存在
    反复断网 针对中央端点的振荡连接（向上/向下循环、部分数据包丢失） 地方决策继续进行，无需中央往返；队列仍然存在；带有抖动的回退和限制重复流量的断路器；无数据丢失或重复上传；一旦连接恢复，积压的工作就会消失
    中央停电 返回超时/5xx 带抖动的退避；没有决策障碍
    重复上传 重放相同的幂等键 一次集中检验，一致收货
    断电 在选定状态期间杀死主机/进程 恢复数据库/队列；不明确的窗口未标记为 OK
    磁盘已满 填充测试量或强制执行配额 警报、安全清理、在可追溯性丢失之前暂停
    加速器/GPU 故障 终止或停止推理子进程；强制 CUDA/加速器错误 没有捏造OK；可恢复的故障使用相同的清单重新加载或切换到经过验证的CPU运行时并记录切换；不可恢复故障故障和块检查（设计09.7）
    数据库故障 锁定/损坏一次性测试数据库 安全失败、保留诊断、执行经过测试的恢复路径
    容器重启 独立重启各个服务 监督恢复，无需重复产品决策
    时钟漂移 偏置挂钟 保持单调排序/相关性并警惕漂移
    校验和失败 更改媒体/包字节 拒绝工件并保留可恢复的任务/版本

    故障测试仅在具有一次性数据的隔离环境中运行。断电测试包括数据库提交、媒体重命名、队列创建、上传传输和接收持久性之前/之后的中断。

    22.9 性能和稳定性¶

    性能测试使用生产分辨率图像和候选边缘硬件。测量捕获、条形码、产品检测、ROI、组件检测、聚合、规则、持久性和 UI/事件交付的阶段时序。单独报告预热并监控 CPU、GPU、内存、温度、磁盘 I/O 和队列增长。

    长时间运行的测试包括正常产品流、突发、空闲期、摄像头重新连接、中央中断、重复网络断开、加速器/推理故障和保留清理。通过意味着没有无限的内存/文件描述符/队列增长，没有数据丢失，并且延迟在客户同意的限制内稳定。工期和工作量根据实际操作模式商定；本文档并未发明它们。

    22.10 测试数据和地面实况治理¶

    固定装置不包含不受控制的客户数据。每个评估项目都有一个不可变的标识符、源组、产品类型、预期组件状态、条形码基本事实（如果适用）、注释/审查出处以及允许的使用。更正创建新的注释版本。培训、验证、测试和客户验收清单均受校验和控制。

    针对每个必需的缺失组件情况，有意收集真实的 NG 示例。合成去除或分期可以作为补充，但必须与自然发生的缺陷分开报告。训练策略中的数据集数量只是起点，而不是保证。

    22.11 发布质量门¶

    候选人只有在以下情况下才能晋升：

    1. 所需的静态检查（Ruff、MyPy、ESLint、格式）和自动化测试通过。
    2. 数据库和API兼容性检查通过。
    3. 安全扫描没有发现不可接受的发布阻止结果。
    4. 按产品、组件、模型和规则版本将模型/系统指标与批准的基线进行比较。
    5. 锁定回归集中没有出现无法解释的 NG-OK 回归。
    6. 发布范围内的离线、重启、重试、磁盘压力和回滚测试均通过。
    7. 证据、版本、时间戳、设备、日志溯源齐全。
    8. 一旦通过基线评估确定了客户特定的目标，就会得到满足，或者批准明确的偏差。

    在代表性基线测量后，数字门被记录在发布/验收计划中；它们不是在这里发明的。

    22.12 缺陷管理和证据¶

    缺陷包括严重性、环境、应用/模型/规则/配置版本、设备/相机标识符、时间戳、步骤、预期/实际结果、相关图像/日志和隐私分类。漏检的 NG 被视为最高检查质量问题，并触发遏制、受影响范围分析、回归夹具创建和发布审核。

    测试报告和清单与发布来源一起保留。片状测试仅在所有者和补救期限内被隔离；隔离不能绕过安全相关的大门。

    22.13 未解决的问题和需要验证¶

    • 基线评估后客户商定的接受阈值和统计置信度方法。
    • 产品类型、确切所需的组件类别、缺陷分类法和真实所有者。
    • 候选相机/SDK、边缘 CPU/GPU、传输速率和延迟/吞吐量预算。
    • 边缘和中央版本所需的支持版本兼容性窗口。
    • 长时间运行的测试持续时间、生产工作周期和预期的停机持续时间。
    • 天然存在的 NG 样品的可用性以及上演缺失组件案例的许可。
    • 所需的浏览器、操作系统、安全扫描仪和外部测试义务。
    • 包含客户生产数据的测试证据的保留期限和访问控制。
