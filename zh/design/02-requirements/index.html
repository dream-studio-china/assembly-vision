    AssemblyVision Requirements¶

    1. 需求语言和优先级¶

    MUST 表示释放义务，SHOULD 表示可以根据书面理由放弃的预期行为，MAY 表示选项。优先级为P0 生产关键型、P1 为预期目标所需，以及P2 未来或有条件的。需求ID是稳定的并且遵循Appendices中的约定。

    2. 业务和安全要求¶

    身份证 优先 要求 验证
    BR-001 P0 每次完成的物理产品检验，系统必须生成一个可追溯的业务结果 OK 或 NG。 端到端和验收测试
    BR-002 P0 OK 必须为已解决的产品规则所需的每个组件提供有效的证据。 规则引擎测试
    BR-003 P0 缺失、不确定、无效、未解决或不完整的检查证据不得产生OK。 故障注入测试
    BR-004 P0 评估必须优先考虑 NG 召回和假阴性减少，而不是早期假阳性减少。 评估报告审核
    BR-005 P0 生产验收必须使用培训中排除的测量客户生产数据，并且不得依赖未经验证的准确性保证。 数据集沿袭和验收报告
    BR-006 P1 早期生产必须支持对所有 NG 结果、配置的低置信度案例以及抽样 OK 审核进行人工审核。 工作流程测试

    3. 边缘功能需求¶

    身份证 优先 要求 验证
    边缘-001 P0 对生产至关重要的捕获、推理、聚合、规则和最终决策必须在边缘计算机上执行，而无需中央往返。 断网测试
    边缘-002 P0 边缘必须集成工业相机捕获并暴露显式的连接、降级、断开连接和故障状态。 适配器和故障测试
    边缘-003 P0 边缘必须界定属于一种物理产品的帧，并防止产品之间的证据混合。 序列和边界测试
    边缘-004 P0 条形码解码必须是一个单独的功能；检测可以定位其区域，但不得替代解码。 组件/API 测试
    边缘-005 P0 产品类型解析必须明确且可追溯；未解析或冲突的身份不得产生 OK。 规则测试
    边缘-006 P0 第一阶段检测必须在全框架中定位完整的产品，并报告类别、框、置信度和可选的跟踪数据。 合同范本测试
    边缘-007 P0 ROI 生成必须应用可配置的边距、剪辑到图像边界、保留全帧/ROI 坐标映射并拒绝无效的几何图形。 单位/性能测试
    边缘-008 P0 第二阶段检测必须识别生成的产品 ROI 中配置的所需组件。 模型评估
    边缘-009 P0 时间聚合必须根据所需组件独立地组合证据，并且不得使用整体产品多数投票。 聚合器测试
    边缘-010 P0 确定性规则引擎必须发出决策、缺失和低置信度列表、原因代码和活动模型/规则/产品配置版本。 黄金测试
    边缘-011 P0 边缘必须以原子方式持久保存检查元数据和所需证据，以便在进程重新启动或断电后进行恢复。 恢复测试
    边缘-012 P0 边缘必须坚持上传工作，通过退避重试，通过幂等性防止重复，验证媒体校验和，并在中断后恢复。 韧性测试
    边缘-013 P0 清理必须保护待上传或主动审核策略仍需要的记录和文件。 保留测试
    边缘-014 P1 本地 FastAPI 服务和本地服务的 Vue 应用程序应该公开实时状态、最近结果、证据、存储/健康状态、队列状态、日志、配置和离线时手动重试。 本地浏览器E2E
    边缘-015 P1 检查暂停/恢复只有在其操作权限和安全行为获得批准后才可以公开。 验收程序

    4. 核心功能需求¶

    身份证 优先 要求 验证
    中央-001 P1 中央 API 必须幂等地摄取检查信封和选定的媒体并返回持久收据。 API/集成测试
    中央-002 P1 摄取必须检测已接受的幂等性密钥的有效负载冲突，而不是默默地替换数据。 冲突测试
    中央-003 P1 中央历史记录必须支持基于时间、设备、线路、条形码、产品、决策、模型、规则和原因的分页查询。 API/查询测试
    中央-004 P1 该服务必须管理设备、产品、产品组件、版本化规则、版本化模型元数据、用户、权限和审核记录。 授权/端到端测试
    中央-005 P1 手动审核必须保留原始自动化结果、审核者结果、原因、审核者身份和时间戳。 审核测试
    中央-006 P1 仪表板必须报告设备运行状况、上传延迟、OK/NG 趋势、缺少组件、条形码故障和特定于版本的性能，而不将经过审核的标签作为原始预测提供。 数据质量测试
    中央-007 P1 当远程配置分发进入生产范围时，它必须使用不可变版本包、兼容性检查、分阶段激活、确认和回滚。一个月的演示程序可以使用手动安装的校验和验证包。 分布测试
    中央-008 P1 媒体存储必须使用文件系统抽象或具有数据库元数据和完整性检查的 S3 兼容对象存储。 存储集成测试
    中央-009 P0 中央不可用不得改变或阻止边缘检查决策。 停电测试
    中央-010 P2 未来的模型包分发可以在验证签名/批准要求后共享版本化分发机制。 发布资质

    5. 数据及上传要求¶

    5.1 Common Inspection Record¶

    每次检查必须包含在边缘生成的全局唯一的检查ID；设备ID；检查开始/结束时间戳；条形码值和读取状态（如果有）；解析的产品类型和解析来源；最终经营成果；内部决策状态；检测到、缺失和低置信度的组件；每个组件的汇总证据；产品盒和 ROI 映射；帧质量总结；产品检测器模型、组件检测器模型、规则和产品配置版本；原因代码；媒体参考和校验和；和上传状态。

    5.2 上传个人资料¶

    结果 所需的中央有效负载
    OK 元数据、条形码、产品类型、决策、组件/置信度摘要、版本、设备/时间、一个代表性关键帧
    NG 完整元数据、缺失/低置信度组件、多个关键帧、带注释的关键帧、产品投资回报率、可选事件剪辑、相关错误
    系统异常 异常类型、设备/相机状态、可用的相关图像、有界日志摘录、时间戳

    不得上传每个视频帧。当批准的政策要求时，可以保留完整或滚动的本地视频。准确的计数、格式和保留期限是需要验证的配置决策。

    6. 质量属性¶

    身份证 优先 要求 验证
    QA-001 P0 离线检查必须在经过验证的中断持续时间内持续进行，该持续时间受本地存储​​容量的限制。 浸泡/断电测试
    QA-002 P0 检查和上传状态必须在容器重新启动和主机重新启动后继续存在，而无需重复的业务决策。 重启测试
    QA-003 P0 所有可变操作配置必须在激活之前进行版本控制、验证，并可归因于参与者或来源。 审核测试
    QA-004 P0 日志必须按设备 ID、检查 ID、上传任务 ID、请求 ID 和活动版本（如果适用）进行结构化和关联。 可观察性测试
    QA-005 P0 磁盘监控必须在耗尽之前发出警告，并应用安全、确定性的清理策略；当无法提交强制证据时，disk-full 不得产生 OK。 磁盘满测试
    QA-006 P0 必须记录时钟健康状况和中央接收时间，以便可以检测到时钟漂移；订购不能仅依赖挂钟时间。 时钟偏差测试
    QA-007 P1 API 必须使用模式验证、有界有效负载、分页、记录错误和生成的 OpenAPI 合约。 合同/安全测试
    QA-008 P1 运行时服务必须使用健康检查、重新启动策略、持久卷、环境配置、非根容器和只读文件系统（如果可行）。 部署检查
    QA-009 P1 性能验收必须根据观察到的线路时序而不是发明的目标来衡量平均/P95 延迟和吞吐量。 负载/验收测试
    QA-010 P1 对中央管理、配置、审查和证据的访问必须经过角色授权和审核。 授权测试
    QA-011 P1 边缘和中央实现必须使用 Python 3.12，Web 应用程序必须在批准的技术基线下使用 Vue 3 和 TypeScript。 建造检验
    QA-012 P1 测试和评估必须报告 NG 召回率、假阴性/阳性率、每个组件/产品的召回率、采集阶段、条码成功率、延迟、吞吐量、上传延迟以及审核/纠正率。 发布报告

    7. 按范围划分的范围要求¶

    7.1 静态训练和检查 MVP¶

    适用的要求包括 BR-002、BR-003、EDGE-005 到 EDGE-008、EDGE-010，以及可为静态图像填充的跟踪字段。 MVP 验证标准 YOLO 标签，通过单独的仅供开发人员使用的 CLI 训练产品和组件模型，准备 ROI 坐标组件标签，并根据文件名基本事实验证保留的静态结果。它使用文件夹输入和输出文件；它不声称 EDGE-001 到 EDGE-004 或操作耐久性。

    7.2 一个月目标¶

    目标是一个受控集成演示器，适用于一个产品系列、一台相机、一个经过验证的窗口机制和一个条形码路径。它实现持久的本地决策、离线操作、选定的媒体上传、一个幂等的中央摄取/历史路径、最少的飞行员身份验证、基本的本地仪表板和最小的中央检查/审查视图。通用管理、报告、远程配置交付和完整的弹性矩阵都被推迟。

    7.3 生产目标¶

    所有 P0 和适用的 P1 要求必须有客观证据。发布还需要客户商定的阈值、操作手册、安全审查、恢复/浸泡测试、可接受的保留、包回滚以及谨慎的人机交互部署。

    7.4 未来¶

    P2 要求和集成单独批准。 Kubernetes、自动再训练、Tauri 打包、PLC/MES 集成和边缘 PostgreSQL 不是默认的生产依赖项。

    8. 限制和非要求¶

    • 边缘部署不能依赖于Kubernetes；核心设计仍然对 Docker Compose 友好。
    • 在没有测量证据的情况下，AssemblyVision 不保证 100% 的准确性或近乎零遗漏的 NG 案例。
    • 该设计未假设确切的相机/扫描仪供应商、GPU、操作系统、条形码标准、传送带速度、网络可用性、组件类别、保留期、服务器位置或接受阈值。
    • 主仪表板不会使用 Tkinter、PyQt 或 PySide。未来的轻量级桌面包装器可能会托管本地 Web 应用程序。
    • .pyc 文件和 Docker 镜像减少了随意的源浏览，但不是反逆向工程或源安全边界。
    • 训练数据、笔记本、生产运行时数据和长期机密不得包含在客户端运行时映像中。

    9. 开放问题和需要验证¶

    1. 哪些确切的阈值、置信策略和所需的证据可以证明每个组件的存在？ 2、UNCERTAIN是暴露给运营商还是只保留在内部，而业务输出仍然是NG？
    2. 1个月目标中哪些边缘操作需要身份验证？
    3. 当存储降级时，哪些元数据/媒体对于本地提交的结果是必需的？
    4. 边缘必须支持多长的中断持续时间和磁盘预留？
    5. 哪些授权、审计保留、加密和数据驻留义务集中适用？
    6. 根据基线数据商定哪些可衡量的绩效和接受阈值？
    7. 权威的未解决列表是Global Open Questions。
