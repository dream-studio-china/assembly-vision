    9. 元件检测¶

    9.1 责任¶

    第二阶段从 product detection and ROI 检测有效产品 ROI 内已配置的组件类。它向 temporal aggregation 发出帧级观察；它不直接发出 OK 或推断抽象全局 missing_component 类。

    9.2 检测模型¶

    Ultralytics YOLO 是最初的实现。必需的类可能包括 component_a、component_b、component_c 和 manual，但实际的分类是产品配置数据。条形码解码仍然是一个单独的子系统； YOLO 可以定位条形码区域，但不得取代基于标准的解码。

    每个模型包包含：

    • 不可变版本和 SHA-256 校验和；
    • 权重和运行时间格式；
    • 类 ID 到名称的映射；
    • 预期的色彩空间、尺寸和信箱政策；
    • 经过验证的阈值范围和兼容的产品配置模式版本；
    • 培训/评估来源和发布状态。

    如果校验和、类映射、运行时兼容性或所需的配置类未验证，则加载失败。

    9.3 框架级契约¶

    对于每个有效的 ROI，返回原始合格检测和标准化 ComponentDetection 记录，其中包含组件键、置信度、ROI 框、全帧框、可用的可见区域估计、帧 ID、质量状态和模型版本。在业务聚合之前保留检测，以便可以审核阈值。

    def detect_components(roi, required, manifest):
    predictions = model.predict(roi.image)
    observations = map_to_domain(predictions, roi.transform, manifest.class_map)
    return [
        item for item in observations
        if item.component_key in required
        and item.confidence >= required[item.component_key].observation_threshold
        and spatially_valid(item, required[item.component_key])
    ]

    observation_threshold 控制证据收集，其本身并不是存在的证明。聚合器应用更严格的每个组件接受策略。

    9.4 产品特定的空间约束¶

    规则可以定义预期的标准化区域、最小框面积、最大框面积或每个组件的允许计数。这些约束减少了错误匹配，但必须容忍测量的生产位置和装配变化。坐标在生成的产品 ROI 内标准化，而不是在全帧内标准化。

    当重复的框引用一个物理组件时，模型 NMS 首先处理重叠。稍后评估业务数量限制。如果规则只需要一份手册，并且有信心检测到两份手册，则证据是矛盾的，并且在没有明确规则的情况下无法产生OK。

    9.5 配置¶

    component_detection:
  model_version: component-yolo-1.0.0
  iou_threshold: 0.50
components:
  manual:
    observation_threshold: 0.45
    high_confidence: 0.85
    medium_confidence: 0.65
    expected_count: 1
    min_box_area_ratio: 0.02
    allowed_zone: [0.05, 0.10, 0.95, 0.90]
  component_a:
    observation_threshold: 0.50
    high_confidence: 0.90
    medium_confidence: 0.70
    expected_count: 1

    每个组件的设置均使用规则/产品配置进行版本控制。产品窗口固定配置和型号版本。阈值更改需要审核记录和回归评估。

    M1 静态管道在每个组件中实现 observation_threshold 管道配置； high_confidence、medium_confidence、 expected_count、min_box_area_ratio 和 allowed_zone 位于 规则 模式（设计 11）并由规则引擎而不是规则引擎进行评估 管道配置如上所示 (AUDIT-001)。

    9.6 证据语义¶

    • 合格检测仅针对其映射组件而言是肯定的框架证据。
    • 没有检测到是指缺乏积极的证据，本身并不能证明该组件缺失。
    • 保留低置信度观察结果用于诊断，但除非时间策略明确积累了足够的独立证据，否则不能升级为呈现。
    • 被拒绝的质量框架不提供正面或负面证据。
    • 一个组成部分的证据不能补偿另一组成部分。
    • 未知的模型类被记录并忽略以满足所需的组件。

    9.7 故障处理¶

    推理超时、内存不足、输出格式错误、模型进程崩溃、转换失败或版本不匹配会使受影响的帧无效。如果无法提供所需证据，则最终结果为NG。实现绝不能从另一个框架、ROI、产品或模型调用中进行检测。

    在可恢复的加速器故障后，工作线程可以重新加载或使用经过验证的 CPU 运行时（如果已配置）。回退运行时必须使用相同的清单并单独进行性能测试；记录切换运行时间。服务器连接对本地推理没有影响。加速器/GPU 故障根据弹性矩阵 (22.8) 进行故障注入：可恢复故障可能会回退，不可恢复故障必须故障并阻止检查，永远不会从不完整的证据中产生 OK。

    9.8 性能和并发性¶

    保持模型实例正常运行并将并发绑定到测量的 GPU/CPU 容量。背压必须是明确的。仅在测量每个组件的 NG 召回率后才优化输入大小、运行时间或帧采样；禁止默默地丢弃帧以满足吞吐量。采样必须保留最低有效帧要求和产品窗口标识。

    9.9 验证¶

    • 单元测试类映射、阈值边界、空间约束、计数和坐标转换。
    • 合同测试模型清单和不兼容的包拒绝。
    • 评估每个组件、产品类型、位置、批次和型号版本的精确度和召回率。
    • 包括故意缺失的组件、困难的当前组件、空的 ROI、反射和遮挡。
    • 按物理产品、捕获会话、批次或日期（而不是相邻视频帧）分割数据集。
    • 错误注入超时、OOM、张量格式错误和工作进程重启；没有人可以从不完整的证据中得出OK。
    • 故障注入加速器/GPU故障；验证重新加载或验证的 CPU 回退使用相同的清单，记录运行时切换，并且永远不会从不完整的证据中产生 OK。
    • 部署硬件上的基准平均/P95 推理延迟和持续吞吐量。

    9.10 未解决的问题和需要验证¶

    • 定义准确的组件分类、所需数量和产品类型映射。
    • 确定哪些组件需要空间约束或额外的 OpenCV 检查。
    • 在边缘硬件基准测试后选择模型输入大小和运行时间。
    • 根据保留的生产数据建立每个组件的观察、中等和高置信度阈值。
    • 收集足够的真实缺失组件示例并确认标签指南。
