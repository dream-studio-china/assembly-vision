    13. 上传与同步¶

    13.1 目的和边界¶

    上传子系统将本地保存的检查记录和选定的媒体异步同步到中央服务器。它使用 local storage and retention 中定义的事务发件箱。它从不参与图像推理或本地规则评估，并且当本地受保护的存储仍然可用时，服务器不可用不得停止检查。

    13.2 上传范围¶

    对于 OK，上传检查元数据、条形码、产品类型、决策、组件/置信度摘要、版本、设备/时间戳和一个代表性关键帧。对于 NG，上传完整的元数据、缺失/不确定的组件、多个关键帧、带注释的图像、产品 ROI、可选事件剪辑和相关诊断。对于系统异常，上传异常类型、设备/摄像机状态、相关媒体/日志摘录和时间戳。

    不要上传每个视频帧。介质选择在本地进行并记录在检查清单中。

    13.3 任务和协议设计¶

    一项检查具有稳定的客户端生成的 inspection_id 和清单校验和。每个上传任务都有一个稳定的 upload_task_id、设备 ID、可为空的检查 ID、工件身份、有效负载哈希、SHA-256 校验和（如果适用）、字节大小、尝试计数、下次尝试时间、时间戳、租用和状态。规范状态包括 PENDING、IN_PROGRESS、RETRY_WAIT、SUCCEEDED、PERMANENT_FAILURE 和 CANCELLED。

    元数据摄取使用稳定的幂等键inspection:{device_id}:{inspection_id}。架构和清单版本保留在散列有效负载内，而不是更改密钥。中央服务器强制 (device_id, inspection_id) 和 (device_id, idempotency_key) 的唯一性，使用接受的元数据自动存储收据，并将其返回以进行相同的重播。具有不同不可变内容的重播会返回冲突并被隔离而不是被覆盖。

    大型媒体应在合理的情况下使用可恢复或预签名的对象上传。仅在服务器确认预期大小/校验和并将对象绑定到检查后才接受完成。

    13.5 重试策略¶

    重试连接失败、超时、HTTP 408、429 和 5xx，在配置的范围内遵守 Retry-After。不要无限期地自动重试身份验证/授权失败、架构不兼容、校验和冲突或无效内容。使用具有完全抖动的指数退避：

    delay = random(0, min(max_delay, base_delay * 2 ** min(attempt, exponent_cap)))

    工作线程并发和带宽是有限的，因此上传不会导致推理不足或填满内存。工作线程崩溃后，租约会恢复任务。断路器可减少中断期间的重复流量，但会定期探测恢复情况。

    脱机持续时间受本地受保护存储容量的限制，而不是受服务器上软件依赖性的限制。如果容量达到停止阈值，边缘必须停止接受检查，而不是删除受保护的证据或发出不可审计的OK决策。

    13.7 排序和同步¶

    服务器不得要求全局按时间顺序到达。设备可能会延迟上传或无序上传。设备 UTC 时间戳与时钟健康元数据一起保留；服务器接收时间是分开的。元数据先于媒体绑定，但检查可以集中可见，同时所需媒体具有生命周期PENDING；已验证的媒体变为AVAILABLE，终端故障变为FAILED，保留清理记录变为PURGED。

    配置/模型分发是一个单独的拉取/下载工作流程。上传确认无法激活新的规则或模型，并且中央数据永远不会追溯性地改变不可变的本地决策。人工审查会创建额外的中央记录，而不是重写原始证据。

    13.8 安全和配置¶

    将 TLS 与每设备凭据和最低权限范围结合使用。凭证在映像外部配置、可轮换且从不记录。验证服务器身份、响应大小、内容类型和超时。

    upload:
  base_url: https://central.example.invalid/api/v1
  connect_timeout_seconds: 5
  request_timeout_seconds: 30
  worker_concurrency: 2
  base_retry_seconds: 2
  maximum_retry_seconds: 900
  exponent_cap: 8
  task_lease_seconds: 120
  maximum_bandwidth_mbps: null
  circuit_failure_threshold: 5
  circuit_open_seconds: 60
  media_chunk_bytes: 8388608  # reserved; single POST envelope until the
                              # Edge-to-central resumable contract freezes

    占位符 URL、null 带宽、电路阈值/开放持续时间以及 media_chunk_bytes 需要站点配置；环境等价物 是AV_EDGE_UPLOAD_MAXIMUM_BANDWIDTH_MBPS， AV_EDGE_UPLOAD_CIRCUIT_FAILURE_THRESHOLD, AV_EDGE_UPLOAD_CIRCUIT_OPEN_SECONDS和AV_EDGE_UPLOAD_MEDIA_CHUNK_BYTES。

    13.9 故障处理与操作¶

    失败 行为
    DNS/网络/服务器中断 坚持并重试；当地检查仍在继续
    服务器提交后超时 重放相同的幂等键；服务器返回相同的收据
    工人坠毁 租约到期且任务符合条件
    HTTP 401/403 暂停受影响的任务，警告凭证错误，不要热循环
    HTTP 409 内容不匹配 永久故障/隔离；保存当地证据
    校验和不匹配 重新读取本地文件，如果本地有效则重试；隔离若地方腐败
    本地文件丢失 永久介质故障、警报、保留检查元数据
    队列积压增长 按年龄/计数/字节发出警报；保护推理资源

    按状态显示队列计数和字节数、最早的挂起时间、尝试率、成功/失败率、上传延迟、吞吐量、电路状态和上次成功联系。手动重试仅重置符合条件的任务并保留尝试历史记录。

    13.10 Verification¶

    • 在每个服务器提交边界超时后集成测试幂等重播。
    • 测试重复的任务交付、无序检查、重复的介质以及冲突的校验和。
    • 故障注入 DNS 失败、连接重置、响应缓慢、429、5xx、401、409 和工作线程终止。
    • 运行长时间的离线测试，继续检查，重新启动边缘，恢复网络，并验证完全耗尽而没有重复。
    • 验证上传负载不能违反检查延迟/资源限制。
    • 验证保留不会在验证收据之前删除所需的工件。
    • 合同测试客户端/服务器模式兼容性和不支持的版本处理。

    13.11 Open Questions and Validation Required¶

    • 确认中央服务器位置、API 所有权、身份验证方法和证书配置过程。
    • 定义最大预期中断持续时间和积压，以调整本地存储和服务器摄取容量。
    • 商定哪些媒体是结果强制的以及哪些媒体可以抽样。
    • 在文件大小测量后选择直接 API 上传与预签名的 S3 兼容分段上传。
    • 定义带宽限制、上传调度窗口以及客户网络代理/防火墙要求。
    • 定义永久上传失败的操作所有权和解决目标。

    13.12 实施状态（边缘发件箱和调度程序里程碑）¶

    持久上传发件箱及其工作人员的实现是 assemblyvision_edge：

    • 原子投影和发件箱：persist_inspection_and_enqueue_uploads 插入不可变的投影、媒体、证据和一个 INSPECTION 任务 在单个 SQLite 事务中为每个工件加上一个 MEDIA 任务，因此崩溃 无法在没有所需上传任务的情况下留下已完成的检查 （设计12.4步骤3+4）。启动协调应用相同的操作 每个有效的包，修复搁浅的 LOCAL_ONLY 记录而不是 跳过它们。
    • 订购、租赁的工人：UploadScheduler 在一个任务中声明到期任务 即时交易； MEDIA 任务只有在检查后才到期 任务保存经过验证的成功收据，因此元数据始终先于媒体。 每个声明都带有一个每个任务的防护令牌（lease_owner），并且陈旧 IN_PROGRESS 租约到期后任务被回收；每个终端或重试 更新需要匹配的令牌，因此迟到的工作人员无法覆盖 较新的支架。
    • 故障分类（设计 13.9）：运输错误和 408/429/5xx 安排具有完全抖动的指数退避，尊重 根据响应时间测量的数字Retry-After；本地丢失/损坏 证据（MEDIA_EVIDENCE_MISSING、MEDIA_CHECKSUM_MISMATCH、 INSPECTION_EVIDENCE_MISSING）和服务器冲突（409）成为永久性的 失败，同时保留当地证据。
    • 验证收据：只有当有界类型收据时，2xx 才是成功 回显幂等键、对象、种类、字节大小和校验和 实际发送的有效负载；媒体收据还需要一个中心对象 标识符。已验证的收据和中央对象标识符将被保留。 检查同步是根据所有必需的任务重新计算的： QUEUED 未完成时， PARTIAL 在带有待处理媒体的元数据之后， SYNCED 仅当每个必需任务都有经过验证的收据时，并且 FAILED 任何永久性故障。
    • 接收器和配置：DirectoryUploadSink（本地/开发和 测试，密钥幂等）和 HttpUploadSink （HTTPS POST 到 {base_url}/inspection-uploads 带有幂等密钥和负载）。的 通过 UploadSettings 支持的 serve 路径启用工作线程 和 AV_EDGE_UPLOAD_* 环境变量（端点或本地接收器， 单独的 AV_EDGE_UPLOAD_TOKEN 凭证、超时、重试/租用/批量 可调参数、带宽限制）。中央端点需要 HTTPS；明确的 开发 HTTP 仅限于环回。没有配置目的地 工作人员保持明确禁用状态，并且任务在上传中仍然可见 API。
    • 合同06覆盖：测试覆盖成功上传、网络 中断、重试/退避、Retry-After计时、重复排队、进程 重新启动租约回收和防护、丢失文件、校验和不匹配、 服务器幂等性冲突、收据验证、媒体之前的有序元数据 消耗、同步状态和无重复消耗。
    • 可观察性 (E1)：上传 API 报告任务状态；设备状态 公开持久队列事实（挂起计数/字节、最旧的挂起年龄） 存储库加上进程本地工作人员活跃度（尝试/成功/失败 来自调度程序的计数器、失败率、上次尝试/成功、上次错误）， 与 UPLOAD_BLOCKED （排队工作但没有工作人员）和 UPLOAD_FAILING （可重试积压或在工作待处理时未成功的尝试） 警报。任务负载大小记录在队列中，因此队列字节不需要 媒体阅读。

    剩下的连接试点：中央摄取端点及其 服务器端收据合同、媒体绑定确认和保留 对经过验证的收据进行控制。

    13.13 实施状态（上传弹性，E3）¶

    上传弹性里程碑在发件箱顶部添加了中断行为 调度程序（设计13.5/13.9，E3任务）：

    • 带宽限制：令牌桶限制器限制序列化 每秒实际发送到 HTTP 接收器的请求主体字节数 UploadSettings.maximum_bandwidth_mbps（None 禁用限制）。的 单位是传输写入的 JSON 信封（Base64 有效负载加上 元数据），而不是原始媒体字节；本地目录接收器报告零 网络字节。突发的上限为一秒的令牌，并且限制器从不 门本地持久性。超过一次突发的金额将拆分为每次突发 等待更新受保护的上传租约并在工作停止或租约时中止 损失（PR-022 F01/F02）。累计发送字节数和配置的上限为 通过调度程序运行状况和设备状态暴露。
    • 断路器：连续可重试失败 (circuit_failure_threshold) 开路；打开调度程序时 没有声明任何内容，并且在 circuit_open_seconds 之后有一个半开探针 判断恢复情况——成功关闭电路，失败重新打开电路。 永久性故障永远不会计入电路中。电路状态和最后一次 通过稳定的 UPLOAD_CIRCUIT_OPEN 警报来暴露更改；耐用的 队列永远不会被电路改变。
    • 受控手动重试：POST /api/v1/uploads/{upload_task_id}/retry 仅将 RETRY_WAIT / PERMANENT_FAILURE 任务重置为 PENDING attempt_count + 1；未知任务为 404，不合格任务为 409 没有突变。
    • 长时间停电消耗：故障注入测试离线运行数天 检查、进程重新启动以及耗尽整个队列的恢复 在媒体上传之前通过有序元数据实现无重复。

    13.14 可恢复的大媒体客户端合同（E3e）¶

    大型媒体（NG 剪辑、完整视频片段）可能会超过单次上传 信封。边缘侧边界和中央协议合约是 此处定义；中央端点未实现且分块传输 仅在边缘到中心合约冻结后才开始：

    • 每个媒体上传任务都保持稳定的upload_task_id和幂等性 钥匙；重试任何块或整个对象都会重用相同的密钥，因此 中央服务器可以对每个块和完成进行重复数据删除。
    • 传输按照配置的 media_chunk_bytes 上限进行分块 （UploadSettings.media_chunk_bytes，默认8 MiB，保留直到 合同冻结）。每个块都携带任务幂等键， 从零开始的块索引、总对象大小和 SHA-256 以及块 字节；块写入通过 (task, chunk index) 是幂等的。
    • 仅当服务器确认预期总数时才接受完成 大小和 SHA-256 并将对象绑定到检查；坚持的 然后媒体收据携带中央对象标识符，与 今天的单信封路径就是这样。
    • 在中央协议可用之前，每个任务都使用单个 POST 信封；块设置是占位符，不得假设为 改变转移行为。
