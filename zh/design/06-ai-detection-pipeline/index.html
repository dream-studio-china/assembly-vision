    6. AI检测流程¶

    6.1 目的¶

    本文档定义了从获取的图像到持久的产品级决策的端到端检查流程。详细的子系统行为在 camera and image acquisition、product detection and ROI、component detection、temporal aggregation 和 rule engine 中指定。

    安全不变量是：

    只有当每个必需的组件都有足够的有效证据并且每个强制性管道阶段都可验证时，才可以进行检查。缺失、不确定、无效或不可用的证据会产生 NG，而不是 OK。

    这是一种自动防故障的分类策略，而不是完美的检测准确性。

    6.2 按交付阶段划分的范围¶

    范围 包含
    静态训练和检查 MVP X-AnyLabeling YOLO 标签、产品和组件模型训练、文件夹输入、产品检测、ROI 提取、组件检测、确定性规则、JSON 结果、ROI 和注释图像、保留验证
    一个月生产目标 相机捕获、条形码分辨率、产品窗口、帧质量、每个组件时间聚合、本地持久性、异步上传
    未来 经过验证的视角标准化、硬件触发/PLC 适配器、模型集成、跨复杂场景的跟踪

    静态 MVP 故意排除视频聚合、中央服务器依赖性和自动驱动。其训练 CLI 仅供开发人员使用，永远不会成为检查运行时的依赖项。生产检查仍然完全可以在边缘计算机上执行；服务器可用性不能阻止或改变本地决策路径。

    6.3 管道合同¶

    所有阶段都会交换包含 inspection_id、捕获时间戳、坐标空间标识符和版本元数据的类型化、不可变记录。坐标表示为具有明确图像宽度和高度的像素空间 xyxy 值。管道记录：

    • 来源和框架标识；
    • 镜架质量和拒收原因；
    • 条形码和产品类型解析状态；
    • 产品检测、ROI 变换和组件检测；
    • 每个组件的汇总证据；
    • 最终决定和原因代码；
    • 产品模型、组件模型、产品配置和规则版本。

    实现应该在实时阶段之间使用有界的进程内队列。队列饱和是可观察到的，并且必须根据配置的策略丢弃，而不混合产品；所需证据被丢弃的检查是NG和INSUFFICIENT_VALID_FRAMES。

    单帧 MVP 证据不被视为时间证据。每个必需的组件必须独立地通过其配置的单帧阈值。

    6.5 实时处理流程¶

    实时管道对每个物理产品执行以下步骤：

    1. 从权威触发器或经过验证的输入事件打开产品窗口。
    2. 使用确定性质量门捕获帧并拒绝不可用的帧。 3、解析条码和产品类型；不要猜测不明确的映射。
    3. 准确检测一种可检测产品并得出其投资回报率。
    4. 检测每个有效 ROI 中的组件并按组件密钥保留证据。
    5. 使用配置的退出、超时或触发条件关闭窗口。
    6. 独立地汇总每个所需组件的证据。
    7. 评估固定的规则和配置版本。
    8. 在发布完成之前以事务方式保留结果和媒体。
    9. 独立于检查执行的排队上传。

    仅当批处理保持在产品窗口延迟预算内并保留帧与检查的相关性时，才可以对推理进行批处理。

    6.6 配置¶

    pipeline:
  max_inflight_inspections: 2
  frame_queue_size: 12
  inspection_timeout_ms: 2500
  minimum_valid_frames: 3
  fail_on_multiple_products: true
  require_barcode: true
  persist_before_complete: true
models:
  product_manifest: /opt/assemblyvision/models/product/manifest.json
  component_manifest: /opt/assemblyvision/models/component/manifest.json
quality:
  min_laplacian_variance: 80.0
  min_mean_brightness: 35.0
  max_mean_brightness: 225.0

    上面的 pipeline.* 键描述了生产窗口管道，并且是 deferred：M1静态单帧CLI仅接受product_detection， component_detection、components 和 roi 部分并拒绝未知 键（AUDIT-001）。

    配置在启动时进行模式验证。无效的配置会妨碍检查准备工作。当产品窗口打开时，活动模型、规则和产品配置版本将被固定，并且无法在该窗口内更改。

    6.7 故障处理¶

    失败 所需行为
    图像无法读取或相机帧损坏 排除框架；如果证据不足，则返回 NG
    条形码缺失、不明确或在需要时未映射 NG；不使用推断的产品类型
    没有产品、有多个产品或无效的投资回报率 NG；当输入无效时跳过组件推理
    模型加载/推理错误 标记子系统不健康并检查NG；永远不要重复使用以前的检测
    超时或队列溢出 以 NG 方式关闭受影响的窗口；保留诊断
    本地结果无法持久保存 不要公布OK；引发阻塞本地存储故障
    服务器/网络不可用 继续本地检查并排队上传

    异常在子系统边界处转换为显式原因代码。原始异常和堆栈跟踪属于结构化日志，而检查记录包含稳定的业务原因代码。

    6.8 可观测性¶

    记录阶段延迟、有效/拒绝帧计数、产品检测成功、ROI 失败、条形码读取成功、每个组件的置信度分布、按原因的决策计数、队列深度、推理设备和活动版本。日志包括inspection_id、frame_id、device_id；它们不得包含凭据或无限制的图像数据。

    6.9 验证¶

    • 单元测试阶段契约、阈值边界、坐标变换和原因代码映射。
    • 运行黄金图像测试，并将预期检测和决策固定到模型清单上。
    • 验证每个注入的阶段异常是否都会生成 NG 或阻止就绪，而不是 OK。
    • 在窗口边界测试混合产品类型和版本变化。
    • 测量平均和 P95 延迟、吞吐量、NG 召回、产品检测成功和每个组件召回。
    • 在确定性推理支持允许的情况下，从持久输入、配置和版本元数据中再现结果。

    6.10 未解决的问题和需要验证¶

    • 测量传送带速度后确认生产延迟和吞吐量预算。
    • 选择并验证边缘推理硬件和执行提供商。
    • 确认条形码解析是否对每种产品类型都是强制的。
    • 通过客户操作确定一个框架中多个产品的批准行为。
    • 使用未用于培训的生产数据建立测量的验收阈值。
