    19. 培训与评估¶

    19.1 目标和范围¶

    训练生成用于全帧的产品检测器和用于产品 ROI 的组件检测器。评估可衡量探测器行为和完整的产品级检测系统。主要的安全目标是极高的 NG 召回率和相应的低假阴性率，这在保留的生产数据中得到了证明；没有数据集大小或模型指标可以保证完美的性能。

    模型元数据遵循Data Model and Database。模型注册和审查表面在 Central Admin Dashboard 中描述，代码所有权在 Monorepo and Code Organization 中描述。

    19.1.1 静态训练和检查 MVP¶

    MVP 在相机集成之前实现了开发人员控制的训练到检查循环。 X-AnyLabeling 是选定的注释工具，并导出标准 YOLO 文本标签。产品和组件盒以全框坐标进行注释。训练 CLI 验证导出的数据集，从全帧图像训练产品检测器，然后使用产品 ROI 变换来裁剪组件训练图像，并在组件训练之前将组件框重新映射到 ROI 坐标。

    运行时检查 CLI 仅使用生成的不可变权重工件和清单。训练代码位于单独的 training/ 工作区中，永远不会由运行时导入，并且被排除在运行时发行版之外。配置的文件名约定为保留验证提供了预期的 OK 或 NG 标签；它不能替代检测器训练期间的边界框标签。

    第一个 MVP 在开发人员具有 16 GB 内存的 Apple Silicon Mac 上运行小型模型并测量图像尺寸。它记录再现性元数据并报告保留的静态设置结果，但不声明生产精度、生产吞吐量或生产验收。具有 SHA-256 清单的普通模型工件对于此 MVP 来说已经足够了；模型加密和仅限 .pyc 的分发打包被推迟。

    最小 YOLO 数据集布局为：

    dataset/
├── images/{train,val}/
├── labels/{train,val}/
└── data.yaml

    每个标签文件共享其图像基名并包含标准化的 YOLO 类和框坐标。 data.yaml 类名顺序是权威的类 ID 映射。培训和验证小组必须将衍生作物及其源产品/会话放在一起。

    19.2 任务定义¶

    19.2.1 产品检测器¶

    输入是一个完整的大约四兆像素的生产帧。输出是产品类别、边界框和置信度。第一个目标是一个 product 类，除非产品类对于 ROI 处理在视觉上是必需的。产品标识通常应来自条形码/产品映射，而不是视觉分类。

    初始收集目标是大约 300 到 800 个真实生产图像，包括轻微的位置变化、正常生产变化、空传送带/背景底片、部分进入/退出帧、模糊、反射和预期遮挡。这是一个规划范围，而不是接受门槛。

    19.2.2 元件检测器¶

    输入是由生产 ROI 代码生成的产品 ROI。输出类是具体的必需组件，包括适用的手册。训练可见的所需组件；不要训练通用的 missing_component 类。初始规划是每个组件类大约 300 到 500 个标记实例，加上有意创建的缺失组件场景，在可行的情况下，每个缺失场景开始近 100 个产品实例。

    19.2.3 系统决策¶

    该系统结合了框架质量、产品检测、ROI 生成、跨框架的组件证据、条形码/产品分辨率和确定性规则。组件模型的失误可以通过时间证据来恢复；时间聚合不会提高检测器的单帧精度。最终产品级指标必须执行精确的生产预处理、阈值、聚合和规则版本。

    19.3 数据清单和来源¶

    每个源图像/帧都与一个清单相关联，其中包含：

    • 数据集/源记录 ID 和不可变文件校验和。
    • 站点、线路、摄像机和捕获设置标识符（如果允许）。
    • 捕获会话 ID、生产日期、产品批次和物理产品实例 ID。
    • 视频/检查窗口 ID、帧索引和时间戳。
    • 在允许的情况下，受保护元数据中的产品代码/类型和条形码。
    • 故意的缺陷场景和已知的缺失组件。
    • 相机角度/设置修订、照明/曝光修订和软件捕获版本。
    • 注释版本、注释者、审阅状态和排除原因。
    • 同意、保留和允许使用分类。

    原始数据是不可变的。更正创建新的注释/数据集版本。对个人或商业敏感的标识符进行假名化以进行培训，同时保留受控的可追溯性地图。

    19.4 集合设计¶

    使用实际生产的相机、光学器件、安装、照明、传送带背景、捕获软件和图像编码进行收集。初始模型针对一个固定的生产角度进行优化。显着的角度变化（包括接近 45 度的变化）是需要评估、额外收集/微调和完全重新验证的域变化。

    集合必须代表：

    • 每个受支持的产品和所需的组件。
    • 跨批次/日期和普通位置变化的真正 OK 产品。
    • 针对每个缺失的组件和缺失的手册，物理构建了 NG 产品。
    • 条码成功、损坏/遮挡/无法读取的条码以及未知的映射情况。
    • 空帧、部分产品、多产品异常、模糊、反射、遮挡、曝光变化和安全相机位置公差。
    • 用于窗口/聚合测试的连续 OK、连续 NG 和混合产品序列。

    不要通过数字擦除组件来合成所有 NG 示例。合成编辑可能会增加罕见的变化，但物理捕获的缺陷是必要的，因为阴影、包装变形和显示的背景有所不同。

    19.5 注释协议¶

    使用稳定的组件代码、包含/排除规则、最小可见性、遮挡/截断标志和困难情况示例定义版本化的类本体。产品盒一致地封装可见的产品。组件框使用 ROI 坐标，但保留源帧变换元数据。

    工作流程：

    1. 注释器从锁定的本体中进行标记，并标记不明确/不可用的图像，而不是猜测。
    2. 自动检查拒绝无效框、未知类别、不可能的图像尺寸、重复项和缺少所需元数据。
    3. 第二位审核员检查所有 NG 场景、所有模糊标签以及具有统计意义的普通标签样本。
    4. 在批量重新标记之前对分歧进行裁决并更新本体指南。
    5. 数据集发布冻结文件校验和、注释哈希、本体版本和出处清单。

    跟踪每类盒子计数、产品实例计数、会话、批次和缺陷场景。当许多帧来自一个产品通道时，仅帧数就夸大了多样性。

    19.6 防泄漏数据分割¶

    19.6.1 分割单元¶

    最小拆分组是整个检查/视频窗口中的物理产品实例。首选结合捕获会话、产品批次、生产日期和设置修订的更高级别组。从一个源组派生的所有相邻帧、裁剪、增强、重新编码和注释都保留在一个分割中。

    切勿随机分割单个视频帧。训练和验证中几乎相同的帧会产生误导性的指标，并根据重复的证据调整时间聚合。

    19.6.2 推荐设置¶

    设置 目的 访问和重用规则
    培训 拟合模型重量 可重复采样和增强
    验证 选择架构、超参数、阈值和聚合策略 允许重复使用；不是最终的无偏估计
    内部测试 发布前锁定工程对比 有限的评估；在没有创建新的测试版本的情况下，切勿对故障进行训练/调整
    客户验收 使用生产数据进行最终的特定地点验证 不用于训练或模型选择；客户同意的协议
    生产审核 持续漂移和抽样 OK/NG 审查 时间向前；仅在评估快照冻结后才晋升为培训

    百分比取决于可用的独立组。合理的计划开始时间为 2015 年 70 月 15 日，按分组实例进行训练/验证/内部测试，但优先考虑每个组件和产品足够的 NG 示例。客户接受集仍然是独立的，不是在调整后雕刻出来的。

    19.6.3 分体结构¶

    使用具有固定种子和清单的确定性、版本化组分配。在样本量允许的情况下，按产品、缺少组件的情况、站点/设置以及相关操作条件在组级别进行分层。报告任何对于独立评估来说太小的层，而不是跨分割移动类似重复的帧。

    在发布之前，运行泄漏检查：

    • 跨分割的精确 SHA-256 重复检测。
    • 感知哈希/嵌入最近邻审查，以检查近似重复项和提取的视频帧。
    • 物理产品、窗口、会话、批次和日期的组 ID 重叠检查。
    • 派生文件沿袭检查，确保作物和增强遵循其源拆分。
    • 条形码/产品实例标识符在允许标识符的情况下重叠检查。
    • 手动检查最接近的交叉分割图像对。

    19.7 Preprocessing and Augmentation¶

    训练和评估使用与生产相同的颜色转换、调整大小/信箱、ROI 扩展/剪切、方向逻辑和图像标准化。将这些参数存储在模型清单中。

    增强可能包括有界平移、缩放、温和透视、曝光/对比度、模糊、传感器噪声、压缩和部分遮挡（如果每个都代表合理的生产变化）。避免在固定相机下物理上不可能出现的大旋转或背景。除确定性生产预处理外，请勿增强验证、测试或验收图像。直观地审核类框转换。

    19.8 训练再现性¶

    每次运行都会记录源修订、环境/容器摘要、Python/CUDA/框架版本、随机种子、数据集/本体版本、拆分清单、基本权重、架构、图像大小、纪元、优化器/计划、增强、用于报告的阈值以及输出工件校验和。存储人类可读的配置和机器可读的运行元数据。

    训练代码必须支持 CI 中合成装置的试运行。完整运行在受控 GPU 基础设施上执行，而不是在边缘设备上执行。模型工件是不可变的并链接到评估报告；重新训练不会覆盖已发布的语义版本。

    19.9 检测器级指标¶

    对于产品和组件检测器报告：

    • 记录的 IoU 阈值的精确率-召回率曲线和平均精度，包括 mAP50 和 mAP50-95（如果适用）。
    • 每类精度、召回率、AP、支持度和置信度分布。
    • 在操作置信度/IoU 标准下产品检测成功。
    • 空/背景帧的错误检测。
    • 导致组件丢失的本地化/ROI 遏制失败。
    • 按产品、组件、批次/会话、位置范围、图像质量范围以及样本数量允许时的设置修订进行衡量。
    • 在代表性边缘硬件上分别进行推理预处理、模型和后处理延迟。

    mAP 对于模型开发很有用，但不是生产验收指标。根据验证数据选择阈值，将更高的成本分配给错过的 NG 结果，然后在测试/验收评估之前冻结。

    19.10 产品级系统指标¶

    令 NG 为真正有缺陷/不完整的产品，并预测 OK 为合格产品：

    NG recall = true NG predicted NG-or-uncertain / all true NG
False-negative rate = true NG predicted OK / all true NG = 1 - NG recall
False-positive rate = true OK predicted NG-or-uncertain / all true OK
OK precision = true OK predicted OK / all predicted OK

    如果UNCERTAIN遵循物理NG路径，则将其计为已捕获以进行安全召回，但单独报告，因为它增加了人工处理。还报告：

    • 每个组件缺失案例召回和缺失计数。
    • 按产品和按产品/组件召回。
    • 产品检测、ROI 生成、条形码读取和产品解析成功率。
    • 不可用的窗口和不确定的利率。
    • 平均、中值、P95 和 P99 端到端延迟；预期触发率下的吞吐量。
    • 按原始决定/原因进行手动审查和纠正率。
    • 按模型、规则和产品配置版本划分的指标。
    • 上传延迟和证据完整性与检查质量分开。

    每个比率包括分子、分母、置信区间和原始未命中计数。对于罕见的安全故障，零观察失误并不能证明零风险；报告二项式置信界。总体准确性永远不够，因为 OK 普遍性可能会隐藏遗漏的缺陷。

    19.11 时间和视频评估¶

    评估完整、有序的检查窗口，而不是打乱的帧。该工具可重现生产帧采样、质量排除、窗口边界、ROI 转换、聚合和规则。场景包括相邻产品、连续缺陷、混合产品类型、延迟条形码事件、丢帧、部分窗口、重复触发器和多个产品。

    比较单帧基线和配置的时间策略以量化系统的稳健性。报告每个组件检测运行的分布以及由帧混合引起的故障。阈值和策略优化仅使用验证窗口。

    19.12 误差分析¶

    每个误报都会受到原始帧/窗口、标签、检测器输出、质量过滤器、条形码/产品分辨率、ROI 映射、聚合证据、规则和精确版本的优先审查。分配一个或多个受控根本原因：

    • 注释/真实错误。
    • 产品未检测到或定位不良。
    • ROI 裁剪/转换错误。
    • 元件检测器缺失/混乱。
    • 质量过滤器拒绝了有用的证据。
    • 时间/窗口混合或帧不足。
    • 条形码/产品/规则映射错误。
    • 模型/规则不兼容或软件缺陷。
    • 未代表的域条件。

    修复程序是针对回归套件进行测试的。发现的测试失败只有在当前评估被冻结后才能进入未来的训练集；后续性能必须使用新版本的未触及测试集或时间推移验收样本。

    19.13 验收评估¶

    客户验收集使用未用于培训、验证、阈值选择或内部测试调整的生产数据。该协议在运行前商定，并分别涵盖产品类型、每个缺少的组件/手册、条形码故障、允许的位置偏移、正常变化、连续/混合决策、离线操作、重新启动和长时间运行操作。

    每个结果都保留事实真相、决策、证据、图像/剪辑引用、模型/规则/产品版本、设备、时间戳和相关日志。主要指标是真实的 NG 召回率。在基线数据收集和风险审查之后，与客户一起确定数字验收目标和所需的样本量；本文件不构成任何保证。

    19.14 生产监控和再培训¶

    按版本和产品监控输入和结果信号：产品盒位置/尺寸、框架质量、置信度分布、条形码故障、不确定/NG率、组件原因、手动更正和延迟。漂移警报会触发调查，而不是自动重新训练或阈值更改。

    生产抽样必须包括经审查的不合格案例、低置信​​度案例、例外情况以及预测合格产品的随机/分层样本；仅审查预测的 NG 无法估计假阴性。策展人删除重复项、更正标签、保留来源并批准添加。再培训升级重复泄漏检查、锁定评估、兼容性检查、分阶段推出和回滚准备。

    19.15 模型推广门¶

    仅当满足以下条件时才能发布候选人：

    1. 工件、清单、数据集和评估校验和完整且可重现。
    2. 所需的每个产品/每个组件层具有足够的数据或记录的限制。
    3. NG召回、假阴性计数、条形码/产品处理或延迟方面没有出现不可接受的回归。
    4. 规则和类兼容性验证通过。
    5. 内部测试结果由指定的工程/质量审批人员审核。
    6. 根据需要完成现场/客户验收。
    7. 确定推出和回滚版本。

    mAP 更好但产品级 NG 召回率更差的挑战者不会仅在 mAP 上得到推广。

    19.16 未决问题和需要验证¶

    • 确认支持的产品/组件、预期缺陷发生率以及每个场景实际创建的 NG 产品的可行数量。
    • 确认图像、条形码和评论标签的生产许可、隐私、保留和传输规则。
    • 定义可用于防泄漏分组的物理产品、批次、会话和相机/设置标识符。
    • 就注释本体、歧义政策、审查抽样和裁决所有者达成一致。
    • 基线评估后建立客户接受度目标、置信度、样本量和UNCERTAIN的处理方法。
    • 确认代表性边缘 CPU/GPU、所需吞吐量、传送带时序和延迟预算。
    • 定义允许的相机位置/角度/曝光容差以及声明域更改的过程。
    • 确认生产正常审核抽样所需，以估计误报和模型漂移。

    19.17 单产品数据采集和注释清单¶

    本节是常见情况的权威数据质量规范：一个 产品位于一台固定摄像机/照明/定位站。它转换了 19.2 中的规划范围成为具体的采购计划，指出了硬性规定 数据集适配器强制执行的注释规则，并定义切换 为培训渠道提供支持。对于操作步骤 参见Runbook 11；的 Imaging Workflow and Training Cost 中的外部清单 保留支持材料。

    19.17.1 为什么单一固定产品更容易¶

    固定相机下的固定产品会瓦解类内方差： 产品检测器任务变得几乎恒定（“板存在/不存在/部分/ 多个”），而分量检测器只需要区分“这部分是 此处”来自同一板上的“此垫是空的”。公共多板数据集 （例如通用 PCB 组件集）将一类分散到数十个视觉上 不同的产品，这就是为什么小型多板模型通用性较差的原因 而小型单一产品模型可能是有效的。瓶颈从来都不是 好的一面；它是缺失组件 (NG) 面：物理缺失 生产线上的零件很少，难以构建，并且每种故障模式都需要模型 从未见过有假阴性的风险。

    19.17.2 收集数量（计划范围，而非接受阈值）¶

    产品检测器（第 1 阶段，全画幅）：

    内容 建议计数
    跨批次/日期和位置变化的 OK 产品 100-300
    空传送带/背景（产品缺失）- 明确的空标签 30-60
    部分进入/退出框架 20-40
    一框内有多个产品（异常） 10-20
    模糊、反射、遮挡、曝光变化 每个 10-20 个

    组件检测器（第 2 阶段，ROI）：

    内容 建议计数
    每个所需组件类的标记实例 每班300-500
    每个缺失场景的物理缺失部分 每个缺失位置 ≥ 100
    缺少多个组件（组合） 每个组合 20-50
    负投资回报率作物（空焊盘，无组件） 与缺失样品的顺序相同

    条形码（与 YOLO 分开）：可读、损坏/遮挡和不可读的情况 用于产品类型解析和故障安全路径。

    最小闭环（让管道运行并测量趋势）可以 从 40-60 个 OK 图像开始，每个缺失位置加上 10-20 个样本，然后扩展到 上表；展开 verify 暴露遗漏 NG 的位置。

    19.17.3 硬注释规则（由适配器强制执行）¶

    • 两个数据集，两阶段语义。 dataset_product 承载一个类 product = 独立注释的全板框。 dataset_components 以固定顺序携带所需的组件类（data.yaml顺序 是类 ID 映射）。缺少的组件由 ** 不存在表示 组件盒的**；永远不要训练通用的 missing_* 类。
    • 即使组件丢失，产品盒也是强制性的。 第一阶段必须 对于有缺陷的电路板也可以本地化完整的产品。图像与 组件盒但无产品盒为数据错误，被拒收；的 产品盒永远不能从现有组件盒的组合中派生出来。
    • 显式空标签。 每个背景/底片图像必须有一个 显式空标签文件；需要图像/标签配对。适配器 拒绝每个分割中没有标签文件的任何图像，并且 av-train 验证拒绝丢失的标签文件，除非记录 --allow-missing-labels 使用旧版选择加入。
    • 仅限物理 NG。 不要通过数字擦除来合成所有 NG 组件；阴影、包装变形和显示的背景不同 （19.4）。
    • 固定捕获条件。 使用生产相机、光学器件收集， 安装、照明、传送带背景、捕获软件和编码。一个 显着的角度变化是需要重新验证的域变化（19.4）。
    • 第二次审查。 审查员检查每个 NG 样本、所有不明确的标签、 和普通标签样本（19.5）；争议的裁决是针对 锁定本体。

    19.17.4 防漏电分裂和切换¶

    • 按物理产品实例/捕获会话分割，绝不是随机分割 框架；目标为 2015 年 70 月 15 日，按分组实例 (19.6)。保留的 test split 仅用于验证而不用于调整。
    • 使用 X-AnyLabeling 进行注释并导出 YOLO 布局（train/val/test + classes.txt 或 data.yaml)，然后运行 scripts/adapt-xanylabeling.py <export> <out> --product-class product --required '<comma,separated>'。 适配器验证每个标签行，强制执行 19.17.3，保持显式 背景负片，拒绝丢失的标签文件和同干图像 每个分割的冲突，将 Roboflow 的 valid 分割标准化为 val，并且 发布 dataset_product + dataset_components + test-expected.json + manifest.json 原子地与数据集相关 data.yaml 路径。 Roboflow 导出使用 scripts/adapt-roboflow-dataset.py。
    • 使用模型冻结数据集校验和以及注释/本体版本 舱单（19.8，合同10）；验证集绝不能复制到 培训或验证。
