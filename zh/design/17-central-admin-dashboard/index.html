    17. 中央管理仪表板¶

    17.1 目的和边界¶

    中央管理仪表板提供整个车队的历史记录、审查、配置、模型生命周期可见性、报告、用户和审计。它不执行生产检查，并且不能是边缘设备的运行时依赖项。

    Vue 3 应用程序使用 REST API and Events 中的中心契约、Data Model and Database 中的架构以及 Training and Evaluation 中的求值语义。

    17.2 角色和权限¶

    能力 观众 审稿人 配置管理器 车队管理员 组织管理员/审核员
    仪表板/历史/媒体 是的 是的 是的 是的 是的
    提交审核更正 没有 是的 没有 没有 可配置
    起草/发布产品和规则 没有 没有 是的 没有 可配置
    注册/发布模型版本 没有 没有 是的 没有 可配置
    注册/分配/禁用设备 没有 没有 没有 是的 可配置
    管理用户和角色 没有 没有 没有 没有 是的
    查看审核日志/导出敏感数据 明确许可 明确许可 明确许可 明确许可 是的

    服务器强制执行每个权限和组织范围。路由防护提高了可用性，但不是安全边界。如果身份提供者支持，敏感导出和发布操作需要最近的身份验证。

    17.3 导航和页面¶

    路线 页 核心功能
    /overview 机队概览 KPI、业务结果/延迟趋势、活动警报、设备状态、上传延迟
    /devices 和 /devices/:id 车队管理 站点/线路过滤、上次查看、版本、分配、事件历史记录
    /inspections 和 /inspections/:id 检查历史 跨设备搜索、证据/媒体、版本溯源、审核状态
    /reviews NG审核工作队列 索赔/公开、比较证据、附加处置/组件更正、提交原因
    /products 产品管理 稳定的产品、不可变的版本、条形码映射、组件
    /rules 规则管理 起草、验证、比较、发布、分配影响
    /models 模型注册 清单/工件、评估摘要、生命周期、兼容性
    /reports 报告和出口 已保存的过滤器、异步作业、过期下载
    /users 用户和角色 组织分配和最低权限角色
    /audit 审计追踪 演员/动作/资源/时间搜索以及之前/之后的详细信息

    站点和线路过滤器保留在 URL 中，因此可以共享和重新访问视图。所选择的时区是明确的；存储的数据仍为 UTC。 UI 绝不会默默地更改页面之间的指标过滤器。

    17.4 机队概览¶

    概述从数据新鲜度和过滤上下文开始，然后介绍：

    • 所选期间的总检查和合格/不合格/不确定计数。
    • 仅当审查的基本事实足够时才进行 NG 召回；否则将其标记为不可用或初步的。
    • 结果率、条码读取失败率、产品检测失败率、ROI 失败率和手动纠正率。
    • 平均和 P95 检查延迟、检查吞吐量、上传延迟和最早的待上传。
    • 按组件和产品划分的缺失组件分布。
    • 模型/规则版本与样本计数和置信区间（如果适用）的比较。
    • 设备状态表显示就绪、检查、暂停、故障、脱机、上次查看、磁盘状态、活动版本和积压。

    图表必须在工具提示或相邻细节中显示分子、分母、样本计数、时间段和活动过滤器。 “准确性”不能成为唯一的标题指标。空数据或延迟数据不会绘制为零。

    17.5 设备管理¶

    设备列表支持组织授权的站点、线路、运行状态、型号/规则版本和上次查看的过滤器。设备详细信息包括身份、注册/证书状态、所需配置与报告配置、运行状况时间表、上传积压、最近检查和事件。

    配置分配是一个版本化的期望状态操作：

    1. 选择兼容的已发布产品/规则/模型包。
    2. 显示类、运行时和产品版本兼容性验证。
    3. 预览受影响的设备和当前版本。
    4. 要求原因和可选的推出窗口。
    5. 用乐观并发来保存。
    6. 跟踪设备中所需的、下载的、验证的、激活的、失败的和回滚的报告。

    MVP 一次可以分配一台设备。分阶段队列部署、金丝雀、自动回滚和维护窗口是稍后的功能，但架构/状态名称不应意味着立即成功激活。

    17.6 检查检索和证据审查¶

    搜索支持限时、站点、线路、设备、业务结果、内部决策、条形码、产品、组件原因、审核状态、模型版本和规则版本。结果使用服务器端键集分页。过滤器芯片和 URL 查询状态使主动约束变得明确。

    检查详细信息分别显示设备捕获和中央接收时间戳、最终决策、条形码/产品、证据、质量、媒体、精确的不可变版本、上传收据和审查修订。检测叠加使用源尺寸并与边缘仪表板共享经过测试的查看器包。媒体 URL 的生命周期很短，仅在授权后才会刷新。

    17.7 手动 NG 审核工作流程¶

    该队列优先考虑未解决的 NG/不确定案例，并可能支持产品/原因抽样。这并不意味着只有 AI 标记的 NG 案例才能建立假阴性表现；需要抽样合格审核和故意有缺陷的验收数据。

    审核流程：

    1. 打开稳定的检验修订版并显示原始结果，无需修改。
    2. 检查关键帧、ROI、带注释的图像、可选剪辑、组件证据和质量原因。 3、选择人性化和元件修正；切勿重写机器字段。 4.需要受控原因代码；允许有限制的评论。
    3. 显示确切的更改并使用幂等密钥和乐观修订提交。
    4. 附加一个ReviewRecord；不要覆盖检查结果。
    5. 通过单独策划的工作流程对培训待办事项进行合格的更正。

    并发审阅返回冲突并显示较新的修订版本。审阅者选择是否仍然需要新的更正。未经明确确认，键盘快捷键不得提交。

    17.8 产品和规则配置¶

    稳定的产品标识与不可变的产品版本是分开的。产品草案定义条形码映射和所需的组件代码。规则草案定义了每个组件的置信度/时间策略、最小可用框架和不确定处理。

    该编辑器提供结构化字段、单位、范围、受控组件引用、验证错误以及与先前发布版本的语义差异。出版要求：

    • 适用范围内无重复的元件代码或不明确的条码映射。
    • 每个必需的组件都由兼容的组件模型类表示。
    • 阈值排序和时间计数有效。
    • 产品、规则和模型兼容性检查已通过。
    • 捕获的参与者、原因、时间戳和审核记录。

    已发布的版本是只读的。回滚意味着分配较早的有效版本，而不是编辑历史记录。

    17.9 模型注册表¶

    注册表存储元数据和工件引用，而不是任意训练执行。版本页面显示任务、运行时、输入形状、类、SHA-256、数据集版本、评估报告、创建/发布状态和当前设备分配。

    出版需要经过验证的工件和批准的评估记录。用户界面清楚地区分了离线检测器指标和产品级系统验收。它不得允许直接替换已发布版本下的工件。模型二进制上传使用分阶段对象存储、进度反馈、校验和验证和服务器端授权。

    自动化训练、超参数搜索和部署升级管道属于稍后的范围。初始模型注册和批准可以是受控的手动过程。

    17.10 报告和导出¶

    交互式仪表板查询仍然受到限制。较大的 CSV/JSON 报告作为异步作业运行，因为聚合和文件创建可能会超出 HTTP 请求的生命周期。报告捕获过滤器快照、列、请求者、创建/到期、行计数、状态和失败代码。下载使用过期 URL 并进行审核。

    电子表格导出通过转义以电子表格控制字符开头的单元格来防止公式注入。导出尊重组织范围、权限、保留和条形码屏蔽策略。不要在表格导出中包含原始媒体；如果需要，使用单独授权的证据包。

    17.11 用户和审计¶

    用户管理显示身份提供者状态和组织角色。角色替换需要乐观并发并防止最终组织管理员被删除。设备凭证与人类用户分开管理。

    审核搜索支持参与者、操作、资源、请求 ID 和有限时间。 JSON 被渲染为带有秘密字段的安全结构化差异之前/之后。审计记录无法通过仪表板编辑或删除。

    17.12 前端架构¶

    • admin-web 拥有路由、页面组合、授权指令和特定于中心的存储。
    • 生成的API客户端和域模式是共享的；检测查看器和基本状态/UI原语可以与边缘共享。
    • Pinia 存储会话、权限、组织上下文和小型 UI 首选项。查询结果使用具有取消和过时处理功能的请求/查询层，而不是全局镜像数据库。
    • ECharts 适配器标准化空值、样本计数、可访问的描述、单位和时区标签。
    • 中央 WebSocket 使活动设备、检查、审查和报告查询无效。 REST刷新是权威的。
    • 长过滤器值在 URL 中可预测地序列化；敏感标记和评论永远不会放在那里。

    17.13 性能、弹性和安全性¶

    • 延迟加载路由包、媒体查看器和图表模块。使用服务器聚合而不是下载原始检查来计算图表。
    • 当过滤器更改时取消过时的请求。限制比较系列以避免不可读的图表和昂贵的查询。
    • 显示数据新鲜度和部分结果警告。当 WebSocket 丢失时，轮询可能会以有限的时间间隔继续。
    • 对 cookie 会话应用 CSP、CSRF 保护、输出转义、依赖固定，并且无第三方运行时 CDN 要求。
    • 通过包含组织和授权上下文来防止跨租户缓存密钥。清除组织/会话更改的查询缓存。
    • 记录安全敏感操作并使用请求 ID 导出。切勿公开对象存储凭据或内部堆栈跟踪。

    17.14 测试与验收¶

    Vitest 涵盖权限矩阵、指标格式、时区转换、过滤器、差异渲染和审核验证。组件测试涵盖图表空/部分状态、大表、媒体过期和冲突。 Playwright 涵盖登录/会话到期、组织隔离、检查搜索/详细信息、并发审查、产品/规则发布验证、模型注册、设备分配、报告完成、角色更改和审核搜索。

    API 合约测试根据 OpenAPI 验证生成的客户端。安全测试尝试跨角色和组织进行直接路由/API 访问。性能测试使用实际基数并验证有界仪表板查询延迟；确定基础设施规模后，必须商定确切的阈值。

    17.15 MVP 及后续范围¶

    一个月 MVP：设备概述/详细信息、检查历史记录/详细信息、基本 NG 审查、产品/规则列表和受控版本创建、简单模型注册、基本摘要图表和审核捕获。接下来是报告、全面的用户管理、分阶段部署、保存的仪表板视图、警报确认和高级模型比较。静态训练和检查 MVP 中没有中央仪表板。

    17.16 未解决的问题和需要验证¶

    • 确认组织/站点/线路层次结构、租户模型和跨组织支持角色。
    • 选择 OIDC 提供商、MFA/升级要求、会话持续时间和角色审批流程。
    • 就仪表板指标定义、时区、刷新频率和可接受的查询延迟达成一致。
    • 确认手动审核原因分类、OK 审核的抽样政策以及审核者分配/声明规则。
    • 确认报告格式、屏蔽、最大范围、保留和批准要求。
    • 定义模型发布审批者和设备分配前所需的证据。
    • 确认配置推出是否需要维护时段或在 MVP 中立即进行设备轮询。
