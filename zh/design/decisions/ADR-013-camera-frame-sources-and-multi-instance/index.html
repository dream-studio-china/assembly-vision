    ADR-013：相机帧源和多实例边缘¶

    1. 现状¶

    已接受

    2. 背景¶

    静态训练和检查 MVP 和只读 M1 边缘 API 运行于 静态文件夹输入。一个月的目标需要相机采集 （设计 07），并且在实践中，一台边缘主机必须驱动多个独立的 检查线，每条都有自己的相机和自己的模型/规则/产品 （设计 04 §2 组件图显示单个协调器；车队模型 在设计 14 中，每条线处理一个设备）。

    真实相机 SDK（Basler、FLIR、供应商 IP 相机）依赖于部署 并且不得阻碍开发或 CI。录制或模拟的源必须 使用与实时摄像机完全相同的下游管道，因此 FrameSource设计07 §7.3中的协议是单缝。远程来源 通过 TCP/IP 到达：RTSP 流是常见的工业相机传输， 普通 HTTP 图像端点是相机或 PLC 的廉价后备方案 公开单个 JPEG 的快照。

    该决策记录了源是如何抽象的、多个独立的 实例由assemblyvision serve配置和运行，以及如何预览 在 WebSocket 运行时里程碑存在之前到达仪表板。

    3. 决定¶

    1. vision-core中的FrameSource协议（设计07§7.3）：open() -> CameraCapabilities，configure(settings) -> AppliedSettings， frames(stop: Event) -> Iterator[CapturedFrame]、close()。框架带有 单调时间戳、挂钟 UTC、序列号、维度、像素 格式、采集状态和 PIL RGB 图像。读取/解码失败引发 FrameStreamError；他们从不默默地跳过证据（自动防故障）。
    2. 可插拔源，全部实现协议：folder（静态图像 目录，可选循环），video（本地视频文件），opencv-device （本地相机索引或/dev/videoN，包括虚拟相机，例如 Linux v4l2loopback 或 OBS 虚拟摄像机）、rtsp（通过远程 RTSP 流 PyAV 与 OpenCV 后备），http-image（轮询远程 JPEG URL 配置的间隔）和 gige-vision （GenICam/GenTL 通过 Harvester 和 供应商 GenTL 生产商）。供应商 SDK 适配器可以稍后添加到 相同的协议而不改变管道。 生产首选适配器是 gige-vision GenICam/GenTL 消费者，而 opencv-device 仍然是 UVC USB 兼容源。 Linux 是主要的生产运行时；仅在以下情况下才支持 Windows 所选相机的 GenTL 生产商或 UVC 驱动程序通过相同的一致性 套房。初始目标配置文件在 25-30 时约为 4 兆像素 FPS。 GigE Vision设备通过序列号绑定，支持 连续/软件/硬件触发模式，并公开应用的像素格式 以及通过键入相机状态进行采集设置。生产时首选硬件触发 边界。最初不需要 PTP；单调时间控制持续时间 UTC 仍然是可追溯性元数据。巨型帧是可选的并且需要 经过验证的相机/NIC/交换机支持。
    3. 多实例配置（pipeline.yaml、instances:列表）：每个 实例是一个独立的检查管道，有自己的camera， 模型、阈值、ROI 和规则。现有的扁平单配置形式 仍然支持 inspect、av-train 和 M1 serve 行为。 未知实例 ID、重复的 instance_id、缺少 url/path/device 对于选定的源类型，无效的 fps 在加载时会被拒绝。
    4. 每实例设备身份：当未配置device_id时， device_id = uuid5(NAMESPACE, instance_id) 因此重新启动的服务会保留 每行的稳定身份和每个实例的记录都是可追踪的。安 显式 device_id 会覆盖推导。
    5. serve生命周期：serve在启动时打开每个配置的源； 报告失败的实例（非致命），而不会阻止其他实例，并且 不影响已经可读的历史/健康状况。关机设置各 源的停止事件并关闭所有源。每个实例都带有 inspection.enabled: true 运行一个捕获/检查循环来提供 每个捕获帧的现有单帧管道（每个帧是一个 检查，匹配当前 MVP 语义）；默认是 inspection.enabled: false 所以 serve 只开放源并提供服务 预览直到窗口/时间里程碑落地。
    6. WebSocket之前预览：GET /api/v1/camera/{instance_id}/preview 以速率受限的 JPEG 形式返回最近捕获的帧（最新 仅帧，无无限缓冲； 404 未知实例，503 不是 准备好了）。此 REST 预览是实时仪表板的临时传输 查看； WebSocket 运行时通道（设计 15 §15.4）稍后重用相同的通道 框架管道无需更换。
    7. 运行时依赖：opencv-python-headless（视频、本地设备、 MJPEG 后备）、av（PyAV、RTSP）和 httpx（HTTP 图像轮询）是 edge-service的运行时依赖； vision-core 将它们保留为可选 额外的（video，rtsp，http）因此中央/轻量级消费者保持免费 其中。

    4. 后果¶

    4.1 正面¶

    • 相同的管道消耗实时、记录和模拟帧，因此 确定性回归装置可跨采集模式工作。
    • 开发和 CI 不需要相机硬件：文件夹、视频和本地 HTTP 服务器执行真实相机使用的每条代码路径。
    • 一台边缘主机服务多条独立线路，每条线路都有稳定的线路 设备标识，与车队模型匹配（每条线路一台设备）。
    • 远程 TCP/IP 源（RTSP、HTTP 图像）无需供应商 SDK 即可集成，并且 供应商适配器仍然是未来的协议实现。
    • 仪表板在 WebSocket 里程碑之前获得真实的相机预览。

    4.2 负面和权衡¶

    • 每个实例加载自己的模型实例；内存随时间线性增长 权重共享合理之前的实例数量（“共享模型” 第三阶段中的悬而未决的问题仍然悬而未决）。
    • RTSP 可靠性取决于 PyAV/OpenCV 构建和网络行为；有界的 实现了带退避的重新连接，但存在帧丢失和抖动行为 必须在目标网络上进行验证。
    • 每帧检查（每个捕获的帧进行一次检查）不是产品 窗户；重叠产品和证据混合问题直到 产品窗口/时间里程碑。
    • REST 预览只是权宜之计；它不能成长为流路径，并且 对于实时仪表板，WebSocket 里程碑应该取代它。
    • 添加依赖项（av、opencv-python-headless、httpx）会增加 运行时占用空间和图像大小。

    5. 开放式问题和需要验证¶

    • 选择真正的相机供应商/SDK 并根据 FrameSource收缩和重新连接行为。
    • 验证目标产品上的 RTSP 延迟、重新连接和帧丢失 网络。
    • 在内存之前决定是否需要按实例模型权重共享 成为一个约束（上下文第 3 阶段“共享模型”）。
    • 确认 HTTP 图像轮询对于客户快照是否足够 需要相机或 MJPEG 解析器。
