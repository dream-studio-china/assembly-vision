    ADR-002：Python 后端¶

    1. 现状¶

    已接受

    2. 背景¶

    后端必须集成工业相机、OpenCV、Ultralytics YOLO、条形码库、数值/图像处理、API、持久性和模型评估。实施团队需要运行时视觉代码和训练/评估代码之间的共享语言，同时保留类型化模式和生产质量测试。

    3. 决定¶

    使用Python 3.12作为边缘和中央后端服务。使用 FastAPI、Pydantic、SQLAlchemy、Alembic、Uvicorn 或适当的中央进程管理器、Pytest、Ruff 和 MyPy。视觉集成使用 Ultralytics YOLO 和 OpenCV。 SQLite 最初允许在边缘使用； PostgreSQL 是集中使用的，并且在证据表明有需要后，对于大型边缘安装来说是可选的。

    对性能敏感的工作应首先使用优化的模型运行时、OpenCV/数值库、仅在延迟允许的情况下进行批处理以及分析。仅针对测量到的瓶颈引入本机扩展或单独的服务。

    4.范围¶

    该决策涵盖应用程序后端、边缘决策运行时、可重用视觉包、命令行工具、培训和评估。它不需要 Python 来实现 Vue 前端、Nginx、数据库、相机固件或未来的所有集成。

    5. 后果¶

    5.1 正面¶

    • 与计算机视觉和机器学习紧密结合的生态系统。
    • 跨原型、测试和运行时共享模式和算法。
    • 使用生成的 OpenAPI 合约快速实现 API。
    • 广泛的相机/供应商 SDK 集成选项。

    5.2 负面和权衡¶

    • Python 打包、本机依赖项、GPU 驱动程序和供应商 SDK 需要仔细构建映像。
    • 如果在优化库之外编写，受 CPU 限制的 Python 代码可能会成为瓶颈。
    • 字节码分发并没有强有力地保护源逻辑。
    • 静态类型是部分的，取决于严格的 MyPy/Pydantic 使用。

    6.替代方案¶

    • C++ 后端： 强大的运行时控制，但应用程序交付速度较慢，并且与所选 Web 堆栈的直接集成较少；为可测量的本地需求预留。
    • C#/.NET： 对于工业集成可行，但与所选培训/视觉工作流程的一致性较弱。
    • Node.js/TypeScript 后端： 对于 Web API 很有用，但对于主要 YOLO/OpenCV 管道来说不是首选。
    • 立即混合语言服务： 由于 MVP 不必要的操作和合同复杂性而被拒绝。

    7. 开放式问题和需要验证¶

    • 相机 SDK 和 GPU 运行时与 Python 3.12 和所选操作系统的兼容性。
    • 中央CPU并发是否需要Gunicorn或其他部署模式。
    • 测量到的需要本机加速的性能瓶颈。
