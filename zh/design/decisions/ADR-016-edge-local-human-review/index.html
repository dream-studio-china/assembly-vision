    ADR-016：边缘本地人工审核（可选）¶

    1. 现状¶

    已接受

    2. 背景¶

    Design 24 将人工审查放在中央服务器上：证据上传、 中央审查队列和仅附加处置。中央服务器没有 尚未存在，设计 24.11 要求边缘检查和审查保持 在中央服务器不可用时工作。运营商需要配置 本地NG案例（以及审计抽样OK案例），由机器决策 保持不变。

    边缘没有后端角色模型：API 公开单个查看器 凭证。仅仅为了审查而引入 RBAC 系统将是一个巨大的代价 架构变更背后没有客户需求。

    3. 决定¶

    1. 人工审核是可选的且是附加的。 人工审核从来都不是必需的。 检查完成，永远不会改变 InspectionRecord 或其投影， 并且不向现有检查 API 添加任何字段或端点。审查数据 位于单独的仅附加 review_records 表中（迁移 0008）并且 一个单独的 ReviewRecord 域模型。
    2. 可以审查任何检查，但处置必须兼容 机器结果（设计 24.3）：UNCERTAIN 可能被确认为 NG/OK， 重新检查，或没有结论；简单的 NG 可能会被确认为 NG/OK 或 不确定；采样的OK可能被确认为OK，纠正为NG，或者 尚无定论。不兼容的处置将被拒绝 (422 REVIEW_DISPOSITION_INVALID)，而不是被记录。设计24.3”系统 异常”行（具有操作故障处理）位于外部 边缘局部范围，并被推迟到中央审查存在。
    3. 审阅者身份是调用者提供的且是本地的。 审阅者姓名是 提交的必填字段；没有边缘角色系统。记录 快照原始机器结果和原因代码，以便保留 即使检查投影后来被清除，也是可以解释的。
    4. 记录仅可附加并通过引用进行链接。 稍后对 相同的检查取代之前的最新检查（除非调用者 明确针对该检查的另一次审查）；记录从来都不是 被覆盖，并且评论只能取代对相同内容的评论 检查（409 REVIEW_CONFLICT）。
    5. INCONCLUSIVE 总是需要一个原因，由请求模型强制执行 和域记录。
    6. 审核队列列出每个检查及其审核状态 （has_review、latest_disposition）并支持业务结果和 审查了过滤器，因此最初的全 NG 推出策略和 OK 审核抽样 两者都是可表达的。 Web UI 默认为 NG/未清项目。
    7. 评论仅通过现有查看者凭证公开。 未来 中央审查流程或 RBAC 是一个单独的 ADR；保留本地审核记录 稍后同步的有效输入（设计 24.5/24.11）。

    4. 后果¶

    4.1 正面¶

    • 审核工作离线且无需中央服务器，匹配设计 24.11。
    • 对现有检查管道、API 或 UI 的零侵入：否 InspectionRecord 更改，现有端点没有更改，以及详细信息视图 通过附加的 ReviewPanel 组件进行集成。
    • 机器决策保持不变；更正以参考为准。

    4.2 负面和权衡¶

    • 审稿人的身份是自我主张的；没有边缘侧授权 谁可以审查。部署必须记录谁被允许操作 仪表板。
    • 本地评论尚未在任何地方同步；中央服务器审查 队列和培训待办事项交接仍然是未来的工作。
    • CORRECTED_NG和CONFIRMED_OK记录在本地但不改变 统计或驱动任何自动再训练（设计 24.9 保持训练 受管理且离线）。

    5. 开放式问题¶

    • 边缘本地审查处置是否应作为审查的一部分上传 一旦中央服务器存在，检查同步，以及它们如何映射到 中央审查记录。
    • 是否需要对关键缺陷类别进行双重审查/裁决，以及 它住在哪里。
