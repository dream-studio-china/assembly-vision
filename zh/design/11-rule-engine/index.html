    11. 规则引擎¶

    11.1 目的和独立性¶

    规则引擎将解析的产品身份、管道状态和每个组件的聚合证据转换为确定性的检查决策。它独立于YOLO，不包含图像推理。输入来自 AI detection pipeline 和 temporal aggregation。

    11.2 决策语义¶

    外部产生结果为OK或NG：

    • OK：产品类型和规则有效，每个强制管道门都通过，并且每个所需组件独立地具有满足计数和约束规则的PRESENT证据。
    • NG：任何必需的组件是MISSING、UNCERTAIN或UNVERIFIABLE；或任何强制管道/配置门失败。

    可以显示和报告内部UNCERTAIN证据状态，但它映射到外部NG。引擎没有允许的默认值。未知产品、缺少规则、格式错误的配置、模型/规则不兼容或评估异常是 NG 或阻止系统准备就绪。

    11.3 版本规则配置¶

    schema_version: 1
rule_id: model-a-presence
rule_version: 3
product_type: model_a
compatible_component_model_versions:
  - component-yolo-1.0.0
barcode_required: true
required_components:
  component_a:
    expected_count: 1
  component_b:
    expected_count: 1
  manual:
    expected_count: 1
mandatory_gates:
  product_detected: true
  roi_valid: true
  minimum_valid_frames_met: true

    规则发布后不可更改。编辑创建新版本。产品窗口引脚规则、产品配置、型号版本；决策记录存储所有这些。仅应在生产中安装经过签名或以其他方式身份验证的配置包，并在激活之前进行本地验证。

    11.4 评估算法¶

    def evaluate(context, rule):
    reasons = []
    if not compatible(context.versions, rule):
        reasons.append("VERSION_INCOMPATIBLE")
    if rule.barcode_required and not context.product_identity.verified:
        reasons.append("PRODUCT_IDENTITY_UNVERIFIED")
    for gate in rule.mandatory_gates:
        if not context.gates.get(gate, False):
            reasons.append(f"GATE_FAILED:{gate}")
    for key, requirement in rule.required_components.items():
        evidence = context.components.get(key)
        if evidence is None:
            reasons.append(f"COMPONENT_UNVERIFIABLE:{key}")
        elif evidence.state != "PRESENT":
            reasons.append(f"COMPONENT_{evidence.state}:{key}")
        elif not count_satisfied(evidence, requirement):
            reasons.append(f"COMPONENT_COUNT_INVALID:{key}")
    return InspectionDecision(result="NG" if reasons else "OK", reasons=sorted(reasons))

    排序和稳定的组件迭代产生可重现的原因排序。引擎返回所有适用的原因，而不是一开始就停止，除非无法安全地解析输入。

    11.5 原因代码¶

    原因代码是稳定的机器可读标识符，分组为：

    • 身份：BARCODE_UNREADABLE、PRODUCT_TYPE_UNKNOWN、PRODUCT_MAPPING_AMBIGUOUS、PRODUCT_IDENTITY_UNVERIFIED；
    • 管道：CAMERA_DISCONNECTED、NO_PRODUCT、MULTIPLE_PRODUCTS、ROI_INVALID、INSUFFICIENT_VALID_FRAMES、INFERENCE_ERROR、IMAGE_READ_ERROR、PRODUCT_IDENTITY_MISSING、PRODUCT_IDENTITY_TRANSITION、WINDOW_MAX_DURATION_EXCEEDED、COMPONENT_POLICY_MISSING、GATE_FAILED:<gate>；
    • 组件：带有组件键的COMPONENT_MISSING、COMPONENT_UNCERTAIN、COMPONENT_UNVERIFIABLE、COMPONENT_COUNT_INVALID、COMPONENT_SPATIAL_INVALID；
    • 配置：RULE_NOT_FOUND、CONFIG_INVALID、VERSION_INCOMPATIBLE；
    • 系统：INSPECTION_INTERRUPTED、DECISION_PERSISTENCE_FAILED、RULE_EVALUATION_ERROR。

    规范的机器可读集的实现是 packages/python/domain/src/assemblyvision_domain/reason_codes.py；设计11.5 并且该模块必须保持同步 (AUDIT-001)。

    人类可读的文本是单独本地化的。分析使用原因代码加上结构化参数，而不是解析的显示消息。

    对于开发上传路径，条形码解析提供身份 验证标志和持久条形码/产品分辨率字段；规则 评价不变。解析为产品的精确条形码映射 除活动规则产品类型外，其他产品类型均未经验证。

    11.6 配置生命周期¶

    草案规则经过模式验证并针对回归语料库进行模拟。发布需要授权和审核条目。边缘安装会持久写入程序包，验证校验和和兼容性，然后在产品窗口之间自动激活它。如果激活失败，请保留最后验证的版本并报告失败。如果某个产品不存在有效规则，则该产品为 NG；禁止通用许可规则。

    回滚将之前发布的不可变版本安装为新的激活事件。历史记录始终保留决策时使用的版本。

    11.7 故障处理¶

    • 缺少密钥和未知组件状态无法关闭NG。
    • 未知的可选字段将被拒绝或根据显式架构版本策略进行处理，而不会进行静默解释。
    • 评估异常在边界处捕获、记录并使用 RULE_EVALUATION_ERROR 转换为 NG。
    • 版本冲突的重复组件证据无效。
    • 中央服务器中断不会阻止使用最后本地安装的有效规则。
    • 新下载的无效规则无法替换活动规则。

    边缘仪表板可能会因全局配置错误而显示系统未就绪状态。当决策持久性失败时，它不得显示 OK 结果。

    11.8 验证¶

    • 对每个证据状态、门、身份状态、计数和原因代码使用表驱动的单元测试。
    • 属性测试：OK 意味着每个必需的组件都存在并且每个强制门都为真。
    • 属性测试：在没有证据的情况下添加所需的组件无法保留OK。
    • 针对固定检查上下文的黄金测试已发布规则版本。
    • 测试格式错误的 YAML、不受支持的架构版本、不兼容的模型、缺少规则和评估异常。
    • 在活动和空闲产品窗口期间集成测试原子激活。
    • 根据部署期间持续存在的证据审核 OK 结果样本。

    11.9 未决问题和需要验证¶

    • 确认面向客户的界面是否仅支持OK/NG或还显示内部不确定类别。
    • 当条形码可读但未知时，定义精确的产品到条形码映射和行为。
    • 按产品变型定义所需的组件数量和任何条件要求。
    • 建立规则发布、批准、签署和紧急回滚角色。
    • 确认下游驱动语义和时序；这里不假设任何 PLC 行为。
