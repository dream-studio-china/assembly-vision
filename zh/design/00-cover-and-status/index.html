    AssemblyVision 软件架构：覆盖范围和状态¶

    1. 文件控制¶

    领域 价值
    系统 AssemblyVision - 工业装配检测系统
    文件集 软件架构及实现蓝图
    状态 工程验证草案
    架构基线 边缘客户端和中央服务器架构
    品质优先 最大限度地减少误报、保持可追溯性，然后减少误报
    项目事实来源 docs/source-brief.md

    该文档集描述了建议的实现。它没有声称已部署 AssemblyVision、已存在图像或条形码记录或已实现任何准确性目标。生产验收必须基于未用于培训的测量客户数据。

    3. 范围范围和现状¶

    视野是范围标签，而不是仅凭日历时间就可以确定生产准备情况的承诺。

    地平线 预期结果 包含 明确排除或推迟 状态
    静态训练和检查 MVP 证明带标签的静态图像训练到检查流程 X-AnyLabeling YOLO 框标签、单独的培训 CLI、产品/ROI/组件培训、确定性规则、文件夹检查、JSON/ROI/带注释的输出、验证报告、重点测试 相机 SDK、视频、时间聚合、中央服务器、仪表板、身份验证、PLC/MES、自动再训练、模型加密和 .pyc 分发打包 定义；带注释的图像、保留的图像、产品规则和所需的开发人员硬件
    一个月目标 演示一个有界产品/相机路径的受控集成试点 相机/条形码适配器、持久的本地决策、边缘 API/仪表板、产品窗口、聚合、持久上传队列、一个中央摄取/历史记录/审查路径、最低飞行员安全性、Compose、有针对性的弹性基线 通用管理/报告、远程包裹交付、最终验收、完全弹性/浸泡矩阵、生产保证 建议的;需要现成的硬件、模型、数据和小型并行团队
    生产目标 谨慎操作，谨慎接受 强化恢复、保留、审计、访问控制、配置/模型治理、可观察性、人工审查、发布/回滚、生产验收 任何 100% 准确度的声明 需要验证和客户同意
    未来 仅在有运营证据后才能延长 模型包分发、可选的中央 Kubernetes、可选的 Tauri Edge shell、合理的边缘 PostgreSQL、集成和自动化 不属于最初承诺的一部分 候选范围

    4. 有效的架构决策¶

    1. 生产关键型采集、推理、聚合、规则和最终决策在边缘工业计算机上执行。
    2. 中央连接丢失不得停止检查；本地持久性和延迟同步是强制性的。
    3. 第一个实现在集成相机/视频路径之前处理静态图像。 4、产品检测创造产品投资回报率；组件检测在该 ROI 上进行。硬编码区域可能只是粗略或后备捕获区域。
    4. 直接检测所需组件的存在。该设计不依赖于通用的 missing_component 模型类。
    5. 条码解码是一项单独的功能；物体检测可以定位条形码，但不能取代解码。
    6. 时间证据是按所需组件汇总的，而不是通过整个产品的多数投票来汇总的。 8.规则引擎是确定性的并且版本独立于模型。
    7. UNCERTAIN是内部决策状态，始终映射到业务NG；不确定性不能产生OK。 10.每次持续检查都会识别设备、时间、产品类型解析、模型版本、规则版本、产品配置版本、证据、决策和原因代码。
    8. 中央服务器接收选定的证据，而不是每一帧。在政策要求的情况下，完整或滚动的视频保留在本地。
    9. 运行时数据、生产媒体、秘密和模型权重不存储在 Git 存储库中。

    Appendices 包含扩展此集合时使用的一致性检查表。

    五、质量及验收情况¶

    工程目标是高 NG 召回率和极低的假阴性率。早期推出允许额外的错误 NG 结果，因为它们可以手动审查。仅整体准确性并不是可接受的成功衡量标准；验证必须报告 NG 召回率、假阴性和假阳性率、每个组件和每个产品的性能、条码/产品/投资回报率成功率、延迟、吞吐量和运营弹性。

    这里没有定义数字接受阈值。阈值和置信策略需要针对隔离的客户生产数据进行基线评估，包括故意不完整的产品和操作故障场景。

    6. 所有权和变更控制¶

    影响边缘自治、决策语义、可追溯性字段、上传幂等性或模型/规则兼容性的架构更改需要对所有受影响的文档进行明确审查。仅当需求、图表、接口、状态机、原因代码和跟踪链接保持一致时，更改才完成。

    建议的文档角色是：

    • 产品负责人：业务分类和审核政策。
    • 愿景引导：数据集、模型清单、阈值和评估证据。
    • 边缘领先：获取、决策路径、局部持久性和恢复。
    • 平台领导：摄取、身份、管理和中央操作。
    • 客户运营代表：场地限制和验收批准。

    这些角色是职责，而不是确认的人员配置事实。

    7. 开放式问题和需要验证¶

    1. 谁批准需求和生产验收，将使用什么变更控制流程？
    2. 第一个版本包含哪些产品类型和组件类别？
    3. 基线评估后将商定哪些测量可接受阈值？
    4. 承诺的目标日期是什么？在此之前可以访问哪些硬件/站点？
    5. 适用哪些数据分类、保留义务和客户政策？
    6. Appendices 中的全局列表中的哪些项目会阻止静态训练和检查 MVP、一个月目标和生产发布？
