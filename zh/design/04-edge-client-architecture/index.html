    AssemblyVision 边缘客户端架构¶

    1. 职责与边界¶

    边缘客户端拥有生成和保留生产决策所需的所有操作：硬件捕获、触发器/窗口管理、条形码解码、产品类型解析、两阶段视觉、可选的 OpenCV 检查、时间聚合、规则、本地记录/媒体、运行状况、本地 API/Web UI 和延迟上传。它必须在没有网络或中央服务器的情况下进行检查。

    边缘不训练模型，依赖于活动规则的中央查询，也不上传每个帧。更广泛的边界如Architecture Overview所示。

    2. 边缘组件架构¶

    flowchart LR
    Hardware[相机扫描仪传感器适配器] --> Coordinator[检验协调员]
    Coordinator --> Quality[镜框品质]
    Coordinator --> Identity[条形码和产品解析器]
    Quality --> Product[产品检测仪]
    Product --> ROI[投资回报率引擎]
    ROI --> Component[元件检测器]
    ROI --> CV[可选的 OpenCV 检查]
    Component --> Aggregate[每个组件聚合器]
    CV --> Aggregate
    Identity --> Rules[确定性规则引擎]
    Aggregate --> Rules
    Rules --> Persist[本地存储库和媒体管理器]
    Persist --> DB[(SQLite)]
    Persist --> Media[(媒体音量)]
    Persist --> Upload[(持久上传任务)]
    Upload --> Sync[上传调度程序]
    Sync -->|当可用时| Central[中央摄取API]
    API[本地FastAPI] --> Persist
    API --> Coordinator
    Web[本地Vue应用程序] --> API
    Health[健康监测器] --> Hardware
    Health --> DB
    Health --> Media
    Health --> API

    一月目标部署一个包含 FastAPI、捕获编排、持久性和上传调度的 edge-service。决策关键型工作在有界工作任务中运行，并且可以使用监督推理子进程进行 SDK/GPU 隔离；在测量的隔离或扩展需求证明其复杂性合理之前，它不是单独部署的服务。 API 或浏览器请求失败不得停止捕获和决策任务。

    一个edge-service进程可以运行多个独立的检查实例， 每个将自己的相机源与其自己的模型/规则/产品及其 拥有稳定的设备身份（device_id = uuid5(namespace, instance_id)除非 显式配置），匹配每条线路一台设备的车队模型 （ADR-013）。实例共享进程及其存储，但从不共享 证据；每个实例的模型加载意味着内存随着实例的增长而增长 计数直至重量分配合理。

    3、检验处理¶

    3.1 窗口和身份¶

    协调员在接受证据并固定活动包版本之前创建 inspection_id。硬件触发可在可用时提供最清晰的边界；条形码事件添加身份，但可能会延迟到达或失败；跟踪/区域处理仅图像流，但需要仔细调整；超时限制资源使用，但其本身不能证明物理分离。生产机制应仅结合经过验证的信号并明确测试连续/多个产品。

    条形码输出包括原始值、符号系统（如果可用）、时间戳、来源、读取质量/状态和错误。版本化解析器将身份映射到产品配置。没有读取、读取冲突、未知值或缺少配置会阻止 OK 并发出原因代码。

    3.2 两阶段愿景¶

    对于每个可用帧，产品检测器都会处理完整图像。 ROI 引擎选择明确的候选产品，通过配置的边距进行扩展，剪辑到边界，并记录全帧和 ROI 坐标之间的转换。零面积、过度剪裁、无产品或多产品模糊性都是无效证据。

    组件检测器在生成的 ROI 上运行并发出类别、框、置信度、帧 ID 和模型版本。所需的类来自固定的产品配置。可选的 OpenCV 检查使用自己的算法/配置版本发出命名观察结果；它们不能无形地改变检测器的输出。

    3.3 每个组件的聚合和规则¶

    聚合器排除无效/模糊的帧，并使用配置的策略评估每个所需的组件，例如一个高置信度观察、两个中等置信度观察、相邻帧证据、可见区域限制和最小可用帧计数。阈值仍然特定于型号/产品，并且需要评估。

    规则引擎仅使用类型化的聚合证据和固定配置。它返回内部 OK、NG 或 UNCERTAIN、组件列表和原因代码。 UNCERTAIN始终映射到业务NG；演示可以显示内部原因，但不能将业务结果更改为OK。

    4. 检验状态模型¶

    stateDiagram-v2
    [*] --> Idle
    Idle --> WindowOpen:已验证的开始事件
    WindowOpen --> Collecting:第一个相关帧或身份事件
    Collecting --> Evaluating:已验证的结束事件或有限超时
    Evaluating --> Persisting:做出的决定
    Evaluating --> Persisting:异常产生保守的结果
    Persisting --> Completed:提交的元数据和所需证据
    Persisting --> RecoveryRequired:提交或媒体最终确定失败
    RecoveryRequired --> Persisting:重试成功
    RecoveryRequired --> Faulted:不可能安全恢复
    Completed --> Queued:上传策略创建任务
    Completed --> Idle:无需上传任务
    Queued --> Idle:持久记录的任务
    WindowOpen --> Cancelled:无效或重复的开始
    Collecting --> Cancelled:根据批准的政策取消运营商
    Cancelled --> Persisting:取消记录及原因
    Faulted --> Idle:授权恢复和健康检查通过

    每个终端路径都会创建一个可审计的记录，其中存储仍然可用。取消或异常路径不能产生 OK。

    5. 设备状态模型¶

    stateDiagram-v2
    [*] --> Starting
    Starting --> Ready:依赖项和活动包有效
    Starting --> Faulted:强制依赖无效
    Ready --> Inspecting:检查窗口打开
    Inspecting --> Ready:已提交检查
    Ready --> Degraded:非关键依赖性受损
    Inspecting --> Degraded:网络或上传不可用
    Degraded --> Ready:健康恢复且积压可接受
    Degraded --> Faulted:决策关键依赖失败
    Ready --> Paused:授权暂停
    Degraded --> Paused:授权暂停
    Paused --> Ready:授权简历和检查通过
    Inspecting --> Faulted:相机存储或活动包故障
    Faulted --> Starting:授权重启或恢复
    Starting --> Maintenance:维修授权
    Ready --> Maintenance:维修授权
    Maintenance --> Starting:维护完成

    网络或中央故障是降级的，而不是决策关键的。相机故障、无效的活动模型/规则兼容性、无法持久保存强制记录或不安全的磁盘耗尽等故障。这些状态的精确线路信号需要站点协议。

    6. 本地持久化和恢复¶

    6.1 数据布局¶

    SQLite 最初存储检查、帧元数据、组件证据、媒体清单、上传任务、设备事件、本地配置和已安装的模型/规则版本。媒体位于显式安装的数据根下，按日期和检查 ID 分区，绝不位于容器层或存储库内。

    实用的写入协议是：

    1. 将介质写入目标卷中的临时文件，刷新它，计算校验和和大小，然后自动重命名它。
    2. 在一项数据库事务中，插入检查、证据、最终媒体清单和上传任务。 3.提交后才发布已完成的事件。
    3. 启动时，协调临时文件、不完整的检查、丢失的文件以及崩溃留下的任务IN_PROGRESS。

    SQLite 使用 Alembic 迁移、外键、WAL 模式（如果在所选文件系统上进行验证）、有界繁忙超时、定期完整性检查和支持的备份过程。单个存储库编写器或短事务可以减少锁争用。

    6.2 保留和磁盘压力¶

    保留类别针对完整/滚动视频、关键帧、NG 剪辑、带注释的图像、ROI 图像、日志和数据库记录进行独立配置。清理从过期的、成功上传的、未受保护的工件到价值较低的数据。它必须遵守参考资料、法律/审查保留、待处理/失败的上传以及最低证据政策。警告和严重水印会触发原因编码的健康事件；无法保留强制性证据的缺陷或保守地终止检查。

    确切的持续时间和水印有意未指定，以待容量和策略验证。

    7. 上传调度程序¶

    上传任务包含任务 ID、检查 ID、工件类型、适用的本地路径、校验和、有效负载哈希、尝试计数、下次尝试时间和状态。幂等性密钥在重试后保持稳定。指数退避使用抖动和配置的上限；永久性验证/身份验证失败会停止自动重试并引发可操作事件，而暂时性网络/5xx 故障仍会排队。

    元数据在媒体清单之前或与媒体清单一起接受。当测量的大小需要时，大型媒体应使用服务器发出的上传会话或有界多部分协议。中央耐用收据标志着成功。清理不能仅仅因为传输了字节而删除受保护的本地证据；它需要收据和到期政策。

    8. 本地API和Web应用程序¶

    版本化本地 API 组为 /api/v1/health、/api/v1/device、/api/v1/camera、/api/v1/inspection、/api/v1/inspections、/api/v1/media、/api/v1/uploads、/api/v1/configuration、/api/v1/logs 和 /api/v1/ws/runtime，详细信息请参见 REST API and Events。变异调用使用适合本地威胁模型的授权、验证、审计条目和重试时的幂等性。 WebSocket 事件是建议性的；重新连接后，UI 通过 REST 恢复真实情况。

    Vue 应用程序显示摄像头预览、当前身份/产品、最新结果/证据叠加、延迟、摄像头/模型/磁盘/网络/中央状态、队列深度、最近记录、本地日志和重试控件。它仅使用本地端点并在离线状态下仍然有用。预览交付必须受到速率限制，并且不得阻碍推理。

    9. 进程、并发和背压¶

    • 根据经过验证的窗口策略，有界捕获缓冲区有利于最近的帧；禁止无界队列。
    • 对于选定的 CPU/GPU 资源，推理并发性受到明确限制。
    • 每帧携带检查ID、帧ID、序列、捕获时间戳和来源；较晚的结果将从关闭/不同的窗口中丢弃并记录。
    • 上传缓慢、UI、注释渲染或中央调用无法阻止捕获/推理。
    • 使用负载/运行状况检查和原子活动版本切换在窗口之间进行模型激活；以前的包仍然可以回滚。
    • 正常关闭会停止新窗口，为活动窗口提供有界完成策略，提交状态并释放硬件。

    10. 健康与可观察性¶

    结构化日志和指标涵盖捕获率/丢包、可用帧、阶段延迟、产品/投资回报率/条形码成功、每个结果/原因计数、队列年龄/深度、重试结果、磁盘水印、数据库错误、包版本和服务重启。关联使用设备、检查、帧、上传任务和请求 ID。健康端点区分活跃度、就绪度和详细的运行状态；与相机断开连接的进程可能处于活动状态，但尚未准备好进行检查。

    11. 部署与源码打包¶

    边缘使用 Compose，无需 Kubernetes。映像是多阶段的，以非 root 身份运行，声明运行状况/重新启动策略，并显式挂载配置/数据/媒体/日志卷。在适配器允许的情况下，运行时文件系统是只读的。前端源代码被编译为静态资源。 Python .pyc-only 打包可能会减少随意浏览，但它不是健壮的混淆；不提供任何 Git 历史记录、训练数据、笔记本、生产数据、实验设置或嵌入的长期机密。

    12. 交付范围¶

    12.1 静态训练和检查 MVP¶

    使用文件夹源、经过训练的模型适配器、ROI、组件证据、规则、JSON/媒体输出、保留验证和重点测试来实现边缘 CLI 路径。一个单独的仅供开发人员使用的培训 CLI 会生成模型工件；它不是边缘运行时的一部分。

    12.2 一个月目标¶

    添加选定的硬件适配器、产品窗口、条形码解析器、edge-service 内的有界决策工作者、SQLite/媒体管理器、聚合、队列/重试、本地 Web UI、Compose 和恢复/运行状况测试。整合最初的集中摄取，而不将其引入决策中。

    12.3 生产目标¶

    验证时序/硬件、强化迁移/备份/保留、凭据、包签名/回滚、故障状态、长时间运行的操作、支持诊断和验收指标。通过 NG 审核和抽样 OK 审核进行谨慎的推出。

    12.4 未来¶

    仅通过明确的要求和验证来考虑 Tauri、更大的边缘 PostgreSQL、PLC/MES 适配器、高级跟踪和远程包自动化。

    13. 假设¶

    • 硬件 SDK 可以隔离在适配器后面并允许可恢复的重新连接。
    • 所选主机支持容器访问硬件和持久安装的存储。
    • 产品吞吐量允许在硬件基准测试后进行有界两阶段推理。
    • 经批准的流程可以在边缘失去连接之前提供活动包。

    14. 开放式问题和需要验证¶

    1. 适用哪些相机/扫描仪/传感器供应商、SDK、触发模式、像素格式和重新连接行为？
    2. 支持哪些操作系统、CPU/GPU、内存、磁盘类型/容量和容器运行时？
    3. 什么打开/关闭窗口，观察到的传送带时间是多少，以及产品在视图中是否可以重叠？
    4. 每个产品/型号验证了哪些帧质量、ROI、置信度、聚合和超时阈值？
    5. 在对外报告结果之前，特别是在磁盘压力下，哪些本地证据是强制性的？
    6. 适用哪些保留、隐私、加密、本地访问控制和维护策略？
    7. 什么协议和安全状态行为将结果/设备故障连接到生产线？
    8. 除了休闲浏览威慑之外，合同还要求什么级别的源代码打包？
    9. 参见Global Open Questions。
