    AssemblyVision 架构概述¶

    1. 架构驱动因素¶

    AssemblyVision 必须在受控但不完全注册的成像环境中做出保守的产品决策，在网络和中央中断时保持运行，保留可重复的证据，并从带标签的静态图像训练和检查证明发展为公认的生产系统。结果是具有异步中央同步的边缘优先架构。

    详细义务见Requirements；共享条款和决策规则位于Appendices中。

    2. 系统上下文¶

    flowchart LR
    Product[实物产品] -->|通过检查区域| Edge[AssemblyVision 边缘客户端]
    Camera[工业相机和可选的扫描仪或传感器] -->|框架和事件| Edge
    Operator[线路操作员] <-->|本地状态和控制| Edge
    Edge -->|通过批准的集成输出 OK 或 NG| Line[外线流程]
    Edge <-->|延迟元数据媒体配置和运行状况| Central[AssemblyVision central server]
    Reviewer[质量审核员] <-->|review and corrections| Central
    Admin[系统管理员] <-->|设备用户规则模型和报告| Central
    Vision[视觉工程师] -->|approved manifests and packages| Central

    外线工艺以边界显示；确切的机制以及 AssemblyVision 是否驱动设备尚未确定。中央服务器从不同步参与检查决策。

    3. Logical Architecture¶

    3.1 边缘决策平面¶

    边缘决策平面拥有采集、产品窗口关联、条形码/产品分辨率、帧质量、产品检测、ROI 生成、组件检测、可选 OpenCV 检查、每个组件时间聚合、确定性规则评估和持久本地记录。它公开本地状态并对选定的记录进行排队以供上传。参见Edge Client Architecture。

    3.2 中央管理平面¶

    中央平面摄取完整的边缘记录和证据，呈现车队/历史/报告/审查工作流程，管理用户和审计，并为延迟边缘分发准备版本化配置。参见Central Server Architecture。

    3.3 训练和发布平面¶

    离线培训/评估生成产品和组件检测器工件、清单和报告。批准先于分发；仅在边缘端完整性和兼容性验证之后才会激活。培训不是由审查更正直接触发的，并且生产包是不可变的。

    Docker Compose 是边缘和中心的部署基线。边缘服务使用显式持久卷并且不依赖于 Kubernetes。 Central Kubernetes 仍然是未来的扩展选项，而不是架构先决条件。

    5. 主要数据流¶

    1. 经过验证的触发/窗口机制创建全局唯一的边缘检测 ID 并捕获相关帧。 2.条码解码和其他配置的身份源解析产品类型；保守地记录分歧。
    2. 框架质量门禁不可用的框架。第一阶段 YOLO 在每个可用的全帧中检测产品。
    3. ROI 引擎展开并裁剪产品框，记录坐标变换，并可选择应用经过验证的方向/视角标准化。
    4. 第二阶段 YOLO 检测 ROI 中的配置组件；可选的 OpenCV 检查添加类型化证据，而不是默默地覆盖模型输出。 6.时间聚合器使用活动版本化策略来组合每个所需组件的证据。 7.确定性规则引擎产生内部状态、业务结果、组件列表和原因代码。只有完整有效的证据才能产生OK。 8.本地事务记录元数据和媒体引用。在相关上传任务准备就绪之前，媒体将通过校验和完成。
    5. 本地仪表板接收状态更新，并且持久上传调度程序在连接允许时发送特定于结果的信封。
    6. 中央服务幂等地存储元数据、验证媒体、返回收据并使记录可用于历史记录/审查/报告。

    6. Core Interface Contracts¶

    接口 契约原则 失败行为
    检查运行时的硬件适配器 带时间戳的帧/事件加上明确的健康状态 关闭或使窗口失效；永远不要推断健康的输入
    阶段到阶段的管道 类型化的不可变值对象；坐标空间和版本元数据 输入原因代码和保守的决定
    工人到本地的坚持 上传资格前进行的检查和媒体清单 重新启动时恢复未完成的工作
    边缘 API 到边缘 Web REST 用于状态/历史/控制，WebSocket 用于瞬时实时更新 UI 退回到轮询；检查继续
    边缘到中心 版本化 HTTPS REST 信封、幂等密钥、校验和；可恢复媒体策略 具有有限退避和抖动的持久重试
    管理 Web 的中央 API 经验证的 REST 和 WebSocket/SSE 合理性 显示陈旧性和上次成功更新
    中心到边缘配置 不可变包、兼容性约束、校验和/签名策略、分阶段确认 保留最后一个已知良好的活动版本

    OpenAPI 是生成的 TypeScript API 客户端的来源。领域事件有效负载使用显式模式版本；数据库行不会直接作为 API 合约公开。

    7. 技术基线¶

    面积 基线
    Python 服务 Python 3.12、FastAPI、Uvicorn（或集中的 Gunicorn）、Pydantic、SQLAlchemy、Alembic
    愿景 Ultralytics YOLO、OpenCV、适配器专用相机/条形码库
    边缘持久性 SQLite 最初；本地文件系统卷；可选的 PostgreSQL 仅适用于演示的大型安装
    中央坚持 PostgreSQL； S3 兼容存储或文件系统抽象
    异步中心工作 Celery、Dramatiq、RQ 或仅在工作负载/代理选择合理后才可使用；仅在需要时使用 Redis
    网页 Vue 3、TypeScript、Vite、Router、Pinia、Axios 或生成的 OpenAPI 客户端、批准的组件库、ECharts、VueUse
    品质 Pytest、Ruff、MyPy、Vitest、ESLint、Prettier、结构化日志记录
    运行时 Docker 多阶段构建、Compose、Nginx（如果适用）、非 root 用户、健康检查、重启策略

    当媒体最终确定、报告/导出生成、缩略图、通知和包准备会导致 API 请求缓慢或不可靠时，后台执行是合理的。正常的检查不依赖于中央工作人员。 MVP 不应仅仅为了匹配目标图而添加代理。

    8. 可靠性和一致性模型¶

    • 边缘检测记录对原始自动化决策具有权威性。
    • 中央摄取是至少一次传输，通过 (device_id, inspection_id) 唯一性、幂等性密钥、有效负载哈希和媒体校验和实现有效一次持久性。
    • 重复的相同请求将返回现有收据；具有不同内容的重复密钥会返回冲突和审核事件。
    • 配置最终被交付，但在本地自动激活。在窗口启动时运行检查引脚版本；更新仅适用于稍后的窗口。
    • 边缘在可能的情况下使用本地单调时间进行持续时间/窗口排序，并记录挂钟和中央接收时间以进行可追溯。
    • 存储压力、不兼容的包、相机故障和未解析的身份使系统降级/故障并防止不合理的OK。

    9. 安全性和源代码分发¶

    中央 API 需要经过身份验证、授权和加密的传输。设备凭证必须是唯一且可替换的；图像中没有嵌入长期的秘密。应根据批准的本地威胁模型来保护边缘管理控制。审核记录涵盖配置、模型/规则激活、审查、用户/角色更改以及所需的证据访问。

    客户端映像使用多阶段构建、构建的 Web 资产、非根运行时、显式卷和只读文件系统（如果可行）。在可行的情况下，Python 可以作为编译后的 .pyc 进行分发，而无需原始 .py，但 .pyc 和 Docker 不会阻止高级逆向工程。公认的目标是避免随意浏览源代码；未部署 Git 存储库、数据集、笔记本和实验配置。

    10. 交付的演变¶

    10.1 静态训练和检查 MVP¶

    使用仅限开发人员的培训 CLI 从 X-AnyLabeling YOLO 标签生成产品和组件模型工件。进程内边缘 CLI 使用这些工件来检查文件夹输入并写入证据，同时保留未来的架构和版本字段。训练代码独立于边缘运行时，并且永远不会由边缘运行时导入。

    10.2 一个月目标¶

    在有界任务中运行捕获和决策工作，可以选择在监督推理子流程中运行，因此 UI/API 负载在不提前添加第二个边缘部署单元的情况下无法阻止捕获。添加硬件适配器、产品窗口、SQLite/媒体卷、队列调度程序、本地 Web 资产、中央摄取/历史记录和初始管理。使用 Compose 进行部署并练习中断并重新启动恢复。

    10.3 生产目标¶

    强化凭证、审计、包升级/回滚、备份、保留、介质完整性、可观察性、警报、支持程序、模式迁移、浸泡/故障测试和受控部署。接受门是证据驱动的。

    10.4 Future¶

    根据测量扩展中央工作人员/存储；可选择采用 Kubernetes、边缘 PostgreSQL、桌面包装、外部集成和批准的再培训自动化。保留边缘决策边界。

    11. Assumptions¶

    • HTTPS 连接间歇性地可用于同步，但不假定可靠性级别。
    • 可以通过批准的流程来配置设备身份和凭证。
    • 一旦确定大小，本地存储就足以满足所需的中断/保留间隔。
    • 模型运行时间可以满足所选硬件上观察到的生产线时序；这必须进行基准测试。
    • 可以针对重复和混合框架情况验证一种产品窗口机制。

    12. 开放问题和需要验证¶

    1. 硬件、操作系统、加速器、网络路由和中央托管限制是什么？
    2. 什么事件打开/关闭检查窗口，以及如何物理处理重复/多个产品？
    3. 哪个协议将结果传递给外线进程（如果有）？
    4. REST 轮询、WebSocket 或其他批准的渠道是否适合通过客户网络进行配置交付？
    5. 需要哪些设备身份、PKI、静态加密、签名和秘密轮换控制？
    6. 哪些中央异步作业证明代理和 Redis 在预期规模上是合理的？
    7. 适用哪些地方和中央恢复目标、保留期限和容量裕度？
