    AssemblyVision简介¶

    1. 目的¶

    AssemblyVision 是一种输送线计算机视觉系统，旨在检查成品中是否存在所需的装配组件。检查目标可能包括完整的产品、大型部件、手册或说明书、条形码以及产品型号或类型。

    对于每个物理产品，业务结果是：

    • OK：所有必需的组件在活动规则下都有足够的有效证据。
    • NG：组件缺失、证据不确定、产品身份无法可靠解析或检验无法可靠完成。

    系统优先避免放行错误标记为 OK 的有缺陷或不完整的产品。因此，它倾向于保守的 NG 决策和早期操作期间的人工审查。这是一个工程目标，而不是精度保证。

    2. 确认的操作环境¶

    已知环境包括大约四兆像素的工业相机、固定照明、通常固定的相机和受控检查区域。产品可能会轻微移动且无法完美套准，但大幅不受控制的旋转并不正常。目前的检查涉及大型零件和组件的存在，而不是微型组件或微小的螺钉。

    AssemblyVision 必须实现相机捕获、条形码识别、图像/视频持久性和结果持久性。这些是必需的功能，而不是预先存在的工厂服务。当与中央服务器断开连接时，边缘机器必须继续检查。

    3. 利益相关者和关注点¶

    利益相关者的角色 主要关注点
    线路操作员 现状清晰，结果保守，理由可诉，线下延续
    质量审核员 证据、版本可追溯性、更正捕获、可搜索历史记录
    工厂支持 相机/设备运行状况、磁盘状态、重启恢复、诊断
    视觉工程师 代表性数据、每个组件指标、模型/配置兼容性
    软件工程师 确定性接口、可测试性、可观察性、可部署性
    管理员 设备、产品、规则、模型、用户、权限治理
    企业主 高 NG 召回率、受控推出、可衡量的接受度

    这些角色描述了所需的观点，但并不断言客户的组织结构。

    4. 系统边界¶

    AssemblyVision 包括：

    • 边缘采集、条形码解码、产品类型解析、两阶段检测、可选 OpenCV 检查、时间聚合、确定性规则、本地 API/仪表板、本地持久性、运行状况监控和同步。
    • 集中摄取、集中历史记录、队列和配置管理、报告、手动审查、审计以及后续模型包分发。
    • 培训和评估工作流程，生成版本化模型清单和验证报告，同时保持在生产决策路径之外。

    中央服务器不在实时决策路径中。物理传送带驱动、PLC/MES 行为、相机硬件选择和工厂网络操作都是外部的，除非后续集成明确将它们纳入范围。该文档并不假设 NG 结果会自动停止或转移产品。

    5. 架构原则¶

    5.1 基于安全的决策¶

    只有完整、有效、足够有力的证据才能产生OK。缺失、陈旧、混合、低质量、未解决或不兼容的证据会产生内部UNCERTAIN或NG；内部 UNCERTAIN 始终映射到业务 NG。

    5.2 边缘自治¶

    检查不能等待中央API。决策路径使用的配置和模型包在激活之前在本地安装和验证。上传是异步且可恢复的。

    5.3 证据和再现性¶

    结果保留足够的结构化证据和不可变的版本标识符来解释哪些输入、模型、配置和规则产生了决策。媒体存储遵循明确的保留政策，不得被视为唯一记录。

    5.4 围绕概率模型的确定性策略¶

    模型提供检测和置信值。单独可测试的确定性规则引擎应用批准的阈值和所需组件策略。时间聚合通过结合帧证据来提高系统的鲁棒性；它不会提高模型固有的单帧精度。

    5.5 增量交付¶

    该实施从标记的静态图像训练和检查垂直切片开始，然后添加物理采集和本地持久性，然后是同步和中央工作流程，最后是基于测量证据的生产强化。

    6. 范围范围¶

    6.1 静态训练和检查 MVP¶

    X-AnyLabeling 生产 YOLO 产品和组件盒标签。仅限开发人员的培训 CLI 训练全框架产品和 ROI 组件模型，而静态图像运行时 CLI 则使用其清单、检查单独的文件夹、评估规则并写入 JSON、ROI 图像、带注释的图像和保留的验证报告。它无需摄像头、视频、中央服务或仪表板即可建立模式和确定性行为。训练代码不是运行时分发的一部分。

    6.2 一个月目标¶

    目标连接相机和条形码解码器，为每个物理产品窗口创建一个检查记录，在本地保留，公开本地 FastAPI/Vue 接口，聚合每个组件的帧证据，并将选定的记录/证据上传到初始中央服务。包括 Docker Compose 打包、离线测试、重试、保留、运行状况和客户现场评估。

    6.3 生产目标¶

    生产添加了经过验证的操作限制、访问控制、防篡改审计历史（如果需要）、包批准和回滚、强大的磁盘/电源/时钟处理、受监控的服务目标、审查工作流程、记录的支持运行手册以及使用保留的生产数据的客户验收。

    6.4 未来¶

    潜在的扩展包括中央模型分发、用于中央规模的可选 Kubernetes、Tauri 边缘包装器、PLC/MES 集成、在大型边缘安装中合理的 PostgreSQL，以及具有明确批准门的重新培训自动化。在没有必要证据的情况下，他们不得使 MVP 复杂化。

    7. 阅读指南¶

    从 Requirements 开始，然后是 Architecture Overview。实施团队应使用 Edge Client Architecture 和 Central Server Architecture。共享术语、原因代码、跟踪约定和未解决的决策位于 Appendices 中。

    8. 假设¶

    • 检查环境保持足够的控制以评估固定角度模型；显着的摄像机角度变化需要重新验证。
    • 可以集成一种可靠的物理产品界定方法，但尚未选择其机制。
    • 可以为商定的保留/上传策略配置本地存储。
    • 可以根据批准的安全流程收集代表性的生产示例，包括故意丢失的组件。
    • 在谨慎推出期间可以进行人工审核；其人员配置和工作流程尚未确定。

    这些假设是验证项目，而不是工厂事实。

    9. 开放问题和需要验证¶

    1. 哪些产品、所需组件以及产品到规则的映射定义了第一个版本？
    2. 哪种物理事件界定了检查窗口：传感器、触发器、条形码、跟踪、区域、超时或经过验证的组合？
    3. NG 业务结果如何在运营中使用，自动生产线驱动是否在范围内？
    4. 有哪些相机、条码硬件/标准、计算硬件、操作系统和加速器可用？
    5. 测得的周期时间、视野、模糊/曝光限制以及可接受的决策延迟是多少？
    6. 谁进行审查和样品审核，以及如何批准更正的标签进行培训？
    7. 适用哪些安全、隐私、保留和托管限制？
    8. 参见综合Global Open Questions。
