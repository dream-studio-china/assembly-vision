    AssemblyVision 中央服务器架构¶

    1. 职责与边界¶

    中央服务器接收延迟的检查结果和选定的证据，维护跨设备历史记录和报告，管理设备/产品/规则/模型/用户，支持手动审核，记录审核事件并分发批准的配置。它是一个管理和证据平面，从来不是生产检验的同步依赖。

    最初的自动化决策是来自边缘的仅附加事实。中央审查和更正是相互关联的事实；它们不会覆盖原始结果。请参阅Architecture Overview和Edge Client Architecture。

    模块可以从一个具有明确域边界的可部署 FastAPI 开始。仅出于可衡量的扩展、隔离或所有权需求而引入单独的服务。工作人员有理由进行长期运行的媒体衍生品、导出/报告、通知、包组装和完整性/协调扫描，而不是简单的 CRUD。

    3. 摄取架构¶

    3.1 检验范围¶

    边缘发布一个版本化信封，其中包含身份、时间戳、产品解决方案、业务/内部结果、组件和聚合证据、原因代码、框架/投资回报率摘要、不可变版本和媒体清单。服务器对设备进行身份验证，验证架构和大小，验证设备所有权/状态和兼容引用，计算规范的有效负载哈希，并保留在事务中。

    (device_id, inspection_id) 和幂等键是唯一的。相同的重试将返回先前的收据。具有不同规范散列的重用身份/密钥返回 409 Conflict，记录安全/数据完整性事件，并保留原始事件。收据包括中央记录 ID、接受的模式版本、服务器接收时间和媒体上传状态。

    3.2 媒体传输¶

    OK通常会贡献一帧代表性的帧。 NG 提供多个关键帧、注释、ROI 以及可选的简短事件剪辑。例外情况只能提供有限的诊断证据。 API最初可以直接接受小媒体；生产应使用经过验证的大小限制，并可选择为较大对象发出上传会话。

    字节被暂存、校验和/大小验证，然后在不透明的存储密钥下最终确定。 PostgreSQL 存储媒体类型、校验和、大小、内容类型、状态、保留类别和对象密钥，而不是公共文件系统路径。部分/孤立上传是异步协调的。根据安全模型，检索使用授权的 API 流或限时链接。

    4. 领域和持久化模型¶

    核心 PostgreSQL 聚合是：

    • 租户/位置：验证所需租户层次结构的组织、站点、生产线和设备。
    • 身份/访问：用户、角色、分配、设备凭证和会话/令牌。
    • 配置：产品、所需组件、不可变规则版本、模型包/版本、兼容性声明和设备分配。
    • 检查：检查、组件结果、证据摘要、媒体元数据、设备事件和上传收据。
    • 审查/审计：审查记录和仅附加审计事件。

    使用 UUID/ULID 样式的不透明主键，同时保留唯一的边缘业务标识符。基于测量的查询，对接收和检查时间、设备/时间、条形码（在政策允许的情况下）、产品/结果、模型/规则版本、审核状态和原因代码进行索引。时间存储为时区感知 UTC；边缘观察时间和服务器接收时间均被保留。当必须保留引用时，软删除适用于托管配置；检查/审查使用保留工作流程而不是随意删除。

    PostgreSQL 事务保护聚合不变量。对象存储与 PostgreSQL 不是事务性的，因此需要显式的 PENDING、AVAILABLE、FAILED 和 DELETED 媒体状态以及协调。

    5. 管理和配置¶

    5.1 设备和产品管理¶

    管理员注册设备、将其分配到批准的组织/线路范围、轮换凭据、查看上次查看/队列/版本运行状况以及隔离受损或不兼容的设备。产品识别所需的组件集，但不嵌入可变的生产策略。规则版本参考产品配置并声明阈值/聚合策略；模型清单标识工件校验和、类、运行时兼容性、培训/评估沿袭和批准状态。

    5.2 分发生命周期¶

    包会经历草稿、验证、批准、分配、下载、边缘验证、激活和确认状态。不可变内容收到新版本而不是就地编辑。在更广泛的分配之前，推出支持较小的设备群。边缘保留最后一次已知良好的包裹，并仅在检查之间激活。中心地位将分配与实际确认区分开来；任何仪表板都不应暗示仅通过分配即可激活。

    模型分发是未来的范围，但一个月目标中的配置/规则分发应该已经使用兼容的版本和确认语义。

    6. 人工审核和报告¶

    审核呈现原始图像、覆盖图、投资回报率、组件证据、自动原因和固定版本。审核者记录已确认的OK、已确认的NG、不可审核或其他已批准的分类法，以及更正原因和注释。原始自动化结果保持不变。并发审查使用声明/版本检查来防止静默覆盖；每个转换都经过审核。

    报告将自动计数与经过审查的真实情况分开，并清楚地说明样本覆盖范围。所需的视图包括 OK/NG 趋势、缺失组件、条形码故障、产品/系列/设备故障、模型/规则版本性能、设备运行状况/上次查看、上传延迟、审核率和纠正率。估计的假阴性指标需要抽样 OK 审核或独立标记的验收数据；未经审查不能被解释为正确性。

    7. API 和 Web 架构¶

    建议的版本组为 /api/v1/device-ingest、/devices、/lines、/inspections、/media、/reviews、/products、/rules、/models、/device-configurations、/dashboard、/reports、/events、/audit-logs 和 /auth。集合 API 使用游标分页和有界过滤器。变异请求在客户端重试时使用乐观并发和幂等性。

    FastAPI生成OpenAPI； Vue 3 TypeScript 应用程序使用生成的客户端。 Pinia 保存会话/UI 状态而不是复制服务器事实。路由器级和组件级防护改善了用户体验，而服务器授权仍然具有权威性。 WebSocket 或 SSE 可以提供设备/仪表板更新，并在重新连接后通过 REST 重新同步。

    8. 授权、审计和安全¶

    • 设备身份验证与人工身份验证不同，其范围仅限于该设备的摄取/配置。
    • 根据策略要求，人员权限可单独查看、审查、配置编辑、批准、推出、用户管理、导出和审核访问。
    • TLS 保护传输；秘密存储/轮换和静态加密遵循选定的托管/客户控制。
    • 审核记录包括参与者、操作、目标、先前/新版本引用或有界差异、时间戳、请求/相关 ID 和结果。
    • 根据经过验证的数据分类处理条形码和媒体访问；日志避免凭证和不必要的原始负载。
    • 上传强制执行内容类型、大小、校验和、恶意软件/内容策略（如果需要）、速率限制和不透明对象密钥。

    确切的身份提供商和租赁模型尚未解决，并且不得由初始表列表暗示。

    9. 可靠性、工作和运营¶

    除了数据库/对象存储依赖项之外，API 是水平无状态的。 PostgreSQL 在需要时使用经过测试的备份和时间点恢复。对象存储使用与数据库保留和备份策略兼容的生命周期规则。健康检查区分活跃度/就绪度；可观察性将请求、设备、检查、媒体、作业和用户/审核 ID 关联起来。

    异步作业是可重试的和幂等的，持久存储状态，对瞬时/永久故障进行分类，并在合理的情况下使用死信/运算符处理。仪表板查询优化仅在查询测量之后从索引和预聚合表/物化视图开始； Redis 是可选的而不是记录系统。

    指标涵盖摄取量/错误/幂等重播/冲突、媒体验证、API 延迟/错误、数据库/对象存储运行状况、作业滞后/失败、设备上次查看、上传延迟、包确认、审核积压和审核失败。警报必须是可操作的，并避免将故意离线的设备视为无法解释的健康设备。

    10. 部署¶

    最初的中央部署是 Docker Compose 友好的：Nginx、内置管理资产、FastAPI API、PostgreSQL、对象存储实现以及只有合理的工作人员/代理。容器使用多阶段构建、非 root 用户、运行状况检查、重启策略、显式机密/配置和持久卷。架构迁移是一个受控发布步骤，并非由每个 API 副本同时运行。

    未来的 Kubernetes 部署可能会取代编排，同时保留 API 和持久性边界。不假定确切的托管位置、可用性拓扑、备份目标和数据驻留。

    11. 交付范围¶

    11.1 两天 MVP¶

    没有建立中央服务器。静态输出使用未来兼容的标识符、原因代码和版本，因此集成不需要重新定义决策。

    11.2 一个月目标¶

    实施设备范围的幂等摄取、PostgreSQL 检查历史记录、选定的证据存储、初始设备/产品/规则元数据、基本管理仪表板、审查捕获和 Compose 部署。推迟复杂的分析和模型二进制分发。

    11.3 生产目标¶

    添加批准的身份/授权、凭证轮换、审计、备份/恢复测试、保留、安全媒体访问、转出/回滚、协调、警报、报告正确性控制、性能/浸泡测试和操作运行手册。

    11.4 未来¶

    仅当需求和负载合理时才添加签名模型分发、更大规模的工作人员和分析、外部身份/集成以及 Kubernetes。

    12. 假设¶

    • 边缘客户端可以进行身份验证并最终到达 HTTPS 端点。
    • 中央关系数据库和持久对象存储可以在选定的托管环境中运行。
    • 设备/产品标识符可以集中管理，无需在检查期间进行集中查找。
    • 只有在标签批准和数据集治理之后，审核结果才可以用作培训候选。

    13. 开放性问题和需要验证¶

    1. 系统是单客户还是多租户，什么组织/站点/线路层次结构是真实的？
    2. 中央托管在哪里，适用哪些可用性/恢复目标，以及允许哪些连接路径？
    3. 需要哪些身份提供商、角色、设备凭证机制、TLS/PKI、签名和秘密存储？
    4. 适用哪些条形码/介质分类、驻留、保留、删除、导出和审核义务？
    5. 哪些检查/媒体量、有效负载大小、查询并发性和报告计划决定工作/存储设计？
    6. 哪些审核结果和工作流程状态得到批准，谁可以更改标签或发布包？
    7. 1个月的目标是否需要远程配置交付，还是仅需要管理和手动边缘安装？
    8. 哪些工作适合使用代理/Redis，哪些对象存储实现可用？
