    20. 部署和操作¶

    20.1 目的和范围¶

    本文档定义了 AssemblyVision 的打包、安装、升级、操作、备份和恢复方式。它涵盖了边缘检测系统和中央服务，而不使中央服务器成为实时检测的依赖。

    20.1.1 当前和 MVP 范围¶

    • 静态训练和检查 MVP 在开发人员环境中运行。仅供开发人员使用的培训 CLI 会生成本地模型工件；检查 CLI 生成 JSON、ROI 图像、带注释的图像和保留的验证输出。
    • 此 MVP 未实现加密模型工件或仅限 .pyc 的客户运行时打包；训练代码被简单地排除在任何运行时分发之外。
    • 为期一个月的目标是使用 Docker Compose 打包边缘和中央应用程序。
    • SQLite 可接受作为初始边缘数据库； PostgreSQL 是中央数据库。
    • 持久运行时数据存储在容器层之外。
    • 边缘不需要 Kubernetes。

    20.1.2 生产目标¶

    • 可复制的多阶段图像，由不可变版本或摘要固定。
    • 非根容器、运行状况检查、重启策略、资源限制和显式持久卷。
    • 使用持久上传队列进行离线边缘检查。
    • 受控、可逆的配置、规则、应用程序和模型部署。
    • 配置、数据库和所需证据的备份和恢复练习。

    20.1.3 未来范围¶

    • 如果规模或组织标准证明合理，则在 Kubernetes 上进行集中部署。
    • 舰队部署编排和分阶段部署环。
    • 在异常大型的边缘安装中可选 PostgreSQL。

    20.2 部署单元¶

    单位 地点 责任 需要检查
    edge-service 边缘 本地 API、相机/条形码编排、推理、聚合、持久性、上传和运行状况 是的
    edge-web 边缘 具有离线功能的操作员仪表板 不，但操作上很重要
    nginx-edge 边缘 静态 UI 和本地反向代理 没有
    central-api 中环 摄取、管理、报告 API 没有
    central-worker 中环 可选媒体处理、报告、通知、包准备 没有
    admin-web 中环 管理和审查 UI 没有
    postgres 中环 中央交易商店 没有
    object-storage 中环 上传的图像和剪辑存储 没有
    redis 中环 可选的作业代理/缓存；仅当工人需要时 没有

    相机访问可能需要供应商 SDK、主机设备映射或主机端适配器。在选择容器隔离和设备权限之前必须验证此集成。

    20.3 图像构建¶

    每个应用程序都使用多阶段构建。构建阶段解决固定依赖项、运行编译并仅发出运行时工件。运行时阶段不包含 Git 元数据、测试、训练数据、笔记本或包管理器缓存。 Python 模块可以编译为 .pyc 并在可行的情况下删除原始项目 .py 文件；这是包装卫生，而不是强有力的代码保护。

    运行时要求是：

    1. 作为专用非根 UID/GID 运行。
    2. 显式挂载应用程序代码只读目录和运行时目录。
    3. 仅写入数据库、介质、队列、临时卷和日志卷。
    4. 在运行时接收机密，而不是通过图像层或前端包。
    5. 通过运行状况 API 公开构建标识符和应用程序版本。
    6. 固定基础镜像并在发布前扫描它们。

    20.4 Edge Docker 组合示例¶

    该示例是一个模板。设备路径、图像注册表、存储路径和资源限制需要站点验证。

    services:
  edge-service:
    image: registry.example.invalid/assemblyvision/edge-service:${AV_VERSION}
    user: "10001:10001"
    read_only: true
    restart: unless-stopped
    environment:
      AV_DATABASE_URL: sqlite:////var/lib/assemblyvision/db/edge.db
      AV_MEDIA_ROOT: /var/lib/assemblyvision/media
      AV_CENTRAL_URL: ${AV_CENTRAL_URL}
      AV_DEVICE_ID: ${AV_DEVICE_ID}
      AV_CONFIG_ROOT: /etc/assemblyvision
    volumes:
      - edge-db:/var/lib/assemblyvision/db
      - edge-media:/var/lib/assemblyvision/media
      - edge-config:/etc/assemblyvision:ro
      - edge-models:/opt/assemblyvision/models:ro
      - edge-tmp:/tmp
    healthcheck:
      test: ["CMD", "python", "-m", "assemblyvision.healthcheck", "http://127.0.0.1:8000/api/v1/health/live"]
      interval: 15s
      timeout: 3s
      retries: 4
      start_period: 30s
    networks: [edge-private]

  edge-web:
    image: registry.example.invalid/assemblyvision/edge-web:${AV_VERSION}
    user: "101:101"
    read_only: true
    restart: unless-stopped
    depends_on:
      edge-service:
        condition: service_healthy
    ports:
      - "127.0.0.1:8080:8080"
    networks: [edge-private]

networks:
  edge-private: {}

volumes:
  edge-db: {}
  edge-media: {}
  edge-config: {}
  edge-models: {}
  edge-tmp: {}

    depends_on 仅控制启动顺序； UI 必须容忍服务重新启动。 edge-service 内的决策关键任务必须在没有 DNS 访问中央服务器的情况下启动和继续。当需要相机SDK或GPU隔离时，可以在容器内添加监督推理子流程；可单独部署的边缘工作人员被推迟，直到测量证明其合理为止。

    20.5 中央 Docker 撰写配置文件¶

    中央配置文件包含 Nginx、central-api、可选的 central-worker、PostgreSQL、对象存储和可选的 Redis。后台执行适用于大型媒体、缩略图、导出、报告生成、通知和模型包准备的校验和验证。检查摄取本身仍然是同步幂等 API 操作，在确认边缘之前持久记录收据。

    持久卷必须涵盖 PostgreSQL 和对象存储。数据库迁移在应用程序替换之前作为一次性发布任务运行；它们必须在滚动更换过程中向后兼容，或者需要有记录的维护窗口。

    20.6 Nginx 示例¶

    server {
    listen 443 ssl;
    server_name assemblyvision.example.invalid;

    ssl_certificate     /run/secrets/tls.crt;
    ssl_certificate_key /run/secrets/tls.key;
    client_max_body_size 64m;

    root /usr/share/nginx/html;
    index index.html;

    location /api/v1/ws/ {
        proxy_pass http://central-api:8000;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_read_timeout 75s;
    }

    location /api/ {
        proxy_pass http://central-api:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_read_timeout 60s;
    }

    location / {
        try_files $uri $uri/ /index.html;
    }
}

    生产 TLS 策略、证书自动化、上传限制和请求超时必须反映客户网络和预期的 NG 剪辑大小。媒体上传 API 应支持可恢复或有界分段上传，而不是依赖于任意大的代理限制。

    20.7 配置和秘密¶

    配置优先级是键入的应用程序默认值、受管理的不可变包、批准的站点配置和仅部署环境覆盖。环境/本地覆盖可能会更改连接、路径、资源限制和非安全显示选项；他们不得更改产品映射、所需组件、阈值或模型/规则兼容性。产品规则和模型清单是签名/版本控制的域工件，而不是普通的环境变量。机密包括中央凭据、设备凭据、TLS 私钥和对象存储凭据。它们是从具有最低权限的主机秘密存储或部署系统安装的。

    每个有效的配置快照都会记录其版本和校验和。验证发生在激活之前。无效配置会使最后一个已知良好的版本保持活动状态并发出事件。影响相机几何形状、产品映射、所需组件、阈值或模型的更改需要审核记录和明确的激活操作。

    20.8 模型和规则更新顺序¶

    更新是拉取式或集中式启动的，但绝不会直接从未经验证的下载中激活。模型和兼容规则版本作为原子发行集安装。

    sequenceDiagram
    participant A as 行政人员
    participant C as 中央服务器
    participant E as 边缘更新代理
    participant V as 验证器
    participant I as 检验员
    A->>C:批准签署的发布清单
    C-->>E:宣布可用版本
    E->>C:下载包和清单
    E->>E:验证身份、校验和和签名
    E->>V:运行兼容性和烟雾检查
alt 验证成功
        V-->>E:有效的
        E->>I:请求安全窗口激活
        I-->>E:检查窗口关闭
        E->>E:原子切换主动释放
        E->>I:重新启动或重新加载
        I-->>E:新版本带来健康
        E->>C:报告安装成功
else 验证或健康检查失败
        V-->>E:无效的
        E->>E:保留或恢复最后的已知良好版本
        E->>C:报告故障和诊断
    end

    激活不得将物理产品检查拆分为多个版本。回滚恢复以前的应用程序/模型/规则集，同时保留检查和上传数据。

    20.9 发布和升级流程¶

    1. 根据经过审查的提交构建不可变的工件并生成软件物料清单。
    2. 运行单元、集成、安全、模型、弹性和验收候选测试。
    3. 签署清单并将工件发布到受控注册表。
    4. 迁移前备份边缘配置/数据库和中央数据库。
    5. 部署到非生产边缘或转出环并执行烟雾检查。
    6. 停止接受新产品窗口，允许活动窗口完成并保持状态。
    7. 应用迁移、安装工件并运行准备情况检查。
    8. 恢复检查并将遥测数据与基线进行比较。
    9. 如果运行状况、延迟、证据完整性或检查行为违反批准的发布标准，则回滚。

    20.10 备份与恢复¶

    资产 备份方法 恢复目标定义
    边缘配置、规则、清单 关于更改和预定的加密副本 恢复最后批准的集
    边缘 SQLite SQLite在线备份或静默复制；写入期间从不原始副本 恢复数据库并协调媒体/上传队列
    边缘媒体 基于保留；保留尚未上传的证据 恢复检查而不删除未决证据
    中央 PostgreSQL 完整备份加上事务日志策略（如果支持） 恢复执行后客户同意的 RPO/RTO
    中央对象存储 根据部署进行版本控制/复制 根据数据库校验和协调对象

    确切的备份频率和恢复目标是验收决策。在代表性恢复成功之前，备份不会被视为可操作。

    20.11 操作手册¶

    20.11.1 相机断开¶

    1、停止打开检查窗口，并呈现明显不可用状态；切勿在没有图像的情况下推断 OK。 2. 记录相机状态、适配器错误和时间戳。 3. 检查电源、电缆、链路、供应商服务和专有设备所有权。 4. 在安全的情况下仅重新启动相机适配器/worker；避免删除排队的记录。 5. 在继续之前验证曝光、对焦、取景和已知的测试产品。 6. 通过日志和摄像头诊断升级重复断开连接。

    20.11.2 本地磁盘压力或满磁盘¶

    1. 在配置的警告和严重水印时发出警报。
    2. 根据保留顺序仅删除过期、上传的媒体；切勿删除待上传或可追溯性所需的数据库记录。
    3. 在关键保留处，禁用可选的全视频录制并尽可能保留决策元数据/关键证据。
    4. 如果不能保证持久的检查记录，则暂停检查并要求操作员干预。
    5. 在恢复之前扩展/替换存储、验证文件系统运行状况并协调数据库路径。

    20.11.3 中央或网络中断¶

    1. 继续本地检查并持久排队上传。
    2. 显示断开连接状态和队列年龄/大小，而不阻塞决策。
    3. 确认本地容量能够覆盖停电；应用保留保障措施。
    4. 恢复时，使用指数退避、抖动、幂等密钥和校验和验证重试。
    5. 核对已确认的收据并调查永久失败的任务。

    20.11.4 边缘应用程序重启或断电¶

    1. Supervisor根据配置的策略重新启动容器。
    2. 启动时，运行数据库完整性和迁移检查，发现不完整的窗口，并在需要结果时将生命周期状态 ABORTED 与业务 NG 持久保存，或者仅在身份明确时恢复。
    3. 协调临时媒体文件和持久上传任务。
    4. 验证相机、模型、规则、存储和本地 API 准备情况。 5.如果停机不干净，需要进行烟雾检查。

    20.11.5 发布失败¶

    1. 在产品窗口之间保持检查暂停。
    2. 捕获失败的版本、日志、验证输出和迁移状态。
    3. 以原子方式重新激活最后一个已知良好的应用程序/模型/规则集。
    4. 运行准备情况和已知样本检查。
    5. 经授权操作员确认状态后方可恢复；保留失败的工件以供分析。

    20.12 运营所有权¶

    客户姓名线路操作员和现场 IT 联系人；供应商指定应用程序和模型支持所有者。部署记录必须说明谁可以暂停检查、批准配置、安装版本、恢复备份和声明服务恢复。支持边界必须区分工厂硬件/网络故障和 AssemblyVision 缺陷。

    20.13 未解决的问题和需要验证¶

    • 边缘操作系统、CPU/GPU 模型、驱动程序堆栈和资源限制。
    • 相机供应商、SDK、设备映射、触发接口和容器兼容性。
    • 中央服务器位置、可用性设计、DNS、代理和防火墙规则。
    • 预期的输送机速率、检查延迟预算和重新启动安全程序。
    • 本地和中央保留期、磁盘容量以及磁盘压力下可接受的降级。
    • 备份频率、加密/密钥所有权以及客户批准的 RPO/RTO。
    • TLS 证书颁发机构、设备注册、注册表访问和离线安装过程。
    • 最大关键帧和 NG 剪辑大小以及是否需要断点续传。
