    18. Monorepo 和代码组织¶

    18.1 目标¶

    AssemblyVision 使用一个 Python/TypeScript monorepo 来协调域合约、边缘和中央版本、前端客户端、迁移、部署和评估。存储库必须保留运行时边界，而无需为每个管道步骤创建包。

    相关合约定义在Data Model and Database和REST API and Events中。前端所有权在 Edge Dashboard 和 Central Admin Dashboard 中描述； ML 工作流程在 Training and Evaluation 中描述。

    18.2 组织原则¶

    1. apps/包含独立可运行/可部署的进程和Web应用程序。
    2. packages/ 包含由至少两个应用程序或需要独立测试的内聚域重用的代码。
    3. 将产品检测、ROI、组件检测、时间聚合和规则放在 vision-core 中。一旦第二个具体消费者需要domain和vision-core，就提取它们；标记为“训练和检查”的 MVP 就是该触发器，因为训练重用了域模式和 ROI/预处理。
    4. 运行时应用程序代码永远不会从 training/ 导入。
    5. 边缘代码不得导入中央持久性或需要中央连接。
    6. 前端使用生成的 API 合约和小型共享视觉原语；特定于页面的商店和组件保留在其应用程序中。
    7. 生产数据、凭证、数据集和模型权重是外部工件，会被 Git 忽略。
    8. 每个可部署的应用程序都拥有组合/配置；共享包在导入时不得读取环境变量。

    18.4 应用程序的责任¶

    18.4.1 edge-service¶

    拥有相机适配器、条形码读取器、检查管道、SQLite 存储库、文件系统媒体、持久上传发件箱、本地 API/WebSocket、启动恢复和运行状况的依赖组合。基础设施适配器实现面向域的协议。它必须在没有中央凭据或连接的情况下启动和检查。

    建议的内部方向是api -> application -> domain/protocols，并使用infrastructure实现协议。 API 处理程序不直接调用 SQLAlchemy。捕获回调不得同步执行数据库上传或浏览器广播。

    18.4.2 central-api¶

    拥有身份验证/授权、租户范围界定、摄取、查询 API、配置/模型注册、审查、审计、预签名媒体会话和 WebSocket 通知发布。它使用 PostgreSQL 和对象存储。小额交易内联完成。

    18.4.3 central-worker¶

    仅运行应比 HTTP 请求寿命更长的作业：报告/导出生成、昂贵时的媒体验证/衍生品创建、保留批次以及通知扇出（如果引入）。普通的 CRUD 或检查元数据摄取不需要它。 MVP 可以使用 PostgreSQL 支持的作业表；仅当重试、调度或吞吐量证明合理时，才会添加 Redis 和工作框架。

    18.4.4 Web 应用程序¶

    edge-web 和 admin-web 拥有路由级功能和部署品牌。它们共享生成的 API 客户端、检测坐标渲染、基本状态指示器和格式。复杂的产品/规则编辑器和车队图表仍然仅位于中央；边缘运行状况/队列控制仍然仅限边缘。

    18.5 Python 包边界¶

    套餐 内容 不得包含
    domain Pydantic API/事件值模型、枚举、稳定错误代码 FastAPI 路由器、SQLAlchemy 表、相机 SDK、存储客户端
    vision-core 图像源协议、文件夹源、相机/条形码适配器协议、YOLO 包装器、ROI、聚合、确定性规则、管道 边缘数据库、中央 API、仪表板代码、培训编排
    platform-common 在两个应用程序需要它们之后，可选择提取窄记录/配置/校验和/遥测实用程序 域业务规则，通用“utils”垃圾场

    SQLAlchemy 持久性模型保留在每个应用程序中，因为边缘和中心架构不同。上传协议 DTO 可能位于 domain 中；上传重试实现属于edge-service。如果只有一个应用程序使用助手，请将其保留在该应用程序中。

    18.6 TypeScript 包边界¶

    • api-client 包含边缘和中央 OpenAPI 文档的确定性生成客户端以及最小的身份验证/错误包装器。生成的代码是隔离且可替换的。
    • ui 包含真正共享的、以演示为中心的组件：检测查看器、状态徽章、媒体安全格式和常见的可访问原语。它不包含路由感知组件或应用程序商店。
    • eslint-config 集中 lint 规则。最初不需要用于图表、域类型、身份验证或验证的单独包；它们保留在应用程序或 API 客户端中，直到证明可以重复使用。
    • Vue、Element Plus/Naive UI 和 ECharts 应在适当的情况下相互依赖，以防止重复的运行时副本。

    18.8 MVP 与后来的软件包¶

    18.8.1 静态训练和检查 MVP¶

    必需：一个包含 edge-service 运行时发行版的根 uv 工作区、具有 av-train CLI 的单独的仅供开发人员使用的 training 发行版以及共享的 domain 和 vision-core 包。 training 从 X-AnyLabeling 标签生成产品和组件 YOLO 工件；它永远不会被边缘运行时发行版导入或包含在其中。 vision-core 拥有共享的 ROI 生成和坐标映射，因此组件数据集准备和运行时推理使用相同的转换。不需要 TypeScript 设置、数据库、Web 应用程序、中央应用程序、时间聚合、上传和相机 SDK。

    18.8.2 一个月 MVP¶

    必需：edge-service、edge-web、中央 API 代码库以及演示器所需的最小中央检查/审查 Web 视图。运行时部署最多从两个Python应用程序发行版开始（边缘运行时和中央API）；已提取的 domain 和 vision-core 包仍与仅限开发人员的培训发行版共享。将配置、日志记录、持久性和作业保留在应用程序本地，直到另一个具体消费者证明提取是合理的。仅共享 TypeScript 中生成的 API 合约和经过验证的检测查看器原语。单独的 central-worker、platform-common、共享图表/身份验证/验证包、通用管理 UI 和报告作业被推迟。

    18.8.3 仅在合理时添加¶

    潜在的后续软件包包括具有冲突的本机依赖性的特定于供应商的相机适配器、专用的 MES/PLC 集成包、多个流程的中央应用程序/域提取、由另一个应用程序重用的图表组件以及模型分发工具。不要为它们预先创建空包。

    18.9 依赖关系和版本管理¶

    使用带有 uv 和每个应用程序/包 pyproject.toml 声明的一个根 Python 工作区；生产应用程序锁定解析来自已提交的 uv.lock。将 pnpm 工作区与一个提交的锁定文件结合使用。显式固定主要/次要运行时依赖项和模型运行时/CUDA 组合。改造是通过测试来审查的，而不是盲目合并的。

    Python 支持 3.12。 TypeScript 使用严格的基本配置。每个包仅导出公共入口点。循环依赖项使 CI 通过导入/依赖项检查失败。本机相机 SDK 和 GPU 包使用可选的依赖项组，因此中心图像不包含它们。

    18.10 配置和秘密¶

    类型化设置存在于每个可运行的应用程序中，并由 platform-common 组成共享原语。解决顺序已记录：默认值、配置文件、环境变量，然后是明确批准的运行时覆盖。示例文件不包含任何秘密。凭证来自已安装的机密或部署机密存储，并且绝不是模型/配置包的一部分。

    config/ 下的配置模式和示例受源代码控制。有效的运行时配置和版本校验和是可观察的，敏感字段已被编辑。

    18.11 模型、数据和生成的工件¶

    • models/manifests/ 可能包含小清单和校验和以供开发参考。模型权重存在于工件注册表/对象存储中，并被 Git 忽略。
    • training/ 包含可重现的代码、X-AnyLabeling-to-YOLO 数据集验证、组件 ROI 准备和小型综合测试装置，而不是生产数据集或未经策划的导出。它仅供开发人员使用，并且不包含在运行时发行版中。
    • 静态训练和检查 MVP 使用带有校验和的普通本地模型工件。模型加密和仅限 .pyc 的运行时打包被推迟到单独合理的分发范围。
    • 运行时数据库、图像、剪辑、日志、缓存和报告使用显式外部卷，而不是存储库路径。
    • OpenAPI 文档和生成的客户端是确定性生成的。所选策略可以提交生成的输出以方便前端构建或在 CI 中重新生成，但 CI 始终检查偏差。
    • 构建的前端资产和编译的 Python 运行时层是构建输出，而不是源目录。

    18.12 测试布局¶

    单元测试位于其拥有的应用程序/包旁边。根测试涵盖边界：

    套房 范围
    contract OpenAPI 生成、客户端生成/类型检查、事件 JSON 架构、边缘中心摄取兼容性
    e2e 浏览器加上已部署的 API/数据库/对象存储工作流程
    resilience 网络丢失、重启、租约过期、磁盘已满、校验和不匹配、重复上传
    performance 管道延迟、API/仪表板查询、上传恢复、持续运行
    fixtures 小型合成/非敏感图像、API 有效负载和工厂构建器

    测试不会从生产数据目录导入装置。 ML 评估数据集在外部进行版本控制，并与快速 CI 分开调用。

    18.13 CI 和构建流程¶

    1. 验证可用工具的格式、Ruff、MyPy、ESLint、TypeScript 和 Markdown 链接/图表。
    2. 运行更改包单元测试，然后运行合同测试和集成测试。
    3. 生成 OpenAPI 和 TypeScript 客户端并因漂移而失败。
    4. 仅使用声明的工作区依赖项在隔离的多阶段 Docker 构建中构建每个应用程序。
    5. 扫描依赖项/映像并生成 SBOM。
    6. 运行 Compose 烟雾测试以进行边缘离线启动和中央摄取。
    7. 仅发布经过审查、标记的修订版的不可变图像/工件；在清单中记录源修订。

    培训作业并不是 CI 运行的每个应用程序的一部分。他们的代码测试在 CI 中运行；完整的培训/评估在受控的机器学习环境中运行，并发布签名/验证的报告和模型工件。

    18.14 Ownership and Change Rules¶

    使用代码所有者进行愿景/规则、边缘运行时、中央/安全、前端共享包、迁移和培训/评估。 Pydantic 合约变更需要 API/客户端漂移检查。已发布的事件更改需要兼容性审查。数据库更改需要迁移和回滚/前恢复注释。共享 UI 添加需要两个具体的消费者；否则他们仍然是本地人。

    18.15 未解决的问题和需要验证¶

    • 选择构建环境支持的uv工作区和pnpm版本。
    • 确认 CI 提供程序、容器注册表、工件/模型注册表和 SBOM/签名要求。
    • 确认相机 SDK 许可或本机库是否需要单独构建的适配器包/图像。
    • 决定在每个消费者构建期间是否提交或生成生成的 OpenAPI 客户端。
    • 验证报告/媒体工作负载是否证明 central-worker 和一个月演示中的工作经纪人是合理的。
    • 确认支持的边缘操作系统、CPU/GPU架构以及离线依赖安装过程。
