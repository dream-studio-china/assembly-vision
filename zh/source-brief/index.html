    任务：生成完整的 AssemblyVision 软件架构文档¶

    您是首席软件架构师、工业计算机视觉工程师、MLOps 工程师和全栈技术作家。

    您的任务是为名为 AssemblyVision 的工业 AI 检测平台生成完整的、内部一致的、面向实施的软件架构文档集。

    不要生成肤浅的自述文件或人工智能生成的通用概述。制作一个实用的工程蓝图，小型软件团队可以使用该蓝图立即开始实施。

    该文档必须描述初始 MVP 和目标生产架构。

    1. 项目背景¶

    1.1 项目名称¶

    装配愿景

    完整标题：

    AssemblyVision — 工业装配检测系统

    1.2 商业目的¶

    AssemblyVision 是一种用于基于传送带的生产线的工业计算机视觉系统。

    该系统检查已完成的产品并验证是否存在所有必需的装配组件。

    检查目标包括：

    • 完整的产品
    • 几个大型装配部件
    • 产品手册或说明书
    • 产品条形码
    • 产品型号或产品类型

    主要业务产出为：

    • OK：可靠地检测到所有必需的组件
    • NG：一个或多个所需组件缺失、不确定或无法可靠验证

    1.3 质量优先¶

    系统必须优先考虑减少漏报。

    该项目中的假阴性意味着：

    真正有缺陷或不完整的产品被错误地分类为合格产品。

    企业在早期生产阶段接受一定数量的错误 NG 结果，因为这些产品可以进行手动审核。

    因此，工程优先级是：

    1. 最大限度地减少漏报
    2. 保持可追溯性
    3. 提高稳健性
    4. 逐步减少误报 5、提高运营效率

    不要将系统描述为保证 100% 的准确性。

    使用以下语言：

    • 极低的假阴性率
    • 以接近零遗漏 NG 案例作为工程目标
    • 基于测量验证数据的生产验收
    • 高NG召回率
    • 谨慎推出人工验证

    2. 确认的生产条件¶

    当前的物理环境具有以下特点：

    • 约四百万像素的工业相机
    • 固定照明
    • 修复了正常生产期间的相机问题
    • 受控的检查环境
    • 产品可能在图像内略有移动
    • 产品位置不完全固定
    • 产品通常不会进行大幅度的不受控制的旋转
    • 检查对象是大型部件
    • 目前不需要微型部件或微小螺钉检查
    • 检查任务主要集中于组件的存在
    • 系统必须自行实现相机捕获
    • 系统必须自行实现条码识别
    • 系统必须自行实现图像和视频存储
    • 系统必须自行实现检验结果存储
    • 客户端计算机在与中央服务器断开连接时必须继续检查

    不要声明图像保存或条形码记录已经存在。

    这些功能必须作为 AssemblyVision 的一部分来实现。

    3. 最终架构决策¶

    AssemblyVision 使用 边缘客户端和中央服务器架构。

    所有生产关键型图像处理和检查决策都必须在客户端工业计算机上进行。

    不一定需要中央服务器进行实时检查。

    3.1 边缘客户端职责¶

    边缘客户端在客户工厂内部运行，负责：

    • 工业相机集成
    • 视频流或帧捕获
    • 触发处理
    • 产品窗口管理
    • 条码识别
    • 产品类型解析
    • YOLO产品检测
    • 投资回报率生成
    • YOLO组件检测
    • 可选的 OpenCV 检查
    • 多帧时间聚合
    • 规则评估
    • 最终 OK 或 NG 决定
    • 本地检查数据库
    • 本地图像存储
    • 本地视频或视频剪辑存储
    • 上传队列
    • 网络中断后重试
    • 本地设备健康监控
    • 本地FastAPI服务
    • 本地Vue仪表板

    如果中央服务器或网络不可用，检查管道必须继续运行。

    3.2 中心服务器职责¶

    中央 Web 服务器负责：

    • 接收上传的检查结果
    • 接收选定的关键图像帧
    • 接收可选的 NG 视频剪辑
    • 集中检查历史记录
    • 跨设备、跨线路报告
    • 设备管理
    • 产品配置管理
    • 规则配置管理
    • 模型版本管理
    • 用户和权限管理
    • 手动NG审核
    • 数据仪表板
    • 统计分析
    • 审核日志
    • 远程配置分发
    • 未来模型包分发

    3.3 上传策略¶

    不要将每个视频帧上传到中央服务器。

    边缘客户端应根据需要保留完整或滚动的本地视频。

    推荐的上传策略：

    For OK inspections¶

    上传：

    • 检查元数据
    • 条形码
    • 产品类型
    • 最终决定
    • 检测到的组件
    • 信心总结
    • 型号版本
    • 规则版本
    • 设备ID
    • 检查时间戳
    • 1个有代表性的关键帧

    用于 NG 检查¶

    上传：

    • 完整的检查元数据
    • 缺少组件
    • 低置信度组件
    • 多个关键帧
    • 带注释的关键帧
    • 产品投资回报率图像
    • 可选的围绕检查活动的短视频片段
    • 相关错误日志

    对于系统异常¶

    上传：

    • 异常类型
    • 设备状态
    • 相机状态
    • 相关图片
    • 相关日志摘录
    • 时间戳

    上传子系统必须支持：

    • 离线缓冲
    • 持久上传队列
    • 退避重试
    • 幂等性
    • 防止重复
    • 上传状态跟踪
    • 校验和验证
    • 本地保留政策

    4. 技术决策¶

    4.1 边缘后端¶

    用途：

    -Python 3.12 - 快速API - 独角兽 - Ultralytics YOLO - OpenCV - 派丹提克 - SQLAlchemy - 蒸馏器 - SQLite最初用于本地存储 - PostgreSQL 可选用于较大的边缘安装 - pytest -拉夫 - 我的Py - structlog 或标准结构化日志记录

    第一个 MVP 可能在本地使用 SQLite。

    4.2 中央后端¶

    用途：

    -Python 3.12 - 快速API - Uvicorn 或 Gunicorn - 派丹提克 - SQLAlchemy - 蒸馏器 - PostgreSQL - Redis 合理的地方 - Celery、Dramatiq、RQ 或其他合理的后台作业系统 - S3兼容的对象存储或文件系统抽象 - pytest -拉夫 - 我的Py

    不要仅仅为了建筑外观而引入后台工作者。解释哪些作业需要异步执行。

    4.3 Web 前端¶

    本地边缘仪表板和中央管理仪表板都使用：

    • 视图3
    • 打字稿
    • 维特 -Vue路由器
    • 皮尼亚
    • Axios 或生成的 OpenAPI 客户端
    • Element Plus 或 Naive UI
    • 电子图表 -Vue使用
    • 维泰斯特 -ESLint
    • 更漂亮

    使用 Vue 和 TypeScript 因为系统需要：

    • 复杂的管理页面
    • 可重复使用的桌子
    • 数据仪表板
    • 实时状态
    • 图像检查视图
    • 检测框覆盖
    • 规则配置
    • 设备状态
    • 上传队列可视化
    • 人工审核
    • 类型化 API 集成

    本地边缘仪表板必须是本地服务的 Web 应用程序。

    可以通过以下方式打开：

    • 标准浏览器
    • 浏览器信息亭模式
    • 未来版本中的轻量级桌面包装器，例如 Tauri

    不建议使用 Tkinter、PyQt 或 PySide 构建主仪表板，除非将它们作为被拒绝的替代方案进行讨论。

    4.4 部署¶

    用途：

    • 码头工人
    • Docker 撰写
    • Nginx（如果适用）
    • 持久卷
    • 多阶段构建
    • 非根容器
    • 基于环境的配置
    • 健康检查
    • 重启政策

    边缘部署不能依赖于Kubernetes。

    中央服务器可能支持 Kubernetes 作为未来的选项，但最初的设计应该保持 Docker Compose 友好。

    5. 检测架构¶

    使用两级检测管道。

    5.1 第一阶段：产品检测¶

    第一个检测器定位完整的产品。

    输入：

    • 全相机框架

    输出：

    • 产品类别
    • 边界框
    • 信心
    • 可选的跟踪信息

    目的：

    • 处理轻微的产品位置变化
    • 避免依赖硬编码的绝对投资回报率
    • 标准化组件检查的输入

    5.2 ROI提取¶

    投资回报率引擎：

    • 接收产品边界框
    • 使用可配置的边距扩展它
    • 将坐标剪切到图像边界
    • 裁剪产品区域
    • 记录全帧和ROI坐标之间的映射
    • 可选择标准化方向或视角

    不要假设产品位置是完全固定的。

    硬编码的全帧 ROI 可用作后备或粗略捕获区域，但最终产品 ROI 应从产品检测中生成。

    5.3 第二阶段：组件检测¶

    第二个检测器处理产品 ROI。

    可能的课程包括：

    • component_a
    • component_b
    • component_c
    • manual
    • 其他配置组件

    具体所需的组件列表取决于产品类型。

    系统应该检测所需的组件，而不是训练抽象的全局 missing_component 类。

    5.4 条码识别¶

    条形码识别必须作为单独的功能来实现。

    它可能会使用：

    • 工业扫描仪SDK
    • OpenCV 条形码 API
    • pyzbar 或 ZXing 兼容解决方案
    • 供应商特定的相机或扫描仪 SDK

    条形码识别不得作为 YOLO 分类任务实现，除非 YOLO 仅用于定位条形码区域。

    条形码可识别或帮助解决：

    • 产品标识
    • 产品类型
    • 必要的检验规则
    • 追溯记录

    5.5 规则引擎¶

    规则引擎必须是确定性的并且独立于人工智能模型。

    示例：

    product_type: model_a
required_components:
  - component_a
  - component_b
  - manual

    规则引擎评估聚合的检测证据并返回：

    • OK
    • NG
    • UNCERTAIN，如果采用这样的状态
    • 缺少组件列表
    • 低置信度成分列表
    • 失败原因代码

    规则引擎必须存储：

    • 规则版本
    • 产品配置版本
    • 型号版本

    6. 视频和时间聚合¶

    YOLO 将视频作为单独的帧进行处理。

    然而，业务决策是根据实际产品做出的。

    在帧级检测和最终规则评估之间引入时间聚合器。

    6.1 产品检验窗口¶

    系统必须对属于同一物理产品的帧进行分组。

    可能的机制包括：

    • 硬件触发
    • 条形码事件
    • 产品追踪
    • 进入和退出检测区域
    • 有时间限制的检查窗口
    • 输送机传感器集成

    讨论权衡。

    6.2 聚合策略¶

    不要使用简单的整体产品多数投票。

    每个所需组件的汇总证据。

    示例：

    component_a:
frame 1: detected at 0.91
frame 2: not detected
frame 3: detected at 0.88
final state: present

    component_b:
frame 1: not detected
frame 2: not detected
frame 3: not detected
final state: missing

    支持可配置的策略，例如：

    • 一次高置信度检测
    • 两次中等置信度检测
    • 相邻帧检测
    • 最小可见面积要求
    • 最低框架质量要求
    • 排除模糊或不可用的帧

    解释清楚：

    时间聚合不会提高底层 YOLO 模型的单帧精度。它通过跨框架结合证据来提高系统级的稳健性。

    7. 本地存储架构¶

    边缘客户端必须维护本地持久存储。

    商店：

    • 检查元数据
    • 条形码
    • 产品类型
    • 帧时间戳
    • 最终结果
    • 检测到的组件
    • 缺少组件
    • 置信度值
    • 产品边界框
    • 投资回报率元数据
    • 型号版本
    • 规则版本
    • 关键帧路径
    • 带注释的图像路径
    • 视频剪辑路径
    • 上传状态
    • 重试次数
    • 错误信息

    本地系统必须支持：

    • 断电恢复
    • 重新启动恢复
    • 上传简历
    • 磁盘空间监控
    • 可配置的数据保留
    • 安全清理
    • 防止删除仍在等待上传的文件

    定义存储策略：

    • 完整视频
    • 滚动视频
    • 关键帧
    • NG剪辑
    • 带注释的图像
    • 投资回报率图像
    • 日志
    • 数据库记录

    8. 前端架构¶

    8.1 边缘仪表板¶

    本地边缘仪表板应包括：

    • 当前相机预览
    • 最新检查结果
    • 当前条形码
    • 当前产品类型
    • 当前检测到的组件
    • 缺少组件
    • OK 或 NG 指示器
    • 检查延迟
    • 相机连接状态
    • AI模型状态
    • 本地磁盘状态
    • 网络状态
    • 中央服务器连接
    • 上传队列状态
    • 最近的检查记录
    • 本地配置
    • 本地服务日志
    • 上传失败时手动重试
    • 如果操作适当，紧急检查暂停或恢复

    仪表板在离线时必须保持可用。

    8.2 中央管理仪表板¶

    中央仪表板应包括：

    • 多设备概览
    • 多行概览
    • 检验统计
    • OK 和 NG 趋势
    • 缺失组件分布
    • 条码失败率
    • 型号版本性能
    • 规则版本性能
    • 设备健康状况
    • 设备上次查看状态
    • 上传延迟
    • 历史检验查询
    • 图片和视频审核
    • 手动NG验证
    • 产品配置
    • 规则管理
    • 模型包管理
    • 用户和角色
    • 审核日志
    • 导出和报告

    8.3 前端代码重用¶

    Monorepo 应支持可重用的前端包：

    • 共享 UI 组件
    • 图像查看器
    • 检测叠加
    • 状态徽章
    • 数据表
    • 图表组件
    • TypeScript 域类型
    • API客户端
    • 身份验证助手
    • 验证模式
    • 格式化实用程序

    明确区分边缘 Web 应用程序和中央管理 Web 应用程序。

    9. Monorepo架构¶

    使用支持 Python 和 TypeScript 的 Monorepo。

    使用基于以下原则的结构：

    • apps/包含可运行的应用程序
    • packages/python/包含可重用的Python包
    • packages/typescript/ 包含可重用的前端包
    • training/包含训练和评估代码
    • models/ 包含本地开发模型工件或元数据
    • deploy/ 包含部署定义
    • docs/包含架构文档
    • tests/包含跨应用程序测试
    • 运行时生产数据不得存储在 Git 存储库中

    10. 源码分发和客户端部署¶

    完整的边缘应用程序在客户控制的硬件上运行。

    目标是避免直接暴露可读源代码，而不是保证免受高级逆向工程的影响。

    记录以下部署方法：

    • 将Python模块编译成.pyc
    • 在可行的情况下从最终运行时映像中删除原始 .py 文件
    • 使用多阶段 Docker 构建
    • 仅部署构建的前端静态资产
    • 不部署Git存储库
    • 不要部署训练数据集
    • 不要部署笔记本
    • 不部署内部实验配置
    • 不要在图像中嵌入长期秘密
    • 使用非 root 运行时用户
    • 在可行的情况下使用只读容器文件系统
    • 将运行时数据存储在显式卷中

    明确指出：

    • .pyc没有很强的反逆向工程保护
    • Docker 不是源代码安全边界
    • 这个级别被接受，因为直接的要求只是避免直接随意的源浏览

    不要在 MVP 中过度设计许可或混淆。

    11. Training Strategy¶

    11.1 产品检测器¶

    初始目标：

    • 大约 300 至 800 张真实生产图像
    • 一个主要的 product 类
    • 包括轻微的位置变化
    • 包括正常的生产变化
    • 包括仅背景或空帧底片
    • 使用实际生产的相机和灯光

    11.2 元件检测器¶

    初始目标：

    • 每个组件类大约有 300 到 500 个标记实例
    • 使用产品 ROI 图像
    • 包括正常存在的情况
    • 故意制造缺少手册和缺少组件的案例
    • 在可行的情况下，从每个缺失组件场景大约 100 个图像开始

    不要假设这些数字保证了目标准确性。

    将它们描述为必须根据测量的验证性能进行调整的起点。

    11.3 数据分割¶

    避免相邻视频帧泄漏。

    通过以下方式分割数据集：

    • 产品批次
    • 捕获会话
    • 生产日期
    • 实物产品实例

    不要在训练集和验证集中随机分割几乎相同的相邻帧。

    11.4 摄像机角度¶

    初始模型应针对一个固定的生产角度进行优化。

    如果相机保持固定，第一条生产线不需要多角度数据。

    如果摄像机角度发生显着变化：

    • 测试当前模型
    • 从新角度收集数据
    • 微调现有模型
    • 重新验证整个系统

    接近 45 度的摄像机角度变化应被视为有意义的域变化。

    12. 人机交互策略¶

    谨慎推出。

    初始生产阶段：

    • AI执行自动检查
    • 所有 NG 结果均可供人工审核
    • 低可信度案件可能会被审查
    • 可以审核 OK 结果的样本
    • 存储更正
    • 错误分类的案例被添加到培训积压中

    后期减少人工审核必须基于生产证据，而不是固定的日历日期。

    曲目：

    • 人工审核率
    • 手动修正率
    • 假阳性率
    • 估计假阴性率
    • 每个产品的性能
    • 每个组件的性能
    • 按型号版本的性能
    • 按规则版本划分的性能

    13. MVP 范围¶

    13.1 两天静态图像 MVP¶

    第一个 MVP 仅处理静态图像。

    所需工作流程：

    Input folder
→ Read image
→ Detect product
→ Generate ROI
→ Detect components
→ Evaluate rules
→ Output OK or NG
→ Save JSON
→ Save annotated image
→ Save ROI

    第一天：

    • 初始化 Monorepo
    • 实现文件夹图像源
    • 装载产品检测器
    • 检测产品边界框
    • 实施ROI提取
    • 保存 ROI 图像
    • 保存初始 JSON 输出

    第二天：

    • 负载成分检测器
    • 检测所需的组件
    • 实施初始规则引擎
    • 做出 OK 或 NG 决定
    • 保存缺少组件的原因
    • 保存带注释的图像
    • 添加CLI命令
    • 添加最少的测试
    • 添加运行指令

    不包括在两天 MVP 中：

    • 相机SDK集成
    • 实时视频
    • 时间聚合
    • 中央服务器
    • 完整的边缘仪表板
    • 完整的管理仪表板
    • 认证
    • PLC集成
    • 制造执行系统集成
    • 自动再培训

    13.2 一个月目标¶

    第一周：

    • 时间聚合
    • 上传队列
    • 中央API
    • 初始中央数据库
    • 初始管理仪表板

    第 4 周：

    • Docker部署
    • 离线弹性

    17. 生成生成文件和未解决问题的最终摘要。

    生成轮廓后不要停止。

    生成每个所需文件的完整内容。
