    13 — 调试和可观察性¶

    本地开发和调试系统的实用指南：如何 启动它，运行状况/状态/日志表面告诉您什么，常见故障 签名及其原因，以及可用的开发工具。

    寻找错误的起点¶

    • CLI 路径 (assemblyvision inspect)：最快的重现。看看 每个图像的标准输出线 (path\tOK|NG\treasons\tinspection_id) 和 <output>/<inspection_id>/inspection.json 捆绑（完整记录并附原因） 代码、证据、版本）。配置错误退出 2 并显示消息 标准错误。
    • 服务器路径 (assemblyvision serve)：检查/health/live， /health/ready、/device/status、/inspection/state、/logs，然后 /inspections 用于持久记录。 WebSocket 运行时通道显示 实时转换（inspection.started/completed， device.status_changed、upload.changed)。
    • 前端：VITE_API_MODE=mock 使用确定性数据运行（无 后端）； VITE_API_MODE=http 与真实服务对话。浏览器开发工具 网络选项卡显示实际的 /api/v1 请求和 problem+json 尸体。

    健康和状态表面¶

    端点 意义 典型故障读数
    GET /api/v1/health/live 进程处于活动状态（未经身份验证） non-2xx → 进程关闭或关闭
    GET /api/v1/health/ready 决策关键部门允许检查 503 NOT_READY → pipeline未加载或存储无法保证持久化
    GET /api/v1/device/status 完整状态 参见下面的字段表
    GET /api/v1/inspection/state 窗口/暂停/故障状态 faulted: true、paused: true
    GET /api/v1/logs 有界日志环（500 个条目） 组件/级别/消息/跟踪

    调试时重要的 device/status 字段¶

    • inspection_ready / inspection_error_code — false 与 CONFIG_INVALID 等表示配置/规则/清单验证在加载时失败； 检查serve的stderr。
    • sync_ready — 如果没有配置或集中上传目标，则为 false 无法到达； 不阻止检查。
    • camera_connected, model_loaded — false → 检查相机源配置 和模型权重的存在。
    • storage_mode：NORMAL | WARNING | CRITICAL | STOP； storage_write_fault: true 锁存，直到 probe_persistence 成功（探测文件 + fsync + BEGIN IMMEDIATE 写）。
    • upload_circuit_state: CLOSED | OPEN | HALF_OPEN — OPEN 表示工作人员 达到连续失败阈值并且未尝试上传 （队列真相位于 /api/v1/uploads 中）。
    • alerts[]：稳定代币 - STORAGE_WRITE_FAULT、DISK_STOP、 DISK_CRITICAL、DISK_WARNING、STORAGE_INTEGRITY_FAULT、 CLEANUP_FAULT、UPLOAD_BLOCKED、UPLOAD_FAILING、UPLOAD_CIRCUIT_OPEN。
    • cleanup_*_count — 保留工作人员进度/错误。
    • integrity_scan_* — 启动完整性扫描结果。

    常见故障特征和原因¶

    签名 可能的原因 去哪里看
    inspect退出2“配置错误” 无效的配置/规则/清单（密钥未知、阈值超出范围、模型版本不匹配、规则/组件不匹配、与不同内容重用的规则标识）配置/规则 YAML，清单；标准错误消息
    inspect 退出 1 并出现每个图像错误 至少一张图像的图像读取/推理/ROI/输出失败 stderr 每个图像错误；捆绑目录
    verify 退出 1 DANGER: NG predicted as OK 保留集上的模型回归 — 阻止晋升 报告行；失败的图像+证据包
    verify DANGER: ... full expected set 未标记/失败/不匹配的样品 每图像行； --expected 文件
    /health/ready 503 NOT_READY 没有--config/--rule（管道未建）或存储无法保证持久性 服务参数； device/status 存储字段
    device/status inspection_ready: false、inspection_error_code: CONFIG_INVALID serve 加载期间配置/规则/清单验证失败 服务标准错误； configuration/effective
    401 UNAUTHENTICATED 在除 /health/live 之外的所有路线上缺少/错误的 Authorization: Bearer 标头或会话 令牌配置 (AV_EDGE_API_TOKEN / --api-token)
    429 RATE_LIMITED 每分钟每个 IP 失败的身份验证尝试次数 >5 次 等待Retry-After: 60；修复令牌
    404 DEV_TOOLS_DISABLED 于 /dev/* 开发工具未启用 使用 --enable-web-test 重新启动 serve
    410 MEDIA_PURGED 关于媒体内容 保留清除的神器（审核墓碑遗存） 保留策略+cleanup_*计数器；预期行为
    storage_write_fault: true 锁定 持久化/写入探测失败 (ENOSPC/EROFS/I-O) 文件系统状态；探测仅在成功时清除
    上传任务卡住 IN_PROGRESS 工人在租赁期间死亡；租约到期后回收陈旧任务 /api/v1/uploads；租赁设置
    UPLOAD_CIRCUIT_OPEN 连续可重试失败 (transport/408/429/5xx) 修复连接/凭据； open_seconds 之后半开探针

    重现管道问题¶

    • 无模型权重：占位符显示在 models/manifests/ 下 参考不存在的重量——任何使用它们的检查/发球都会失败 负载时（大小/SHA-256 不匹配）。运行 scripts/e2e-demo.sh 生成真实的 权重，或将清单指向真实的工件。
    • 无需训练的管道逻辑：使用 fake- detector 测试惯用语 — FakeProductDetector/RaisingComponentDetector/RaisingRuleEngine 在 apps/edge-service/tests/test_pipeline.py 驾驶真实 InspectionPipeline 带有存根检测结果。
    • 配置验证：config/examples/*.yaml + load_pipeline_config 单元测试是有效形状的参考；为每个新添加一个测试 验证门。
    • API/DB 问题：带有 tmp 输出根的 TestClient(create_app(ServerSettings(output_root=tmp, db_path=tmp/...))) 和 Bearer test-edge-token （参见tests/test_api_auth.py）。

    开发工具（网络测试工具，ADR-014）¶

    • 位于serve --enable-web-test后面；默认禁用 （404 DEV_TOOLS_DISABLED）。
    • POST /api/v1/dev/inspect-frame — 通过上传照片/图像 实例管道； persist=true 写入出现在中的证据包 历史；可选的 barcode 查询模拟键盘扫描仪输入。
    • POST /api/v1/dev/inspect-video — 每帧摘要（≤30 个采样帧， <100 MB），没有任何内容保留。
    • 仪表板/dev页面（管理）将工具与日志选项卡和 客户端产品-bbox 覆盖。切勿在生产主机上启用。

    结构化日志记录¶

    • 日志是由/api/v1/logs提供的JSON形式的记录（内存环， 容量 500) 与 logged_at、level、component、message、 trace_id。
    • 运行时使用的字段（根据设计 23）：event、device_id、 inspection_id、correlation_id、模型/规则版本、attempt、 error_code、retry_at。 X-Request-ID 通过 API 响应传播。
    • 切勿记录凭据、授权标头、原始图像字节或完整信息 条形码值（政策要求时屏蔽）；绝对文件系统路径 从查看器提供的日志消息中删除。
    • CLI 的本地日志格式：%(asctime)s %(levelname)s %(name)s: %(message)s (stderr)； -q/--quiet 抑制 INFO。

    隔离技巧¶

    • 存储/保留故障锁定并只能通过probe_persistence清除 — 通过删除写入权限、填充卷或损坏来重现 一捆；重新启动时验证故障锁存器。
    • 上传/保留测试使用 _AdvancingClock 和 _ScriptedSink 固定装置 (tests/test_upload_scheduler.py) 模拟时间和中心响应 确定性地。
    • 通过注入假 OpenCV/PyAV/，无需硬件即可测试帧源 通过 monkeypatch.setattr(backend, "_module", Fake) 收割机后端。
