    E3 Pipeline: Upload Resilience¶

    1. 目的¶

    使边缘上传路径在退化网络和长中心网络下具有弹性 在不削弱边缘优先、故障安全检查合同的情况下实现停电。 E3 添加带宽限制、断路器、受控手动重试、长 停电排水测试，以及可恢复的大媒体客户合同 PR #17（设计 13，ADR-005）提供耐用的发件箱和调度程序。

    本地检查绝不能依赖于上传健康状况：节流和电路 开放状态保留队列并停止新流量，但绝不阻塞持久性 检测持久性，同时受保护的存储仍然可用。

    2. 范围和非目标¶

    范围内¶

    • 根据配置的上限对上传流量进行带宽限制。
    • 在断电期间和定期暂停尝试的断路器 探针恢复，可观察电路状态。
    • 受控的手动重试端点，仅重置符合条件的任务和 保留尝试历史记录。
    • 长时间断电排水测试证明无重复、有序恢复。
    • 可恢复的大媒体客户端合约（边缘端和协议合约 仅；中心端点未实现）。

    超出范围¶

    • 中央摄取 API、PostgreSQL 模型、对象存储和手册 审查（中央工作在E1-E6和合同冻结后开始）。
    • 超越单个 POST 信封的多路径/并行媒体上传。
    • 预签名的 S3 兼容分段上传实现（延迟决策） 设计13.11直到文件大小测量）。
    • 静态加密、备份和安全删除义务（站点 决策、E2 生产支持）。

    3. Safety Invariants¶

    在每个 E3 变更和测试中，以下不变量是强制性的：

    1. 节流和电路开路状态绝不能丢弃、延迟提交或 重新排序持久任务状态；任务仍保持 PENDING/RETRY_WAIT 不变 尝试和退避完好无损。
    2. 电路打开必须停止新的网络尝试（无热循环），同时 检查持续不断；队列必须完全排空并且 恢复后无重复。
    3. 手动重试仅重置符合条件的任务（RETRY_WAIT 或 PERMANENT_FAILURE)，递增attempt_count，并且从不触及 SUCCEEDED、IN_PROGRESS（在其他地方租用）或CANCELLED任务。
    4. 手动重试必须保留已验证的接收门：重试媒体 在经过验证的中央收据之前，任务绝不会重新授权删除。
    5. 仅当服务器确认预期时才接受大媒体完成 大小和校验和并将对象与检查绑定；分块/可恢复 每个任务的流必须保持幂等性。 6.上传健康可观察性必须区分队列真实性（持久性）和 工作线程活跃度和电路状态（进程本地）以及电路开路状态 不得报告为健康。

    4. 生产启用前所需的决策¶

    E3 可能会使用保守的默认值来实现，但这些输入是发布的 用于在客户站点启用激进上传行为的拦截器：

    • 上传流量的带宽上限和调度窗口。
    • 电路故障阈值和开路持续时间与预期停电一致 模式。
    • 哪些媒体类型足够大，需要可恢复传输。
    • 中央摄取合同和媒体绑定保证（部署中央 终点；测试水槽不是生产授权）。

    5. 交付管道¶

    每个门都可以独立审查。

    E3a: Bandwidth Throttling¶

    实施

    • 在UploadScheduler驱动中实现有界速率限制器（令牌桶） 由现有的 UploadSettings.maximum_bandwidth_mbps 占位符；一个 None上限意味着没有节流。
    • 仅将限制器应用于网络负载字节（媒体和元数据），从不 本地持久化；限制器在睡眠时不得持有任务租约 长于租约期限而无需续约。
    • 通过调度程序健康状况公开发送的累积字节数和当前上限/ 设备状态，以便操作员可以确认上限是否已强制执行。

    退出标准

    • 参数化测试证明，在配置上限的情况下，总上传量 已知有效负载字节的时间至少是理论上的最小值，并且 如果没有上限，就不会引入人为延迟。
    • 节流下的长媒体上传不会缺乏检查：调度程序 停止发送，同时本地检查持久性继续提交。

    E3b：断路器¶

    实施

    • 添加类型化电路设置（failure_threshold、open_seconds） UploadSettings；默认关闭。
    • 跟踪连续失败（传输错误和可重试的 HTTP 状态）。 当达到阈值时，电路打开：调度程序停止 要求/尝试任务。 open_seconds后，它半开并允许 尝试探测；成功关闭电路，失败重新打开电路。
    • 通过调度程序健康状况公开电路状态和最后状态更改 具有稳定UPLOAD_CIRCUIT_OPEN警报的设备状态；电路状态为 进程本地活跃度，而不是队列真相。

    退出标准

    • 故障注入测试证明：阈值故障会开路并产生 进一步尝试为零；半开探针成功将其关闭并恢复排水； 半开探针故障重新打开它；开路不会改变任务 状态和恢复消除了积压的重复。

    E3c：受控手动重试¶

    实施

    • 添加POST /api/v1/uploads/{upload_task_id}/retry（查看者验证） 包装存储库重试转换：仅 RETRY_WAIT / PERMANENT_FAILURE任务通过attempt_count + 1重置为PENDING； 未知任务返回 404，不符合条件的任务返回 409 状态。
    • 使端点远离自动重试循环：调度程序从不使用它。
    • 为新端点重新生成 OpenAPI/TypeScript 工件。

    退出标准

    • API 测试证明：重试符合条件的任务会将其重置为 PENDING 并 增加尝试次数；重试 SUCCEEDED/IN_PROGRESS/CANCELLED/unknown 返回 409/404，无突变；重试的任务会幂等地重新排出； 重试后，收据门控保留资格不会改变。

    E3d：长时间断电排水测试¶

    实施

    • 添加运行长时间离线的故障注入测试（sink 失败），继续检查持久性，重新启动边缘，恢复 连接性，并验证完全无重复的排水与订购 元数据先于媒体语义。

    退出标准

    • 测试证明，无需重新启动即可完成数千个排队任务 重复，不会过早保留删除，并进行检查 每条记录的同步达到SYNCED。

    E3e: Resumable Large-Media Client Contract¶

    实施

    • 记录可恢复的大媒体合同（设计13.3/13.11）：稳定 任务身份、块幂等性、大小/校验和完成确认、 以及对象到检查的绑定；定义边缘侧边界和 无需实现中央端点的中央协议合约。

    退出标准

    • 合同被记录并审查；边缘侧定义了 media_chunk_bytes 占位符并明确说明传输仅开始 中央合同冻结后。

    6. 强制测试矩阵¶

    面积 所需案例
    节流 上限时间限制；无上限无延迟；长媒体不能缺少检查
    电路 门槛打开；打开时零尝试；半开成功/失败； open 不会改变任务；无重复恢复
    手动重试 合格重置+尝试增量； 404 未知； 409 不符合资格；幂等重排；保留门不变
    长时间停电 长时间离线+检查持续；重新启动；恢复;完全无重复引流；在媒体之前订购元数据
    可观察性 队列真相 vs 工作线程活跃度 vs 电路状态；稳定的警报代码； OpenAPI/TS 合约更新

    7. 合并和释放门¶

    • 通过类型化接口进行重点更改，并且没有非结构化字典 公共边界。
    • 对每个更改的安全不变量进行回归测试。
    • 公共架构更改时的当前 OpenAPI/TypeScript 工件。
    • 通过强制性质量命令：ruff check/format、mypy、pytest、 mkdocs build --strict、pnpm -r build/lint/test、边缘网络 e2e。
    • 审查节流/电路/手动重试不能丢失或 重复的任务，并且在没有经过验证的收据的情况下无法重新授权删除。
