    C1 中央服务器 M1：试点摄取、历史记录和回顾¶

    1. 目的¶

    为 AssemblyVision 提供第一个中央服务器路径，而不会削弱 边缘优先架构。中央服务器是管理和证据平面： 它接收延迟的边缘上传，存储选定的证据，提供 跨设备历史记录和人工审核，并且在不更改的情况下仍然不可用 或在边缘阻止任何生产检验决策。

    该任务实现了设计 05 定义的中央一个月/M1 边界：

    • 设备范围的幂等检查和媒体摄取；
    • PostgreSQL检查历史和选定的证据元数据；
    • 通过 MinIO 兼容 S3 的对象存储；
    • 试点设备上传身份验证和单一管理员路径；
    • 概述、历史和审查的最小中央管理视图；
    • Docker Compose 部署和有针对性的弹性证据。

    该工作必须使 E6-A16（针对经过验证的重复上传幂等性） 中央收据）可执行。未完成E6现场验收， 仍然需要真实的硬件、看不见的客户数据和客户见证。

    2. 范围和非目标¶

    范围内¶

    • uv 工作区中的新 apps/central-service FastAPI 应用程序。
    • pnpm 工作区中的新 apps/admin-web Vue 3 + TypeScript 应用程序。
    • PostgreSQL 迁移和租户范围的中央持久性模型。
    • 中央 Compose 部署中的 MinIO，通过类型化存储进行访问 具有不透明、租户范围的对象键的抽象。
    • 当前边缘兼容的单信封上传端点： POST /api/v1/inspection-uploads。
    • 严格验证的收据、幂等重放、有效负载冲突检测以及 媒体到检查的绑定。
    • 集中检查历史记录、详细信息和授权媒体元数据查询。
    • Pilot 身份验证：单独的每台设备上传凭据加上一个 管理 UI 的管理员会话/令牌路径。
    • 仅附加中央人工审核队列和审核提交。
    • 初始中心产品/规则/模型元数据注册和不可变 需要发布版本来验证引用的引用。包裹递送 边缘仍然是手动的。
    • 类型化 OpenAPI 输出和生成/同步的 TypeScript 中央 API 类型。
    • 编写健康检查、受控模式迁移、集中备份/恢复 存储库质量门所需的文档和测试。

    超出范围¶

    • 边缘检查管道中的任何同步中心依赖性。
    • OIDC PKCE、外部身份提供商集成、完整的生产 RBAC、 设备 mTLS/PKI、凭证轮换或多组织自助服务。
    • 远程配置/模型包分发、分阶段部署、激活、 回滚或确认流程（CENTRAL-007 生产范围）。
    • 报告/导出、异步报告工作人员、通用管理、 高级分析、仓库/BI 集成或 Redis。
    • WS /api/v1/ws/organization； M1 使用有界 REST 刷新/轮询。
    • 预签名上传、分段上传或可恢复/分块媒体传输。 边缘 media_chunk_bytes 设置是一个休眠占位符，直到 边缘到中心的可恢复协议被明确冻结并在 双方。
    • 边缘本地review_records的集中摄取。 M1中央评论是 新创建的中央仅附加记录，用于集中摄取检查； 边缘本地审查同步需要单独的受管理合同。
    • 集中保留自动化、生命周期删除、数据驻留策略以及 生产备份/灾难恢复目标。 M1保留足够的元数据和对象 这些后续控件的生命周期状态。

    3. 锁定 M1 决策¶

    决定 M1选择 生产跟进
    供货范围 设计 05 起的一个月试点边界 全面管理、分析、治理和车队部署
    存储库布局 此 monorepo 中的 apps/central-service、apps/admin-web 和 packages/typescript/api-client-central 保持相同的有界模块接口
    数据存储 PostgreSQL 仅在测量体积后才需要分区/物化视图
    对象存储 MinIO，使用第一个版本中的 S3 兼容抽象 客户选择的 S3 兼容服务/生命周期策略
    设备认证 每设备试点上传令牌，绑定到已注册设备 mTLS 或短期设备凭证、轮换、隔离/重新注册
    人工认证 一个试点管理员会话/令牌路径 OIDC 授权码 + PKCE 和完整组织范围的 RBAC
    管理界面 概述、历史/详细信息、评论 车队/配置/模型/报告/用户/审核屏幕
    实时更新 REST 刷新和有界轮询 尽力而为的组织 WebSocket 与 REST 重新同步
    媒体传输 现有的小单POST信封，由central写入MinIO 仅在交付合同和边缘支持后才进行预签名/恢复流程

    4. 强制性安全性和兼容性不变量¶

    此任务中的每个实现和测试都必须保留这些不变量。

    1. 绝对不能出现中央不可用、拒绝、响应缓慢或维护的情况 阻止、延迟提交或更改边缘检查决策。边缘耐用 发件箱对于待上传的内容仍然具有权威性。
    2. 中心服务器必须保存原始边缘检测记录作为 不变的事实。中央审查记录是仅附加的链接事实，并且 永远不会覆盖原始的人工智能/内部/业务决策、时间戳、 模型校验和、规则版本或源媒体身份。
    3. 当前的边缘上传线合约是M1兼容性边界。 在请求任何边缘上传之前，M1 必须接受现有的 JSON 信封 实施变更。
    4. 相关元数据获取完毕后才返回成功回执 持久地致力于。仅在写入字节后才返回媒体收据， 尺寸/校验和经过验证，并绑定到耐用的中央检查 对象标识符。
    5. (device_id, idempotency_key)、(device_id, inspection_id) 和 (device_id, device_sequence) 唯一性有效保护-一次 坚持。相同重播返回原始收据；重复使用的密钥或 具有不同规范请求哈希的源身份返回 409 和 保留原件。
    6. 所有租户拥有的数据库行都带有organization_id；每个查询范围 尽管 M1 有一名管理员和一名试点租户，但它是在服务器端进行的。
    7. 对象密钥由中央服务器生成。服务器绝不能 公开存储凭据或接受客户端控制的文件系统路径。
    8. PostgreSQL 不得声明媒体AVAILABLE，直到最终的 MinIO 对象被创建。 存在并经过校验和验证。部分/孤立对象处理是明确的 通过 PENDING、AVAILABLE、FAILED 以及后来的协调。
    9. 试点设备凭证与人类凭证不同，从未记录， 并且仅在显式环回开发之外通过 HTTPS 接受。
    10. 请求验证是类型化和有界的。未知字段被拒绝 突变边界；错误使用 RFC 7807 application/problem+json 和 切勿公开凭据、对象密钥、内部路径、SQL 或堆栈跟踪。
    11. M1 不得静默激活边缘配置。想要的任务 不是激活确认。
    12. 仪表板指标不得将经过审核的标签呈现为原始人工智能预测或 表示没有测量样本覆盖率的准确率/召回率值。

    5. 首先实施现有的边缘合约¶

    5.1 端点和认证¶

    现有边缘 HttpUploadSink 发布到：

    POST {AV_EDGE_UPLOAD_BASE_URL}/inspection-uploads

    配置的边缘基础URL包含/api/v1；因此M1提供：

    POST /api/v1/inspection-uploads

    请求中携带Authorization: Bearer <device-upload-token>， Content-Type: application/json。中央服务将令牌解析为 恰好有一个已注册的活动设备，并拒绝来自的不匹配的 device_id 解码后的检查有效负载。

    5.2 M1 接受的信封¶

    M1 接受 INSPECTION 和 INSPECTION 的边缘当前有界 JSON 信封 MEDIA任务：

    {
  "idempotency_key": "inspection:{device_id}:{inspection_id}",
  "kind": "INSPECTION",
  "object_id": "edge-object-uuid",
  "inspection_id": "edge-inspection-uuid-or-null",
  "checksum_sha256": "sha256-or-null",
  "size_bytes": 123,
  "payload_b64": "base64-payload"
}

    对于 INSPECTION，payload_b64 解码为版本化边缘 InspectionRecord。对于MEDIA，它解码为原始选择的媒体字节； 检查上传必须已经有经过验证的收据，因为边缘 调度程序强制执行元数据优先于媒体排序。

    中央边界适配器必须将此电线包络转换为类型化的中央边界 命令。核心域和存储库接口必须使用类型化模型，而不是 非结构化词典。

    5.3 所需收据¶

    响应正文最多 64 KiB，并且必须包括：

    {
  "idempotency_key": "same value as request",
  "object_id": "same value as request",
  "kind": "INSPECTION or MEDIA",
  "checksum_sha256": "same value as request",
  "size_bytes": 123,
  "central_object_id": "required and non-empty for MEDIA"
}

    边缘在接受 2xx 结果之前验证每个回显字段。媒体 没有 central_object_id 的收据是永久性的 INVALID_RECEIPT 失败 位于边缘，绝不能由中央发出。

    5.4 状态语义¶

    状况 中央回应 边缘处理
    新的有效检查/介质持续存在 201 + 验证收据 成功
    相同的设备/密钥/哈希重播 200 或 201 + 原始收据 成功，无重复
    相同的设备/密钥或源身份，不同的哈希 409 PAYLOAD_CONFLICT 永久性故障；当地证据仍然存在
    引用的检查/版本/设备无效 409 或输入 422 问题 永久性故障
    临时数据库/对象存储/维护故障 503 + 可选数字 Retry-After 可重试
    速率限制/超时 429 / 408 + 可选 Retry-After 可重试
    认证/授权失败 401 / 403 永久存在，直至操作员/配置干预
    格式错误、过大或无效的证据 400 / 413 / 422 问题 永久性故障

    中央实现必须针对边缘兼容测试这些语义 请求装置和收据验证逻辑。它不得返回 202 检查，除非响应明确包含安全的收据状态 供边缘使用；正常的 M1 摄取在成功之前提交。

    5.5 有意的M1转移边界¶

    M1不实现media-uploads:initiate、complete、直接浏览器 上传、预签名上传或媒体分块。当前部署的边缘发送 单个 Base64 信封并且不消耗这些路径。过早暴露 未使用的替代方案会产生两个不兼容的事实来源。

    M1被接受后，单独的合同/ADR可能会引入断点续传： 稳定的上传任务身份、从零开始的块幂等性、总 SHA-256 和 尺寸确认以及物体到检查的装订。只有这样，边缘才可能 使用其保留的 media_chunk_bytes 设置。

    6. 目标架构和代码组织¶

    apps/
  central-service/                 # FastAPI API, repositories, migrations, storage
  admin-web/                       # Vue 3 central administration application
packages/
  python/
    domain/                        # Existing canonical edge/central inspection models
  typescript/
    api-client-central/            # Generated/synchronized central OpenAPI client
    ui/                            # Existing shared display primitives where appropriate

    central-service 一开始是一个带有显式域模块的可部署组件：

    central_service/
  api/             # routers, auth dependencies, problem responses, OpenAPI
  ingest/          # envelope adapter, canonical hash, receipt service
  persistence/     # SQLAlchemy Core schema, Alembic, repositories
  storage/         # MinIO/S3 interface, staging/finalization, integrity checks
  review/          # queue policy and append-only review service
  query/           # history/detail/dashboard projections
  auth/            # pilot administrator/device upload credentials
  observability/   # structured logs, metrics, health/readiness

    不添加worker、Redis、包分发服务、微服务拆分 无需测量 M1 需要。长时间运行的作业超出了此任务的范围。

    7. 交付管道¶

    每个阶段都可以独立审查，通常应作为一个阶段交付 或更集中的 PR 到 main。

    C1a：工作空间、服务和组合基础¶

    实施

    • 使用 Python 3.12 将 apps/central-service 添加到 [tool.uv.workspace].members 兼容 FastAPI、SQLAlchemy Core、Alembic、PostgreSQL 驱动程序和类型 MinIO/S3 客户端依赖项。
    • 使用 Vue 3、TypeScript、Pinia 将 apps/admin-web 添加到 pnpm 工作区， Element Plus、ECharts、Vitest 和 Playwright 约定符合 apps/edge-web。
    • 添加packages/typescript/api-client-central和中央OpenAPI生成/ 漂移检查，反映了边缘 API 合约规则。
    • 添加中央 Compose 服务：PostgreSQL、MinIO、central-service，并构建 admin-web；使用命名持久卷、非根映像、运行状况检查、 显式环境/秘密文件，并且没有隐式迁移竞争。
    • 添加/health/live和/health/ready。当需要模式时，准备失败， PostgreSQL、MinIO 存储桶访问或 Pilot 凭证配置无效。

    退出标准

    • Compose 从干净的卷集中调出所有四个服务。
    • API 迁移命令是受控发布步骤，不由 每个 API 副本同时进行。
    • 生成、提交 OpenAPI 并检查偏差。
    • 边缘运行时代码不导入中央依赖项。

    C1b：租户、设备和 Pilot 身份验证基础¶

    实施

    • 为organizations、sites、production_lines创建迁移， devices，试点管理员身份/会话记录，设备上传令牌 哈希值和最低 audit_logs 支持。
    • 种子或引导恰好一个试点组织、地点、线路、注册 设备、上传凭证和管理员通过显式迁移， 管理命令，或撰写引导流程。没有隐式默认设备 根据上传请求创建。
    • 为摄取路由和试点实施设备上传身份验证 管理 UI 的管理员令牌/会话路径。设备与人 凭证是独立的，不能授权彼此的路由。
    • 实施GET /api/v1/auth/me、GET /api/v1/sites、GET /api/v1/lines、 和最小的 GET /api/v1/devices / GET /api/v1/devices/{id}。

    退出标准

    • 未知、禁用或组织不匹配的设备令牌无法关闭。
    • 设备凭证无法查询人工管理端点。
    • 管理员凭据无法模拟设备上传。
    • 每个租户拥有的查询在存储库测试中都是组织范围的。

    C2a：检查摄取和验证收据¶

    实施

    • 添加 upload_receipts、inspections 和 inspection_components 迁移。 保留边缘inspection_id、设备序列、捕获/完成时间、 原始决策、产品解决方案、原因代码、模型/规则/配置 版本和校验和、推理元数据以及中央接收时间。
    • 实现严格类型化的信封解析器 POST /api/v1/inspection-uploads，包括有界Base64解码， 规范请求散列、模式版本验证、有效负载大小限制、 设备身份匹配和不可变版本/引用检查。

    退出标准

    • 重放相同的字节会返回相同的收据，并且只留下一个 检查行。
    • 重用幂等密钥、检查 ID 或设备序列 不同的规范哈希返回 409 PAYLOAD_CONFLICT 并保留数据。

    C2b：MinIO 媒体摄取和绑定¶

    • 发生故障时，仅在安全的情况下保留 PENDING 或 FAILED 生命周期记录 为了和解；在最终对象存在之前永远不要报告 AVAILABLE。
    • 仅在对象绑定并验证后返回central_object_id。
    • 为暂存/孤立对象添加幂等完整性/协调命令 和行。这是M1维护命令，而不是连续工作人员。

    退出标准

    • 大小/校验和不匹配会返回永久性的类型问题并且不会产生任何问题 AVAILABLE 媒体行。

    • 仅在所有必需的媒体之后，端到端边缘发件箱测试才能达到 SYNCED 收据已核实； E6-A16重复上传受理案例执行 针对中央而不是目录接收器。

    • 添加了中央运行手册：摄取积压 (C1)、对象存储故障 (C2)、 凭证泄露 (C3)、备份/恢复 (C4) 和试点升级/回滚 (C5)，全部在 docs/runbooks/README.md 和 mkdocs nav 中索引 （uv run mkdocs build --strict 通过）。
    • M1 仍然被标记为受控飞行员：没有声称生产 HA，最终 RPO/RTO、完全保留实施、OIDC 或远程部署（第 13 节 退出标准 8)。

    8. M1数据库和对象存储规则¶

    8.1 所需的 M1 表¶

    域名 桌子 M1用途
    租户/设备 organizations、sites、production_lines、devices、飞行员证书/会话记录 确定每个请求的范围并验证边缘上传
    食入 inspections、inspection_components、inspection_media、upload_receipts 不可变的边缘事实、证据和幂等性
    审查/审计 review_records、audit_logs 仅附加审查和问责制
    初始治理 products、product_components、product_versions、rules、rule_versions、model_packages、model_versions、所需分配 验证/固定元数据；仅手动安装包

    行必须使用时区感知的 UTC 时间戳。检查记录同时保存 边缘观察/捕获时间戳和中央接收时间戳。 JSON 只是 用于有界的不可变快照、证据详细信息或之前/之后的审计 数据；它不能替代可过滤列和唯一性 上面的限制。

    8.2 所需的索引和唯一性¶

    • UNIQUE(device_id, idempotency_key) 于 upload_receipts。
    • UNIQUE(device_id, inspection_id)和UNIQUE(device_id, device_sequence)。
    • UNIQUE(device_id, source_media_id) 用于边缘起源的媒体身份。
    • (organization_id, completed_at DESC, id DESC) 和 (device_id, completed_at DESC, id DESC) 用于键集历史分页。
    • 部分条形码索引 (organization_id, barcode, completed_at DESC) 其中 条形码非空；条形码从来都不是全球唯一的。
    • 产品/结果、模型/规则版本、待审核等的查询索引 仅在测试/查询计划确定需要后才进行有界原因代码过滤。

    8.3 对象键和生命周期规则¶

    • 生成不透明的密钥，例如 org/{organization_id}/device/{device_id}/{year}/{month}/{media_id}。
    • 在 PostgreSQL 中不存储媒体字节，也不存储边缘提供的路径作为存储键。
    • 暂存、验证、最终确定，然后标记AVAILABLE；保留明确的 PENDING / FAILED 表示工作中断。
    • M1 不会自动删除中央媒体。它记录生命周期和 保留未来受治理清理所需的元数据。
    • 媒体 URL 是经过授权的且短暂的。浏览器/管理员用户永远不会收到 MinIO 根凭据或存储桶范围的权限。

    9. API、类型和错误合约规则¶

    • 中央公共请求/响应模式是 Pydantic 模型类型，并且具有 extra="forbid" 用于突变体。
    • FastAPI OpenAPI 已提交并进行了偏差检查。 api-client-central是 由其生成或同步； admin-web 不得手投服务器 JSON。
    • 所有错误都使用有界的 application/problem+json type、title、status、detail、code、request_id 和字段错误。
    • 光标分页使用 {items, next_cursor} 默认 50/最大 200 和 拒绝游标/过滤器不匹配。
    • 变异的人类/管理员 API 在并发情况下使用 If-Match 修订检查 编辑很重要。可重试的设备摄取使用幂等性密钥来代替。
    • 所有不可变的边缘标识符和原始决策都是在之后写入一次 接受摄入。
    • 新的中心字段是在模式版本中添加的。删除/更改 字段含义需要新的 API/架构版本和协调迁移。

    13. M1退出标准¶

    仅当满足以下所有条件时，M1 才适合受控飞行员：

    1. 已注册的边缘设备发送当前检查和选定的介质 通过 HTTPS 的信封；中央退货验证兼容收据。 2、相同重播不重复，返回之前回执； 有效负载冲突无法通过 409 关闭，并且不会覆盖证据。
    2. 真正的边缘调度器仅在之后到达 QUEUED → PARTIAL → SYNCED 需要中央收据，使 E6-A16 可以针对中央执行。
    3. 中央 PostgreSQL 历史和 MinIO 证据绑定仍然受控 重新启动和代表性备份/恢复。
    4. Pilot 管理员 UI 支持概览、跨设备历史记录/详细信息以及 在执行组织范围时仅进行附加审查。
    5. 原始边缘决策和证据来源通过以下方式保持不变： 摄取和审查。
    6. 编写健康/就绪、迁移、请求/错误、身份验证和 记录恢复证据；所有强制性质量关卡均已通过。
    7. 文件明确将 M1 标记为受控飞行员，但未声明 生产 HA、最终数据驻留合规性、完整 RBAC、远程 推出、可恢复媒体上传或通用准确性。
