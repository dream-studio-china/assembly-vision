    PR-015 评论：每个组件的时间聚合和产品窗口¶

    Scope¶

    针对 main 对 feat/temporal-aggregation 进行代码审查（PR #15）。的 审查涵盖 ADR-010 产品窗口和每个组件的聚合 实现、其边缘运行时集成、配置、生成的 API 合同、文档和重点测试。

    审查的相关要求：

    • docs/design/10-temporal-aggregation.md
    • docs/design/decisions/ADR-010-per-component-temporal-aggregation.md
    • docs/contracts/03-ai-rule-and-safety-contracts.md
    • docs/contracts/06-testing-quality-and-ci-contracts.md

    合并决策¶

    在 F1-F7 解决之前不要合并。

    PR 引入了帧观测的正确高级分离， 时间聚合和规则评估。然而，目前仅限时间 窗口实施可以合并来自不同物理产品的证据， 返回OK。它也无法完成空闲窗口，而是使用处理时间 比采集时间，接受不可用的帧作为证据，并允许 未配置或资格不足的证据无法满足规则。这些是 产品决定安全缺陷，而非化妆品后续工作。

    解决状态¶

    本次审查 (F1-F7) 中的所有发现均已在 feat/temporal-aggregation 通过集中提交，每个提交都进行回归测试 在修复之前失败并在修复之后通过：

    • F1 - window_strategy: identity 将每个产品窗口密封为一个 CapturedFrame 上携带的经过验证的每帧产品标识；失踪的 身份、中间窗口身份转换或已确认的多产品 框架关闭窗口作为完整性违规 (PRODUCT_IDENTITY_MISSING / PRODUCT_IDENTITY_TRANSITION / MULTIPLE_PRODUCTS）永远无法释放OK。仅限时间的策略是 明确的发展后备。集成测试证明是互补的 来自一个区间内的两个身份的组件永远不会产生 OK，a 相同身份完整窗口仍然准确地生成一个OK，并且缺少一个 身份中间窗口中止为 NG。经探测器确认 MULTIPLE_PRODUCTS 结果被传播到这条完整性路径而不是 保留作为仅诊断框架原因。
    • F2 - ProductWindowManager.expire() 将空闲窗口最终确定为 GAP； 检查循环在每个空捕获轮询时调用它。最终产品 正常判定不再有帧，正常到期后关闭 不添加第二条记录。
    • F3 - 运行时为窗口提供 CapturedFrame.monotonic_ts_ns （获取时间）而不是推理后time.monotonic()；陈旧的 无序时间戳将被丢弃并计数。空闲期满保留 捕获时间截止，防止排队的到期前帧重新打开 最终产品窗口。因此，快速推理与延迟推理不能改变 窗口会员资格。
    • F4 - frame_observations() 源自 quality_usable 产品检测质量门并保留其原因代码；无法使用的 帧没有贡献任何检测，没有有效机会，也没有计数 证据。
    • F5 - 每帧拒绝原因是帧诊断 仅FrameQualitySummary；规则引擎根据汇总的证据做出决定， 并且只有窗口完整性违规（中断、身份混合、丢失 身份，规则评估失败）独立强制NG。
    • F6 - 启用的临时配置必须提供一个策略 对于每个规则所需的组件（在规则加载后验证 实例管道构建）并拒绝不需要的组件的策略；一个 缺失的策略防御性地解析为 UNVERIFIABLE COMPONENT_POLICY_MISSING； medium_confidence < high_confidence 是严格的 在数据类和 YAML 解析器中。
    • F7 - detection_count，框区域和中心摘要仅包括 等于或高于策略 medium_confidence 计数证据的检测 阈值；低置信度框无法夸大精确的 expected_count。

    后续 TODO¶

    阻塞结果¶

    F1。仅时间分组可以合并不同的产品并返回OK¶

    严重性： P0 / 严重

    地点：

    • apps/edge-service/src/assemblyvision_edge/temporal/window_manager.py:117-139
    • apps/edge-service/src/assemblyvision_edge/api/state.py:250-255

    ProductWindowManager.feed() 接受到达的每个非重复帧 在 maximum_window_ms 内。无产品标识、触发边界、条形码、 进入/退出事件、经过验证的跟踪器连续性或多产品检查 分离其证据。因此第一个产品只提供 component_a 和仅提供 component_b 的第二种产品以及 manual可以形成一个全PRESENT窗口并被评估为OK。

    这违反了设计 10 中的物理产品证据隔离不变量 第 10.2 和 10.3 节，混合窗口排除要求 10.8、ADR-010 第 3 节和合同 06 第 5 节要求的混合产品 测试。

    分辨率：

    1. 将经过验证的相关性/边界机制作为明确的要求 启用时间检查：例如，硬件触发、条形码事件、 经过验证的跟踪器身份，或经过站点验证的进入/退出区域协议。
    2. 携带相关身份和捕获时间来源 FrameObservation 并强制 ProductWindowManager 中的连续性。
    3. 如果无法证明连续性，请使用耐用的按钮关闭/中止窗口 窗口完整性原因并产生 NG/UNVERIFIABLE；从不聚合其 对另一种产品的观察。
    4. 不要将简单的时间间隔作为生产安全的产品边界 除非证明没有重叠的站点验证约束被编码并且 强制执行。

    验收标准：

    • 集成测试从两个方面进行互补的所需组件检测 一个持续时间/间隙间隔内的不同产品标识并进行验证 这两种产品都不产生OK。
    • 身份转换、边界信号缺失和已确认的多产品 将每个结果框入具有稳定原因的中止或未经验证的 NG 记录中 代码。
    • 具有所有必需组件证据的相同身份窗口仍然可以产生 恰好有一个 OK 记录。
    • 合同要求的混合产品测试保留在正常测试套件中。

    F2。最终空闲窗口通常不会最终确定¶

    严重性： P1/高

    地点：

    • apps/edge-service/src/assemblyvision_edge/api/state.py:246-255
    • apps/edge-service/src/assemblyvision_edge/temporal/window_manager.py:117-139

    当较晚的帧到达时，间隙过期仅由 feed() 检查。当 next_frame()超时，运行时立即继续。一款产品位于 因此，流的末尾保持打开状态，直到进程关闭，此时 force_close()丢弃收集到的证据并发出中断的NG。 这导致设计 10 第 10.8 节的超时关闭行为失败，否则会失败 完整的决定。

    分辨率：

    1.添加不中断的expire(now_monotonic)操作 ProductWindowManager；它应该将活动窗口关闭为 GAP 一旦 空闲时间达到配置的限制。 2. 在每个空的 next_frame() 轮询中调用 expire(time.monotonic()) 并发送 通过 inspect_window() 返回的窗口。 3. 保留force_close()专用于关机/重启中断。

    验收标准：

    • 一个完整的窗口，后面没有 maximum_window_ms 的框架，仍然存在 没有收到触发帧的正常决策。
    • 正常到期后关闭不会产生第二次中断 记录。
    • 在到期之前关闭会创建一条 NG 记录，其中包含 INSPECTION_INTERRUPTED并且没有重建部分证据。

    F3。窗口成员资格由推理后时间决定，而不是捕获时间¶

    严重性： P1/高

    地点：

    • apps/edge-service/src/assemblyvision_edge/api/state.py:251-252
    • packages/python/vision-core/src/assemblyvision_vision/sources/frame_source.py:33-38

    运行时在 frame_observations() 完成后提供 time.monotonic()。 推理延迟、队列积压或调度程序延迟可能会因此而分裂 连续捕获的帧或合并单独捕获的产品。每个 CapturedFrame 已包含其获取单调时间戳 monotonic_ts_ns，但窗口管理器不使用它。

    分辨率：

    1. 将CapturedFrame.monotonic_ts_ns转换为秒并传递给 ProductWindowManager.feed() 用于所有成员资格和持续时间比较。
    2. 仅将运行时单调时钟用于空闲到期轮询。
    3. 明确拒绝陈旧/无序的捕获时间戳，因为它们不可用 证据或窗口完整性故障；不要默默地重新排序它们。

    验收标准：

    • 给定相同的捕获时间戳、快速检测器和有意的 延迟检测器产生相同的窗口成员资格和最终决策。
    • 来自不同捕获时间窗口的排队帧不能仅仅因为合并 摊位后它们很快就会被排干。
    • 无序时间戳记录了NG/丢弃行为和回归 覆盖范围。

    F4。时间路径将每个检测到的产品框架标记为质量可用¶

    严重性： P1/高

    地点：

    • apps/edge-service/src/assemblyvision_edge/pipeline.py:254-272
    • apps/edge-service/src/assemblyvision_edge/temporal/window_manager.py:65-70

    frame_observations() 无条件设置 quality_usable=True，尽管 available ProductDetection.quality.usable 携带实际的质量门 结果。具有高置信度组件的模糊或无法使用的框架 检测可以计入minimum_valid_frames并建立PRESENT。 这违反了合同 03 第 5 节和设计 10 第 10.3 节和 10.6 节。

    分辨率：

    1. 从评估的帧质量门设置FrameObservation.quality_usable （outcome.product_detection.quality.usable 当检测到产品时）。
    2. 在观察中保留帧质量拒绝原因代码 FrameQualitySummary。
    3. 确保不可用的框架无法提供检测、有效机会、 或将证据计数到时间聚合器。

    验收标准：

    • 具有高置信度组件框的 quality.usable=False 框架不会 建立PRESENT并且不增加usable_frame_count。
    • 剩余可用帧低于minimum_valid_frames的窗口 将每个必需的组件解析为 UNVERIFIABLE 并生成 NG。
    • 持续的帧质量摘要对被拒绝的帧进行计数并包括 其质量原因代码。

    F5。尽管有足够的有效时间证据，任何被拒绝的帧都会强制 NG¶

    严重性： P1/高

    地点：

    • apps/edge-service/src/assemblyvision_edge/pipeline.py:289-328

    所有每帧失败原因都复制到 window_reasons 中，并合并到 最终决定原因，并且final_reasons无条件改变 否则成功的规则决策将发送给内部NG。因此，一个窗口 需要有效的高置信度证据加上一个瞬态NO_PRODUCT，ROI 失败或检测器错误不能是OK。

    这与设计 10 第 10.3 和 10.8 节相矛盾：被拒绝的帧不 贡献，而队列丢失和推理错误减少了有效机会， 只能将证据移向UNCERTAIN或UNVERIFIABLE。这也使得 新的聚合鲁棒性对于间歇性拒绝的帧无效。

    分辨率：

    1. 保留拒绝帧的原因作为帧诊断并在 FrameQualitySummary，而不是将它们全部视为窗口级 决定原因。
    2. 让规则引擎根据聚合证据和强制门做出决定。
    3. 仅针对记录的窗口完整性故障独立强制 NG，例如 作为中断、身份混合或强制条形码/产品解析 失败。

    验收标准：

    • 满足所有组件策略且minimum_valid_frames的窗口仍然存在 OK 当它还包含一个被拒绝的非完整性帧时。
    • 该框架的原因仍然存在，其可用机会计数为 零。
    • 即使有其他帧，中断或混合身份窗口仍保持NG 满足每个组件的策略。

    F6。缺失的策略和相同的阈值不会失败关闭¶

    严重性： P1/高

    地点：

    • apps/edge-service/src/assemblyvision_edge/temporal/aggregator.py:127-164
    • apps/edge-service/src/assemblyvision_edge/config.py:599-622

    Required components need not have a temporal policy. The aggregator substitutes 1.0 for both thresholds when a policy is absent, and uses inclusive >=, so an exact-confidence 1.0 detection can become PRESENT without a configured, versioned policy. The configuration parser also allows medium_confidence == high_confidence, despite the design 10 requirement observation_threshold <= medium_confidence < high_confidence.

    Resolution:

    1. After loading the rule, reject an enabled temporal configuration unless it supplies exactly one policy for every required component and no unknown component keys.
    2. Enforce medium_confidence < high_confidence in both ComponentTemporalPolicy and configuration parsing.
    3. Defensively resolve missing policies to UNVERIFIABLE with an explicit configuration reason if invalid configuration reaches the aggregator.

    Acceptance criteria:

    • Configuration loading rejects missing required policies, extra policy keys, and equal medium/high thresholds.
    • An aggregation unit test proves that an absent policy cannot yield PRESENT, including for confidence 1.0.
    • A valid complete policy retains the documented high-hit and medium-hit paths.

    F7。低于阈值的检测可以满足精确的元件计数¶

    Severity: P1 / High

    Locations:

    • apps/edge-service/src/assemblyvision_edge/temporal/aggregator.py:159-164
    • apps/edge-service/src/assemblyvision_edge/temporal/aggregator.py:201-240

    Once a high-confidence or qualifying medium hit establishes PRESENT, _present() computes detection_count, boxes, and centers from every raw detection for that component in the selected frame. A low-confidence false positive can therefore inflate a frame from one qualifying detection to the rule's exact expected count. For example, with expected_count=2, detections at 0.95 and 0.50 in one frame can report detection_count=2 after the 0.95 detection establishes presence.

    Resolution:

    1. Define and document a count-evidence confidence threshold; at minimum it must be medium_confidence.
    2. Pass only qualifying detections to the count, area-ratio, and center summary used by count/spatial rules.
    3. Keep below-threshold observations available in diagnostics if needed, but never use them to satisfy a business rule.

    Acceptance criteria:

    • One high-confidence detection plus one below-medium detection reports a count of one and fails an expected_count=2 rule as NG.
    • Two qualifying detections in one valid frame satisfy an expected_count=2 rule.
    • Area and spatial evidence used for count-based rules comes only from the same qualifying set as the count.

    剩余审查说明¶

    • The OpenAPI enum, generated TypeScript type, and runtime validator correctly include UNVERIFIABLE.
    • The aggregation unit tests cover many threshold, duplicate, adjacency, and component-isolation cases. They need the product-isolation, idle-expiry, acquisition-time, quality-gate, missing-policy, and count-confidence cases specified above before the implementation is safe to merge.
