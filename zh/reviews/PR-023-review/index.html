    PR-023 评论：运行时和现场事件频道 (E4)¶

    1. 审查决定¶

    状态：已解决

    PR #23 具有预期的 E4 结构：瞬态服务器端运行时事件， 显式模拟触发接缝，以及校验和/设备键控共享模型 注册表。实施正确地保持检查持久性领先 inspection.completed 发布并序列化共享的推理 超解预测器。

    初步审查发现了三个阻止运行时通道的 P1 问题 在支持的配置中正常工作并满足其 有界缓冲合约，加上两个 P2 间隙。所有调查结果现已修复并 回归测试涵盖（参见第 3.1 节）。

    PR23-F01 - P1：跨域认证的WebSocket使用错误路径，无法携带查看者凭证¶

    参考文献

    • apps/edge-web/src/pages/LiveInspection.vue:95-115
    • apps/edge-web/src/services/client.ts:20-24, 54-67
    • apps/edge-web/tests/client.test.ts:69-103
    • apps/edge-service/src/assemblyvision_edge/api/routers/ws.py:25-57
    • docs/design/15-rest-api-and-events.md:157-160

    问题

    对于支持的跨域开发设置，VITE_API_BASE_URL 是 边缘原点，例如 http://edge-host:8000。 runtimeWsUrl() 将其转换为 ws://edge-host:8000/ws/runtime，但服务器端点是 /api/v1/ws/runtime；连接在身份验证之前收到 404 考虑过。

    即使路径已更正，仪表板也无法在以下情况下进行身份验证： api_token已配置。现有的跨源流有意保留 内存中的查看者承载令牌并将其添加到 fetch 请求中。浏览器 WebSocket 无法设置 Authorization 标头，跨域模式不会 接收同源会话 cookie，并且禁止查询字符串令牌。 因此，服务器使用 4401 关闭每个此类套接字。

    这使得 E4 实时更新路径在文档中不可用 受令牌保护的 Vite-to-edge 开发配置。也违反了 ADR-006/design-15 对经过身份验证的浏览器事件的一致要求 无需 URL 令牌即可交付。

    所需的解决方案

    1. 集中 API 到 WebSocket URL 构建并始终保留 /api/v1 前缀。 HTTP 客户端使用的仅原始基本 URL 必须映射 到ws(s)://<origin>/api/v1/ws/runtime。
    2. 添加一张短期、单一用途、一次性的 WebSocket 票证 经过身份验证的 REST 请求。它的范围必须限于运行时通道， 很快就会过期，并在套接字接受期间被原子消耗。
    3. 将票证发送到 URL 之外，例如作为专用协商票证 Sec-WebSocket-Protocol值。在accept()之前验证一下，只选择一个 修复了非秘密响应子协议，并且从不记录票证。不要放 查询参数或浏览器存储中的长期持有者令牌。
    4. 保留同源部署和承载的 cookie 身份验证 对可以设置标头的非浏览器客户端进行身份验证。更新 仅当工单流是跨源且 存在承载支持的查看器会话。
    5. 记录票证有效期、单次使用行为、故障关闭代码，以及 反向代理要求。添加对过期票证的有界清理。

    验收标准

    • 使用VITE_API_BASE_URL=http://edge-host:8000，浏览器连接到 ws://edge-host:8000/api/v1/ws/runtime； HTTPS 基础使用 wss。
    • 同源身份验证会话无需放置任何凭据即可连接 在网址中。
    • 跨源令牌保护仪表板通过 REST 获取票证并 接收运行时事件；它的 WebSocket 握手没有不记名令牌或 URL 中的票证。
    • 无效、过期、重播、错误渠道、未经验证的门票 在发送任何事件之前被拒绝。一次成功连接效果相同 票证无法用于第二次连接。
    • 测试涵盖 URL 映射、票证发行/消费/重播/过期路径、 现有的承载和会话路径，并断言 URL 中没有出现任何秘密或 应用程序日志。

    PR23-F02 - P1：跨线程队列传递可以使用 QueueFull 删除事件，而不是断开慢速消费者的连接¶

    参考文献

    • apps/edge-service/src/assemblyvision_edge/api/events.py:86-119
    • apps/edge-service/src/assemblyvision_edge/api/events.py:121-143
    • apps/edge-service/src/assemblyvision_edge/api/state.py:411-425
    • docs/tasks/E4-runtime.md:54-56, 91-103, 157-158

    问题

    检查和上传工作线程从非 asyncio 线程调用 publish()。对于一个 非循环发布者，总线先调用queue.full()，然后调度 queue.put_nowait(envelope) 分别通过 call_soon_threadsafe 进行。

    在这两个操作之间队列可能会变满。预定的 put_nowait 然后在事件循环内引发 asyncio.QueueFull。它不是 捕获后，套接字未发送_Disconnect，并且下一个事件可能会丢失 除了事件循环异常之外，默默地。 asyncio.Queue 不是 跨线程同步原语，因此即使预调度能力 检查不得用作正确性决策。

    这违反了 E4 不变量 2：必须断开慢速消费者的连接而不是 导致无限制/容易出错的传递路径。它还破坏了序列间隙 恢复，因为失败的回调不能保证稍后的消息 会暴露差距。

    所需的解决方案

    1. 对于每个跨线程发布，安排一个调用的回调 _deliver(queue, envelope) 在所属事件循环上。 _deliver()必须使 填充度决定并将信封入队或排出并入队 恰好有一个 _Disconnect 哨兵。
    2. 不要从检查/上传中访问或改变 asyncio.Queue 线程。仅保留订阅图和序列簿记在 螺纹锁。
    3. 使计划的交付能够容忍关闭事件循环：事件发布 仍然尽最大努力，绝不能进行检查、坚持或 上传工作者。安全地删除/取消订阅无效订阅。
    4. 保留每个订阅连接的事件顺序并确保消费者被标记 因为断开连接无法接收以后的正常信封。

    验收标准

    • 确定性工作线程测试在生产者之后填充队列 调度点但在交付运行之前。结果是一个_Disconnect， 没有未捕获的QueueFull，也没有哨兵之后的正常事件。
    • 重复的工作线程发布到完整队列保持非阻塞，离开 队列有界，并且不产生事件循环异常处理程序输出。
    • 在套接字/事件循环开始关闭后发布是无操作的 订阅并且不会中断检查循环或上传调度程序。
    • 现有的测试仍然证明单调序列分配和即时 同循环传递行为。

    PR23-F03 - P1：默认每帧检查从未发布 inspection.started¶

    参考文献

    • apps/edge-service/src/assemblyvision_edge/api/state.py:358-392
    • apps/edge-service/src/assemblyvision_edge/pipeline.py:239-258
    • apps/edge-service/src/assemblyvision_edge/api/state.py:438-471
    • docs/design/decisions/ADR-013-camera-frame-sources-and-multi-instance.md:53-61
    • docs/tasks/E4-runtime.md:26-28, 98-114

    问题

    inspection.started 仅在之后的时间窗口分支中发出 ProductWindowManager.feed() 打开一个窗口。默认ADR-013运行模式 没有临时策略并直接调用pipeline.inspect_frame()。那 路径在持久持久化后发布 inspection.completed 但从未发布 发布inspection.started。

    每帧检查是启用多实例的默认设置 运行时，而不是死分支。因此，仪表板和任何其他事件 尽管 E4a，消费者仍收到默认模式的不完整生命周期 明确承诺来自真实检查循环的开始和完成事件 过渡。

    所需的解决方案

    1. 在两种模式的推理之前定义生命周期标识。的 每帧管道必须接受调用者提供的检查 ID（或公开 输入开始检查操作），以便运行时可以发布一个 inspection.started 在调用 inspect_frame() 并发布相同内容之前 完成时的 ID。
    2. 保留ProductWindowManager拥有的时间窗口ID；不更换 身份密封窗口行为或为其生成第二个 ID。
    3. 仅在_persist_projection()成功后发布inspection.completed， 就像当前代码一样。失败的推理/持久路径不得发出 错误完成；如果引入了明确的故障事件，请记录其 语义并保持 REST 权威。
    4. 在开始和完成的有效负载中一致地包含 instance_id 因此，多实例仪表板可能会使正确的资源失效。

    验收标准

    • 启用的非临时实例恰好发出一个 inspection.started 且 一个 inspection.completed 表示一个捕获的帧，按此顺序，其中 相同的 inspection_id、instance_id 以及递增的事件序列。
    • 临时身份窗口实例仍然为每个打开的窗口发出一个启动信号 每个持久的最终窗口完成一次，包括差距和身份 过渡边界。
    • 推理失败、投影失败、暂停、存储停止、无帧 路径不会产生完整的事件。他们的事件行为经过测试 并记录下来。
    • 仪表板协调测试证明任一模式都会刷新最终结果 REST 记录并且从不将开始事件视为已完成的决策。

    4. 非阻塞改进¶

    PR23-F04 - P2：共享 TypeScript 事件契约仍然使用 payload 而不是服务器的 data 信封¶

    参考文献

    • packages/typescript/api-client/src/edge/websocket.ts:10-15
    • packages/typescript/api-client/tests/websocket.test.ts:34-70
    • apps/edge-service/src/assemblyvision_edge/api/events.py:27-41
    • docs/design/15-rest-api-and-events.md:162-177

    WSEventEnvelope 仅公开 type、sequence、source_id 和 payload， 而服务器发出设计 15.6 字段并将有效负载命名为 data。 LiveInspection.vue 目前仅检查 type，因此这不会阻止其 当前刷新行为。它确实使共享客户合同不正确 并且序列测试验证了合成的遗留形状而不是真实的形状 服务器信封。

    推荐解决方案

    更新 API 客户端类型以精确模拟版本 1 信封： event_id、type、schema_version、occurred_at、source_id、sequence、 correlation_id和data。之前添加最小运行时结构验证 序列处理，保留未知事件类型的容忍度，并使用 实际的服务器字段名称。

    验收标准

    • TypeScript 使用者可以访问 event.data 和所有强制信封 没有强制转换的字段。
    • 有效的服务器信封发送；畸形的信封不会损坏 序列基线；未知事件类型仍然可交付/可忽略。
    • 包测试和至少一个仪表板测试使用真实的 v1 信封 固定装置而不是 payload。

    PR23-F05 - P2：无法观察到所需的 WebSocket 连接和事件计数¶

    参考文献

    • apps/edge-service/src/assemblyvision_edge/api/events.py:76-84
    • apps/edge-service/src/assemblyvision_edge/api/app.py:87-93
    • docs/tasks/E4-runtime.md:162, 169-172
    • docs/contracts/07-deployment-observability-and-operations.md:84-98

    总线保留connection_count和last_sequence，但都不暴露 通过运营指标、结构化状态或经过身份验证的支持 端点。也没有发布/慢速消费者断开计数器。 E4的 强制矩阵明确要求可观察的连接和事件计数， 因此操作员无法区分空闲仪表板和失败的事件源。

    推荐解决方案

    添加包含活动连接、事件的类型化运行时事件运行状况快照 按类型发布、消费者断开连接缓慢以及传递回调失败。 通过现有的经过身份验证的设备/状态或可观察性将其公开 表面，文档单位/重置语义，并避免放置无界 每个连接的标识符转化为指标。

    验收标准

    • 连接打开/关闭、发布事件、缓慢消费和失败传递 计数器在测试中确定性地变化。
    • 操作员可以通过经过身份验证的现有值检索当前值 带有记录字段的状态/指标表面。
    • 计数器收集保持非阻塞并且不会暴露凭据， 身份或有效负载内容。

    5. 积极的发现¶
