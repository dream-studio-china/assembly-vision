    PR-022 评论：上传弹性 (E3)¶

    1. 审查决定¶

    状态：已解决

    PR #22 建立了正确的 E3 结构：速率限制器、进程本地 断路器、受控重试路线、持久中断覆盖范围和 明确延迟的可恢复媒体协议。初步审查发现一个P0 （油门可能会永远阻止每个大上传）和两个 P1 间隙（ 限制器没有限制实际发送的字节，并且手动重试不是 原子跃迁）。所有发现现已修复并由回归测试覆盖 （参见第 3.1 节）。

    PR22-F01 - P0：大于一桶容量的有效负载永远阻塞¶

    参考文献

    • apps/edge-service/src/assemblyvision_edge/upload/scheduler.py:50-71
    • apps/edge-service/src/assemblyvision_edge/upload/scheduler.py:487-503
    • docs/tasks/E3-upload-resilience.md:80-95

    问题

    _TokenBucket.acquire() 将令牌限制为配置速率的一秒，但是 要求存储桶在返回之前包含完整的 amount。对于任何 有效负载大于 rate_bytes_per_second * 1.0，该谓词永远不能 真实：

    tokens <= rate * 1 second < amount

    调度程序在调用 acquire() 之前已经租用了该任务。那么它 在 250 毫秒内无限循环休眠并且从不调用接收器或写入任务 过渡。例如，1 Mbps 的 8 MiB 媒体任务有 125,000 字节的存储桶 容量并永久卡住。工人可以保留过去的任务租约 到期后，stop()无法立即完成被阻止的worker。

    这是生产数据流故障，而不仅仅是吞吐量问题：大 恢复后证据永远不会耗尽，而持久队列将其报告为 IN_PROGRESS。它违反了E3不变量1和E3a不休眠的要求 超出租约而无需续签。

    所需的解决方案

    1. 不要求一个令牌预留等于一个完整的媒体对象。率 相反，限制请求主体段的有界序列。
    2. 在实际传输写入边界处应用段限制器。超文本传输协议 接收器应该以有界块的形式传输序列化的请求主体并获取 在将每个块交给 httpx 之前对其进行预算；不要等待一次 然后一次性发射整个媒体对象。
    3. 在存储库中添加受保护的上传租约续订操作，并续订 在任何可能超过当前到期时间的等待之前激活租约。中止 如果续订失败，则请求无需终端转换，允许当前 所有者恢复任务。
    4. 通过调度程序停止事件取消限制。关闭 不得等待任意媒体传输持续时间。
    5. 将所有节流排除在检查持续性和开发之外 目录接收器。仅发送到网络目的地的字节受到影响 到这个政策。

    验收标准

    • 确定性测试发送大于一秒容量的有效负载 配置率低。它完成而不是循环，调用接收器，并且 至少需要配置的理论最小传输时间。
    • 相同的测试证明有效租约在整个租约到期前已续签 节流传输；续订失败会阻止旧所有者发送或 更新任务。
    • 停止/关闭测试会立即中断节流等待并离开 租用的任务可通过现有的租用回收路径恢复。
    • 并行本地检查持久性测试证明不会阻止任何一个节流 SQLite/发件箱提交也不会更改其顺序。
    • 现有的无上限行为仍然立即存在，并且正常有效负载低于 存储桶容量仍然遵循配置的限制。

    PR22-F02 - P1：配置的上限未绑定 HTTP 网络有效负载字节¶

    参考文献

    • apps/edge-service/src/assemblyvision_edge/upload/scheduler.py:500-504
    • apps/edge-service/src/assemblyvision_edge/upload/scheduler.py:174-191
    • docs/tasks/E3-upload-resilience.md:80-86

    问题

    调度程序保留len(payload)，但HttpUploadSink发送JSON 包含 Base64 数据的信封。因此媒体请求的正文更大 比原始媒体字节加上 JSON 元数据大约三分之一。的 然后，在原始字节等待之后，将完整的信封在一次写入中传递给 httpx。 因此，实际网络上配置的带宽最大值超出了 有效负载和 upload_bytes_sent 指标报告更小的、不同的单位。

    这与 E3a 将限制器应用于网络有效负载的要求相矛盾 字节，并使容量规划/可观察性在中断期间产生误导。

    所需的解决方案

    1. 定义一个显式指标：写入到的应用程序请求主体字节 网络。使用相同的指标进行速率限制和 bytes_sent 遥测。
    2. 对 HTTP 信封进行一次序列化，测量其序列化字节，然后进行流式传输 这些字节通过 PR22-F01 中描述的段限制器。仅计数 实际产生给传输的主体字节；记录是否 协议标头被有意排除。 3.更新UploadSink边界或引入类型化的prepared-request 对象，因此调度程序不会猜测特定于接收器的线路尺寸 信封。目录/开发接收器必须报告零网络字节而不是 比假装文件系统写入消耗的 WAN 容量要多。
    3. 更新设计 13.13 和设备状态字段描述以命名所选的 单位精确。

    验收标准

    • 使用二进制媒体的测试验证速率限制器预算序列化 Base64 JSON 正文，而不是 len(raw_media)。
    • 通过配置上限，测量的请求主体吞吐量保持在或低于 记录的有界爆发后的上限；没有上限，没有限制器 引入了延迟。
    • upload_bytes_sent 等于 HTTP 接收器产生的请求主体字节 跨越成功和可重试的尝试。目录接收器的值为零。
    • OpenAPI、生成的 TypeScript 和状态文档描述相同 字节单位并保留可为空/不受限制的行为。

    PR22-F03 - P1：手动重试不是原子状态转换并导致聚合同步状态过时¶

    参考文献

    • apps/edge-service/src/assemblyvision_edge/api/routers/uploads.py:41-56
    • apps/edge-service/src/assemblyvision_edge/persistence/repository.py:993-1026
    • apps/edge-service/src/assemblyvision_edge/persistence/repository.py:1781-1816
    • docs/tasks/E3-upload-resilience.md:48-50, 120-135

    问题

    该路由检查一个存储库调用的资格并执行突变 在另一个。在它们之间，调度程序可以声明任务，或者第二个手册 重试可以重置。 EdgeRepository.retry_upload() 然后返回当前 不合格的任务而不是报告过渡冲突，以及路线 返回 HTTP 200。尽管没有重试，但操作员被告知重试成功 执行并且该任务可以由另一个工人租用。

    当转换成功时，存储库仅更改 status， attempt_count和last_error_code。它不会清除过时的终端字段 (completed_at)、设置updated_at、清除旧的重试截止日期或重新计算 检查的聚合同步状态。因此重试媒体任务 来自 PERMANENT_FAILURE 的检查仍可报告为检查 FAILED 再次挂起，直到稍后的终端工作人员转换恰好刷新它。

    这违反了 E3c 的承诺，即不符合条件的任务会返回 409 当前状态，并且它使队列/检查真相在重试期间不一致。

    所需的解决方案

    1. 将路由的先读后写流程替换为一个存储库操作 在一笔即时交易中拥有完整的决定权。
    2. 返回区分NOT_FOUND、NOT_RETRYABLE的类型化结果 （包括当前任务/状态）和RETRIED。将其映射到 404、409 和 200 在没有初步查找的路线中。
    3. 对任务 ID 和合格状态进行转换比较和设置。上一个 成功转换设置status='PENDING'，增量attempt_count， 清除 last_error_code、next_attempt_at、completed_at 和租赁字段， 并从一个注入/当前 UTC 时间戳设置 updated_at。
    4. 在同一个事务中，调用 _refresh_inspection_sync() 来执行任务 检查ID。重试不得更改任何已验证的收据或授权 保留；它只是将聚合状态返回到 QUEUED 或 PARTIAL。

    验收标准

    • 确定性竞赛测试在观察到资格后暂停，然后进行 工作人员领取任务（或再次重试获胜）。延迟的HTTP请求返回 409 TASK_NOT_RETRYABLE与当前状态；它永远不会返回 false 200 并且永远不会改变工人的租约。
    • 两个同时重试请求恰好产生一个 200 转换和一个 409； attempt_count 只增加一次。
    • 重试 RETRY_WAIT 和 PERMANENT_FAILURE 会清除终端/重试 字段，设置更新的 updated_at，并返回立即到期的 PENDING 任务。
    • 重试永久失败的媒体任务会将其检查状态从 FAILED 到 QUEUED/PARTIAL 由其他已验证任务指定。它是 在任务成功并获得新的经过验证的收据之前，不符合保留资格。
    • SUCCEEDED、IN_PROGRESS、CANCELLED和未知任务案例保留其 现有状态并返回 409/404，无突变。

    PR22-F04 - P2：操作员客户端和 Runbook 不会公开新的 E3 控件¶

    参考文献

    • packages/typescript/api-client/src/edge/ApiClient.ts:46
    • packages/typescript/api-client/src/edge/HttpApiClient.ts:162-167
    • packages/typescript/api-client/src/edge/MockApiClient.ts:505-508
    • docs/design/13-upload-and-synchronization.md:98-112
    • docs/runbooks/04-upload-backlog.md:15-23
    • docs/design/16-edge-dashboard.md:26, 162

    生成的OpenAPI类型声明了重试操作，但是维护的 ApiClient、HTTP 客户端和模拟客户端仅公开 listUploads。的 因此，仪表板没有键入路径来执行新的受控重试 设计16个列表作为MVP队列操作。设计 13.8 还省略了新的 电路设置来自其配置示例，并且 Runbook 04 没有说明 操作员如何解释UPLOAD_CIRCUIT_OPEN，检查电路状态，或 纠正永久性原因后，请安全地使用手动重试。

    推荐解决方案

    1. 在输入的内容中添加retryUpload(uploadTaskId: string): Promise<UploadTask> API接口、HTTP客户端、模拟客户端。验证返回的任务并 将 404/409 视为键入的 API 错误，而不是将其视为成功。
    2. 仅针对 RETRY_WAIT 和 向上传队列 UI 添加重试操作 PERMANENT_FAILURE；完成后刷新状态与渲染冲突 没有乐观突变的反馈。
    3. 用电路阈值/开路持续时间扩展设计 13.8，并解释 保留media_chunk_bytes设置。扩展运行手册 04 并开路 诊断、退避/探测行为、手动重试资格和规则 重试永远不会授权清理。

    验收标准

    • TypeScript 单元测试涵盖成功重试和 404/409 错误映射 HTTP 客户端；模拟和接口实现保持类型完整。
    • UI 测试证明重试仅在符合条件的州可见，永远不会改变本地 服务器成功之前的状态，并显示冲突响应。
    • Runbook 名称 UPLOAD_CIRCUIT_OPEN、upload_circuit_state、带宽 遥测和修复后重试程序；它明确保留 幂等性密钥和接收门控删除。
    • 配置示例记录了所有支持的 E3 环境/设置 值并明确将分块标记为推迟到中央合同冻结。

    5. 重新审核前所需的回归矩阵¶

    面积 所需证据
    大媒体节流 大于一桶容量的有效负载完成，具有有限的吞吐量，更新其租约，并在停止/故障时保持可恢复。
    实际线数限制 Base64 JSON 正文（而不是原始源字节）受到速率限制并计入状态遥测。
    本地安全第一 节流/积压的上传不能延迟单独的检查/发件箱提交。
    断路器 阈值/开放/半开放成功/失败，开放时无索赔，排除永久故障，并且无重复恢复保持通过。
    重试 CAS 调度程序/操作员竞争和两个操作员竞争产生一个权威转换；不合格/未知的情况不会发生变异。
    同步和保留 重试的永久媒体会立即重新计算聚合同步状态，并且在没有新的经过验证的收据的情况下无法成为清理资格。
    公共合同 OpenAPI/生成的类型/客户端接口、状态单元、设置文档和运行手册一致地描述了实现的行为。

    6. 生产启用条件¶

    即使上述调查结果得到解决，E3仍不授权生产 可恢复媒体上传。中央摄取端点，块接收格式， 对象绑定、大小/校验和确认以及兼容性/版本处理 保持明确推迟，直到边缘到中心协议合同冻结。

    特定于站点的阻止程序也仍然存在：批准的带宽上限/调度 窗口、电路阈值/开放持续时间值、最大停电/积压大小、 需要可恢复传输、保留策略和响应的媒体类 当受保护的本地容量达到其停止储备时的程序。
