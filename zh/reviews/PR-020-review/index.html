    PR-020 评论：保留和磁盘安全 (E2)¶

    1. 审查决定¶

    状态：已解决

    PR20-F01 - P0：投影失败可以发布未记录的 OK¶

    参考文献

    • apps/edge-service/src/assemblyvision_edge/api/state.py:290-310
    • apps/edge-service/src/assemblyvision_edge/api/state.py:337-359

    问题

    检查循环从之前的记录中分配runtime.last_result 调用_persist_projection()。 _persist_projection() 捕获所有 存储库失败，记录它并返回。因此 OK 可能会暴露于 即使 SQLite 投影/发件箱未提交，运行时消费者也是如此。一个 数据库错误也可以被 SQLAlchemy 包装并绕过狭窄的 isinstance(exc, OSError) 存储故障检查。

    这违反了 E2 不变量 7 和契约 03：结果不得成为 当完整的可审计持久性不可用时，可操作OK。

    失败场景

    1. inspect_frame()写入/返回OK记录。
    2. runtime.last_result 变为 OK。
    3. SQLite提交失败，因为该卷是只读的、已满的、锁定超过 恢复，或返回包装的数据库 I/O 错误。
    4. _persist_projection()记录失败并返回；没有耐用的发件箱 存在，而调用者仍然可以观察 OK。

    所需的解决方案

    1. 使成功的持久投影/发件箱持久性成为 发布 last_result 或任何物理/业务 OK 信号。
    2. 让 _persist_projection() 返回类型化的成功/失败结果 吞下错误。在内部保留原始异常 日志/诊断，无需通过 API 公开堆栈跟踪。
    3. 将每个持久性故障转换为锁存存储/准入故障。 处理 SQLite/SQLAlchemy 操作错误以及原始 ENOSPC， EROFS和EIO。
    4. 停止/排出产品摄入量，直至强制坚持明确成功 恢复探针或受控操作员恢复可清除故障。

    验收标准

    • 原始 ENOSPC、原始 EROFS、SQLite/SQLAlchemy 写入的故障注入测试 错误，发件箱交易失败证明last_result不是OK， 没有结果发布为 OK，并且 inspection_ready 变为 false。
    • 失败的 persist_inspection_and_enqueue_uploads() 不会留下任何部分 检查/发件箱行并锁定稳定的存储故障警报。
    • 在记录的恢复过程之后成功的强制写入是 仅支持恢复准入的路径。

    PR20-F02 - P1：过期的清理支架可以在检查围栏之前断开链接¶

    参考文献

    • apps/edge-service/src/assemblyvision_edge/retention/worker.py:128-187
    • apps/edge-service/src/assemblyvision_edge/persistence/repository.py claim_retention_batch() 和 finalize_media_purge()。

    问题

    工作人员仅在终端数据库转换中验证隔离令牌， path.unlink() 之后。如果工人 A 逾期逾期，工人 B 会收回该租约 神器，并且A恢复，A仍然可以删除该文件。 A则失去最终确定性； B 遇到文件丢失并记录完整性错误。证据是 在没有匹配的 PURGED 审核转换的情况下被删除。

    这违反了 E2 不变量 4 和 5。

    所需的解决方案

    1. 添加受保护的 confirm_or_renew_retention_claim() 比较和设置操作 就在破坏性 I/O 之前。它必须要求当前所有者， AVAILABLE 生命周期，无保留/故障，且租约未到期。
    2. 使用返回的更新截止日期进行最终确定和失败转换。 不要对批次中的所有文件使用批次开始时间戳。
    3. 大小/重试租约持续时间，以便工作人员可以在慢速文件系统之前更新 操作，更新失败时停止处理。

    验收标准

    • 确定性两人测试：A 索赔并在到期后暂停； B回收； 一份简历。断言 A 从不调用 unlink，B 单独执行 PURGED 过渡。
    • 路径验证和破坏性 I/O 之间的租约过期被拒绝 无需更改文件或行。
    • 审核状态由当前所有者保持有效 PURGED 或 AVAILABLE/有故障，原始证据完好；永远不会失踪，没有 相应的权威转变。

    PR20-F03 - P1：索赔后保留或完整性故障不会取消删除¶

    参考文献

    • apps/edge-service/src/assemblyvision_edge/retention/worker.py:144-187
    • apps/edge-service/src/assemblyvision_edge/persistence/repository.py finalize_media_purge()。

    问题

    仅在索赔时评估资格。持有、接受锁， 人工审查锁定，或在索赔未失效后应用完整性错误 主动主张。最终确定仅检查所有权/到期时间。工人可以 取消链接并标记在声明和声明之间受到保护的PURGED证据 删除。

    这违反了 E2 不变量 3。

    所需的解决方案

    1. 以原子方式清除每个保持/故障更新或使活动无效 删除声明。
    2. 以原子方式重新验证完整的资格谓词，作为 从 F02 取消链接前的索赔确认/续订：生命周期、保留状态、 完整性状态、截止日期、检查同步、验证媒体接收、 和当前的击剑令牌。
    3. 在最终确定中重复围栏资格检查，以便同时保留或 应用保护后，故障无法将已删除的文件变成PURGED。

    验收标准

    • 声明工件，然后在处理之前应用审核/验收保留； 断言没有取消链接，也没有 PURGED 转换。
    • 在处理之前应用完整性错误重复；断言没有取消链接， 持久的FAULT，并且没有未来的资格。
    • 比赛测试证明保持/故障和工人终端转换不能同时进行 成功获得相同的工件。

    PR20-F04 - P1：路径验证有符号链接 TOCTOU 窗口¶

    参考文献

    • apps/edge-service/src/assemblyvision_edge/retention/worker.py:146-163
    • apps/edge-service/src/assemblyvision_edge/retention/worker.py:201-220

    问题

    _resolve_path() 检查输出根中的已解析路径，但返回 原始未解析的路径名。并发进程可以代替中间进程 验证后、path.unlink() 之前带有符号链接的捆绑目录。 后面的取消链接是由前面的解析授权的，可以删除文件 在可信检查包之外。

    这违反了 E2 不变量 9。

    所需的解决方案

    1.执行相对于可信目录文件描述符的遍历和解除链接 在目标平台支持的情况下使用 no-follow 语义。 2. 将输出 root/bundle 目录作为可信描述符打开并拒绝 遍历期间的符号链接组件；仅取消链接最终的基本名称 可信父描述符。 3. 如果部署平台缺少所需的 no-follow 原语，请禁用 清理而不是从容易出现竞争的路径名检查中声明路径安全。

    验收标准

    • 测试用符号链接替换中间包目录 验证和删除；没有外部文件被删除并且媒体行被删除 故障/受保护。
    • 遍历、绝对路径、最终文件符号链接和中间目录 符号链接情况都证明清理保留在预期的包内。

    PR20-F05 - P1：成功的 Stat 调用清除了存储写入故障¶

    参考文献

    • apps/edge-service/src/assemblyvision_edge/api/state.py:327-335
    • apps/edge-service/src/assemblyvision_edge/api/state.py:380-393

    问题

    _note_storage_write_fault() 在合格的 I/O 上设置 storage_write_fault 错误，但以后每一次成功的 refresh_storage() 都会无条件地设置它 为假。因此，短暂的完整/只读/数据库写入失败可以清除 当statvfs工作时，无需证明强制输出和SQLite/outbox 毅力已经恢复。

    所需的解决方案

    1. 将写故障视为锁存准入故障。
    2. 仅通过执行以下操作的显式恢复路径清除锁存器： 强制持久性探测（原子媒体/捆绑和 SQLite/发件箱写入）和 记录恢复事件，或通过审核的操作员操作（其策略） 需要相同的探头。
    3. 将容量观察与写入健康状况分开；一个可读的文件系统是 没有证据表明它是可写的。

    验收标准

    • 注入存储/数据库写入失败，然后模拟成功 disk_usage/statvfs；断言 inspection_ready 仍然为 false 并且 STORAGE_WRITE_FAULT 仍然存在。
    • 仅成功的存储观察无法清除锁存器。
    • 只有记录的持久性恢复探针才能清除故障并恢复 摄入量。

    PR20-F06 - P1：精确阈值进入较不严重模式¶

    参考文献

    • apps/edge-service/src/assemblyvision_edge/retention/storage.py:71-77

    问题

    实现使用 <，而 E2 任务和设计指定操作“at 或低于”警告、严重和停止阈值。正好 5%、10% 或 20% free 仍处于不太严格的模式。恰好在配置的停止储备处， 新产品的摄入可以继续。

    所需的解决方案

    使用 <= 进行字节和 inode 压力比较。记录任何滞后现象 分别；它不能默默地重新定义阈值条目语义。

    验收标准

    • 参数化测试证明了准确的警告、严重和停止边界 空闲字节和空闲索引节点百分比。
    • 恰好在停止阈值处，状态为 STOP、inspection_ready=false， 并且检查循环拒绝/排出新帧。

    PR20-F07 - P1：关键模式不抑制可选捕获¶

    参考文献

    • apps/edge-service/src/assemblyvision_edge/api/state.py:254-313
    • apps/edge-service/src/assemblyvision_edge/retention/storage.py:71-77

    问题

    只有 STOP 会更改检查循环行为。在 CRITICAL 处，每个管道 仍然收到正常的OutputWriter，所以可选full-video/OK-media capture 不断消耗受限体积。这不符合设计 12.7 或 E2c 所需的临界模式降级。

    所需的解决方案

    1. 定义类型化的捕获策略类，将工件标记为强制或 根据结果/媒体类型可选。
    2. 将当前存储模式传递到输出/捕获边界。临界时， 仅抑制显式可选输出；保留强制元数据和 NG 证据。
    3. 在检查证据中记录压制决定和理由或 设备事件，而不会歪曲所捕获的省略的可选媒体。

    验收标准

    • 在 CRITICAL 处，测试配置的可选 OK/滚动视频工件是否为 当强制性元数据和 NG 证据仍然存在时，不会写入。
    • 在WARNING，除了符合条件的清理请求之外，行为保持正常。
    • 在STOP时，没有新产品按照OK进行检查或排放。

    PR20-F08 - P1：启动完整性故障不会启动就绪状态或发出警报¶

    参考文献

    • apps/edge-service/src/assemblyvision_edge/api/app.py:86-104
    • apps/edge-service/src/assemblyvision_edge/api/state.py:438-476

    问题

    启动扫描仍然存在 integrity_status='FAULT' 并记录警告，但它 不锁存运行时存储未就绪、添加稳定完整性警报或停止 新的检查入场。管道可以通告 inspection_ready=true

    所需的解决方案

    1. 将非零启动完整性报告传播到持久的运行时存储中 故障具有稳定的 STORAGE_INTEGRITY_FAULT 警报和计数/详细信息安全 用于经过身份验证的设备状态 API。
    2. 准入/准备就绪，直到记录在案的和解解决了受影响的问题 强制性证据，或制定明确的政策来区分历史 当前强制持久性准备的证据缺陷。
    3. 持久化一个具有稳定错误代码和计数的设备事件；不记录路径或 对公共客户的敏感标识符。

    验收标准

    • 使用缺失和错误尺寸的介质进行应用程序生命周期测试，断言故障是 设备状态中可见，/health/ready未就绪，正在检查 在恢复之前，循环无法发布后续的 OK。
    • 重复启动不会消除完整性故障或静默恢复 准备状态。

    PR20-F09 - P1：生产启动跳过相同大小的校验和篡改¶

    参考文献

    • apps/edge-service/src/assemblyvision_edge/api/app.py:93-103
    • apps/edge-service/src/assemblyvision_edge/persistence/reconcile.py:126-149

    问题

    scan_storage_integrity()默认为verify_checksums=False，启动 使用该默认值。因此，在生产中不会检测到相同尺寸的篡改。 E2任务需要完整的校验和扫描或显式配置的有界 抽样；该实现既不提供配置、策略、覆盖范围 遥测，也不是启动调用。

    所需的解决方案

    1. 添加类型化完整性扫描设置以进行完整验证或有界验证 确定性采样（样本大小/速率、最大字节、调度）。
    2. 在启动时运行选定的策略并公开上次运行时间、覆盖范围和 通过经过身份验证的状态/指标跳过原因。
    3. 默认生产启用为安全记录策略；不要默默地 通过仅大小扫描获取校验和验证。

    验收标准

    • 寿命测试写入相同大小、不同校验和的介质并验证 配置的策略会检测到它并根据 F08 进行控制/警报。
