    没有严重漏洞或改变边缘机决策的直接途径 被识别出来。最高的风险影响中央凭证泄露 恢复、配置身份、证据完整性、租户归属、 可用性以及飞行员准备声明的准确性。

    3. 积极的发现¶

    以下控制措施实施良好，应予以保留：

    • 边缘运行时不导入中央实现，并且中央保持不变 检查决策路径。
    • 设备上传认证和管理员认证分开使用 代码路径不能互相替换。
    • 凭证存储为独立加盐的 scrypt 哈希值并在 恒定时间 (auth/passwords.py:31-60)。
    • 浏览器会话使用高熵查找/秘密分割，仅存储加盐的 秘密哈希，服务器端过期，并使用 HttpOnly 和 SameSite=Strict cookie（repository.py:896-980、routers/auth.py:55-67）。
    • 检查摄取以原子方式提交不可变的检查投影， 组件证据、接收和验收审核事件。
    • 设备序列、检查ID和幂等性约束提供了强大的 防止重复的支持。
    • 媒体上传通过源媒体 ID 绑定到接受的父清单， 预期大小，以及对象存储之前的预期 SHA-256 (ingest/__init__.py:125-145)。
    • 对象密钥由中心和租户范围生成；客户无法供应 存储路径（ingest/__init__.py:226-237）。
    • 主要历史记录、详细信息、评论和媒体 HTTP 路径范围查询 经过身份验证的管理员组织。
    • 人工审核是附加的，不会更新原始的机器决策。
    • 架构迁移是一个受控的发布步骤； API 检查迁移头 已准备就绪并且不会在启动时迁移。
    • RFC 7807 响应通常避免堆栈跟踪、SQL、秘密、绝对 路径和模型路径。
    • Compose 默认在环回上发布试点 UI，以及中央 API 映像以非 root 用户身份运行。
    • OpenAPI 和生成的 TypeScript 工件具有确定性漂移检查。

    4. 高严重性的发现¶

    H01。已发布的开发凭证成为有效凭证¶

    状态： 已解决（2026 年 8 月 13 日，第一批修复）。

    证据

    • apps/central-service/compose.env.example:1-18 包含正在运行的 PostgreSQL， MinIO root、管理员和设备上传值。
    • 记录的工作流程告诉操作员将此文件复制到 .env （compose.env.example:1-3、README.md:226-230）。
    • 将管理员和设备令牌设置为持久的 凭证存储 (compose.yaml:58-73)。
    • PostgreSQL 和 MinIO 还保留已知的后备密码 （compose.yaml:19-21、compose.yaml:35-36）。

    管理员/设备令牌没有默认值的说法具有误导性 记录的路径：Compose 文件没有默认的插值，但是 已发布的示例提供了已知值。复制的示例会生成一个现成的 与公开的凭据堆栈。

    影响

    意外暴露的飞行员可以以管理员身份访问或注册 设备。发布的 MinIO 根凭证还授予不受限制的对象 商店管理。

    需要改变

    • 从示例中删除可用的秘密。使用空的必需变量或 无法通过 Compose 必需变量表达式的显式占位符。
    • 需要高熵生成值并拒绝已知的开发哨兵 除非启用显式仅环回开发模式。
    • 使用 Docker 机密或已安装的机密文件进行非本地部署。
    • 从受控飞行员中删除 PostgreSQL 和 MinIO 密码回退 简介。

    接受

    • 当秘密未设置或仍然相同时，撰写在开始之前失败 哨兵。
    • 测试检查有效的 Compose 配置，无需打印机密 值并证明受控飞行员配置文件没有已知的凭据。

    H02。凭证泄露操作手册无法执行其承诺的轮换¶

    状态： 已推迟（2026-08-13）并采取缓解措施。自动凭证 旋转是生产范围（与H12共享）；运行手册现在指出 M1 没有就地轮换，并记录经批准的手动数据库级别 撤销程序，因此运营商不再相信引导程序重新运行会撤销 被盗的令牌。

    证据

    • docs/runbooks/central-credential-compromise.md:13-21 指示操作员 禁用/重新注册设备并重新运行引导程序以进行管理员轮换。
    • persistence/bootstrap.py:3-10明确指出现有设备和 管理员永远不会重新输入密钥。
    • repository.py:1073-1137 仅在创建新行时才对凭据进行哈希处理。
    • 不支持设备禁用、凭证轮换或撤销所有管理 - 会话命令/API 存在。

    影响

    操作员可能会遵循紧急程序并错误地得出结论： 被盗的凭证在其仍然有效的情况下被撤销。

    需要改变

    为管理员令牌轮换实施显式事务命令， 设备令牌轮换、设备禁用/重新启用以及组织范围的会话 撤销。每个操作都必须编写一个审计事件，其中包含参与者、目标、 请求/事件关联、原因和结果。在实施之前，修改 Runbook 声明重新运行引导程序不会轮换凭据，并且 在批准的数据库级响应期间，中央访问必须保持停止状态。

    接受

    • 旧令牌在旋转后立即返回401，新令牌是 范围为同一主体。
    • 管理员轮换撤销策略选择的所有会话。
    • 轮换/撤销和失败的尝试是可审核的。
    • 该 Runbook 无需未记录的 SQL 即可执行。

    H03。所需的配置分配破坏了公共版本身份¶

    状态： 已解决（2026 年 8 月 13 日，第一批修复）。

    证据

    • repository.py:4036-4039 将 product_versions.id 分配给 product_pk 并 然后查询products.id == product_pk。应该使用 product_versions.product_id。
    • repository.py:4177-4196正确存储内部整数外键。
    • repository.py:4549-4560 然后直接将这些内部密钥序列化为 字符串而不是加入公共 version_id UUID。
    • 现有测试仅断言版本/设备，甚至保留错误 审计状态下的内部值（test_metadata_repository.py:1142-1197， test_metadata_api.py:537-562）。

    影响

    一旦产品和产品版本整数序列不同，有效的分配 可能会导致产品检测器失败或根据错误的产品代码验证产品检测器。一个 成功的响应返回诸如 "1" 之类的值，而不是请求的值 公共 UUID，破坏了可追溯性以及任何使用所需的消费者 捆绑身份。

    需要改变

    • 通过product_versions.product_id解析产品代码。
    • 返回时将所有四个存储的外键连接到其版本表 所需的配置。
    • 保持内部整数密钥对持久性的私密性。

    接受

    • 种子分歧产品/产品版本主键并证明分配 验证预期产品。
    • 断言创建、更新、获取、列表和审核输出恰好包含这四个 调用者提交的公共 UUID。

    H04。 PostgreSQL 所需配置并发是最后写入获胜¶

    状态： 已解决（2026 年 8 月 13 日，第二批修复）。

    证据

    • repository.py:3997-4016 读取突变前的当前修订版本。
    • repository.py:4172-4185 按设备行 ID 执行无条件更新。
    • _metadata_write依赖于普通的PostgreSQL事务和唯一性 约束（repository.py:2297-2319）；无行锁或条件修订 谓词保护此更新。

    两个 PostgreSQL 事务可以读取相同的修订版，都通过 If-Match， 两者都编写相同的下一个修订版本，并默默地相互覆盖。 SQLite 测试不会公开这一点，因为 BEGIN IMMEDIATE 会序列化编写器。

    需要改变

    使用UPDATE ... WHERE device_row_id = :id AND revision = :expected，验证一个 受影响的行，并将零行映射到 412 REVISION_MISMATCH。如果明确涵盖锁定语义，SELECT ... FOR UPDATE 也是可以接受的。

    接受

    真正的 PostgreSQL 屏障测试会提交两个具有相同 If-Match 的更新： 恰好一个成功，一个返回 412，修订增量一次，一个 相应的审计事件已提交。

    H05。 Central 发出 AVAILABLE 媒体收据而不验证存储的字节¶

    状态： 已解决（2026 年 8 月 13 日，第二批修复）。

    证据

    • ingest/__init__.py:181-214 调用 put_object 并立即保留 AVAILABLE 绑定和收据。
    • storage/object_store.py:69-77 执行单个 PUT 但不执行写入后统计， 可信校验和检查或回读。
    • 设计 14 需要在可用之前验证尺寸/校验和 (docs/design/14-data-model-and-database.md:528-532)。
    • M1 退出标准将这些称为“经过验证的兼容收据” (docs/tasks/C1-central-server-m1.md:663-665)。

    影响

    短写入、存储损坏、对象替换或 S3 兼容 实施缺陷可能会留下数据库行并验证收据声明 当保留的字节不同时，证据存在于预期的哈希值中。

    需要改变

    扩展对象存储协议以返回或检索可信存储 大小和 SHA-256 元数据。在提交 AVAILABLE 之前验证两者。不 使用多部分 ETag 作为 SHA-256。对于有限的 16 MiB 试点，回读哈希 如果测量的话是可以接受的；否则存储并验证支持的 S3 校验和 元数据。

    接受

    • 成功 PUT 后模拟截断/损坏不会产生任何结果 AVAILABLE行，没有成功收货。
    • 有效对象通过精确大小和 SHA-256 验证。
    • 调节独立地检测后来的腐败，而不仅仅是缺席。

    H06。协调可以删除仍在提交的上传¶

    状态： 已推迟（2026-08-13）并采取缓解措施。完整的阶段/最终确定 协议是生产范围； reconcile-media 现在接受 --min-age-hours 阈值（默认 24）并且仅将早于该阈值的未绑定对象分类为 可移动的孤儿，因此其字节先于其绑定的正在进行的上传是 从未删除。 CLI 帮助记录了无主动上传要求。

    证据

    • 摄取在数据库绑定之前写入对象 (ingest/__init__.py:181-214)。
    • 独立协调快照绑定并列出对象键 (storage/object_store.py:139-159)。
    • 维护命令可以删除不在该快照中的所有对象。

    如果协调在对象 PUT 之后但在绑定提交之前运行，则它可以 将活动上传分类为孤立上传，将其删除，并允许摄取提交 指向缺失证据的 AVAILABLE 行。

    需要改变

    使用具有年龄阈值和终结的显式暂存命名空间/状态 协议。协调绝不能删除最近暂存或租用的对象。 协调最终对象发布和绑定恢复与持久状态。

    接受

    屏障测试会暂停 PUT 和绑定提交之间的摄取，同时 协调运行并删除孤儿。活动上传必须存活并且 完成可用，或者在没有可用绑定的情况下失败。

    H07。检查摄取接受违反中央安全和治理声明的记录¶

    状态： 推迟（2026-08-13）。解决受管控版本引用 需要从边缘到中心的合约变更，这与 M1 承诺相冲突 保持当前的信封，所以它是生产范围。试点部署必须 将摄取的记录视为兼容性保留而不是集中记录 管辖；对于单设备试点来说，这种残余风险是可以接受的。

    证据

    • ingest/envelope.py:138-189 验证 Pydantic 形状、设备身份和 仅检查身份。
    • InspectionRecord 对于最终生命周期没有跨字段验证器， 时间戳顺序，或决策映射 (domain/models.py:264-290)。
    • Central 无法解析引用的产品/规则/模型版本或其 验收前的兼容性。
    • Design 05 表示中央验证兼容参考 (docs/design/05-central-server-architecture.md:39-43)。
    • 合同05需要产品配置版本可追溯性 (docs/contracts/05-data-api-and-versioning-contracts.md:20-29,103-113), 但持久化字段可以为空（persistence/schema.py:265）。

    目前接受的示例包括非最终生命周期、之前完成 开始，internal_decision=UNCERTAIN 与 business_result=OK，缺少产品 配置身份和任意未知版本 UUID。

    影响

    受损或有缺陷的设备可以获得经过验证的收据作为证据 该中央后来呈现为受管辖/最终确定，即使它违反了 记录决策和可追溯性模型。

    需要改变

    选择并记录一项明确的参考政策：

    • 受监管的试点：解决组织拥有的已发布版本，验证 产品/规则/模型兼容性和校验和，并拒绝未知版本。
    • 兼容性摄取：接受不可变的未知边缘引用，但标记 检查UNGOVERNED，切勿将收据描述为兼容性 验证。

    在这两种情况下，强制执行最终生命周期、时间戳排序、UNCERTAIN -> NG、 决策/证据的一致性、独特的媒体身份和强制性 生产/试验记录的产品配置标识。

    接受

    阴性摄入测试涵盖了上述所有不变量。无效记录返回 稳定409或422，写不接受的检验/收据，并保留 在适当的情况下进行有界完整性审计。

    H08。检查幂等性和验证不保留请求身份¶

    状态： 已解决（2026 年 8 月 13 日，第二批修复）。

    证据

    • 审核记录保留幂等性密钥，但没有规范的请求哈希 (persistence/schema.py:383-413)。
    • 任何重复该键都会返回旧记录而不比较内容 (repository.py:2109-2123)。
    • 重放路径省略inspection_id，其映射器默认为空字符串 （repository.py:2123、repository.py:4571-4586）。
    • ReviewSubmit不强制执行INCONCLUSIVE的原因，规范化/拒绝 重复的元件代码，或证明属于检验的更正 (api/schemas.py:225-241)。
    • 存在等效的域不变量但被绕过 (domain/models.py:365-414)。

    影响

    可以用矛盾的内容重试相同的密钥并静默返回 第一次评论。重放响应会丢失其检查身份。无效或 不明确的地面实况更正可以进入仅附加记录，而该记录不能 予以修复到位。

    需要改变

    为每个评论密钥保留一个规范的请求哈希。仅重播相同内容 内容；对于更改的内容，返回 409 IDEMPOTENCY_CONFLICT。构建 域审查命令，或在 API 边界重现所有域验证器， 并根据检验证据验证校正组件代码或 受监管的产品版本。

    接受

    • 相同的钥匙/相同的身体返回原始评论并进行正确的检查 身份证。
    • 相同的键/不同的主体返回 409 而没有另一行。
    • INCONCLUSIVE 无原因、重复标准化组件且未知 组件代码返回422。

    H09。速率限制信任攻击者控制的身份并泄漏内存¶

    证据

    • Nginx 附加客户端提供的 X-Forwarded-For (apps/admin-web/nginx.conf:8-14)。
    • API 信任第一个值 (api/rate_limit.py:46-57)。
    • _hits 永远不会驱逐不活动的键 (api/rate_limit.py:17-39)。

    影响

    呼叫者可以旋转伪造的转发值来绕过限制，增长进程 内存，并放大凭证猜测 CPU 成本。运营商也可以相信 当 Compose 静默使用默认值时，配置的限制处于活动状态。

    需要改变

    • 在受信任的外部代理上剥离入站转发标头并设置单个 已验证的客户地址。
    • 忽略转发标头，除非套接字对等方是经过批准的代理。
    • 绑定和过期限制器密钥。
    • 添加更严格的凭据/主体特定的身份验证限制。
    • 明确连接记录的 Compose 设置。

    接受

    测试涵盖欺骗转发链、可信/不可信代理、密钥驱逐、 特定于身份验证的限制、共享 NAT 行为和有效的 Compose 配置。

    H10。代理/主体处理会破坏有效媒体并允许内存放大¶

    状态： 已解决（2026 年 8 月 13 日，第二批修复）。

    证据

    • Nginx 没有 client_max_body_size (apps/admin-web/nginx.conf:1-20)，所以它 标准 1 MiB 限制与 API 的 32 MiB 信封和 16 MiB 冲突 解码媒体限制 (api/settings.py:55-63)。
    • API 在检查配置的绑定之前调用 await request.body() (routers/ingest.py:78-95)。
    • 阻止 SQLAlchemy/MinIO 工作然后在异步路由中运行。

    影响

    合法媒体无法通过附带的代理，通常使用 Nginx HTML 而不是 比输入问题 JSON 更准确。如果在未修复 API 的情况下提高代理限制， 并发请求可以强制将完整的原始 JSON、Base64 和解码的有效负载放入 内存同时阻塞事件循环。

    需要改变

    设置与编码信封开销一致的显式代理边界。强制执行 Content-Length 早期，流到有界缓冲区或临时文件中，上限 并发摄取，并卸载同步数据库/对象存储工作 事件循环。添加容器内存/PID 限制。

    接受

    Compose 集成测试提交接近支持限制的有效媒体和一个 超过每个配置限制的字节。有效上传成功；超大请求 失败并有界413；并发最大请求数保持在批准的范围内 内存/延迟包络。

    H11。备份指令不会创建一致的 PostgreSQL/MinIO 恢复点¶

    状态： 已推迟（2026-08-13）并采取缓解措施。自动快照/PITR 和 真正的 PostgreSQL/MinIO 一致性测试仍在生产范围内；运行手册 现在在两个备份之前停止中央写入，因此恢复的一对共享一个 恢复点，并使用 Compose 服务名称而不是生成的容器 名称。

    证据

    • Runbook 在 API 写入继续时转储 PostgreSQL，然后镜像 MinIO “大约”在同一点 (docs/runbooks/central-backup-restore.md:19-45)。
    • API 仅在恢复期间停止 (central-backup-restore.md:47-54)。
    • 容器名称是硬编码的并且取决于 Compose 项目名称 (central-backup-restore.md:26-27,61-62)。

    影响

    恢复的对可以包含一个可用的绑定，但不包含其对象，或者 没有绑定的对象。这不满足 M1 退出标准 PostgreSQL 历史记录和 MinIO 绑定可以在代表性备份/恢复中保留下来。

    需要改变

    对于试点，在两个备份之前停止中央写入，记录一个共同的 备份 ID/时间、备份两个存储、生成校验和清单、协调 副本，然后才恢复。使用 Compose 服务名称而不是生成的服务名称 容器名称。生产需要单独批准的快照/PITR， 加密、保留和脱离主机策略。

    接受

    当存在上传尝试时，会运行真正的 PostgreSQL/MinIO 恢复测试， 恢复到新的服务，验证每个可用绑定的确切字节， 没有发现无法解释的孤儿，并且无重复地重放收据。

    H12。重复的主体机密可能会被验证为错误的主体¶

    状态： 推迟（2026-08-13）。唯一的凭证身份模型是 生产范围（与H02共享）；单一设备、单一管理员 Pilot 使模糊性几乎无法达到，并且风险被接受。

    证据

    • 设备和管理员身份验证扫描所有加盐哈希并返回 第一场比赛 (repository.py:867-892)。
    • Bootstrap 不会拒绝已被其他设备使用的令牌或 管理员 (repository.py:1073-1137)。

    影响

    如果同一个令牌被意外分配给多个设备或租户， 调用者根据首先返回的匹配行进行身份验证。上传即可 归因于错误的设备/组织。

    需要改变

    使用唯一的公共凭证查找 ID 加上散列秘密，类似于 浏览器会话。将查找 ID 绑定到具有数据库唯一性的一个主体 约束。拒绝重复使用现有凭证的注册/轮换 身份。

    接受

    多租户测试证明重复的凭证注册失败，并且 每个令牌都确定性地解析为一个主体。

    5. 中等严重程度的调查结果¶

    M01。 Pilot 身份验证没有后端授权角色¶

    每个经过身份验证的管理员都可以查看、发布元数据并分配 所需的配置（api/deps.py:84-96、routers/reviews.py:172-230、 routers/metadata.py:408-455、routers/device_configurations.py:116-165）。 这被披露为 M1 延期，但与合同 08 的冲突 提升权限要求 (docs/contracts/08-security-permissions-and-audit.md:11-27)。

    在严格控制的单一试点管理员之外的任何用户之前 已注册，添加默认拒绝组织范围内的审阅者、配置 经理、车队管理员和组织管理员权限。在 在此期间，记录正式的风险接受并保留元数据突变路径 普通观众无法接触到的。

    M02。仅附加/不可变数据仅受存储库约定保护¶

    API 和迁移过程共享 PostgreSQL 所有者凭据 (compose.yaml:46-88)。数据库权限/触发器不会阻止更新或 删除检查、审查、审计行或已发布的版本，以及一些 外键级联删除。设计 14 要求审查/审计行 仅附加到应用程序角色 (docs/design/14-data-model-and-database.md:547-554)。

    使用迁移所有者和受限运行时角色。撤销更新/删除日期 仅附加表并通过显式授予或保护发布转换 数据库强制例程。

    M03。审核条目无法可靠地识别管理员¶

    审查审计写入actor_id=None (repository.py:2180-2189)、元数据审计 帮助者收到用户名，但并不始终坚持管理员 行 ID，以及成功/失败的会话创建未得到完全审核。这落下 未达到合同 08 演员/踪迹要求。

    通过所有突变传递经过身份验证的管理员 ID 和请求 ID 服务；仅保留用户名作为显示快照。审核登录/会话， 审查、发布、分配、轮换和拒绝特权尝试。

    M04。租户所有权并非始终由数据库强制执行¶

    尽管设计 14 的字面意思是“每个 租户拥有的行”声明 (docs/design/14-data-model-and-database.md:464-466)。 许多外键不绑定子组织和父组织。所期望的—— 配置设备存在查找也不在组织范围内 （repository.py:3997-4002）。 HTTP 路由当前解析主体为 范围，但存储库滥用或未来的维护代码可能会创建跨租户 关系。

    添加组织范围的突变谓词和复合租户绑定的外部 安全相关关系的关键，或正式缩小设计不变性 子所有权并证明数据库边界的每条链。

    M05。任意媒体 MIME 反映到管理源中¶

    检查清单可以声明任意 MIME 值，该值存储在 并从经过身份验证的同源媒体路由返回为 Content-Type （ingest/__init__.py:133-145、routers/media.py:68-72）。没有种类/MIME 允许列表、魔字节验证或附件策略。

    按类型将媒体类型列入白名单、验证魔术字节、绑定规范化 MIME 长度，并以不安全的格式作为来自单独的非特权的附件 起源。保留nosniff。

    M06。丢失的对象数据仍然错误 AVAILABLE¶

    协调报告丢失的对象但不转换生命周期，并且 流式传输在丢失对象迭代器失败之前开始 200 响应 被映射（storage/object_store.py:139-159、routers/media.py:48-72）。标记一个 丢失/损坏对象 FAILED 事务性原因/时间并验证 发送响应头之前的可用性。

    M07。元数据唯一性和查询索引不完整¶

    该模式允许包内重复的模型语义版本，并且可以 表面重复的请求列表值的未处理的唯一性失败。查询 索引不涵盖所有合同要求的组织/结果/产品/型号/ 规则路径 (docs/contracts/05-data-api-and-versioning-contracts.md:39-49)。

    添加记录的稳定身份约束，验证重复请求 插入之前的值，将预期约束映射到键入的错误，并验证 具有类似生产基数的查询计划。

    M08。生成的 TypeScript 类型被视为运行时验证¶

    CentralApiClient.request 将任意成功的 JSON 直接转换为 T (packages/typescript/api-client-central/src/client.ts:230-247)。生成 接口仅提供编译时检查。会话标识格式错误， 租户数据、媒体记录、审查修订或所需的配置可以 未选中的 UI 工作流程。

    在客户端边界添加运行时模式以实现安全/工作流程关键 在访问 code/detail 之前响应并验证 RFC 7807 错误。

    M09。管理会话恢复、过期和注销未安全协调¶

    • 受保护的路由没有路由器防护 (apps/admin-web/src/router/index.ts:16-51)。
    • 会话恢复在组件安装后运行（App.vue:18-23），允许 受保护的页面首先发出请求。
    • 401 不会被集中拦截，旧的受保护数据仍然呈现。
    • 导航前注销失败被拒绝（session.ts:51-56、App.vue:25-28）， 而服务器会话可能仍然有效。
    • 正在进行中的请求无法取消，并且可以在之后重新填充页面 注销/会话替换。

    在路由解析之前恢复会话，集中实施全局防护 清除保护状态并在 401 上重定向，在注销中导航 finally 如果撤销失败则发出警告，并按会话绑定/中止请求 一代。

    M10。管理过滤器和列表存在正确性差距¶

    • 概述范围变化竞赛和过时的响应可能会覆盖新范围 (OverviewPage.vue:38-55,137-156)。
    • 概述和历史中的站点/线路负载竞赛。
    • to_at 日期被序列化为午夜，而后端使用 排除上限，不包括所选日期 （OverviewPage.vue:176-188、InspectionsPage.vue:162-176）。
    • 产品/规则/型号/所需配置页面忽略next_cursor；仅 历史/评论页面分页。
    • UTC 标签在多个页面中使用浏览器本地 toLocaleString()。

    添加请求生成/中止处理，在第二天午夜提交以获取 包含日期选择器，实现光标导航，并使用显式 选定的区域设置加上 UTC 格式化程序。

    M11。管理文档和敏感媒体缺乏浏览器/缓存控制¶

    FastAPI CSP 适用于 API 响应，而不适用于 Nginx 提供的 SPA 文档。 apps/admin-web/nginx.conf:1-20 缺少 CSP、frame-ancestors、nosniff、 引荐来源网址、权限和服务器披露控制。经认证的媒体有 没有 Cache-Control: private, no-store (routers/media.py:68-72)。

    在 Nginx/TLS 入口处的 SPA 文档上设置严格的标头以及经过批准的标头 敏感证据的缓存策略。 HSTS 属于实际的 TLS 终止符。

    M12。容器和运行时凭证并非最低特权¶

    • API 使用 MinIO 根凭据 (compose.yaml:31-36,81-84)。
    • 迁移/引导/API 使用相同的 PostgreSQL 所有者。
    • 管理员 Nginx 运行stock root master (apps/admin-web/Dockerfile:21-29)。
    • Compose 缺乏只读文件系统、功能下降、无新权限、 PID/资源限制和有界日志轮换。
    • 基础/服务镜像使用可变标签并且不是摘要固定的。

    使用存储桶范围的 MinIO 服务帐户、受限数据库运行时角色、 非特权 Nginx、容器强化控制、有界日志/资源，以及 在生产曝光之前使用 SBOM 进行摘要固定/扫描的图像。

    M13。 CSRF保护仅依赖于cookie属性¶

    Cookie 验证的注销、审核和配置更新没有 CSRF 令牌或服务器端 Origin/Sec-Fetch-Site 检查。 SameSite=Strict 和 JSON 预检是有意义的缓解措施，但设计 17 需要明确的 CSRF 边界。需要会话绑定令牌或严格的来源/获取元数据 对所有 cookie 验证的突变进行验证。

    M14。准备和维护存在生命周期差距¶

    PostgreSQL/MinIO 就绪调用不会一致地设置有界应用程序 - 级网络超时。 Docker 标记不健康的进程但不重新启动 这仅仅是因为健康检查失败。过期的会话有一个清除存储库 方法但没有预定命令。添加依赖超时、外部警报/ 重新启动策略和受控的过期会话维护作业。

    6. 文件和证据一致性调查结果¶

    D01。对象存储 Runbook 描述了不存在的状态和修复¶

    docs/runbooks/central-object-store-failure.md:11-18,42-52 表示上传失败 离开 PENDING 绑定并协调将其提升为 AVAILABLE 或 将它们标记为FAILED。该实现在 PUT 失败后不会创建任何绑定， 将成功的绑定直接写为AVAILABLE，并且仅进行协调 报告丢失/孤立对象 (storage/object_store.py:139-159)。一样的 过时的 PENDING 声明出现在 docs/runbooks/central-ingestion-backlog.md:53-55。

    实施记录的分阶段生命周期或将两个运行手册重写为 实际的报告/删除和边缘重播行为。请勿声称诚信 当命令仅列出差异时已修复。

    D02。已发布的 Nginx 无法终止 TLS¶

    M1 检查表和部署指南称 TLS 可能会在“admin-web”处终止 nginx 或反向代理” (docs/tasks/C1-central-server-m1.md:720-723, DEPLOYMENT.md:528-531）。自带的Nginx只监听HTTP，没有 证书配置（apps/admin-web/nginx.conf:1-14）。

    明确声明附带的 Nginx 不会终止 TLS。供应一个 可执行的外部 TLS 代理配置文件、证书/CA 程序、可信- 转发策略，以及试点部署前的边缘上传 CA 配置。

    D03。非 Docker 部署无法达到书面准备状态¶

    DEPLOYMENT.md:502-515 不导出设备令牌并且既不运行引导程序也不运行 服务前进行设备注册。准备就绪至少需要一项 管理员和活动设备。将此部分与正确的顺序对齐 已在 QUICKSTART.md:133-149 中显示，包括真实边缘 UUID。

    D04。 M1 功能完整的证据夸大了 CI 并交付了 C3 范围¶

    • 证据表表明每个引用的管理测试都在存储库大门中 (docs/tasks/C1-central-server-m1.md:683-696)。 CI 未设置 CENTRAL_E2E_TOKEN，并且 Compose 支持的流程显式跳过 (apps/admin-web/tests/e2e/smoke.spec.ts:20-24)。
    • C3计划需要审查状态历史过滤器 (docs/tasks/C1-central-server-m1.md:364-367)，但端点没有这样的 参数。
    • 概述要求包括最早的待上传和上传状态 (docs/tasks/C1-central-server-m1.md:590-596)，但仅中央公开 计数和平均上传延迟 (api/schemas.py:191-199)。

    将状态更改为“手动/本地证据，非 CI 强制”并保留日期 工件，或添加启动 PostgreSQL/MinIO/central/admin-web 的 CI 作业， 断言不跳过，并运行完整流程。交付或正式放弃失踪 在调用 C1a-C6 之前完成 C3 过滤器/度量。

    D05。操作手册中的中央待办事项信号不是中央可观察量¶

    docs/runbooks/central-ingestion-backlog.md:5-8,59-64 引用最早的 未收到的边缘任务期限、重试率和最早的待上传。中央确实 不摄取边缘任务状态并且不公开此类指标。独立边缘拥有 来自中央拥有的接收/错误/延迟信号的发件箱信号并提供 每个触发器的可执行 API/日志/SQL 查询。

    D06。设计 15 种混合实现的 M1 和生产目标 API¶

    docs/design/15-rest-api-and-events.md:13-18,116-175 呈现 OIDC/RBAC， 多部分媒体启动/完成、审查状态过滤和验证 除了当前路线之外的模型发布，但没有足够明确的信息 实施覆盖。 M1 使用一个有界信封和声明性模型 无需服务器端工件验证的注册。

    添加从提交的 OpenAPI 生成的“已实现的 M1 API”表。移动OIDC， 完整角色、分段/可断点续传、中央 WebSocket、报告/用户/审计 API 和工件验证出版物在明确标记的生产下 目标。

    D07。模型 PUBLISHED 语义与发布合约冲突¶

    7. 测试和验证差距¶

    现有的测试很广泛，但以下差距解释了为什么绿门 没有检测到高严重性的发现：

    • 没有真正的 PostgreSQL 并发测试涵盖所需配置的 CAS， 元数据发布，或在完整生产语言下审查附加。
    • 大多数存储库测试使用 SQLite metadata.create_all() 而不是应用 每次 Alembic 迁移并将迁移的模式与元数据进行比较。
    • 没有摄取测试拒绝非最终生命周期、反向时间戳、 UNCERTAIN -> OK、缺少产品配置、未知的受管版本、 或不兼容的规则/模型/产品绑定。
    • 成功后没有对象存储测试模拟静默截断/损坏 PUT 或验证持久的 SHA-256。
    • PUT 和绑定提交之间没有协调竞争测试暂停。
    • 没有审查测试检查相同的钥匙/不同的身体，重播检查ID， 不确定的原因、重复的标准化更正或未知的组件。
    • 不存在授权矩阵，因为每个管理员都有相同的权限 有效特权。
    • 无转发头/密钥驱逐/多工作人员/身份验证速率限制测试 存在。
    • 没有 Compose 测试上传超过 1 MiB 或在配置的 API 边界的媒体。
    • 自动备份测试以 SQLite/内存中为重点；真正的 PostgreSQL/MinIO 一致性不是 CI 强制执行的。
    • 没有测试证明运行时数据库角色无法更新/删除检查， 评论、审计行或已发布的元数据。
    • 没有API客户端传输测试涵盖格式错误的JSON/问题主体，401， cookie/会话转换、中止或响应运行时验证。
    • 没有管理组件/E2E 测试涵盖失败的注销、过期、过时的请求、 包含日期、列表分页、租户切换、媒体缓存策略或 可达性。
    • 实质性管理剧作家流程将被跳过，除非 提供CENTRAL_E2E_TOKEN； CI 目前仅运行登录烟雾。

    9. 残余风险和明确延期¶

    仅当部署保持不变时，以下内容才仍然是合法的 M1 延期 严格控制的试点和文件并不意味着：

    • 没有 OIDC、MFA、成熟的用户生命周期或完整的组织范围的 RBAC。
    • 无设备 PKI/mTLS 或自动凭证生命周期。
    • 无生产 HA、水平速率限制协调、最终 RPO/RTO、PITR、 或连续复制。
    • 无中央保留/合法保留/删除执行或最终数据驻留 控制。
    • 无恶意软件扫描或最终媒体数据分类政策。
    • 无服务器端模型工件验证、签名验证、远程 包传送、激活确认或回滚编排。
    • 没有可恢复的大媒体协议。
    • 没有生产能力/浸泡证据、分区策略或工作拓扑。

    这些延迟在更广泛的网络曝光之前成为发布阻碍， 多个人类用户、多个组织、生产证据保留、 或远程配置/模型管理。

    12. 飞行员决策门¶

    中央实现有一个实质性的、类型化的、经过充分测试的 M1 基础。边缘优先的安全边界保持不变，并且幂等 检查路径比典型原型更强。所有十二个高严重性 调查结果现已处理：七个已解决（H01、H03、H04、H05、H08、H09、 H10）和五个被推迟（H02、H06、H11 和缓解措施；H07、H12 到 生产范围）。

    试点准备情况现在取决于部署上下文（请参阅 SECURITY.md “部署上下文”）：

    • 网络部署：推迟的操作项目（凭证轮换、 分阶段媒体生命周期、快照/PITR 备份）保持开放状态，因此试点 在关闭之前，不应将其暴露在严格控制的网络之外。
    • 工厂内网+受控Tailscale：以内网为边界， 专门的站点运营商和仅维护的 Tailscale 通道， 推迟的运营项目是可接受的风险并已采取缓解措施，并且 飞行员可以根据第 13.2 节检查清单进行操作。 H07（受管制 摄入参考）在两种模式下仍然保持生产范围。

    推荐的状态措辞：

    Central M1 功能集已实现并通过当前静态/单元 大门。所有 12 个 AUDIT-002 高严重性调查结果均得到解决或推迟 采取缓解措施。厂内网下可试点上线 + 由专门的站点操作员控制的 Tailscale 部署模式；网络 部署使推迟的操作项目保持开放状态。这不是一个生产 释放并保持在边缘决策路径之外。

    此次审核未修改任何生产或试点代码。
