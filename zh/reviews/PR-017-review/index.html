    PR-017 评论：耐用边缘上传发件箱和调度程序¶

    范围¶

    PR #17 的代码审查（针对 main 的 dev，提交 7c0b9b9）涵盖 事务发件箱、SQLite 租约处理、上传接收器、运行时接线、 配置、文档和 Contract-06 测试覆盖率。

    审查的相关要求：

    • docs/design/12-local-storage-and-retention.md
    • docs/design/13-upload-and-synchronization.md
    • docs/design/14-data-model-and-database.md
    • docs/design/decisions/ADR-005-local-first-storage-and-delayed-upload.md
    • docs/contracts/01-architecture-boundaries.md
    • docs/contracts/04-edge-storage-upload-contracts.md
    • docs/contracts/06-testing-quality-and-ci-contracts.md

    合并决策¶

    已解决 - 所有发现均已在 dev 上修复和验证（PR #17 已更新）。

    最初的审查发现 PR 无法安全地传输二进制媒体， 没有将检查持久性和任务创建作为一个可恢复单元， 允许过时的工人覆盖新的租约持有者，并且可以报告 检查同步，无需经过验证的服务器收据或其要求 媒体。正常的 serve 路径也没有提供配置的方法 调度程序，而编程 HTTP 路径允许纯文本凭证和 证据传输。下面的每个发现 (F1-F8) 现在都有一个修复提交 回归测试，并且完整的质量门通过了。

    解决状态¶

    每个发现都在其自己的提交中通过回归测试固定在 dev 上 修复前失败，修复后通过：

    • F1 - HttpUploadSink 发送带有字节的 base64.b64encode(payload) 打字正文的大小；模拟传输测试往返非 ASCII 字节 准确并验证大小和校验和 (4f8b9b6)。
    • F2 - EdgeRepository.persist_inspection_and_enqueue_uploads 提交 不可变的投影、媒体、证据和所有幂等上传任务合而为一 SQLite 事务；运行时投影、开发导入和启动 协调将其用于每个捆绑包，因此搁浅的 LOCAL_ONLY 记录是 修复而不是跳过，并且中断的 force_close 记录 镜像 (53a6385)。
    • F3 - claim_upload_tasks 在中保留唯一的每个任务防护令牌 lease_owner（迁移0004）并返回ClaimedUploadTask；每个 终端或重试更新需要 IN_PROGRESS 加上匹配的令牌和 返回受影响的行数，因此迟到的工作人员无法覆盖回收的行数 任务（4c651b0）。
    • F4 - MEDIA 任务只有在 INSPECTION 任务完成后才能领取 SUCCEEDED，先订购检查任务；测试证明没有媒体 请求在检查收据之前发送，并且介质在后面被阻止 失败的元数据保留为 PENDING (6e4190d)。
    • F5 - HttpUploadSink 解析有界类型的收据并接受 2xx 仅当它回显幂等键、对象、种类、字节大小和 校验和；已验证的收据和中央对象 ID 会保留（迁移 0005）；检查同步根据每个所需任务重新计算为 QUEUED/PARTIAL/SYNCED/FAILED (d956493)。
    • F6 - UploadSettings 加上 CLI/env 连接 (AV_EDGE_UPLOAD_*) 激活 通过支持的 serve 路径进行调度；配置好的本地接收器 端到端地排水，省略的配置是明确可观察到的 禁用状态，并且无效的数字配置启动失败（ccdefc8）。
    • F7 - 上传端点必须是 HTTPS，具有非空主机且没有嵌入 凭证（仅在显式开发标志下的明文）；水槽使用 单独的 AV_EDGE_UPLOAD_TOKEN 凭据，而不是查看者 api_token， 测试证明查看者凭据从未发送（406150e）。
    • F8 - 注入的时钟锚定响应/失败的每个转换 时间，因此缓慢的请求不会侵蚀Retry-After；确定性测试 验证 next_attempt_at = response_time + 60 (81fc6f4)。
    • 决议后强化 - 最终审查弥补了四个小差距 原始修复：收据现在需要匹配的尺寸/校验和和介质 成功前的中心对象 ID；存储库同步需要持久验证 收据元数据； create_app 重新验证程序化上传设置并 限制明文开发HTTP为环回；介质大小和显式零 带宽配置现在失败关闭（后续提交待处理）。

    阻塞结果¶

    F1。 HTTP 媒体上传会损坏所有非 ASCII 有效负载¶

    严重性： P1/高

    地点：

    • apps/edge-service/src/assemblyvision_edge/upload/scheduler.py:103-110
    • apps/edge-service/src/assemblyvision_edge/upload/scheduler.py:276-288

    HttpUploadSink.upload() 标记主体字段 payload_b64，但生成它 与payload.decode("ascii", errors="ignore")。 JPEG、PNG、剪辑和视频 字节不是 ASCII；这会默默地删除每个无效字节。服务器因此 从其 SHA-256 记录在其中的有效负载接收不同的数据 任务。随后 2xx 响应标志着媒体任务成功。

    这违反了合约 04 中的媒体校验和和完成要求 第 6 节和设计 13.3/13.4。

    分辨率：

    1. 在发送字节之前定义中央摄取有效负载合同。对于 当前 JSON 传输，编码为 base64.b64encode(payload).decode("ascii")；对于制作媒体，更喜欢 记录的预签名/可恢复二进制上传路径而不是嵌入 JSON 格式的大型媒体。
    2. 在类型化请求模型中包含媒体字节大小和 SHA-256，并具有 中央端点在解码或接收流后验证两者。 3.应用有界的request-body/media-size策略，这样Base64扩展就不能 耗尽工人的记忆。

    验收标准：

    • 测试通过上传包含 b"\\x00\\xffJPEG\\x80" 的有效负载 httpx.MockTransport，Base64解码接收到的字段，并断言准确 字节相等并匹配 SHA-256。
    • 服务器端合约测试拒绝格式错误的 Base64、错误的字节大小和 没有创建/绑定对象的校验和错误。
    • 除非收到字节和校验和，否则媒体任务不可能成功 匹配任务元数据。

    F2。检查投影和发件箱创建是单独提交的，恢复会跳过搁浅的记录¶

    严重性： P1/高

    地点：

    • apps/edge-service/src/assemblyvision_edge/api/state.py:299-302
    • apps/edge-service/src/assemblyvision_edge/persistence/reconcile.py:107-122
    • apps/edge-service/src/assemblyvision_edge/persistence/repository.py:194-398
    • apps/edge-service/src/assemblyvision_edge/persistence/repository.py:715-804

    upsert_inspection() 在 enqueue_inspection_uploads() 开始之前提交 第二笔交易。如果入队失败，或者进程在中间终止， 检查仍然是LOCAL_ONLY，没有上传任务。下次启动时， reconcile_output_root()仅在upsert_inspection()返回时调用enqueue "inserted"；相同的搁浅记录返回 "unchanged" 并且是 永久跳过。同样的问题会影响在此 PR 之前保留的记录。

    这破坏了设计 12.4、ADR-005 和 合同 04 第 3 节：已完成的检查可以在没有要求的情况下存在 上传任务。

    分辨率：

    1. 将公共的两次调用工作流程替换为一次存储库操作，例如 例如 persist_inspection_and_enqueue_uploads(record)，验证， 插入不可变的投影/媒体/证据，插入所有幂等 任务，并在一个 SQLite 事务中转换同步状态。
    2. 让reconcile_output_root()为每个有效的调用幂等操作 捆绑，而不仅仅是该通道上新插入的记录。它必须修复任何 LOCAL_ONLY 记录和报告冲突，不进行部分突变。
    3. 为不可变的内容冲突保留当前的安全行为 重复的任务键。

    验收标准：

    • 每个任务插入的故障注入都会回滚检查、证据、 媒体、任务行和状态转换在一起。
    • 数据库预先植入了有效的 LOCAL_ONLY 检查，但没有任务增益 协调后，只有一项检查任务和每个媒体项目一项任务。
    • 在原始投影提交之后和入队之前模拟崩溃， 然后重新启动，将发件箱修复一次。
    • 完全排队的记录的协调不会创建重复的任务。

    F3。租约到期没有所有者/令牌围栏，因此迟到的工作人员可以覆盖较新的工作人员¶

    严重性： P1/高

    地点：

    • apps/edge-service/migrations/versions/0003_upload_lease.py:19-24
    • apps/edge-service/src/assemblyvision_edge/persistence/repository.py:806-944
    • apps/edge-service/src/assemblyvision_edge/upload/scheduler.py:209-256

    迁移仅存储lease_expires_at；它不存储所需的 租赁所有者/令牌。任务被回收后，第一个worker可以从 缓慢的请求和所有三种完成方法仅通过以下方式更新 upload_task_id。其迟到的SUCCEEDED、重试或永久失败更新可以 覆盖第二个工作人员产生的状态。这可能会错误地标记任务 成功，清除新租约，或将验证结果更改为失败。

    合同 04 第 4 节和设计 14.5 要求租赁所有者和到期日 当任务正在进行时。

    分辨率：

    1. 通过 Alembic 迁移添加 lease_owner （每个声明的唯一 UUID/令牌） 并将租赁信息仅公开给内部工作人员模型，如下所示 适当的。 2.让claim_upload_tasks()生成并原子地持久保存一个唯一的令牌 对于每个已声明的任务，返回带有声明的令牌。
    2. 每个终端都需要status = 'IN_PROGRESS' AND lease_owner = :token 或重试更新。将零个受影响的行视为丢失的租约并且不发生变化 检查同步状态。
    3. 考虑对允许超过配置租约的上传进行租约续订； 否则将请求/上传持续时间限制在其下方。

    验收标准：

    • 两名模拟工人在租约到期后领取相同的任务；迟到的第一 工人在第二次索赔后无法修改任务或检查状态。
    • 当前所有者仍然可以转换一次成功、重试或 永久性故障。
    • 迁移、存储库和模式测试证明 lease_owner 和 lease_expires_at仅由匹配的所有者清除。

    F4。媒体任务可以在检查元数据任务之前运行¶

    严重性： P1/高

    地点：

    • apps/edge-service/src/assemblyvision_edge/persistence/repository.py:725-743
    • apps/edge-service/src/assemblyvision_edge/persistence/repository.py:829-866
    • apps/edge-service/src/assemblyvision_edge/upload/scheduler.py:207-238

    检查和所有媒体任务都会收到相同的created_at。然后声称 按随机 upload_task_id 排序关系，因此可以先发送媒体任务。的 设计序列需要在媒体绑定之前摄取元数据（设计 13.4/13.7）。正确拒绝未知检查介质的中央端点 具有 404 的将被 HttpUploadSink 归类为永久故障，即使 尽管元数据稍后会在同一批中成功。

    分辨率：

    1. 明确地建模依赖关系：媒体任务仅在其父任务之后到期 检验任务已验证成功收货，或使用单 检查会话状态机，在发布媒体之前上传元数据 工作。
    2. 将媒体保留在 PENDING 中（有依赖性原因），而不是处理 预元数据服务器响应作为永久证据失败。
    3. 使用服务器确认的所需媒体信息来确定哪些媒体 任务必须运行，而不是假设每个工件都可以立即被接受。

    验收标准：

    • 在元数据证明没有媒体之前，使用返回 404 的端点进行测试 发出请求直至存在匹配的检验收据。
    • 元数据首先成功，随后需要媒体耗尽，并且没有任务 仅仅因为其母体尚未被摄取而被标记为永久。
    • 元数据和媒体之间的重新启动保留了依赖性并完成 仅剩余媒体任务，不重复。

    F5。任何 2xx 响应都被视为已验证成功，并且检查状态变为 SYNCED，而媒体仍处于待处理或失败状态¶

    严重性： P1/高

    地点：

    • apps/edge-service/src/assemblyvision_edge/upload/scheduler.py:119-120
    • apps/edge-service/src/assemblyvision_edge/upload/scheduler.py:234-257
    • apps/edge-service/src/assemblyvision_edge/persistence/repository.py:869-903
    • apps/edge-service/src/assemblyvision_edge/persistence/schema.py:112-132

    HTTP接收器接受空的或任意的2xx主体并替换本地 幂等密钥作为收据。没有打印的中央收据、中央对象 ID、 服务器确认的字节大小，或验证或保留校验和。独立地， mark_upload_succeeded() 一旦完成，就将整个检查设置为 SYNCED 元数据任务成功，包括当其所需的媒体仍待处理或 已达到PERMANENT_FAILURE。

    这违反了合同 04 第 6 节（验证完成、存储中心对象 标识符，仅在确认成功后更新）并滥用记录的 设计14中的PARTIAL/SYNCED/FAILED同步状态。它还使得 未来的保留无法证明每个所需的工件都收到了 已验证收据。

    解决：

    1. 定义中央摄取 API 拥有的类型化请求/接收合约。 收据必须标识幂等性密钥、检查/对象、不可变 内容哈希、字节大小、校验和以及中心对象标识符，其中 适用。
    2. 解析有大小限制的响应；仅当以下情况时才将任务标记为成功 收据与其任务和有效负载完全匹配。保留经过验证的收据并 专用列/表中的中心对象 ID。
    3. 根据所有必需的任务计算检查同步状态： QUEUED 当工作尚未完成时，PARTIAL 在元数据之后以及剩余的 媒体，SYNCED仅在所有必需的任务已验证收据后，以及 FAILED 当所需任务永久失败时。不要让这种状态 授权自行保留，无需存储经验证的收据。

    验收标准：

    • 空、格式错误、过大、幂等键错误、对象 ID 错误、错误 校验和以及错误大小的 2xx 响应使任务可重试或失败； 没有人能将其标记为成功。
    • 成功的媒体任务存储中心对象标识符并进行验证 收据元数据。
    • 元数据成功，待媒体报道PARTIAL；所需的媒体 永久性故障报告FAILED；仅所有必需的任务已验证成功 报告SYNCED。
    • 保留测试证明待处理、部分、失败和无收据的任务不能 使媒体删除符合条件。

    F6。部署的serve命令无法配置或启用上传¶

    严重性： P1/高

    地点：

    • apps/edge-service/src/assemblyvision_edge/cli.py:82-105
    • apps/edge-service/src/assemblyvision_edge/cli.py:266-290

    ServerSettings 包含 upload_base_url 和 upload_sink_dir，但是 正常的 assemblyvision-edge serve 命令没有标志或环境映射 对于设置、超时、重试策略、租用期限、凭据或 带宽。 _run_serve() 因此总是使用两者来构造设置 目的地未设置，并且调度程序始终在支持的 部署入口点。尽管 PR 声称任务会无限期累积 工人已连线。

    这也默默地破坏了设计 13.8 的站点配置和可观察性 要求而不是故意禁用同步 明确说明。

    分辨率：

    1. 在边缘配置合约中添加类型化上传配置部分 （端点、单独的凭证源、连接/请求超时、重试、 租约、工作线程并发/批量、带宽和显式本地开发 水槽）。
    2. 在生产配置加载器中解析并验证它，然后连接它 通过支持的 serve 命令/环境。不要将凭据放入 CLI 进程参数或提交的配置文件。
    3. Surface 调度程序配置/运行状况和显式 sync_ready/alert 状态，以便操作员可以区分故意禁用的接收器和 破碎的工人或不断增长的队列。

    验收标准：

    • 端到端serve配置测试证明配置的本地接收器 启动工作人员并清空发件箱任务。
    • HTTPS 集中配置以配置的 HttpUploadSink 开头 超时/重试/租用值；省略的配置使其禁用并且 产生一个明确的可观察的禁用状态。
    • 无效端点、凭证引用、超时、重试、租用和带宽 值启动失败，并出现可操作的配置错误。

    F7。中央上传接受 HTTP 端点和边缘查看器令牌¶

    严重性： P1/高

    地点：

    • apps/edge-service/src/assemblyvision_edge/api/app.py:103-105
    • apps/edge-service/src/assemblyvision_edge/api/settings.py:22-26
    • apps/edge-service/src/assemblyvision_edge/upload/scheduler.py:82-116
    • apps/edge-service/tests/test_upload_scheduler.py:347,363

    HttpUploadSink 接受任何 URL，包括 http://，并且应用程序 传递本地查看器 API 令牌作为中央持有者凭证。已配置的 明文端点因此会收到检查证据和 本地查看者令牌。这与设计 13.8 的 TLS、每设备凭证相矛盾， 最低权限和配置要求。现有的单元测试编码 将不安全的 HTTP 情况视为有效行为。

    解决：

    1. 在配置加载时验证 upload_base_url 为 HTTPS，包括 非空主机和批准的路径。仅通过显式、 仅测试/本地开发模式无法在生产版本中运行或 非环回部署。
    2. 引入独特的最低权限上传凭证参考；从不 重用api_token，它对本地仪表板客户端进行身份验证。
    3. 在镜像外配置证书验证和轮换，并确保 记录编辑端点凭据和授权标头。
    4. 更改 HTTP 测试以使用带有模拟传输的 https://central.invalid 和 添加针对被拒绝的纯文本 URL 和令牌分离的验证测试。

    验收标准：

    • 生产配置拒绝 http:// 和格式错误的 URL 应用程序启动调度程序。
    • 配置的 HTTPS 接收器接收专用上传凭证；当地的 查看者凭据永远不会包含在其 Authorization 标头中。
    • 测试涵盖证书验证配置并证明凭据确实有效 不会出现在调度程序/应用程序日志中。

    F8。重试期限是从批次开始计算的，而不是从失败响应计算的¶

    严重性： P2 / 中

    地点：

    • apps/edge-service/src/assemblyvision_edge/upload/scheduler.py:209-215
    • apps/edge-service/src/assemblyvision_edge/upload/scheduler.py:244-256

    run_once() 在加载有效负载并执行 HTTP 之前捕获 now 请求。 _process() 使用旧时间创建 next_attempt。慢读 或请求可以消耗服务器的部分或全部 Retry-After 持续时间，因此 下一个请求发生得太早。这违背了记录在案的节流策略 设计13.5。

    分辨率：

    1. 在接收器返回或上升后立即捕获重试基准时间。
    2. 根据该响应/故障时间计算抖动和Retry-After。
    3. 保持任务的updated_at与相同的转换时间一致。

    验收标准：

    • 接收器延迟超过一秒并返回Retry-After: 60 产生next_attempt_at >= response_time + 60 seconds。
    • 传输错误和永久性有效负载故障保留其现有状态 分类。
    • 确定性时钟/注入时间源使此行为可测试 没有时间敏感的睡眠。

    剩余票据¶

    • 设计 13.5/13.9 还需要断路器、有限带宽 执行、队列年龄/计数/字节指标、成功/失败率、延迟、 吞吐量和最后一次联系的可观察性。配置面为 带宽存在，但节流和断路器仍然存在 在启用站点上传之前连接试点完成范围。
    • 中央摄取端点及其经过合同验证的媒体绑定 还不存在；这里实现的边缘侧接收合约定义了什么 端点必须返回，其余的 served 集成测试 属于该端点。
    • EdgeRuntime._run_instance_loop()现在持续中断force_close 通过原子投影 (53a6385) 进行记录，缩小了之前的差距。
    • 验证期间观察到的预先存在的潜在问题（本次未引入 PR): migrations/env.py 在 alembic.ini 上调用 fileConfig 默认disable_existing_loggers=True，标记每个assemblyvision.* 第一次迁移后禁用记录器，因此应用程序自己的 LogBuffer 没有捕获任何应用程序日志记录。 在 E1 边缘可观测性中解决 里程碑：fileConfig(..., disable_existing_loggers=False) 保留应用程序 启用记录器，回归测试证明 /api/v1/logs 返回 新迁移的数据库上的应用程序记录。
