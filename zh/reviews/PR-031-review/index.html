    PR-031 审查：边缘本地人工审查（可选，ADR-016）¶

    1. 审查决定¶

    状态：已解决

    边缘局部人工审核功能 (feat/edge-local-human-review) 是 满足所请求属性的严格附加的可选功能： 它是非侵入性的（没有现有的记录、端点、流程、合同或前端 逻辑改变），跨已建立的层解耦，并建立在 仅附加模型可以干净地扩展到未来的中央审查流程。

    审查未发现 P1 阻滞剂。 P2安全加固项1个（无限制 component_corrections 列表），一个 P2 功能差距（审核队列显示 未清项目的原因代码为空），以及一组 P2 文档/合同 一致性问题已在审查通过中确定并修复（第 3 节）。 其余可接受的权衡（自称审稿人身份，不审稿） 尚未上传同步，没有审查保留政策）在 ADR-016 中明确，并且 下面第 4 节。

    2. 范围和证据¶

    已审核分支：feat/edge-local-human-review（进入 main），7 次提交 审核通过修复：

    审查方法：四次平行分代理审查，涵盖文件/合同 其次是一致性、安全性、解耦/非侵入性和可扩展性 通过综合修复通道。

    主要要求：

    • Human-in-the-Loop Operations，部分 24.1-24.14。
    • ADR-016: Edge-Local Human Review。
    • REST API and Events，第 15.3.3 节。
    • Data Model and Database，部分 14.3/14.5。
    • Contract 01: Architecture Boundaries。
    • Contract 05: Data, API, and Versioning。

    审核通过时执行的验证（全部通过）：ruff check/format， mypy（173 个文件）、pytest（退出 0）、api-client build/lint/test（60 个测试）、 edge-web build/lint/test（49 次测试）、edge-web Playwright e2e（15 次通过）、 mkdocs build --strict和git diff --check。

    3. 所需调查结果¶

    3.1 审核期间修复¶

    PR31-F01 - P2：记录的 422 代码 REVIEW_VALIDATION_FAILED 是死代码，构造可以 500¶

    ReviewRecord 结构位于 try 之外 api/routers/reviews.py，因此域级验证错误将表现为 内部 500 而不是记录的 422。通过移动结构来修复 在将 ValidationError 映射到 422 REVIEW_VALIDATION_FAILED 的 try 内 （请求体路径保留全局VALIDATION_FAILED，匹配 记录 15.3.3 错误）。

    PR31-F02 - P2：设计 24.3“已更正 OK”术语与已实施的处置集不同¶

    设计 24.3 列出了 NG 结果的“已纠正 OK”，而实现 （和 ADR-016/15.3.3）使用 CONFIRMED_OK 进行 NG 到 OK 的更正和 OK 确认；没有 CORRECTED_OK 值。将设计 24.3 更新为 “确认OK”并记录原始机器结果记录在案 区分这两种情况。经验证，处置集在各个方面都相同 allowed_review_dispositions()、ReviewPanel.vue 和 MockApiClient.allowedDispositions()。

    PR31-F03 - P2：边缘审核队列显示未清项目的原因代码为空¶

    list_review_queue 源自最新评论的快照中的 reason_summary， 在任何评论存在之前它是空的——正是评论者的分类数据 需要开放的 NG 项目。修复读取检查自身机器原因 代码（_decision_reasons），与模拟客户端一致。还添加了一个 test_review_queue_reports_review_state 未清项目代码的断言。

    PR31-F04 - P2：无界component_corrections列表（安全强化）¶

    SubmitReviewRequest 和 ReviewRecord.component_corrections 接受 无界列表；一个大的主体将被缓冲并存储在一个 TEXT 单元中 具有读取放大功能。在 API 架构中添加了 max_length=64 领域模型；重新生成 OpenAPI 和生成的 TS。

    PR31-F05 - P2：设计 14 没有记录边缘 review_records 表或边缘审查模型¶

    设计14仅记录了中央ReviewRecord（用户FK，修订链）， 而边缘表（迁移 0008）是一个独特的仅附加模型。添加了 review_records 行到 §14.5 边缘模式表以及 §14.3 中的注释 将边缘（调用者提供的审阅者，supersedes_review_id）与 未来的中心模型。

    PR31-F06 - P2：手写合约和生成合约之间的 TS 可空性/请求类型差异¶

    types.ts处理reason/note/original_reason_codes/ component_corrections/supersedes_review_id 始终存在，而 生成的 api.ts 将它们标记为可选，并重用 SubmitReviewRequest ComponentCorrection 而不是生成的 ComponentCorrectionRequest。 在types.ts中添加了ComponentCorrectionRequest别名（手写的 类型仍然是准确的电汇合同；产生的松动被接受 现在记录在 types.ts 中）。

    PR31-F07 - P2：格式错误的审阅队列游标可能返回 500 而不是 400¶

    _decode_cursor 没有拒绝非 dict JSON 负载或捕获 TypeError，所以 GET /reviews 上精心设计的 ?cursor= 转义了 InvalidCursorError。固定于 共享助手（同时强化 list_inspections/list_uploads），现在 提高400 INVALID_CURSOR。

    PR31-F08 - P2：模拟客户端与服务器验证不同¶

    MockApiClient.submitReview 没有强制审查者非空或者 INCONCLUSIVE-requires-reason 规则服务器适用。添加了相同的检查 (422 VALIDATION_FAILED) 加上一致性契约测试，断言每个 记录的处置是已知的 REVIEW_DISPOSITIONS 值。

    PR31-F09 - P3：通过审阅者姓名进行日志注入¶

    repository.submit_review 使用 %s 记录自由文本审阅者，允许 控制字符伪造日志行（CWE-117）。改为%r （repr-转义），匹配 retry_upload 模式。

    PR31-F10 - P3：填补文档空白¶

    • §15.2.1 一般授权规则现在命名为 ADR-016 审核提交例外 到“改变路由需要operator/edge_admin”语句。
    • §15.3.3幂等性单元从无意义的“确定性每 review_id”改为“无：每次调用都会附加一条新评论”，并且 409 REVIEW_CONFLICT 被记录为还涵盖了 supersedes_review_id 没有对该检查进行审查。
    • §16.3信息架构表获得了/review路由行。
    • ADR-016 决策 2 现在明确推迟设计 24.3“系统异常” 行（和操作故障处置），直到存在中央审查。

    3.2 接受的权衡和推迟的工作¶

    PR31-T01 - P2：审阅者身份是呼叫者提供的自由文本（模拟表面）¶

    任何持有单一查看者凭证的人都可以记录归因于的评论 任何审稿人姓名； API 不会将名称绑定到经过身份验证的会话。 这是明确的、公认的 ADR-016 决定 3/7（无边缘角色模型），并且 审核日志使用 repr 转义身份。服务器派生的操作员身份或 受信任的操作员白名单是已记录的未来强化措施。

    PR31-T02 - P2：审核记录还没有上传/同步管道¶

    review_records 没有 device_id/synchronization_status/payload_hash，并且 不会为评论创建 upload_tasks 行。 ADR-016 §5 将此记录为 开放问题和设计 24.11 允许“稍后同步审核项目”。因为 评论仅附加于本地生成的 review_id、未来的同步地图 直接到现有的发件箱模式（幂等键 review:{device_id}:{review_id}) 没有检查内容哈希 机械。延迟，而不是阻塞。

    PR31-T03 - P3：无评论保留政策或提交率限制¶

    review_records 无限增长（仅追加）并且提交不受限制 速率受限； list_inspection_reviews 未分页。 MVP 可接受 规模；保留/压缩策略和速率限制将在未来加强。

    PR31-T04 - P3：性格演变涉及~8个手动维护的位置¶

    添加配置需要在域枚举 allowed_review_dispositions 中进行编辑， 生成的 OpenAPI/TS（CI 检查）、types.ts、validate.ts、 MockApiClient.allowedDispositions 和两个 Vue 组件。该评论添加了一个 一致性契约测试；从生成的派生 REVIEW_DISPOSITIONS schemas 是推荐的下一个重构。

    PR31-T05 - P3：评论提交通过查看者凭证暴露（合约08偏差）¶

    合同 08 §3 列出了“追加或取代人工审查的行为” 需要提升权限的操作中的“处置”，但边缘审查 提交内容有意使用现有的单一查看者凭据 ADR-016 决策 3/7（无边缘角色模型）。查看者权限是 深思熟虑的操作员便利决定：审查者必须能够 直接从操作员仪表板处置 NG 案例，无需 额外的凭证，并且边缘没有角色系统来强制执行单独的凭证 reviewer角色。这与公认的模拟表面相同 PR31-T01。现在没有做出任何行为改变；未来的 RBAC ADR （reviewer 边缘角色，或单独批准的 PLC/MES 部署 合同）解决了偏差，设计 15 §15.2.1 已经记录了 例外。

    4、确认无创、解耦¶

    • Domain：仅附加在ModelManifest之后的附加模型； InspectionRecord 未受影响。
    • 持久性：inspections表未受影响；新的 review_records 表 + 附加迁移 0008 (down_revision=0007)；添加了存储库方法， 现有方法字节相同。
    • API：12 个现有路由器未受影响（0 行差异）； app.py获得一 导入 + 一个 include_router 条目； OpenAPI diff 删除了 0 行。
    • 检查流程：pipeline.py、state.py、config.py、规则、引擎： 0 行差异。检查帧/视频、持久性、上传和保留 行为不变。
    • 前端：InspectionDetailView.vue +8 行（一条导入，一条添加 <ReviewPanel>); App.vue +1 导航链接； router/index.ts +1 路线。新 组件仅导入 @assemblyvision/api-client、@assemblyvision/ui、 vue，以及现有的客户端工厂 - 没有边缘网络 → 边缘服务导入。
    • api-client：三个新方法/类型/验证器；现有的签名和 模拟数据未受影响。
    • 依赖方向尊重架构边界（域→边缘 服务→ API 客户端→ Web）。

    5. 安全评估¶

    • SQL 注入：干净（所有值绑定；f 字符串仅在模块级别 表名常量）。
    • 光标过滤器旁路：干净（光标中嵌入了 SHA-256 过滤器指纹）。
    • 输入边界：F04 之后清除（reason 200、note 2000、reviewer 128、 component_corrections≤64； extra="forbid"；剥离验证器）。
    • XSS：干净（无 v-html；所有审阅者/原因/注释/处置均通过 逃脱了Vue插值； CSP script-src 'self'）。
    • 防篡改：original_business_result/internal_decision/ reason_codes 是服务器从存储的检查中派生的，而不是 请求；重新检查处置兼容性和取代所有权 在一笔交易中原子地进行。
    • Auth 接线：在 Depends(require_viewer) 下评论路由器；会话cookie HttpOnly + SameSite=strict（无 CSRF 暴露）； 401 测试覆盖。
    • 迁移安全：附加create-table +索引，FK到inspections， schema.py/migration 逐列镜像。

    6.可扩展性评估¶

    • 仅附加记录语义和单一权威域配置 政策使未来的裁决/重新分配附加（新记录类型或 列），从不就地更新（设计 24.6/24.7）。
    • Schema进化使用已建立的Alembic链；添加 adjudication_state/assignment_history 随后跟在 0004/0006 后面 op.add_column 模式。
    • 队列排序/抽样（设计24.4优先级和OK审核抽样）是 未来主要变化；键集光标绑定到当前 (completed_at, inspection_id) 顺序，因此评分排序需要绑定 将光标移动到新的排序键。
    • 添加每个组件修正 UI 插槽（ComponentCorrection 是 已经进行了端到端建模； UI 尚未发送）。
    • OpenAPI + 生成的 TS 经过 CI 漂移检查；手工维护的 types.ts/validate.ts/client层是剩余的漂移风险（T04）。
