    AssemblyVision - 完整的项目背景¶

    上下文快照。最后更新: 2026-08-04

    首先在新会话中读取此文件以快速重建项目状态。

    一、项目概况¶

    AssemblyVision - 工业装配检测系统是边缘优先的工业装配检测系统 用于基于传送带的生产线的计算机视觉平台。检查成品 并验证是否存在所有必需的组装组件。

    • 业务输出：OK（可靠检测到所有必需的组件）或NG（缺失， 不确定或无法验证）。质量优先级是最小化漏报（高 NG 召回率，极低的假阴性率）。从未提出过 100% 准确性的声明。
    • 架构：边缘客户端+中央服务器。所有生产关键型图像处理和 最终决策在边缘工业计算机上执行；永远不需要中央服务器 用于实时检查。
    • 当前存储库状态：仅文档和架构基线。没有申请 代码还存在。下一个具体里程碑是为期两天的静态图像 MVP。

    4. Architecture Summary (from docs/design/)¶

    • 边缘客户端职责：相机集成、捕获/触发、产品窗口 管理、条形码识别、产品类型解析、两阶段YOLO检测、ROI 生成、可选的 OpenCV 检查、每个组件的时间聚合、确定性规则 评估、本地数据库/媒体、带重试的上传队列、运行状况监控、本地 FastAPI、 本地 Vue 仪表板。在中央/网络中断期间检查仍在继续。
    • 中央服务器职责：摄取选定的结果/媒体、历史记录、报告、 设备/配置/规则/模型管理、用户/角色、手动 NG 审核、审计、仪表板、远程 分布。不需要进行检查。
    • 两阶段检测：第一阶段全画幅检测产品；投资回报率引擎 扩展/剪辑它；第二阶段检测所需的组件（component_a、component_b、 component_c、manual、...) 在 ROI 内。条形码解码与 YOLO 是分开的。
    • 时间聚合：跨框架的每个所需组件证据（没有整个产品 多数投票）。聚合提高了系统的鲁棒性，而不是单帧模型的准确性。
    • 规则引擎：确定性，独立于人工智能模型，版本化。仅完整有效 证据可能会产生OK；内部 UNCERTAIN 始终映射到业务 NG。
    • 部署：Python 3.12 / FastAPI / YOLO / OpenCV 边缘后端，Vue 3 + TypeScript 前端、Docker Compose（边缘没有 Kubernetes）、PostgreSQL 中心 + SQLite 边缘 (MVP)。
    • 上传策略：选择性（OK：元数据+一个关键帧；NG：完整元数据+多个关键帧 框架+可选夹子）；持久队列、带有退避、幂等性、校验和的重试。

    6.双语MkDocs（英文+中文）¶

    • 主配置mkdocs.yml是唯一的事实来源（材质主题，美人鱼渲染通过 pymdownx.superfences 自定义围栏，extra.alternate 语言切换器）。
    • scripts/build-docs.sh 管道：translate-docs.py (docs/ -> docs-zh/) -> generate-mkdocs-configs.py （生成 mkdocs-en.yml + mkdocs-zh.yml）-> 构建 site/ 和 site/zh/。
    • 翻译使用 deep-translator GoogleTranslator（免费，无 API 密钥）。限速；一个完整的 翻译大约需要 15-30 分钟。单文件模式：python scripts/translate-docs.py design/03-architecture-overview.md。如果出现任何 API 故障，原始英语块将被保留。
    • 所有内容均已翻译，包括 research/ 和美人鱼图标签。美人鱼语法是 保存；仅节点标签、边缘文本、子图标题、序列消息和状态/ER 标签 被翻译。 research/ 不再有特殊的复制步骤（从 build-docs.sh 中删除）。
    • 翻译后的标题将其原始英文标题保留为显式 {#slug} 属性，以便 跨文档锚点（例如 appendices.md#3-global-open-questions）也适用于中文。
    • 已知的机器翻译质量问题（不是脚本错误）：frames -> 框架（应该是帧）， volume -> 音量（应该是意存储卷），poll -> 民调查（应该是轮询）。发布前进行审查。
    • docs-zh/、site/ 和生成的配置是构建工件，未提交。

    7.约定（AGENTS.md）¶

    • 英语为基础语言；所有文档/评论/提交/自述文件必须是英文。
    • 常规提交：feat:、fix:、docs:、chore:、refactor:。
    • 分支命名：feat/xxx、fix/xxx、docs/xxx。
    • 除非明确要求，否则请勿承诺；未经明确批准，请勿推动或强行推动。
    • 没有泄露任何秘密。使用类型化 Pydantic 模型和 TypeScript 接口。
    • 工程规则：保留边缘优先架构；保留AI推理/规则评估/ 持久化/Web API 分离；不要将 YOLO 逻辑放入 FastAPI 路由处理程序中；不要放 AI模型中的业务规则；边缘不能依赖于中央服务器；运行测试 + Ruff + 我的Py；切勿在未执行的情况下声称测试已通过；永远不要声称 100% 准确。
