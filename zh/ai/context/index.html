    AssemblyVision - 完整的项目背景¶

    上下文快照。最后更新: 2026-08-11

    首先在新会话中读取此文件以快速重建项目状态。

    一、项目概况¶

    AssemblyVision - 工业装配检测系统是边缘优先的工业装配检测系统 用于基于传送带的生产线的计算机视觉平台。检查成品 并验证是否存在所有必需的组装组件。

    • 业务输出：OK（可靠检测到所有必需的组件）或NG（缺失， 不确定或无法验证）。质量优先级是最小化漏报（高 NG 召回率，极低的假阴性率）。从未提出过 100% 准确性的声明。
    • 架构：边缘客户端+中央服务器。所有生产关键型图像处理和 最终决策在边缘工业计算机上执行；永远不需要中央服务器 用于实时检查。
    • 当前存储库状态：静态训练和检查 MVP (ADR-011)， 边缘仪表板前端、M1 FastAPI + SQLite 后端层、 审查驱动的强化、真实数据基线工具、相机/多 实例服务、时间聚合、持久上传发件箱、E1-E5 生产门、条码身份/PLC FIFO 触发合约 全部合并到 main （PR #3-#30）。 Python uv 工作区发布 共享 domain 和 vision-core 包，仅限开发人员使用 av-train 训练CLI，真正的两阶段Ultralytics YOLO检查 (assemblyvision inspect) 和保留验证，以及数据集适配器 用于 Roboflow 和 X-AnyLabeling 导出。前端 pnpm 工作区包括 Vue 3 + TypeScript 操作员仪表板 (apps/edge-web)，一个 Electron kiosk shell (apps/edge-desktop)，类型化的 api-client 合约层，以及 共享 UI 原语。 PR #14 添加了相机帧源、多实例 serve，以及门控网络开发测试工具 (ADR-013/014)； PR #15/#16 已合并 产品窗口/时间聚合里程碑（ADR-010）； PR #17 已合并 持久上传发件箱和调度程序（ADR-005）； PR #18/#19 (E1) 和 #20 （E2 保留和磁盘安全）完成了存储/可观察性门； PR #22/#23/#24 合并了 E3（上传弹性）、E4（运行时/WebSocket）和 E5（部署和安全）； PR #25 交付了 E6 验收准备工具； PR #26/#27/#28 添加了强化的 GigE/GenICam 源和 生产就绪的仪表板主题； PR #29 固定持久性推断 元数据； PR #30 添加了精确映射的条形码身份解析 选择加入 Modbus TCP FIFO 触发合同 (ADR-015)。 PR #31 合并了 边缘本地人工审核功能 (ADR-016)，包括其审核强化 以及已记录的 PR31-T05 观众凭证权衡。 PR #32 和 #33 添加了问题模板和工业自述文件/快速启动/安全更新； PR #34 添加了开发者手册； PR #35 添加了边缘网络 i18n；和公关＃36 修复了 MkDocs README 索引排除。边缘编码是通过 E6准备门。中央服务器M1试点已经开始（C1a 基础已交付）；其有界实施计划是 docs/tasks/C1-central-server-m1.md。

    • 遥控器：https://github.com/dream-studio-china/assembly-vision。 PR #3-#30 合并到main，涵盖MVP、仪表板、M1后端、摄像头/ 多实例 (ADR-013/014)、时间聚合 (ADR-010)、持久上传 发件箱 (ADR-005)、E1-E5 门、E6 验收准备、GigE/GenICam 源、 仪表板主题、持久性修复和条形码标识/PLC 触发器 合同（ADR-015）。 PR #31 到 #36 也被合并：边缘局部人类 审查、问题模板、文档更新、开发人员手册、边缘网络 i18n 和 MkDocs 手动索引修复。尚不存在中央服务器代码； docs/tasks/C1-central-server-m1.md明确了试点实施范围。

    4.架构总结（来自docs/design/）¶

    • 边缘客户端职责：相机集成、捕获/触发、产品窗口 管理、条形码识别、产品类型解析、两阶段YOLO检测、ROI 生成、可选的 OpenCV 检查、每个组件的时间聚合、确定性规则 评估、本地数据库/媒体、带重试的上传队列、运行状况监控、本地 FastAPI、 本地 Vue 仪表板。在中央/网络中断期间检查仍在继续。
    • 中央服务器职责：摄取选定的结果/媒体、历史记录、受管理的 元数据、手动审查记录、有界试点状态以及后续管理/报告/审计。 远程包分发属于生产范围。中央不需要检查。
    • 两阶段检测：第一阶段全画幅检测产品；投资回报率引擎 扩展/剪辑它；第二阶段检测所需的组件（component_a、component_b、 component_c、manual、...) 在 ROI 内。条形码解码与 YOLO 是分开的。
    • 时间聚合：跨框架的每个所需组件证据（没有整个产品 多数投票）。聚合提高了系统的鲁棒性，而不是单帧模型的准确性。
    • 规则引擎：确定性，独立于人工智能模型，版本化。仅完整有效 证据可能会产生OK；内部 UNCERTAIN 始终映射到业务 NG。
    • 部署：Python 3.12 / FastAPI / YOLO / OpenCV 边缘后端，Vue 3 + TypeScript 前端、Docker Compose（边缘没有 Kubernetes）、PostgreSQL 中心 + SQLite 边缘 (MVP)。
    • 上传策略：选择性（OK：元数据+一个关键帧；NG：完整元数据+多个关键帧 框架+可选夹子）；持久队列、带有退避、幂等性、校验和的重试。

    6.双语MkDocs（英文+中文）¶

    • 主配置mkdocs.yml是唯一的事实来源（材质主题，美人鱼渲染通过 pymdownx.superfences 自定义围栏，extra.alternate 语言切换器）。
    • scripts/build-docs.sh 管道：translate-docs.py (docs/ -> docs-zh/) -> generate-mkdocs-configs.py （生成 mkdocs-en.yml + mkdocs-zh.yml）-> 构建 site/ 和 site/zh/。
    • 翻译使用 deep-translator GoogleTranslator（免费，无 API 密钥）。限速；一个完整的 翻译大约需要 15-30 分钟。单文件模式： python scripts/translate-docs.py design/03-architecture-overview.md。任何 API 失败时 保留原始英文块。
    • 所有内容均已翻译，包括research/和美人鱼图标签。美人鱼语法是 保存；仅节点标签、边缘文本、子图标题、序列消息和状态/ER 标签 被翻译。 research/ 不再有特殊的复制步骤（从 build-docs.sh 中删除）。
    • 翻译后的标题将其原始英文标题保留为显式 {#slug} 属性，以便 跨文档锚点（例如 appendices.md#3-global-open-questions）也适用于中文。
    • 已知的机器翻译质量问题（不是脚本错误）：frames -> 框架（应该是帧）， volume -> 音量（应该是意存储卷），poll -> 民调查（应该是轮询）。发布前进行审查。
    • docs-zh/、site/ 和生成的配置是构建工件，未提交。
    • exclude_docs 必须使用 /README.md （锚定），以便根文档 自述文件被排除在外，但不排除嵌套的手册、设计、合同和 运行手册索引页。 uv run mkdocs build --strict 验证站点。

    7.约定（AGENTS.md）¶

    • 英语为基础语言；所有文档/评论/提交/自述文件必须是英文。
    • 常规提交：feat:、fix:、docs:、chore:、refactor:。
    • 分支命名：feat/xxx、fix/xxx、docs/xxx。
    • 除非明确要求，否则请勿承诺；未经明确批准，请勿推动或强行推动。
    • 没有泄露任何秘密。使用类型化 Pydantic 模型和 TypeScript 接口。
    • 工程规则：保留边缘优先架构；保留AI推理/规则评估/ 持久化/Web API 分离；不要将 YOLO 逻辑放入 FastAPI 路由处理程序中；不要放 AI模型中的业务规则；边缘不能依赖于中央服务器；运行测试 + Ruff + 我的Py；切勿在未执行的情况下声称测试已通过；永远不要声称 100% 准确。

    8.1 审查驱动的强化（PR-003 后续）¶

    A code review of the feat/mvp runtime, training, and verification surfaces led to a hardening pass that is committed and validated on feat/mvp (P0 items all fixed; remaining P1/P2 items tracked in docs/reviews/PR-003-review.md):

    • Rule engine: expected_count is enforced as an exact count, declared spatial constraints (min_box_area_ratio, max_box_area_ratio, allowed_zone) are evaluated against per-detection normalized ROI evidence, empty rules are rejected, and unsupported rule schema versions or empty model-compatibility lists fail closed.
    • Verification: incomplete evidence (uncertain states, image-read/inference/ROI/ rule failures) is no longer scored as a true positive, and skipped, failed, and unmatched expected samples make verify exit non-zero.
    • Model integrity: runtime verifies artifact size and SHA-256, validates the loaded model class map against the manifest, rejects absolute artifact URIs, and binds the rule-facing model version to the verified manifest.
    • Detector fail-safe: malformed output (invalid class IDs, non-finite confidence or coordinates, out-of-bounds boxes, bad tensor shapes) is converted to INFERENCE_ERROR at the adapter boundary instead of escaping or mis-indexing.
    • Configuration: thresholds must be finite and in [0, 1], booleans are strict, min_area_pixels must be a positive integer, and unknown keys are rejected in every section.
    • Training data: malformed or out-of-range labels, zero-sized and out-of-frame boxes are fatal; missing label files fail validation unless the recorded --allow-missing-labels legacy opt-in is used; empty label files are valid negatives; component preparation keeps negative ROI crops; and published model versions refuse to be silently overwritten with different bytes.
    • Quality gates: ruff check ., ruff format --check ., mypy ., and pytest now cover the whole repository (edge, packages, training, scripts tests) via the Makefile and a new .github/workflows/ci.yml.

    8.6 持久上传发件箱和调度程序（PR #17，ADR-005）¶

    Merged via PR #17 (dev -> main, 10 commits). Implements the persistent upload queue required by ADR-005 and closes the deferred AUDIT-001 4.4 persistence item. The review-driven hardening pass is recorded in docs/reviews/PR-017-review.md; findings F1-F8 plus a post-resolution pass are resolved with regression tests:

    • 磁盘压力和故障安全运行时（E2c）：StorageSettings / RetentionSettings（AV_EDGE_STORAGE_*/AV_EDGE_RETENTION_*，严格来说 有序停止<严重<警告）驱动空闲字节/索引节点压力模式 等于或低于阈值语义。在临界压力下，可选择 OK 捕获 NG 证据和元数据持续存在时被抑制；在停止压力或在 锁存写入故障运行时停止摄入并报告 inspection_ready=false。检验结果待检验合格后方可公布 投影/发件箱事务提交；写故障只能通过a清除 强制持久性探测（探测文件 + fsync 和 BEGIN IMMEDIATE 写）。设备状态暴露服务器权威阈值和稳定 警报 (DISK_WARNING/DISK_CRITICAL/DISK_STOP/STORAGE_WRITE_FAULT/ STORAGE_INTEGRITY_FAULT/CLEANUP_FAULT)，仪表板呈现它们 而不是固定的客户阈值。
    • 启动完整性 (E2d)：scan_storage_integrity 验证媒体 默认情况下存在、大小和校验和（有界确定性采样是 明确可配置），幂等地隔离畸形/孤立包， 和锁存器STORAGE_INTEGRITY_FAULT；现有的故障仍然被锁定 重新启动。 PRAGMA quick_check 未能关闭腐败。 mark_upload_succeeded 根据任务内的不可变字段验证输入的收据 存储库，并且每当存储准入时 /health/ready 返回 503 由停止压力、写入故障或完整性故障关闭。

    如果没有批准的保留策略，清理将保持禁用状态；客户保留 周期、磁盘大小、保持和停止模式线路行为保持释放 生产支持的阻碍因素（E2 任务第 4 节）。当前套房：781 Python 测试、91 个 TypeScript 单元测试（api-client 45、ui 13、edge-web 30、 桌面 3) 和 12 名剧作家 e2e。

    8.9 运行时和实时事件通道 (E4)¶

    于feat/e4-runtime实现（投递任务 docs/tasks/E4-runtime.md):

    • WebSocket 运行时通道 (E4a)：内存中 RuntimeEventBus 分配 单调的每个源序列号并保持每个连接有界 缓冲区可以断开缓慢的消费者而不是阻塞发布者。 WS /api/v1/ws/runtime 使用相同的查看者承载/会话进行身份验证 模型作为 REST 和流设计 15.6 信封（inspection.started， inspection.completed、device.status_changed、upload.changed）。活动 来自真实的转换：检查循环（在每个新窗口上启动 或每帧检查，在投影/发件箱提交后完成）， 暂停/恢复，以及上传调度程序工作人员。跨源浏览器套接字 无法设置 Authorization 标头，因此仪表板交换其查看器 通过 REST 获得短期、一次性票据的凭证 (POST /api/v1/ws/runtime/ticket) 并将其作为协商的内容发送 Sec-WebSocket-Protocol 值，切勿出现在 URL 中 (PR-023 F01)。仪表板 实时视图消耗提要并在重新连接或序列时重新获取 REST 差距，民意调查减少到缓慢回落。发布永远不会阻塞 检查、持久化或工作人员：跨线程交付执行 拥有事件循环的有界缓冲区决策，因此缓慢的消费者 断开连接而不是提高 QueueFull (PR-023 F02)，并且通道 计数器通过经过身份验证的暴露 GET /api/v1/ws/runtime/stats 端点 (PR-023 F05)。
    • 触发/条形码/身份接缝 (E4b)：一个 TriggerSource 协议加上一个 确定性MockTriggerSource（带有条形码的帧排序身份 相关元数据和有效性跨度）提供 IdentityCorrelator 标记捕获的帧，因此身份密封的产品窗口边界 (PR-015 F1) 按实物产品分组；非循环流之后的帧 不保留身份并关闭窗口。模拟源被限制在后面 显式实例 trigger: 配置（仅开发/测试）并且可以 永远不要伪装成生产硬件。
    • 共享模型权重 (E4c)：进程范围的 ModelRegistry 由 不可变工件 SHA-256 加上推理设备允许实例引用 相同的清单共享一个加载的句柄；持有者将推理序列化 每个工件锁定，因为 ultralytics 预测器保持可变状态，而 不同的工件/设备保持独立，并且不共享可变状态 （ADR-013 第 3 阶段）。
