    AssemblyVision - 完整的项目背景¶

    上下文快照。最后更新: 2026-08-09

    首先在新会话中读取此文件以快速重建项目状态。

    一、项目概况¶

    AssemblyVision - 工业装配检测系统是边缘优先的工业装配检测系统 用于基于传送带的生产线的计算机视觉平台。检查成品 并验证是否存在所有必需的组装组件。

    • 业务输出：OK（可靠检测到所有必需的组件）或NG（缺失， 不确定或无法验证）。质量优先级是最小化漏报（高 NG 召回率，极低的假阴性率）。从未提出过 100% 准确性的声明。
    • 架构：边缘客户端+中央服务器。所有生产关键型图像处理和 最终决策在边缘工业计算机上执行；永远不需要中央服务器 用于实时检查。
    • 当前存储库状态：静态训练和检查 MVP (ADR-011)， 边缘仪表板前端、M1 FastAPI + SQLite 后端层、 审查驱动的强化，真实数据基线工具全部合并 到 main （PR #3、#6、#8、#9、#10、#11）。 Python uv 工作区发布 共享 domain 和 vision-core 包，仅限开发人员使用 av-train 训练CLI，真正的两阶段Ultralytics YOLO检查 (assemblyvision inspect) 和保留验证，以及数据集适配器 用于 Roboflow 和 X-AnyLabeling 导出。前端 pnpm 工作区包括 Vue 3 + TypeScript 操作员仪表板 (apps/edge-web)，一个 Electron kiosk shell (apps/edge-desktop)，类型化的 api-client 合约层，以及 共享 UI 原语。 PR #11（dev -> main）添加了真实数据基线 工具：X-AnyLabeling 数据集适配器、单一产品 数据采集指南（设计§19.17，运行手册 11）和自述文件/快速入门 更新。只读仪表板视图通过 HTTP 显示真实的 CLI 结果 客户端，而操作员工作流操作保留在模拟客户端上。 PR #12（开发 -> 主要）通过验收测试结束了 AUDIT-001 的调查结果 （2026年8月9日合并）；参见第 8.4 节。 PR #14 (feat/camera-frame-sources, open) 添加相机帧源、多实例 serve 和门控网络 开发测试工具（ADR-013/014）；参见第 8.5 节。

    2. 存储库状态¶

    • 遥控器：https://github.com/dream-studio-china/assembly-vision。 PR #3、#6、 #8、#9、#10、#11、#12（以及文档 PR #13）合并到 main； PR #12 已合并 于 2026 年 8 月 9 日完成 AUDIT-001 关闭。公关 #14 (feat/camera-frame-sources, open) 携带相机帧源， 多实例服务、Web 开发测试工具 (ADR-013/014) 以及 产品窗口/时间聚合里程碑（ADR-010）。下一个 里程碑是上传调度程序+权威持久性（AUDIT-001 4.4）并收集真实的客户数据。
    • .obsidian/、.idea/ 和 .vscode/ 被忽略本地编辑器状态。
    • 运行时数据、模型权重、生产媒体、数据集和秘密不得存储在 吉特。构建工件 docs-zh/、site/、mkdocs-en.yml、mkdocs-zh.yml 被 gitignored。

    4.架构总结（来自docs/design/）¶

    • 边缘客户端职责：相机集成、捕获/触发、产品窗口 管理、条形码识别、产品类型解析、两阶段YOLO检测、ROI 生成、可选的 OpenCV 检查、每个组件的时间聚合、确定性规则 评估、本地数据库/媒体、带重试的上传队列、运行状况监控、本地 FastAPI、 本地 Vue 仪表板。在中央/网络中断期间检查仍在继续。
    • 中央服务器职责：摄取选定的结果/媒体、历史记录、受管理的 元数据、手动审查记录、有界试点状态以及后续管理/报告/审计。 远程包分发属于生产范围。中央不需要检查。
    • 两阶段检测：第一阶段全画幅检测产品；投资回报率引擎 扩展/剪辑它；第二阶段检测所需的组件（component_a、component_b、 component_c、manual、...) 在 ROI 内。条形码解码与 YOLO 是分开的。
    • 时间聚合：跨框架的每个所需组件证据（没有整个产品 多数投票）。聚合提高了系统的鲁棒性，而不是单帧模型的准确性。
    • 规则引擎：确定性，独立于人工智能模型，版本化。仅完整有效 证据可能会产生OK；内部 UNCERTAIN 始终映射到业务 NG。
    • 部署：Python 3.12 / FastAPI / YOLO / OpenCV 边缘后端，Vue 3 + TypeScript 前端、Docker Compose（边缘没有 Kubernetes）、PostgreSQL 中心 + SQLite 边缘 (MVP)。
    • 上传策略：选择性（OK：元数据+一个关键帧；NG：完整元数据+多个关键帧 框架+可选夹子）；持久队列、带有退避、幂等性、校验和的重试。

    6.双语MkDocs（英文+中文）¶

    • Master config mkdocs.yml is the single source of truth (Material theme, Mermaid rendering via pymdownx.superfences custom fence, extra.alternate language switcher).
    • scripts/build-docs.sh pipeline: translate-docs.py (docs/ -> docs-zh/) -> generate-mkdocs-configs.py (produces mkdocs-en.yml + mkdocs-zh.yml) -> build site/ and site/zh/.
    • Translation uses deep-translator GoogleTranslator (free, no API key). Rate-limited; a full translation takes ~15-30 minutes. Single-file mode: python scripts/translate-docs.py design/03-architecture-overview.md. On any API failure the original English chunk is kept.
    • All content is translated, including research/ and Mermaid diagram labels. Mermaid syntax is preserved; only node labels, edge text, subgraph titles, sequence messages, and state/ER labels are translated. research/ no longer has a special copy step (removed from build-docs.sh).
    • Translated headings keep their original English slug as an explicit {#slug} attribute so cross-document anchors (e.g. appendices.md#3-global-open-questions) work in Chinese too.
    • Known machine-translation quality issues (not script bugs): frames -> 框架 (should be 帧), volume -> 音量 (should be 存储卷), poll -> 民意调查 (should be 轮询). Review before publishing.
    • docs-zh/, site/, and the generated configs are build artifacts, not committed.

    7.约定（AGENTS.md）¶

    • English is the base language; all docs/comments/commits/READMEs MUST be English.
    • Conventional Commits: feat:, fix:, docs:, chore:, refactor:.
    • Branch naming: feat/xxx, fix/xxx, docs/xxx.
    • Do NOT commit unless explicitly asked; do NOT push or force-push without explicit approval.
    • No secrets committed. Use typed Pydantic models and TypeScript interfaces.
    • Engineering rules: preserve edge-first architecture; keep AI inference / rule evaluation / persistence / Web APIs separated; do not put YOLO logic in FastAPI route handlers; do not put business rules in the AI model; edge must not depend on the central server; run tests + Ruff + MyPy; never claim tests passed without executing; never claim 100% accuracy.

    • 在 docs/design/ 下生成完整的架构文档集（28 个文档 + 12 个 ADR + 附录）来自docs/source-brief.md（以前的docs/doc-task.md）。
    • 通过互联网研究创建了docs/research/（3份报告）。
    • 构建了具有自动翻译功能的双语MkDocs，改编自crud-skeleton项目。
    • 添加了对 translate-docs.py 的美人鱼翻译（仅标签/边缘文本，保留语法）。
    • UNCERTAIN决策状态必须始终映射到业务NG（不可配置）。
    • 边缘部署是第一个生产版本的单个 edge-service 流程（一个单独的 边缘工作者/API 分割被推迟，直到测量证明其合理为止）。
    • 检查分别固定产品检测器和组件检测器模型版本。
    • 一个月的范围是有界受控集成演示，而不是完整的生产 接受；接下来是通用管理、远程分发和全面恢复/浸泡工作。
    • ADR-011 仅在 MVP 培训排除和两天范围内取代 ADR-009。所选择的 标注工具是X-AnyLabeling； MVP 使用标准 YOLO 标签，一个单独的仅供开发人员使用的标签 训练 CLI、真正的两阶段模型以及保留的文件名真实值验证。
    • 模型加密和仅限 .pyc 的运行时打包被推迟。 MVP 保护边界为 训练代码、数据集、笔记本和实验配置未分发。
    • MVP 是端到端实现和验证的 (M1-M5)：共享 domain/vision-core 包被提取；仅供开发人员使用的 training/ 工作区和 av-train 添加了（产品/准备组件/组件）；探测器存根被替换为真实的 Ultralytics YOLO 适配器可加载清单引用的权重并将 ROI 框映射回完整值 框架； assemblyvision verify 报告 NG 召回/漏报/误报；和 scripts/e2e-demo.sh 使用针对误报的硬门运行整个流程。
    • 数据集：scripts/generate-synthetic-dataset.py构建一个带标签的程序集数据集（确切地说 框、缺少组件的 NG 变体）用于框架测试； scripts/adapt-roboflow-dataset.py 将 Roboflow YOLOv8 导出转换为两阶段布局，删除通用 missing* 类， 并且需要一个独立注释的完整产品类（组件盒的联合是 被拒绝）。源 test 分割仅成为保留的验证集；从来没有 复制到训练或验证中，并通过 SHA-256 检查分割重叠。 scripts/adapt-xanylabeling.py 对 X-AnyLabeling YOLO 导出执行相同的操作 （classes.txt/data.yaml 名称；图像优先或分割优先布局）。
    • 真实数据工具：收集和注释指南位于 docs/design/19-training-and-evaluation.md §19.17（单一产品数量， 硬注释规则）和 docs/runbooks/11-data-collection-and-annotation.md （操作流程）。本地试驾下载了CC0 smdComponents 集和 data/test-training/ 下的 CC BY 4.0 PCB 检测集 （gitignored）并训练了板级缺失部分检测器（val mAP50 ~0.94； 60 张图像保留 NG 召回率 0.848，多缺失板上的所有缺失） - a 演示，而不是准确性声明。
    • 只读系统审核（记录在 docs/reviews/AUDIT-001-system-audit.md) 运行 12 次并行子代理审核 加上动态压力测试：没有高运行时漏洞，没有秘密； HTTP 读取路径处理了 200 个并发请求，且错误为零。四 高数据完整性/文档结果（适配器缺失标签制造、陈旧 发布的 data.yaml 中的暂存路径，av-train 相对路径 运行/检测嵌套、过时的 PR 状态）和三个再现的并发性和 记录稳健性缺陷；现已全部关闭（PR #12，第 8.4 节）。
    • 模型改进是开发人员端循环（docs/runbooks/10-model-improvement.md）： 收集/更正数据 -> 重新训练 -> 验证没有回归 -> 碰撞管道配置和规则 compatible_component_model_versions 在一起（av-train --rule 打印建议的凹凸）。

    8.1 审查驱动的强化（PR-003 后续）¶

    对 feat/mvp 运行时、训练和验证表面进行代码审查 到在 feat/mvp 上提交和验证的强化通道（P0 项目全部 固定的； docs/reviews/PR-003-review.md 中跟踪的剩余 P1/P2 项目）：

    • 规则引擎：expected_count 强制执行为精确计数，声明为空间 约束（min_box_area_ratio、max_box_area_ratio、allowed_zone）是 根据每次检测标准化 ROI 证据进行评估，空规则是 被拒绝和不受支持的规则架构版本或空模型兼容性 列表关闭失败。
    • 验证：不完整的证据（不确定状态、图像读取/推理/ROI/ 规则失败）不再被评分为真阳性，并被跳过、失败， 并且不匹配的预期样本使 verify 退出非零。

    • 配置：阈值必须是有限的，并且在[0, 1]中，布尔值是严格的， min_area_pixels 必须是正整数，未知的键将被拒绝 每个部分。
    • 训练数据：格式错误或超出范围的标签、零大小和超出框架 盒子是致命的；丢失的标签文件无法验证，除非已记录 --allow-missing-labels 使用旧版选择加入；空标签文件有效 底片；成分制备导致 ROI 作物为负值；并发表 模型版本拒绝被不同的字节默默地覆盖。
    • 质量门：ruff check .、ruff format --check .、mypy . 和 pytest 现在覆盖整个存储库（边缘、包、训练、脚本 测试）通过 Makefile 和新的 .github/workflows/ci.yml。
