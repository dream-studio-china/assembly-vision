    AssemblyVision - 完整的项目背景¶

    上下文快照。最后更新: 2026-08-09

    首先在新会话中读取此文件以快速重建项目状态。

    一、项目概况¶

    AssemblyVision - 工业装配检测系统是边缘优先的工业装配检测系统 用于基于传送带的生产线的计算机视觉平台。检查成品 并验证是否存在所有必需的组装组件。

    • 业务输出：OK（可靠检测到所有必需的组件）或NG（缺失， 不确定或无法验证）。质量优先级是最小化漏报（高 NG 召回率，极低的假阴性率）。从未提出过 100% 准确性的声明。
    • 架构：边缘客户端+中央服务器。所有生产关键型图像处理和 最终决策在边缘工业计算机上执行；永远不需要中央服务器 用于实时检查。
    • 当前存储库状态：静态训练和检查 MVP (ADR-011)， 边缘仪表板前端、M1 FastAPI + SQLite 后端层、 审查驱动的强化，真实数据基线工具全部合并 到 main （PR #3、#6、#8、#9、#10、#11）。 Python uv 工作区发布 共享 domain 和 vision-core 包，仅限开发人员使用 av-train 训练CLI，真正的两阶段Ultralytics YOLO检查 (assemblyvision inspect) 和保留验证，以及数据集适配器 用于 Roboflow 和 X-AnyLabeling 导出。前端 pnpm 工作区包括 Vue 3 + TypeScript 操作员仪表板 (apps/edge-web)，一个 Electron kiosk shell (apps/edge-desktop)，类型化的 api-client 合约层，以及 共享 UI 原语。 PR #11（dev -> main）添加了真实数据基线 工具：X-AnyLabeling 数据集适配器、单一产品 数据采集指南（设计§19.17，运行手册 11）和自述文件/快速入门 更新。只读仪表板视图通过 HTTP 显示真实的 CLI 结果 客户端，而操作员工作流操作保留在模拟客户端上。 PR #12（开发 -> 主要）通过验收测试结束了 AUDIT-001 的调查结果 （2026年8月9日合并）；参见第 8.4 节。 PR #14 添加了相机帧源， 多实例 serve 和门控 Web 开发测试工具 (ADR-013/014)； PR #15/#16 合并了产品窗口/时间聚合里程碑 （ADR-010）与安全生产； PR #17 合并了持久上传 发件箱和调度程序（ADR-005）；和 PR #18/#19（E1 可观测性）和 #20（E2保留和磁盘安全）完成存储并 可观测性门；参见第 8.5-8.7 节。剩余边数 生产候选工作是上传弹性（E3）、运行时/WebSocket （E4）、部署和安全（E5）以及验收（E6）；中央 服务器尚未实现，并且在这些边缘门之前保持在范围之外 通过。

    2. 存储库状态¶

    • 遥控器：https://github.com/dream-studio-china/assembly-vision。 PR #3、#6、 #8、#9、#10、#11、#12、#14（相机/多实例/开发工具）、 #15/#16（时间聚合+生产安全），#17（持久上传 发件箱/调度程序，ADR-005）、#18/#19（E1 可观察性）和#20（E2 保留和磁盘安全）合并到main。 E3-E6 保留：上传 弹性、运行时/WebSocket、部署和安全性以及验收； 中央服务器尚未实现，并且是故意退出的 范围，直到那些边缘门通过。
    • .obsidian/、.idea/ 和 .vscode/ 被忽略本地编辑器状态。
    • 运行时数据、模型权重、生产媒体、数据集和秘密不得存储在 吉特。构建工件 docs-zh/、site/、mkdocs-en.yml、mkdocs-zh.yml 被 gitignored。

    4.架构总结（来自docs/design/）¶

    • 边缘客户端职责：相机集成、捕获/触发、产品窗口 管理、条形码识别、产品类型解析、两阶段YOLO检测、ROI 生成、可选的 OpenCV 检查、每个组件的时间聚合、确定性规则 评估、本地数据库/媒体、带重试的上传队列、运行状况监控、本地 FastAPI、 本地 Vue 仪表板。在中央/网络中断期间检查仍在继续。
    • 中央服务器职责：摄取选定的结果/媒体、历史记录、受管理的 元数据、手动审查记录、有界试点状态以及后续管理/报告/审计。 远程包分发属于生产范围。中央不需要检查。
    • 两阶段检测：第一阶段全画幅检测产品；投资回报率引擎 扩展/剪辑它；第二阶段检测所需的组件（component_a、component_b、 component_c、manual、...) 在 ROI 内。条形码解码与 YOLO 是分开的。
    • 时间聚合：跨框架的每个所需组件证据（没有整个产品 多数投票）。聚合提高了系统的鲁棒性，而不是单帧模型的准确性。
    • 规则引擎：确定性，独立于人工智能模型，版本化。仅完整有效 证据可能会产生OK；内部 UNCERTAIN 始终映射到业务 NG。
    • 部署：Python 3.12 / FastAPI / YOLO / OpenCV 边缘后端，Vue 3 + TypeScript 前端、Docker Compose（边缘没有 Kubernetes）、PostgreSQL 中心 + SQLite 边缘 (MVP)。
    • 上传策略：选择性（OK：元数据+一个关键帧；NG：完整元数据+多个关键帧 框架+可选夹子）；持久队列、带有退避、幂等性、校验和的重试。

    6.双语MkDocs（英文+中文）¶

    • 主配置mkdocs.yml是唯一的事实来源（材质主题，美人鱼渲染通过 pymdownx.superfences 自定义围栏，extra.alternate 语言切换器）。
    • scripts/build-docs.sh 管道：translate-docs.py (docs/ -> docs-zh/) -> generate-mkdocs-configs.py （生成 mkdocs-en.yml + mkdocs-zh.yml）-> 构建 site/ 和 site/zh/。
    • 翻译使用deep-translator GoogleTranslator（免费，无API密钥）。限速；一个完整的 翻译大约需要 15-30 分钟。单文件模式： python scripts/translate-docs.py design/03-architecture-overview.md。任何 API 失败时 保留原始英文块。
    • 所有内容均已翻译，包括research/和美人鱼图标签。美人鱼语法是 保存；仅节点标签、边缘文本、子图标题、序列消息和状态/ER 标签 被翻译。 research/ 不再有特殊的复制步骤（从 build-docs.sh 中删除）。
    • 翻译后的标题将其原始英文标题保留为显式 {#slug} 属性，以便 跨文档锚点（例如 appendices.md#3-global-open-questions）也适用于中文。
    • 已知的机器翻译质量问题（不是脚本错误）：frames -> 框架（应该是帧）， volume -> 音量（应该是意存储卷），poll -> 民调查（应该是轮询）。发布前进行审查。
    • docs-zh/、site/ 和生成的配置是构建工件，未提交。

    7.约定（AGENTS.md）¶

    • 英语为基础语言；所有文档/评论/提交/自述文件必须是英文。
    • 常规提交：feat:、fix:、docs:、chore:、refactor:。
    • 分支命名：feat/xxx、fix/xxx、docs/xxx。
    • 除非明确要求，否则请勿承诺；未经明确批准，请勿推动或强行推动。
    • 没有泄露任何秘密。使用类型化 Pydantic 模型和 TypeScript 接口。
    • 工程规则：保留边缘优先架构；保留AI推理/规则评估/ 持久化/Web API 分离；不要将 YOLO 逻辑放入 FastAPI 路由处理程序中；不要放 AI模型中的业务规则；边缘不能依赖于中央服务器；运行测试 + Ruff + 我的Py；切勿在未执行的情况下声称测试已通过；永远不要声称 100% 准确。

    8. 最新会议决定¶

    • 在 docs/design/ 下生成完整的架构文档集（28 个文档 + 12 个 ADR + 附录）来自docs/source-brief.md（以前的docs/doc-task.md）。
    • 通过互联网研究创建docs/research/（3份报告）。
    • 构建了具有自动翻译功能的双语MkDocs，改编自crud-skeleton项目。
    • 向translate-docs.py添加了美人鱼翻译（仅标签/边缘文本，保留语法）。
    • UNCERTAIN决策状态必须始终映射到业务NG（不可配置）。
    • 边缘部署是第一个生产版本的单个 edge-service 流程（一个单独的 边缘工作者/API 分割被推迟，直到测量证明其合理为止）。
    • 检查分别固定产品检测器和组件检测器模型版本。
    • 一个月的范围是有界受控集成演示，而不是完整的生产 接受；接下来是通用管理、远程分发和全面恢复/浸泡工作。
    • ADR-011 仅在 MVP 培训排除和两天范围内取代 ADR-009。所选择的 标注工具是X-AnyLabeling； MVP 使用标准 YOLO 标签，一个单独的仅供开发人员使用的标签 训练 CLI、真正的两阶段模型以及保留的文件名真实值验证。

    8.1 审查驱动的强化（PR-003 后续）¶

    对 feat/mvp 运行时、训练和验证表面进行代码审查 到在 feat/mvp 上提交和验证的强化通道（P0 项目全部 固定的； docs/reviews/PR-003-review.md 中跟踪的剩余 P1/P2 项目）：

    • 规则引擎：expected_count 强制执行为精确计数，声明为空间 约束（min_box_area_ratio、max_box_area_ratio、allowed_zone）是 根据每次检测标准化 ROI 证据进行评估，空规则是 被拒绝和不受支持的规则架构版本或空模型兼容性 列表关闭失败。
    • 验证：不完整的证据（不确定状态、图像读取/推理/ROI/ 规则失败）不再被评分为真阳性，并被跳过、失败， 并且不匹配的预期样本使 verify 退出非零。

    • 配置：阈值必须是有限的，并且在[0, 1]中，布尔值是严格的， min_area_pixels必须是正整数，未知的键将被拒绝 每个部分。
    • 训练数据：格式错误或超出范围的标签、零大小和超出框架 盒子是致命的；丢失的标签文件无法验证，除非已记录 --allow-missing-labels 使用旧版选择加入；空标签文件有效 底片；成分制备导致 ROI 作物为负值；并发表 模型版本拒绝被不同的字节默默地覆盖。
    • 质量门：ruff check .、ruff format --check .、mypy . 和 pytest 现在覆盖整个存储库（边缘、包、培训、脚本 测试）通过 Makefile 和新的 .github/workflows/ci.yml。

    通过 PR #17 合并（dev -> main，10 次提交）。实现持久上传 ADR-005 所需的队列并关闭延迟的 AUDIT-001 4.4 持久性 项目。审查驱动的强化过程记录在 docs/reviews/PR-017-review.md；结果 F1-F8 加上决议后通过 通过回归测试解决：

    • 订购、租赁的工人：UploadScheduler 在一个任务中声明到期任务 即时交易； MEDIA 任务只有在检查后才到期 任务有经过验证的收据；每个声明都带有每个任务的防护令牌 (lease_owner)，陈旧的IN_PROGRESS任务在租约到期后被回收， 终端更新需要匹配的令牌。
    • 故障分类：传输错误和408/429/5xx时间表 从响应时间起遵守 Retry-After 的全抖动退避；失踪/ 证据损坏、校验和/大小不匹配以及服务器冲突变得 永久性故障，同时保留本地证据。
    • 验证收据：仅当有界打字收据时，2xx 才是成功 回显幂等键、对象、种类、大小和校验和；媒体收据 需要一个中心对象 ID；保留收据并进行检查 所有任务的同步为 QUEUED/PARTIAL/SYNCED/FAILED。
    • 配置和安全：UploadSettings + AV_EDGE_UPLOAD_*接线 通过 serve （端点或本地接收器、单独的凭据、可调参数）； 中央端点需要 HTTPS（仅开发 HTTP 环回），并且 查看器 api_token 永远不会重复用于上传。

    8.7 可观察性 (E1) 以及保留和磁盘安全性 (E2)（PR #18/#19、#20）¶

    通过 PR #18 和 #19 合并的可观测性（dev -> main）：Alembic fileConfig 副作用，禁用 assemblyvision.* 记录器 迁移已修复，因此 /api/v1/logs 捕获应用程序记录和设备 状态现在公开上传队列字节、最早的挂起年龄、尝试/成功/ 失败计数器、失败率、上次联系和 UPLOAD_BLOCKED/ UPLOAD_FAILING 警报。

    通过 PR #20 合并保留和磁盘安全（dev -> main、E2a-E2d 加上 PR-020 审查强化）。交付任务和强制性安全不变量是 在 docs/tasks/E2-retention-and-disk-safety.md 中；审查及其结果 决议记录在docs/reviews/PR-020-review.md中（已解决）：

    • 持久保留状态 (E2a)：迁移 0007 添加介质 created_at， retention_eligible_at，保留状态，删除声明/租赁/防护列， 清除时间戳/原因、删除错误和完整性状态。 PURGED 行 仍然是审计墓碑。资格需要经过验证的收据 SYNCED 使用包含中心对象 ID 的媒体收据进行检查 保留截止日期，并且没有保留/故障/清除/删除状态。
    • 清洁工人 (E2b)：RetentionCleanupWorker 声称候选人在 使用每个工件的隔离令牌进行进程间 SQLite 租赁。一个有围栏的 取消链接前确认重新验证完整的资格谓词和 在破坏性 I/O 之前立即更新租约；持有和诚信 索赔取消后应用的故障，最终确定重新检查相同的情况 谓词。取消链接通过 O_NOFOLLOW 目录文件描述符运行，因此 并发符号链接交换无法删除检查包之外的文件。 丢失文件是完整性错误，绝不是错误清除；取消链接失败是 可重试且可观察。如果没有经过批准、启用的政策，工人 执行零文件系统突变。
    • 磁盘压力和故障安全运行时（E2c）：StorageSettings / RetentionSettings（AV_EDGE_STORAGE_*/AV_EDGE_RETENTION_*，严格来说 有序停止<严重<警告）驱动空闲字节/索引节点压力模式 等于或低于阈值语义。在临界压力下，可选择 OK 捕获 NG 证据和元数据持续存在时被抑制；在停止压力或在 锁存写入故障运行时停止摄入并报告 inspection_ready=false。检验结果待检验合格后方可公布 投影/发件箱事务提交；写故障只能通过a清除 强制持久性探测（探测文件 + fsync 和 BEGIN IMMEDIATE 写）。设备状态暴露服务器权威阈值和稳定 警报 (DISK_WARNING/DISK_CRITICAL/DISK_STOP/STORAGE_WRITE_FAULT/ STORAGE_INTEGRITY_FAULT/CLEANUP_FAULT)，仪表板呈现它们 而不是固定的客户阈值。
    • 启动完整性 (E2d)：scan_storage_integrity 验证媒体 默认情况下存在、大小和校验和（有界确定性采样是 明确可配置），幂等地隔离畸形/孤立包， 和锁存器STORAGE_INTEGRITY_FAULT；现有的故障仍然被锁定 重新启动。 PRAGMA quick_check 未能关闭腐败。 mark_upload_succeeded 根据任务内的不可变字段验证输入的收据 存储库，并且每当存储准入时 /health/ready 返回 503 由停止压力、写入故障或完整性故障关闭。

    如果没有批准的保留策略，清理将保持禁用状态；客户保留 周期、磁盘大小、保持和停止模式线路行为保持释放 生产支持的阻碍因素（E2 任务第 4 节）。当前套房：781 Python 测试、91 个 TypeScript 单元测试（api-client 45、ui 13、edge-web 30、 桌面 3) 和 12 名剧作家 e2e。

    8.8 上传弹性（E3）¶

    在feat/e3-upload-resilience上实现（投递任务 docs/tasks/E3-upload-resilience.md，设计13.13/13.14):

    • 带宽节流（E3a）：令牌桶限制器限制网络 来自 AV_EDGE_UPLOAD_MAXIMUM_BANDWIDTH_MBPS 的每秒有效负载字节数 （None 禁用）；突发的上限为一秒的令牌和限制器 永远不会限制本地持久性。发送的字节数和上限暴露在 设备状态。
    • 断路器 (E3b)：连续可重试失败 (AV_EDGE_UPLOAD_CIRCUIT_FAILURE_THRESHOLD/_OPEN_SECONDS) 打开 电路；打开时调度程序不声明任何内容，而打开窗口后 单个半开探头判断恢复情况。永久的失败永远不算数。 UPLOAD_CIRCUIT_OPEN 警报；持久队列永远不会改变。
    • 受控手动重试 (E3c)：POST /api/v1/uploads/{id}/retry 仅重置 RETRY_WAIT/PERMANENT_FAILURE 任务 attempt_count + 1； 404 未知，409 不合格，无突变。
    • 长时间停电排水 (E3d)：离线检查、重新启动和恢复的天数 使用媒体之前的有序元数据恢复无重复的排空队列 上传和每次检查SYNCED。
    • 可恢复大媒体合约 (E3e)：设计 13.14 定义分块 传输（稳定的任务身份、块幂等性、大小/校验和完成 确认、对象绑定）； media_chunk_bytes 是一个明确标记的 保留占位符 - 中央端点未实现和分块 仅在边缘到中心合约冻结后才开始传输。
