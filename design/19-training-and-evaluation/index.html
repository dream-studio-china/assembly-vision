    19. Training and Evaluation¶

    19.1 Objective and Scope¶

    Training produces a product detector for full frames and a component detector for product ROIs. Evaluation measures both detector behavior and the complete product-level inspection system. The principal safety objective is extremely high NG recall and a correspondingly low false-negative rate, demonstrated on held-out production data; no dataset size or model metric guarantees perfect performance.

    Model metadata follows Data Model and Database. Model registration and review surfaces are described in Central Admin Dashboard, and code ownership in Monorepo and Code Organization.

    19.1.1 Static Train-and-Inspect MVP¶

    The MVP implements a developer-controlled training-to-inspection loop before camera integration. X-AnyLabeling is the selected annotation tool and exports standard YOLO text labels. Product and component boxes are annotated in full-frame coordinates. The training CLI validates the exported dataset, trains the product detector from full-frame images, then uses the product ROI transform to crop component training images and remap component boxes into ROI coordinates before component training.

    The runtime inspection CLI consumes only the resulting immutable weight artifacts and manifests. Training code is in a separate training/ workspace, is never imported by the runtime, and is excluded from runtime distributions. A configured filename convention provides expected OK or NG labels for held-out verification; it is not a substitute for bounding-box labels during detector training.

    The first MVP runs small models and measured image sizes on the developer's Apple Silicon Mac with 16 GB memory. It records reproducibility metadata and reports held-out static-set results, but does not claim production accuracy, production throughput, or production acceptance. Plain model artifacts with SHA-256 manifests are sufficient for this MVP; model encryption and .pyc-only distribution packaging are deferred.

    The minimum YOLO dataset layout is:

    dataset/
├── images/{train,val}/
├── labels/{train,val}/
└── data.yaml

    Each label file shares its image basename and contains normalized YOLO class and box coordinates. The data.yaml class-name order is the authoritative class-ID mapping. Train and validation groups must keep derived crops and their source product/session together.

    19.2 Task Definitions¶

    19.2.1 Product Detector¶

    Input is a full approximately four-megapixel production frame. Output is product class, bounding box, and confidence. The first target is one product class unless product classes are visually necessary for ROI handling. Product identity should normally come from the barcode/product mapping rather than visual classification.

    Initial collection target is approximately 300 to 800 real production images, including slight position changes, normal production variation, empty conveyor/background negatives, partial entry/exit frames, blur, reflections, and expected occlusion. This is a planning range, not an acceptance threshold.

    19.2.2 Component Detector¶

    Input is the product ROI generated by the production ROI code. Output classes are concrete required components, including the manual where applicable. Train visible required components; do not train a generic missing_component class. Initial planning is approximately 300 to 500 labeled instances per component class, plus intentionally created missing-component scenarios, starting near 100 product instances per missing scenario where practical.

    19.2.3 System Decision¶

    The system combines frame quality, product detection, ROI generation, component evidence across frames, barcode/product resolution, and deterministic rules. A component-model miss can be recovered by temporal evidence; temporal aggregation does not improve the detector's single-frame accuracy. Final product-level metrics must execute the exact production preprocessing, thresholds, aggregation, and rule versions.

    19.3 Data Inventory and Provenance¶

    Every source image/frame is associated with a manifest containing:

    • Dataset/source record ID and immutable file checksum.
    • Site, line, camera, and capture setup identifiers where permitted.
    • Capture session ID, production date, product batch, and physical product instance ID.
    • Video/inspection window ID, frame index, and timestamp.
    • Product code/type and barcode in protected metadata where permitted.
    • Deliberate defect scenario and known missing components.
    • Camera angle/setup revision, lighting/exposure revision, and software capture version.
    • Annotation version, annotator, review state, and exclusion reason.
    • Consent, retention, and permitted-use classification.

    Raw data is immutable. Corrections create a new annotation/dataset version. Personally or commercially sensitive identifiers are pseudonymized for training while retaining a controlled traceability map.

    19.4 Collection Design¶

    Collect with the actual production camera, optics, mounting, lighting, conveyor background, capture software, and image encoding. The initial model optimizes for one fixed production angle. A substantial angle change, including a change near 45 degrees, is a domain change requiring evaluation, additional collection/fine-tuning, and complete revalidation.

    Collection must represent:

    • Each supported product and required component.
    • Real OK products across batches/dates and ordinary position variation.
    • Physically constructed NG products for each missing component and missing manual.
    • Barcode success, damaged/occluded/unreadable barcode, and unknown mapping cases.
    • Empty frames, partial products, multiple-product anomalies, blur, reflection, occlusion, exposure variation, and safe camera-position tolerances.
    • Consecutive OK, consecutive NG, and mixed-product sequences for window/aggregation testing.

    Do not synthesize all NG examples by digitally erasing components. Synthetic editing may augment rare variation, but physically captured defects are necessary because shadows, packaging deformation, and revealed backgrounds differ.

    19.5 Annotation Protocol¶

    Define a versioned class ontology with stable component codes, inclusion/exclusion rules, minimum visibility, occlusion/truncation flags, and difficult-case examples. Product boxes enclose the visible product consistently. Component boxes use ROI coordinates but retain source-frame transform metadata.

    Workflow:

    1. Annotator labels from the locked ontology and marks ambiguous/unusable images rather than guessing.
    2. Automated checks reject invalid boxes, unknown classes, impossible image dimensions, duplicates, and missing required metadata.
    3. A second reviewer examines all NG scenarios, all ambiguous labels, and a statistically meaningful sample of ordinary labels.
    4. Disagreements are adjudicated and ontology guidance updated before bulk relabeling.
    5. Dataset release freezes file checksums, annotation hashes, ontology version, and provenance manifest.

    Track per-class box counts, product-instance counts, sessions, batches, and defect scenarios. Frame count alone overstates diversity when many frames come from one product pass.

    19.6 Leakage-Safe Data Splits¶

    19.6.1 Split Unit¶

    The minimum split group is a physical product instance across its entire inspection/video window. Prefer a higher-level group that combines capture session, product batch, production date, and setup revision. All adjacent frames, crops, augmentations, re-encodings, and annotations derived from one source group stay in one split.

    Never randomly split individual video frames. Nearly identical frames across train and validation produce misleading metrics and tune temporal aggregation on repeated evidence.

    19.6.2 Recommended Sets¶

    Set Purpose Access and reuse rule
    Training Fit model weights May be repeatedly sampled and augmented
    Validation Select architecture, hyperparameters, thresholds, and aggregation policy Repeated use allowed; not a final unbiased estimate
    Internal test Locked engineering comparison before release Limited evaluations; never train/tune on failures without creating a new test version
    Customer acceptance Final site-specific validation with production data Not used for training or model selection; customer-agreed protocol
    Production audit Ongoing drift and sampled OK/NG review Time-forward; promoted to training only after evaluation snapshot is frozen

    Percentages depend on available independent groups. A reasonable planning start is 70/15/15 by grouped instances for train/validation/internal test, but sufficient NG examples per component and product take precedence. The customer acceptance set remains separate, not carved out after tuning.

    19.6.3 Split Construction¶

    Use deterministic, versioned group assignment with a fixed seed and manifest. Stratify at group level by product, missing-component scenario, site/setup, and relevant operating condition where sample size permits. Report any stratum too small for independent evaluation rather than moving duplicate-like frames across splits.

    Before release, run leakage checks:

    • Exact SHA-256 duplicate detection across splits.
    • Perceptual-hash/embedding nearest-neighbor review for near duplicates and extracted video frames.
    • Group-ID overlap checks for physical product, window, session, batch, and date.
    • Derived-file lineage checks ensuring crops and augmentations follow their source split.
    • Barcode/product-instance identifier overlap check where identifiers are permitted.
    • Manual review of the closest cross-split image pairs.

    19.7 Preprocessing and Augmentation¶

    Training and evaluation use the same color conversion, resize/letterbox, ROI expansion/clipping, orientation logic, and image normalization as production. Store these parameters in the model manifest.

    Augmentation may include bounded translation, scale, mild perspective, exposure/contrast, blur, sensor noise, compression, and partial occlusion if each represents plausible production variation. Avoid large rotations or backgrounds not physically possible under the fixed camera. Do not augment validation, test, or acceptance images except deterministic production preprocessing. Audit class-box transformations visually.

    19.8 Training Reproducibility¶

    Each run records source revision, environment/container digest, Python/CUDA/framework versions, random seeds, dataset/ontology version, split manifest, base weights, architecture, image size, epochs, optimizer/schedule, augmentations, thresholds used for reporting, and output artifact checksums. Store human-readable configuration and machine-readable run metadata.

    Training code must support a dry run on synthetic fixtures in CI. Full runs execute on controlled GPU infrastructure, not edge devices. Model artifacts are immutable and linked to evaluation reports; retraining does not overwrite a published semantic version.

    19.9 Detector-Level Metrics¶

    For product and component detectors report:

    • Precision-recall curves and average precision at documented IoU thresholds, including mAP50 and mAP50-95 where appropriate.
    • Per-class precision, recall, AP, support, and confidence distribution.
    • Product-detection success at the operational confidence/IoU criteria.
    • False detections on empty/background frames.
    • Localization/ROI containment failures that cause component loss.
    • Metrics by product, component, batch/session, position band, image-quality band, and setup revision when sample counts permit.
    • Inference preprocessing, model, and postprocessing latency separately on representative edge hardware.

    mAP is useful for model development but is not the production acceptance metric. Thresholds are selected on validation data with higher cost assigned to missed NG outcomes and then frozen before test/acceptance evaluation.

    19.10 Product-Level System Metrics¶

    Let NG be a truly defective/incomplete product and predicted OK be a pass:

    NG recall = true NG predicted NG-or-uncertain / all true NG
False-negative rate = true NG predicted OK / all true NG = 1 - NG recall
False-positive rate = true OK predicted NG-or-uncertain / all true OK
OK precision = true OK predicted OK / all predicted OK

    If UNCERTAIN follows the physical NG path, count it as caught for safety recall but report it separately because it increases manual handling. Also report:

    • Per-component missing-case recall and miss count.
    • Per-product and per-product/component recall.
    • Product-detection, ROI-generation, barcode-read, and product-resolution success rates.
    • Unusable-window and uncertain rates.
    • Average, median, P95, and P99 end-to-end latency; throughput at expected trigger rate.
    • Manual review and correction rates by original decision/reason.
    • Metrics by model, rule, and product configuration version.
    • Upload delay and evidence completeness separately from inspection quality.

    Every rate includes numerator, denominator, confidence interval, and raw miss count. For rare safety failures, a zero observed miss does not prove zero risk; report a binomial confidence bound. Overall accuracy is never sufficient because OK prevalence can hide missed defects.

    19.11 Temporal and Video Evaluation¶

    Evaluate full, ordered inspection windows, not shuffled frames. The harness reproduces production frame sampling, quality exclusion, window boundaries, ROI transforms, aggregation, and rules. Scenarios include adjacent products, consecutive defects, mixed product types, late barcode events, dropped frames, partial windows, duplicate triggers, and multiple products.

    Compare single-frame baseline and configured temporal policy to quantify system robustness. Report per-component detection-run distributions and failures caused by frame mixing. Threshold and policy optimization uses validation windows only.

    19.12 Error Analysis¶

    Every false negative receives priority review with original frames/window, labels, detector output, quality filters, barcode/product resolution, ROI mapping, aggregation evidence, rules, and exact versions. Assign one or more controlled root causes:

    • Annotation/ground-truth error.
    • Product not detected or poorly localized.
    • ROI clipping/transform error.
    • Component detector miss/confusion.
    • Quality filter rejected useful evidence.
    • Temporal/window mixing or insufficient frames.
    • Barcode/product/rule mapping error.
    • Model/rule incompatibility or software defect.
    • Unrepresented domain condition.

    Fixes are tested against regression suites. A discovered test failure may enter a future training set only after the current evaluation is frozen; subsequent performance must use a newly versioned untouched test set or time-forward acceptance sample.

    19.13 Acceptance Evaluation¶

    The customer acceptance set uses production data not used for training, validation, threshold selection, or internal test tuning. The protocol is agreed before running and separately covers product type, each missing component/manual, barcode failure, allowed position shift, normal variation, consecutive/mixed decisions, offline operation, restart, and long-running operation.

    Each result preserves ground truth, decision, evidence, image/clip references, model/rule/product versions, device, timestamps, and relevant logs. The primary metric is real NG recall. Numerical acceptance targets and required sample sizes are established with the customer after baseline data collection and risk review; this document does not invent a guarantee.

    19.14 Production Monitoring and Retraining¶

    Monitor input and outcome signals by version and product: product box position/size, frame quality, confidence distributions, barcode failures, uncertain/NG rates, component reasons, manual corrections, and latency. Drift alerts trigger investigation, not automatic retraining or threshold changes.

    Production sampling must include reviewed NG, low-confidence cases, exceptions, and a random/stratified sample of predicted OK products; reviewing only predicted NG cannot estimate false negatives. Curators deduplicate, correct labels, preserve provenance, and approve additions. Retraining promotion repeats leakage checks, locked evaluation, compatibility checks, staged rollout, and rollback readiness.

    19.15 Model Promotion Gates¶

    A candidate can be published only when:

    1. Artifact, manifest, dataset, and evaluation checksums are complete and reproducible.
    2. Required per-product/per-component strata have adequate data or documented limitations.
    3. No unacceptable regression appears in NG recall, false-negative count, barcode/product handling, or latency.
    4. Rule and class compatibility validation passes.
    5. Internal test results are reviewed by designated engineering/quality approvers.
    6. Site/customer acceptance is completed where required.
    7. Rollout and rollback versions are identified.

    A challenger with better mAP but worse product-level NG recall is not promoted solely on mAP.

    19.16 Open Questions and Validation Required¶

    • Confirm supported products/components, expected defect prevalence, and feasible count of physically created NG products per scenario.
    • Confirm production permission, privacy, retention, and transfer rules for images, barcodes, and review labels.
    • Define physical product, batch, session, and camera/setup identifiers available for leakage-safe grouping.
    • Agree annotation ontology, ambiguity policy, review sampling, and adjudication owners.
    • Establish customer acceptance targets, confidence level, sample sizes, and treatment of UNCERTAIN after baseline evaluation.
    • Confirm representative edge CPU/GPU, required throughput, conveyor timing, and latency budget.
    • Define allowed camera-position/angle/exposure tolerances and the process that declares a domain change.
    • Confirm production OK-audit sampling needed to estimate false negatives and model drift.

    19.17 Single-Product Data Acquisition and Annotation Checklist¶

    This section is the authoritative data-quality spec for the common case: one product on one fixed camera/lighting/position station. It converts the planning ranges in 19.2 into a concrete acquisition plan, states the hard annotation rules that the dataset adapters enforce, and defines the handover that feeds the training pipeline. For the operational step-by-step procedure see Runbook 11; the external checklists in Imaging Workflow and Training Cost remain supporting material.

    19.17.1 Why a Single Fixed Product Is Easier¶

    A fixed product under a fixed camera collapses intra-class variance: the product-detector task becomes near-constant ("board present / absent / partial / multiple"), and the component detector only needs to distinguish "this part is here" from "this pad is empty" on the same board. Public multi-board datasets (such as generic PCB component sets) spread one class across dozens of visually different products, which is why a small multi-board model generalizes poorly whereas a small single-product model can be effective. The bottleneck is never the OK side; it is the missing-component (NG) side: physically missing parts are rare on the line, hard to construct, and every failure mode the model has never seen is a false-negative risk.

    19.17.2 Collection Quantities (Planning Ranges, Not Acceptance Thresholds)¶

    Product detector (stage 1, full frame):

    Content Suggested count
    OK products across batches/dates and position variation 100-300
    Empty conveyor / background (product absent) - explicit empty labels 30-60
    Partial entry / exit frames 20-40
    Multiple products in one frame (anomaly) 10-20
    Blur, reflection, occlusion, exposure variation 10-20 each

    Component detector (stage 2, ROI):

    Content Suggested count
    Labeled instances per required component class 300-500 per class
    Physically missing part per missing scenario ≥ 100 per missing location
    Missing multiple components (combinations) 20-50 per combination
    Negative ROI crops (empty pads, no component) same order as missing samples

    Barcode (separate from YOLO): readable, damaged/occluded, and unreadable cases for product-type resolution and fail-safe paths.

    A minimal closed loop (get the pipeline running and measure trends) can start at 40-60 OK images plus 10-20 samples per missing location, then scale to the table above; expand where verify exposes missed NG.

    19.17.3 Hard Annotation Rules (Enforced by the Adapters)¶

    • Two datasets, two-stage semantics. dataset_product carries one class product = an independently annotated full-board box. dataset_components carries the required component classes in fixed order (the data.yaml order is the class-ID mapping). Missing components are expressed by the absence of the component's box; never train a generic missing_* class.
    • Product box is mandatory even when components are missing. Stage one must localize the complete product for a defective board too. An image with component boxes but no product box is a data error and is rejected; the product box can never be derived from the union of present component boxes.
    • Explicit empty labels. Every background/negative image must have an explicit empty label file; image/label pairing is required. The adapters reject any image without a label file in every split, and av-train validation rejects missing label files unless the recorded --allow-missing-labels legacy opt-in is used.
    • Physical NG only. Do not synthesize all NG by digitally erasing components; shadows, packaging deformation, and revealed backgrounds differ (19.4).
    • Fixed capture conditions. Collect with the production camera, optics, mounting, lighting, conveyor background, capture software, and encoding. A significant angle change is a domain change requiring revalidation (19.4).
    • Second review. A reviewer examines every NG sample, all ambiguous labels, and a sample of ordinary labels (19.5); disputes are adjudicated against a locked ontology.

    19.17.4 Leakage-Safe Splits and Handover¶

    • Split by physical product instance / capture session, never by random frames; target 70/15/15 by grouped instances (19.6). The held-out test split is used once for verification and never for tuning.
    • Annotate with X-AnyLabeling and export the YOLO layout (train/val/test + classes.txt or data.yaml), then run scripts/adapt-xanylabeling.py <export> <out> --product-class product --required '<comma,separated>'. The adapter validates every label line, enforces 19.17.3, keeps explicit background negatives, rejects missing label files and same-stem image collisions per split, normalizes Roboflow's valid split to val, and publishes dataset_product + dataset_components + test-expected.json + manifest.json atomically with dataset-relative data.yaml paths. Roboflow exports use scripts/adapt-roboflow-dataset.py.
    • Freeze dataset checksums and the annotation/ontology version with the model manifest (19.8, contract 10); the verification set must never be copied into training or validation.
